# Оптимизация времени компиляции SchemeShard

> Финальное состояние на 6 сентября 2026 года. Исследование остановлено на
> текущем подтверждённом ускорении; новые гипотезы в эту версию не включались.

## Итог

Оптимизировалась совокупная компиляция всех **214** активных C++ translation
units таргета `ydb/core/tx/schemeshard`, а не несколько выбранных файлов.

На свежем стабильном baseline подтверждено:

| Состояние | Сумма 214 CC, с | Медиана CC, с | p95 CC, с | Wall/span, с |
|---|---:|---:|---:|---:|
| Baseline, прогон A | 8424.382 | 40.739 | 47.551 | 284.685 |
| Baseline, прогон B | 8425.522 | 40.737 | 47.219 | 285.281 |
| Оптимизированная версия | **4677.163** | **21.048** | **32.860** | **165.443** |

Среднее baseline A/B — **8424.952 с**. Относительно него оптимизированная
версия даёт:

- **1.802×** ускорение суммы compile CPU;
- **−44.49%** compile CPU;
- примерно **1.72×** по wall/span;
- примерно **1.94×** по медиане одного CC.

Цель 2× не достигнута: исследование остановлено по решению владельца задачи на
текущем воспроизводимом результате. Более старое исходное измерение 9162.938 с
давало почти 1.96×, но оно получено в другую эпоху нагрузки хоста и поэтому не
используется как финальное сравнение.

## Методика

Baseline хранится в отдельном неизменяемом checkout
`/tmp/ydb_schemeshard_baseline` на commit `9490c3631e5`. Список ровно из 214 CC
actions фиксирован и одинаков для baseline и рабочей версии.

Для каждого aggregate-замера безвредно инвалидировались только эти actions,
после чего выполнялась `relwithdebinfo`-сборка с `-j32` и отключённым remote
store. Из статистики сборки извлекались elapsed times всех 214 компиляций.
Измерительный nonce после каждого прогона удалялся и не входит в diff.

Артефакты финального сравнения:

- baseline A: `/tmp/ydb_ss_final_baseline_j32_a`;
- baseline B: `/tmp/ydb_ss_final_baseline_j32_b`;
- оптимизированная версия: `/tmp/ydb_ss_datashard_fwd_full_j32_2`.

`-ftime-trace` применялся для поиска тяжёлых include и разбора отдельных
translation units, но финальное ускорение рассчитано только по aggregate-замеру.

## Что изменено

### Разгружен `schemeshard_impl.h`

Из общего заголовка убраны многочисленные транзитивные зависимости от Schema,
DataShard, SchemeCache, tablet executor, прикладных protobuf и event headers.
Реальным потребителям добавлены прямые include.

Часть внутреннего состояния `TSchemeShard` скрыта за PImpl или вынесена в узкие
внутренние классы: очереди, login/table-profile/column-table state, pipe pools,
удаление shard-ов, domain links и root/tenant shred managers. Изменение
внутрипроцессного layout допустимо по условиям задачи.

### Разрезан `schemeshard_info_types.h`

Монолитный заголовок физически разделён на обычные заголовки с явными
зависимостями:

- базовые и forward declarations;
- core-типы;
- table/column, topic и subdomain-типы;
- storage/misc/transfer/export object-типы.

Публичный агрегирующий заголовок сохранён для совместимости существующих
потребителей. Условных режимов содержимого заголовка в решении нет.

Последние два разрезания проверялись парными aggregate-прогонами на одном
периоде нагрузки:

- отделение table-типа от object storage: варианты быстрее контролей на
  **96.561 с** и **36.662 с** в двух парах;
- отделение export object-типа: вариант быстрее контроля на **29.630 с**.

Из-за изменения нагрузки хоста эти поздние абсолютные результаты не
подменяют финальное сравнение с устойчивым baseline; парные контроли нужны
только для решения, сохранять ли конкретный refactoring.

### Локализованы protobuf и event-зависимости

Добавлены узкие forward/event headers для DataShard, SchemeCache, backup,
export, import, index build и forced compaction. Полные protobuf/event headers
теперь подключаются в `.cpp`, где действительно нужны тела сообщений.

События и приватные типы SchemeShard, применяемые отдельными подсистемами,
также вынесены из крупных общих заголовков.

Существующая генерация строковых представлений enum переведена с монолитного
агрегатора на пять физических заголовков, содержащих enum. Это сохраняет
прежние `Out<>`-символы и формат диагностических строк после разделения файла.

### Облегчён operation framework

`TSideEffects`, `TMemoryChanges` и `TStorageChanges` переведены на out-of-line
реализации/PImpl. Базовые operation headers больше не требуют полной реализации
SchemeShard и tablet executor. Узкие методы `TOperationContext` дают нужный
доступ без раскрытия всего `TSchemeShard`.

### Разделены независимые утилиты

Лёгкие strongly typed `ui64` identifiers остались в `ui64id.h`, а NiceDb
адаптеры перенесены в `ui64id_nicedb.h`. Потребители идентификаторов больше не
разбирают `flat_cxx_database.h` без необходимости.

### Исправлены скрытые транзитивные зависимости

Полная сборка `ydbd` обнаружила потребителей, которые неявно полагались на
раньше протекавшие include. Для них добавлены прямые зависимости: DataShard и
index-builder events, table/subdomain/OLAP types, config protobuf, Schema,
feature flags и `xrange`. Это compile hygiene; исполняемая логика не менялась.

## Отменённые гипотезы

Изменения без воспроизводимого выигрыша полностью откатывались. Среди них:

- отдельное разделение sys-view типов;
- дополнительное разделение partition config;
- дальнейшее разрезание `schemeshard__operation.h`;
- out-of-line реализация `TCondErase`;
- out-of-line реализация `TPartitionStats` — вариант 4906.772 с против inline
  контроля 4886.598 с;
- отдельные попытки убрать Hive/tablet-counter зависимости.

## Совместимость

- PCH не используется;
- язык и система сборки не менялись;
- сгенерированные protobuf-файлы не редактировались;
- номера полей, сериализация, persistent data и protobuf wire/network format не
  менялись;
- публичные агрегирующие заголовки сохранены;
- внутренний layout и ABI классов внутри процесса изменён там, где это было
  необходимо и разрешено условиями задачи.
