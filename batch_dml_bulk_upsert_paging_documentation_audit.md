Дата проверки: 2026-09-12.

Проверяемая версия: `main`, commit
`35fe6b99b6b321ebc724e0c644432b2301f49da6`.

Область проверки: только строковые таблицы. Проверка выполнена black-box через
YDB CLI и публичный Query/Table API локального кластера. Баги в трекере не
создавались. ASAN не использовался.

- `ydb/docs/ru/core/yql/reference/syntax/batch-delete.md`;

## Итог

Подтверждённых проблем реализации и документации не найдено. Постоянный
regression test не добавлялся: проверенные контракты выполняются, а тест только
на документацию не нужен.

Важно: описанная в документации пагинация является keyset pagination по
последнему primary key, а не серверным snapshot/cursor token. Изменения таблицы
между запросами видны следующим страницам; это ожидаемое следствие независимых
запросов, а не найденный дефект.

## BATCH UPDATE и BATCH DELETE

Создана строковая таблица `batch_audit` с 12 явно заданными партициями, 30 000
строками, TTL-колонкой и синхронным secondary index с покрытой колонкой. Размер
набора превышает документированный размер одной итерации в 10 000 строк.

### Что прошло

- `BATCH UPDATE` по предикату обновил 15 000 строк, расположенных в нескольких
  партициях. Ещё 15 000 строк остались без изменений.
- Синхронный индекс сразу вернул все 15 000 обновлённых строк и новые значения
  покрытой колонки.
- `BATCH DELETE` удалил 7 500 строк из нескольких партиций. В основной таблице
  осталось 22 500 строк, а индекс не содержал записей удалённых строк.
- Идемпотентное присваивание констант разрешено.
- Неидемпотентное выражение вида `value = value + 1` отклонено.
- `RETURNING` для обоих BATCH-операторов отклонён.
- Подзапрос в BATCH DML отклонён.
- Попытка совместить BATCH-оператор с другим statement отклонена.
- Запись `NULL` в `NOT NULL` колонку отклонена; ранее выполненные корректные
  обновления при этом не изменились.

Результаты совпадают с описанными ограничениями: оператор выполняет независимые
итерации по партициям, предназначен для идемпотентных массовых изменений и не
даёт транзакционной атомарности всей операции. Аварийное прерывание клиента
между итерациями не инъецировалось, поэтому конкретное число уже применённых
итераций при таком сбое не фиксировалось.

## Bulk Upsert

Сначала выполнен существующий публичный функциональный тест:

```bash
./ya make --build relwithdebinfo -tA ydb/tests/functional/api \
  -F 'test_public_api.py::TestCRUDOperations::test_bulk_upsert' \
  2>&1 | tail
```

Результат: `1 test: 1 - OK`.

Дополнительная временная проверка через Table API подтвердила:

- пустой batch успешно принимается;
- несколько строк загружаются в обычную строковую таблицу;
- таблица с синхронным secondary index отклоняется с сообщением, что Bulk
  Upsert поддерживает только async-indexed tables;
- таблица с асинхронным secondary index принимает batch, обе строки появились
  в основной таблице;
- batch без обязательной `NOT NULL` колонки отклоняется, проверенный набор не
  оставил строк в таблице.

Временный тест после проверки удалён: он не воспроизводит ошибку реализации.
Документированный неатомарный характер Bulk Upsert подтверждён архитектурой API,
но инъекция сбоя между shard-транзакциями не выполнялась.

## Keyset pagination

### Стабильный набор и параметры

Для таблицы с составным primary key `(city, number)` выполнен точный
параметризованный шаблон документации:

```yql
DECLARE $lastCity AS Utf8;
DECLARE $lastNumber AS Uint32;

SELECT city, number, payload
FROM paging_audit
WHERE (city, number) > ($lastCity, $lastNumber)
ORDER BY city, number
LIMIT 2;
```

При последовательных курсорах `("A", 2)` и `("B", 2)` страницы вернули
соответственно `(B,1), (B,2)` и `(C,1)`. Вместе с первой страницей получен весь
ненулевой набор ровно один раз и в порядке primary key.

### Nullable primary key

Предупреждение документации подтверждено буквально. После строки с ключом
`(NULL, NULL)` обычный предикат

```yql
WHERE (city, number) > (NULL, NULL)
```

вернул пустую страницу, хотя строки после курсора существуют. Это стандартная
трёхзначная логика сравнений с `NULL`.

NULL-aware предикаты, отдельно рассматривающие `IS NULL` и переход к следующей
компоненте ключа, прошли весь набор из восьми комбинаций, включая `(NULL,NULL)`,
`(NULL,1)`, `(A,NULL)` и ненулевые ключи, без повторов и пропусков. Тем самым
проверено не только предупреждение, но и практический обход ограничения.

### Изменения между страницами

Первая страница таблицы содержала ключи `1, 2`. До запроса следующей страницы:

- добавлен ключ `0` позади курсора;
- добавлены ключи `3` и `7` впереди курсора;
- удалён ещё не прочитанный ключ `4`.

Следующие страницы по условию `id > last_id` вернули `3, 6, 7`. Новый ключ `0`
не появился, новые ключи впереди курсора появились, а удалённый ключ `4` не
появился. Это корректное поведение keyset pagination без общей snapshot-
транзакции и важное эксплуатационное ограничение для изменяющегося набора.

## Ограничения аудита

- Не инъецировались разрыв соединения и рестарт DataShard ровно между
  итерациями BATCH DML или shard-записями Bulk Upsert.
- Не проверялись предельные размеры batch, request-size limits и throughput.
- Не проверялась пагинация внутри одной долгоживущей пользовательской
  транзакции; документация описывает последовательность обычных запросов.
- Не проверялись колоночные таблицы.

## Открытые вопросы

1. Стоит ли в разделе пагинации явно сказать в первом абзаце, что это не
   snapshot и не opaque continuation token?
2. Нужен ли готовый документированный шаблон NULL-aware keyset pagination для
   nullable составного primary key, а не только предупреждение о проблеме?
3. Следует ли документировать гарантии результата неуспешного Bulk Upsert
   точнее: какие ошибки гарантированно валидируются до первых shard-записей, а
   при каких возможен частичный результат?
4. Нужен ли BATCH DML способ вернуть агрегированное число изменённых строк без
   materialization через `RETURNING`?
