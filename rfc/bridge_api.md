# API управления Bridge

Bridge позволяет разместить один кластер YDB в нескольких пайлах и хранить копии данных в каждом из них. Пайл — группа узлов кластера. Один пайл имеет роль PRIMARY: в нём выполняется основная работа с данными. Другие пайлы хранят синхронизированные копии и могут принять эту роль.

Хотим управлять переходом к такой схеме на работающем кластере: добавлять и выводить пайлы, переключать работу при обслуживании или аварии, видеть причины задержек синхронизации. Для разных БД нужны разные требования к копиям. Если переход к Bridge отменён, должен быть путь обратно в обычный режим.

Предлагается расширить существующий `Ydb.Bridge.V1.BridgeService` для этих задач.

## Подключить второй пайл или убрать ненужный

У компании есть работающий кластер в одном датацентре. Она готовит второй, чтобы переживать отказ первого. Добавление оборудования должно завершиться появлением синхронизированной копии данных, пригодной для переключения работы.

Сначала клиент определяет исходное состояние через `GetClusterState(include_unbridged_status=true)`. У обычного кластера ответ содержит `unbridged_status` без списка пайлов и поколения. Непустой `bridge_config_node_ids` означает, что узлы уже используют bridge конфигурацию, но состояние Bridge ещё отсутствует. Сам по себе этот отчёт не подтверждает готовность к конвертации. После конвертации ответ содержит `pile_states` и `generation`.

Сначала все узлы запускаются с bridge конфигурацией, описывающей пока один пайл. `ConvertToBridge` преобразует кластер: статические группы — при вызове, существующие пулы хранения и их группы — в фоне. `GetClusterState` показывает `conversion_in_progress`; до завершения преобразования менять состав пайлов нельзя.

После добавления пайла и его узлов в конфигурацию `AddPile` создаёт необходимые части хранилища. Пайл переходит из INACTIVE в DISCONNECTED: он подготовлен, но ещё не получает записи. `UpdateClusterState` переводит его в NOT_SYNCHRONIZED и запускает синхронизацию. Переход в SYNCHRONIZED выполняет сервер после её завершения. Успех `AddPile` ещё не означает готовность резервного пайла.

При выводе пайла сначала отключают его от работы, затем вызывают `RemovePile`. Метод удаляет его части хранилища со всеми данными и переводит пайл в INACTIVE. После этого пайл можно удалить из конфигурации.

`AddPile` и `RemovePile` ждут завершения работы контроллера хранилища. При ошибке фоновой попытки вызов может завершиться ошибкой, а сервер продолжит повторять операцию. Прогресс доступен в `GetClusterState.pending_pile_operation`.

## Переключить работу при обслуживании или аварии

Перед обслуживанием нужно перенести работу в другой пайл, при аварии — исключить недоступный. Решение должно применяться к состоянию, которое проверил администратор: параллельное действие другого администратора или автоматики не должно незаметно изменить исходные условия.

Клиент читает `GetClusterState` и передаёт его `generation=G` в `UpdateClusterState.expected_generation`. Обновление применяется атомарно только к поколению G; после фиксации поколение равно G+1. Неуказанные пайлы сохраняют состояние. Сервер проверяет переходы; вручную объявить несинхронизированный пайл синхронизированным нельзя.

Для плановой смены PRIMARY клиент назначает синхронизированный пайл PROMOTED; перенос работы завершает сервер. Для обслуживания используется SUSPENDED с последующим отключением. При аварии недоступные пайлы переводятся в DISCONNECTED; если их несколько, они исключаются одним запросом. Участников кворума определяет новое состояние.

`ABORTED` при проверке поколения означает, что изменение не применено: нужно перечитать состояние и заново принять решение. `UNAVAILABLE` с причиной отставания поколения означает, что принимающий узел ещё не получил G; запрос можно повторить на другом узле. При иной ошибке или потере ответа изменение уже могло примениться — перед повтором требуется проверить состояние.

Старые узлы игнорируют `expected_generation`. Гарантия действует только при поддержке поля узлами, принимающими и исполняющими запрос.

`GetClusterState(include_pile_connectivity=true)` показывает доступность статических узлов и участие пайлов в кворуме. Это наблюдение одной связной части кластера, а не проверка дисков и не способ выбрать сторону, которая должна пережить разделение сети.

## Понять, почему БД ещё не синхронизирована

После подключения или восстановления пайла нужно понять, идёт ли копирование и что мешает его завершению. Нужен путь от общего состояния пайла к конкретной группе хранения, без просмотра всех групп кластера сразу.

`ListPileSynchronization` показывает по пайлам число БД с завершённой, выполняющейся и ожидающей синхронизацией. `ListDatabaseSynchronization` позволяет выбрать пайл, БД и только незавершённую синхронизацию через `only_incomplete`. Ответ содержит пулы хранения БД, счётчики групп и последнюю ошибку. `ListGroupSynchronization` раскрывает выбранную БД или пул до отдельных групп — единиц хранения данных — с их статусом, фазой и ошибкой.

Во всех трёх представлениях используются одинаковые значения:

| Статус | Что происходит |
| --- | --- |
| SYNCED | Обязательная синхронизация завершена. |
| SYNCING | Синхронизация выполняется. |
| PENDING | Синхронизация требуется, но сейчас не выполняется. |
| NOT_REQUIRED | Синхронизация не требуется, например для обычного хранения. |
| UNKNOWN | Наблюдений недостаточно. |

Автоматизация проверяет счётчики в сводках и `sync_status` у групп; для разбора проблемы доступны `sync_phase` и `last_sync_error`. Последняя ошибка может сохраняться после возобновления работы. SYNCED не подтверждает завершение очистки лишних копий или удаления bridge конфигурации с узлов.

Отчёты содержат время наблюдения и поколение состояния кластера. Независимые запросы не образуют общий атомарный снимок. Результат возвращается полностью либо с ошибкой; при превышении бюджета нужно сузить фильтры. Пагинации нет.

Serverless БД использует хранилище shared БД. Запрос по её пути возвращает состояние этого хранилища и путь владельца в `storage_owner_database_path`; общие счётчики учитывают его один раз. Неизвестное размещение или недоступное имя владельца остаются неопределёнными.

## Хранить БД с разными требованиями к копиям

Критичной БД нужны копии в нескольких пайлах, для другой допустимо обычное хранение. Администратор должен менять режим всей БД одним действием: либо всех её пулов, либо ни одного.

`SetDatabaseBridgeMode` принимает абсолютный `database_path` и обязательный `bridge_mode`: `true` включает bridge хранение, `false` — обычное. При отключении можно выбрать `retain_pile_name` с синхронизированной копией; без него сервер выбирает копию автоматически. Уже обычные данные этот параметр не перемещает.

Контроллер проверяет и меняет все пулы БД одной транзакцией. Успех означает фиксацию режима; синхронизация и очистка продолжаются в фоне. Повторная установка текущего режима допустима. `ListDatabaseSynchronization` показывает BRIDGED, ORDINARY или MIXED по совокупности пулов; в MIXED счётчики синхронизации относятся к bridged пулам.

Требуются non-uniform storage, завершённое преобразование контроллера и отсутствие операции над составом пайлов. DDisk пулы не поддерживаются. Для serverless БД меняется режим shared БД, что затрагивает всех пользователей её хранилища.

При первом преобразовании `ConvertToBridge(skip_storage_pool_conversion=true)` позволяет оставить существующие пулы обычными и включать bridge хранение для нужных БД отдельно.

## Отменить переход к Bridge

Если миграция отменена, кластер должен вернуться в обычный режим с сохранением данных. Это ограниченный откат преобразования: он не переносит произвольный кластер с несколькими пайлами в выбранный пайл.

`Rollback` применим, когда остался единственный исходный пайл, он PRIMARY и синхронизирован, а все bridged группы полностью находятся в нём и используют собственные VDisks — inline размещение. Другие пайлы и переопределения размещения предварительно удаляются; незавершённой синхронизации и другой операции быть не должно.

Вызов преобразует статические группы и запускает работу контроллера. После преобразования остальных групп bridge state удаляется; данные и ID групп сохраняются. Успешный ответ означает запуск отката. `GetRollbackStatus` показывает прогресс, ошибки и узлы, ещё работающие с bridge конфигурацией.

После исчезновения bridge state `GetClusterState(include_unbridged_status=true)` возвращает отчёт об узлах с bridge конфигурацией и неотчитавшихся статических узлах. Без этого флага метод возвращает `NOT_FOUND`. Состояния пайлов и поколение к такому отчёту не применяются.

Затем оператор одним изменением удаляет bridge конфигурацию и имена пайлов узлов, перезапускает узлы без них. `complete=true` означает отсутствие bridge state и bridge конфигурации у всех статических и подключённых динамических узлов. Отключённые динамические узлы в отчёт не входят. Если кластер был только подготовлен к Bridge, но не преобразован, достаточно этих действий с конфигурацией и контроля статуса.

## Общие контракты

Запросы используют `OperationParams`, ответы — `Ydb.Operations.Operation` с типизированным `result`. Изменения, диагностика синхронизации и `GetRollbackStatus` требуют прав администратора. Таймаут и отмена запроса не гарантируют отмену начатого изменения.

Диагностика синхронизации требует self-management и явной bridge конфигурации. Без bridge state она возвращает `NOT_FOUND`; невыполненные условия — `PRECONDITION_FAILED`, неверные параметры — `BAD_REQUEST`, недоступность контроллера — `UNAVAILABLE`.

Контракты определены в [описании сообщений](https://github.com/ydb-platform/ydb/blob/0fc7e20b3d5/ydb/public/api/protos/draft/ydb_bridge.proto) и [составе сервиса](https://github.com/ydb-platform/ydb/blob/0fc7e20b3d5/ydb/public/api/grpc/draft/ydb_bridge_v1.proto).
