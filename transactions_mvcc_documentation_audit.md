# Функциональный аудит транзакций и MVCC

Дата проверки: 2026-09-12.

Проверяемая версия: `main`, commit `35fe6b99b6b321ebc724e0c644432b2301f49da6`.

Область проверки: транзакции только над строковыми таблицами. Проверялись Query API, legacy Table API и интерактивный experimental YDB CLI. Баги в трекере не создавались. ASAN не использовался.

Подтверждённых проблем реализации в проверенной матрице нет. Найдены два места, где документация описывает более сильный или неуточнённый контракт:

Новые regression tests не добавлялись: обе находки относятся к формулировке публичного контракта, а проверенные гарантии реализации соблюдаются.

## Методика

Для настоящих конкурентных транзакций были открыты две независимые сессии experimental CLI. Обычный CLI корректно сообщает, что интерактивные `BEGIN`/`COMMIT`/`ROLLBACK` требуют experimental build. Дополнительно one-shot режимы проверялись через `ydb table query execute --tx-mode`, а implicit transactions — через `ydb sql`.

Использовались две таблицы по две партиции; одна таблица имела обычный global secondary index. Проверялись:

- Serializable RW, Snapshot RW, Snapshot RO, Stale RO и Online RO;
- повторяемое чтение и видимость конкурентного commit;
- write/write, read/write и range/phantom conflicts;
- write skew в Snapshot RW и его запрет в Serializable;
- транзакции по двум таблицам и четырём data shards;
- атомарный rollback multistatement DML;
- явный rollback и rollback при закрытии CLI с открытой транзакцией;
- INSERT/UPDATE/DELETE read-your-writes через secondary index;
- запрет записи в read-only modes;
- запрет DDL внутри интерактивной транзакции и смешивания DDL/DML;
- partial DDL при runtime-ошибке последующего DDL;
- `SHOW CREATE` внутри read-only транзакции.

## Проблемы документации

### D1. Снимок создаётся не при явном BEGIN

В `ydb/docs/ru/core/concepts/_includes/transactions.md` Snapshot Read-Only описан как работающий со снимком базы «на момент её старта», а Snapshot Read-Write — как чтение и запись поверх одного снимка.

Ручной сценарий для обоих snapshot modes:

1. Сессия A выполняет явный `BEGIN snapshot-ro` или `BEGIN snapshot-rw`.
2. До первого data-запроса сессия B коммитит изменение `balance: 405 → 505`.
3. Первый `SELECT` сессии A видит 505.
4. После первого `SELECT` последующие конкурентные commits уже не видны.

Таким образом, `BEGIN` создаёт transaction context, но data snapshot лениво фиксируется первым data-запросом. Это согласуется с рекомендацией SDK не делать отдельный begin round trip, однако не совпадает с буквальным «на момент старта транзакции».

Следует явно написать: снимок фиксируется при первом запросе, обращающемся к данным. Это важно, если приложение выполняет внешнюю работу между `BEGIN` и первым `SELECT`.

### D2. Для Stale/Online RO не описано ограничение one-shot

Обзор Stale Read-Only утверждает, что между разными `SELECT` в одной транзакции согласованность не гарантируется. Фактически Query API и Table API не позволяют открыть такую транзакцию отдельным BeginTransaction. Интерактивный CLI отвечает:

```text
Mode "stale-ro" cannot be used with BEGIN — the Query service does not support
open transactions for this mode. Use it as a one-shot transaction mode for a
single statement.
```

Серверные unit tests также ожидают `BAD_REQUEST` для отдельного `BeginTransaction` в Online RO и Stale RO. One-shot `BeginTx(...).CommitTx()` успешно работает, что и показано в большинстве SDK-примеров.

Нужно рядом с описанием modes явно разделить:

- отдельную интерактивную транзакцию из нескольких RPC — не поддерживается;
- один one-shot запрос/скрипт с немедленным commit — поддерживается;
- что именно означает «между разными запросами» для Stale RO.

## Что прошло

### Serializable

- Два чтения одной строки видят одно значение после конкурентного commit.
- При последующей записи транзакция с инвалидированным read lock abort'ится с `Transaction locks invalidated`.
- Две транзакции прочитали обе строки и записали разные строки: первая завершилась, вторая была отклонена на commit, то есть write skew предотвращён.
- Вставка в ранее прочитанный пустой диапазон инвалидировала range lock; phantom не появился в снимке, а последующая запись abort'илась.
- В проверенных конфликтах выигрывала транзакция, завершившаяся первой.

### Snapshot Read-Write

- Повторные чтения после первого data-запроса используют стабильный снимок.
- Две транзакции, прочитавшие одинаковое состояние и записавшие разные ключи, успешно коммитятся: ожидаемый для Snapshot Isolation write skew.
- INSERT, UPDATE и DELETE немедленно видны той же транзакции через global secondary index; после DELETE строка исчезает из index view.
- Явный rollback и выход из CLI с открытой транзакцией не сохраняют изменения.

### Read-only modes

- Snapshot RO сохранил один согласованный снимок сразу для двух таблиц и четырёх шардов при конкурентном распределённом commit.
- Попытка UPDATE в Snapshot RO, Stale RO и Online RO отклоняется как операция в read-only transaction.
- Все пять tx modes успешно выполняют допустимый one-shot SELECT через Table CLI.

### Атомарность и распределённость

- Две UPDATE по двум таблицам и ключам в разных партициях коммитятся атомарно.
- UPDATE, за которым следует конфликтующий INSERT существующего PK, завершился `PRECONDITION_FAILED`; предшествующий UPDATE был полностью отменён.
- При закрытии сессии с незавершённой Snapshot RW транзакцией CLI сообщил о rollback, а значение в таблице не изменилось.
- Смешанный DDL+DML script отклоняется до выполнения.
- DDL внутри открытой интерактивной транзакции отклоняется CLI, транзакция остаётся доступной для явного rollback.

2. Считается ли lazy snapshot частью стабильного публичного контракта для Snapshot RO и Snapshot RW?

4. Следует ли одинаково явно пометить one-shot ограничение Stale/Online RO во всех SDK-вкладках?
