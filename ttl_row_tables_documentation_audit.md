# Функциональный аудит TTL строковых таблиц

Дата проверки: 2026-09-12.

Проверяемая версия: `main`, commit `35fe6b99b6b321ebc724e0c644432b2301f49da6`.

Область проверки: TTL только для строковых таблиц. Основная проверка выполнена
black-box через YDB CLI на локальном кластере; спорный случай `DyNumber` отдельно
перепроверен существующим functional-test harness. Баги в трекере не создавались.
ASAN не использовался.

## Итог

Подтверждённых проблем реализации и расхождений с документацией в проверенной
матрице нет. Новые regression tests не оставлены: отдельный тест отрицательного
`DyNumber` прошёл, то есть предполагаемый дефект не воспроизвёлся.

## Матрица проверки

Проверены TTL-колонки типов:

- `Date`, `Datetime`, `Timestamp`;
- `Uint32` и `Uint64`;
- `DyNumber`.

Для числовых типов проверены секунды, миллисекунды, микросекунды и наносекунды.
В данных присутствовали даты в прошлом и будущем, Unix epoch, `NULL`, дробный и
отрицательный `DyNumber`, а также `Uint64::max` во всех единицах.

Дополнительно проверены:

- TTL, заданный при `CREATE TABLE`, и включение TTL на заполненной таблице;
- минимальный `TTL_RUN_INTERVAL` через CLI;
- повторная проверка значения после `UPDATE`;
- `RESET TTL` до фонового удаления;
- TTL по колонке первичного ключа;
- согласованное удаление из таблицы с global secondary index;
- запрет удаления активной TTL-колонки;
- `RESET TTL` с последующим удалением бывшей TTL-колонки;
- отклонение неподдерживаемых типов и несовместимых единиц;
- сохранение TTL и единицы измерения в `SHOW CREATE TABLE`.

## Что прошло

### Типы и единицы времени

BRO удалил все заведомо просроченные значения и сохранил будущие значения и
`NULL` для `Date`, `Datetime`, `Timestamp`, `Uint32`, `Uint64` и `DyNumber`.
Поведение соответствует формуле из документации:

```text
eviction_time = valueof(ttl_column) + evict_after_seconds
```

Для `Uint64` отдельно проверено максимальное значение
`18446744073709551615`: оно не было ошибочно признано просроченным при
интерпретации как секунды, миллисекунды, микросекунды или наносекунды.

Для `DyNumber` прошли нулевое, отрицательное, дробное будущее значение и `NULL`.
Ручная проверка отрицательного значения сначала дала неоднозначный результат:
строка была вставлена после уже состоявшегося прохода BRO в таблице с интервалом
15 минут. Изолированный functional test дождался удаления нулевого контрольного
значения из той же партиции и подтвердил, что отрицательное значение также
удаляется. Поэтому это не считается дефектом, а тест не добавлен в репозиторий.

### Фоновые изменения

- После включения TTL на заранее заполненной таблице просроченная строка была
  удалена ближайшим фоновым проходом.
- Если до удаления изменить TTL-значение на дату в будущем, строка сохраняется.
- Если отключить TTL через `RESET (TTL)` до прохода BRO, просроченная строка
  остаётся в таблице.
- Просроченная строка с TTL-колонкой в первичном ключе удаляется корректно.

Это подтверждает документированную повторную проверку условия во второй стадии
BRO в пределах проверенных сценариев.

### Secondary index

В таблице с синхронным global secondary index BRO удалил просроченную строку и
из основной таблицы, и из index view. Будущая строка и строка с `NULL` остались
видимы через индекс. Рассогласования основной и индексной таблиц не обнаружено.

### DDL и CLI

- CLI отклонил интервал запуска `1s` сообщением
  `TTL run interval cannot be less than limit: 900`; `15m` принят.
- Удаление активной TTL-колонки отклонено сообщением `Can't drop TTL column ...,
  disable TTL first`.
- После `ALTER TABLE ... RESET (TTL)` колонка успешно удалена.
- `Int64` и `Utf8` в роли TTL-колонки отклонены.
- Для `Date` отклонена явная числовая единица, а для `Uint64` — отсутствие
  единицы.
- `SHOW CREATE TABLE` сохранил `TTL = INTERVAL('PT0S') DELETE ON ...` и, для
  числовой колонки, суффикс `AS NANOSECONDS`.

## Regression tests

Новых тестов нет, поскольку подтверждённых реализационных проблем не найдено.
Для проверки сомнительного `DyNumber` временно использовался black-box test на
основе `ydb/tests/functional/ttl/test_ttl.py`; он завершился успешно и изменение
было удалено из рабочего дерева.

## Ограничения аудита

- Не проверялись колоночные таблицы и tiering во внешнее S3-хранилище.
- Не проверялось взаимодействие TTL с CDC: оно относится к уже отдельному
  аудиту CDC.
- Не выполнялся рестарт data node точно между стадиями scan и erase: CLI не даёт
  надёжно наблюдать эту внутреннюю границу без инструментированного теста.
- Не проводилось длительное измерение production-задержки BRO и метрик: локальный
  test config ускоряет фоновые операции.

## Открытые вопросы

1. Нужен ли публично наблюдаемый статус последнего scan/erase для диагностики
   задержек TTL без анализа логов?
2. Стоит ли документировать максимальный диапазон времени для каждой числовой
   единицы отдельно от диапазона самого типа?
3. Должен ли `SHOW CREATE TABLE` гарантировать дословно повторно исполняемый DDL
   или только семантически эквивалентное представление настроек?
