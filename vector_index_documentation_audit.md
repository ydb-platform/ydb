# Функциональный аудит векторных индексов

Дата проверки: 2026-09-12.

Проверяемая версия: `main`, commit `35fe6b99b6b321ebc724e0c644432b2301f49da6`.

Область проверки: `vector_kmeans_tree` только на строковых таблицах. Баги в трекере не создавались. ASAN по последнему указанию не использовался.

## Итог

Подтверждённых проблем реализации в проверенной матрице нет. Найдены два расхождения документации с фактической валидацией схемы:

| ID | Тип | Краткое описание | Regression test |
|---|---|---|---|
| D1 | документация/валидация | Реальный диапазон `vector_dimension` — 1..65536, в документации — 1..16384 | не нужен |
| D2 | документация | Filter-колонки не могут быть «любыми»: действуют ограничения key types | не нужен |

Поскольку обе находки относятся к документации и не ломают документированные корректные сценарии, новые regression tests для этой области не добавлялись.

## Методика

Проверка выполнена вручную через основной Query API командой `ydb sql`; ключевые metric-запросы дополнительно повторены через Scripting API командой `ydb yql`.

Проверялись:

- quickstart без индекса и с индексом;
- `distance=cosine`, `similarity=cosine`, `distance=manhattan`, `distance=euclidean`, `similarity=inner_product`;
- `float`, `uint8` и `int8`;
- глобальный, фильтрующий и покрывающий индексы;
- две filter-колонки, equality, частичный prefix и range;
- `NULL`, повреждённый бинарный формат, неверные тип и размерность вектора;
- минимальная и фактическая максимальная `vector_dimension`;
- `adaptive_clusters` и `overlap_clusters`;
- INSERT/UPSERT, UPDATE, DELETE и повторная вставка в одной транзакции с последующим чтением через индекс;
- удаление и повторное создание индекса;
- одинаковые запросы через Query API и Scripting API.

Для маленьких наборов `KMeansTreeSearchTopSize` задавался равным числу листовых кластеров, чтобы поиск был исчерпывающим. В остальных случаях результат оценивался как приближённый и не требовал полного совпадения с exact search.

## Проблемы документации

### D1. Диапазон vector_dimension расходится с валидатором

В [vector_index_parameters.md](ydb/docs/ru/core/yql/reference/syntax/_includes/vector_index_parameters.md) указан диапазон `vector_dimension` от 1 до 16384.

Фактическое поведение DDL:

- `vector_dimension=0` отклоняется;
- `vector_dimension=1` принимается;
- `vector_dimension=16385` принимается;
- `vector_dimension=65536` принимается;
- `vector_dimension=65537` отклоняется с сообщением:

```text
Invalid vector_dimension: 65537 should be between 1 and 65536
```

Нужно синхронизировать контракт. Если 65536 — поддерживаемый предел, документацию следует обновить. Если продукт гарантирует только 16384, валидатор должен отклонять большие значения и сообщать тот же предел.

### D2. Filter-колонки не могут иметь буквально любой тип

[vector-indexes.md](ydb/docs/ru/core/dev/vector-indexes.md#векторный-индекс-с-фильтрацией) говорит, что все колонки перед embedding могут быть «любыми».

Попытка создать индекс `ON (category, embedding)` при `category Json` завершается:

```text
Column 'category' has wrong key type Json for being key
```

Это ожидаемо из внутреннего устройства prefix table, но ограничение следует сформулировать явно: filter-колонки должны иметь типы, разрешённые для ключевых колонок YDB (либо привести точный список/ссылку).

## Что прошло

### Quickstart

Точный и индексный поиск для `[1, 1, 1, 1, 4]` вернули одинаковые три строки и значения из документации:

```text
id  CosineDistance
3   0.10557282
2   0.14671814
1   0.19999999
```

Автоопределение `vector_type`, `vector_dimension`, `clusters` и `levels` на непустой таблице сработало.

### Метрики

Все документированные сочетания типа индекса и сортировки прошли:

| Параметр индекса | Функция запроса | Направление | Ближайший id |
|---|---|---|---|
| `distance=cosine` | `Knn::CosineDistance` | ASC | 1 |
| `similarity=cosine` | `Knn::CosineSimilarity` | DESC | 1 |
| `distance=manhattan` | `Knn::ManhattanDistance` | ASC | 1 |
| `distance=euclidean` | `Knn::EuclideanDistance` | ASC | 1 |
| `similarity=inner_product` | `Knn::InnerProductSimilarity` | DESC | 1 |

Результаты совпали через `ydb sql` и `ydb yql`.

### Типы и NULL

- `FloatVector`, `Uint8Vector` и `Int8Vector` индексируются и ищутся корректно.
- Строка с `embedding=NULL` не попадает в индексный результат.
- Записи с пустой строкой, неверным type byte или другой размерностью принимаются основной таблицей, но функции расстояния возвращают для них `NULL`, а векторный индекс их не возвращает.
- Целевой вектор неверного бинарного типа отклоняется индексным поиском понятной ошибкой `Target vector has invalid format`.

Последнее поведение стоит явно описать как эксплуатационное ограничение: тип `String` не обеспечивает schema-level валидацию embedding при записи, поэтому валидировать сериализацию должен клиент.

### Filtered и covering

Индекс с двумя filter-колонками `ON (tenant, category, embedding)`, `COVER (embedding, payload)` и `adaptive_clusters=true` вернул только требуемую категорию и покрытую колонку.

Реализация также принимает более широкие запросы:

- предикаты filter-колонок можно переставлять;
- можно указать только часть prefix-фильтра;
- можно использовать range вместо equality;
- без полного prefix поиск объединяет подходящие prefix-группы.

Это полезное поведение описано менее явно, чем equality-пример в overview.

### Изменения и lifecycle

- INSERT/UPSERT перед чтением того же запроса сразу виден через индекс;
- UPDATE сразу меняет ближайший вектор;
- DELETE сразу удаляет строку из результата;
- повторная вставка того же ключа сразу видна;
- после `DROP INDEX` обращение к `VIEW` корректно отклоняется;
- повторное создание индекса восстанавливает результат.

### overlap_clusters

`overlap_clusters=2` при `clusters=2` принимается и поиск работает. Значение 3 корректно отклоняется сообщением `overlap_clusters should be less than or equal to clusters`.

При `KMeansTreeSearchTopSize=1` индекс с overlap вернул только часть маленькой выборки. Это соответствует документированному приближённому характеру поиска и не считается дефектом.

## Открытые вопросы

1. Какой предел `vector_dimension` является публично поддерживаемым: 16384 или 65536?
2. Нужно ли документировать точный набор разрешённых типов filter-колонок ссылкой на key types?
3. Нужно ли явно предупредить, что malformed embedding принимается в `String`-колонку после построения индекса и молча отсутствует в ANN-результатах?
4. Стоит ли в overview явно описать partial/range prefix search для filtered vector index, раз реализация его поддерживает?
