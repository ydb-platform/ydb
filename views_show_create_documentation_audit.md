# Функциональный аудит VIEW и SHOW CREATE

Дата проверки: 2026-09-12.

Проверяемая версия: `main`, commit `35fe6b99b6b321ebc724e0c644432b2301f49da6`.

Область проверки: представления над строковыми таблицами и `SHOW CREATE` для
таких представлений. Проверка выполнена black-box через Query/Scripting API YDB
CLI. Баги в трекере не создавались. ASAN не использовался.

## Итог

Проблем реализации не найдено. Найдено одно существенное противоречие между
страницами документации.

| ID | Тип | Краткое описание | Regression test |
|---|---|---|---|
| D1 | документация | `CREATE VIEW` утверждает, что `TablePathPrefix` не сохраняется, но реализация и `SHOW CREATE` используют сохранённый prefix | не нужен |

Новые regression tests не добавлялись: обнаруженное расхождение относится к
описанию уже работающего поведения.

## D1. CREATE VIEW неверно описывает TablePathPrefix

В `ydb/docs/ru/core/yql/reference/syntax/create-view.md` сказано, что внутренний
контекст view не видит `PRAGMA TablePathPrefix` из контекста создания, поэтому
ссылки на таблицы обязательно должны быть абсолютными.

Фактическое поведение противоположно. Следующий запрос успешно создаёт view в
`/local/vdir` и сохраняет относительную ссылку `t`:

```yql
PRAGMA TablePathPrefix = "/local/vdir";
CREATE VIEW v_rel WITH (security_invoker = TRUE) AS
SELECT * FROM t;
```

View читается корректно даже тогда, когда внешний запрос задаёт другой,
несуществующий `TablePathPrefix`. `SHOW CREATE VIEW` возвращает:

```yql
PRAGMA TablePathPrefix = '/local/vdir';

CREATE VIEW `v_rel` WITH (security_invoker = TRUE) AS
SELECT
    *
FROM
    t
;
```

Этот результат согласуется со страницей `show_create.md`, где прямо сказано,
что зафиксированный при создании `TablePathPrefix` включается в `CreateQuery`, и
с существующими unit tests `ViewWithTablePathPrefix`.

Нужно удалить из `create-view.md` утверждение об обязательных абсолютных путях и
описать фактическую модель: view сохраняет собственный контекст prefix, а при
чтении не наследует prefix, PRAGMA и named expressions внешнего запроса.

## Что прошло

### Контекст и вложенные views

- View с относительной ссылкой и сохранённым `TablePathPrefix` создаётся и
  читается.
- Другой prefix внешнего запроса не влияет на разрешение внутренних путей.
- Второй view может ссылаться на первый; фильтрация и `NULL` сохраняют ожидаемую
  семантику.
- Попытка сформировать цикл через удаление и пересоздание одного из двух views
  отклоняется уже при `CREATE VIEW`, потому что разворачивание зависимостей
  обнаруживает отсутствующую/циклическую ссылку.

### Security option

- Отсутствующий `security_invoker` отклонён сообщением
  `security_invoker option must be explicitly enabled`.
- Явный `security_invoker = FALSE` отклонён тем же сообщением.
- `TRUE` принимается и сохраняется в `SHOW CREATE`.

Проверка с двумя реальными пользователями и разными ACL не выполнялась; поэтому
подтверждается валидация опции, но не полная authorization-матрица.

### Schema evolution и invalidation

- `SELECT *` во view сразу подхватывает добавленную колонку исходной таблицы.
- После удаления колонки view с явной ссылкой на неё становится невалидным и
  выдаёт `Member not found`; view со `*` продолжает работать с уменьшенной
  схемой.
- Повторное добавление колонки с тем же именем, но другим типом, восстанавливает
  явно заданный view уже с новым типом результата.
- Удаление underlying table разрешено и делает прямой и вложенный views
  невалидными.
- Создание таблицы с тем же путём восстанавливает оба views без их пересоздания.

Поведение соответствует документированному отсутствию tracking зависимостей и
динамической интерпретации `*`.

### SHOW CREATE и DDL lifecycle

- `SHOW CREATE VIEW` вернул ровно одну строку с `Path`, `PathType=View` и
  `CreateQuery`.
- Полученный semantically identical DDL успешно использован после `DROP VIEW`;
  восстановленный view вернул тот же результат и сохранил prefix.
- `SHOW CREATE TABLE` для view и `SHOW CREATE VIEW` для table отклонены с
  `Path type mismatch`.
- `CREATE VIEW IF NOT EXISTS` не изменил существующее определение.
- Неподдерживаемый `ALTER VIEW` отклонён, как указано в документации.
- Внешний запрос к view принимает typed parameters и корректно обрабатывает
  `NULL`.
- Попытка писать во view отклонена; views остаются read-only.

## Ограничения аудита

- Не воспроизводилась документированная кратковременная stale-plan аномалия
  после `DROP VIEW` + `CREATE VIEW`: она уже явно отмечена как известное
  ограничение.
- Не проверялась конкурентная нагрузка во время переопределения view.
- Не поднимался auth-enabled кластер с несколькими пользователями, поэтому
  фактическое применение ACL underlying tables через `security_invoker` остаётся
  за рамками этой проверки.
- `SHOW CREATE TABLE` для сложных table settings проверяется в других аудитах;
  здесь round-trip ограничен объектами `VIEW`.

## Открытые вопросы

1. Считается ли сохранение `TablePathPrefix` стабильным публичным контрактом или
   пока только текущей реализацией `SHOW CREATE`?
2. Какие ещё элементы контекста создания, кроме `TablePathPrefix`, должны
   сохраняться и выводиться в `CreateQuery`?
3. Следует ли CREATE VIEW хранить schema signature явных колонок, чтобы
   восстановление underlying table с несовместимым типом давало более раннюю и
   понятную ошибку?
4. Планируется ли отдельная операция атомарного `CREATE OR REPLACE VIEW` до
   реализации `ALTER VIEW`?
