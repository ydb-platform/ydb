# YDB bridge control plane (skipper) development

Skipper is an external process that watches a YDB cluster in bridge mode through the public gRPC API, performs automatic failover (Auto mode) and offers reviewed Manual plans (failover, switchover, take-offline, rejoin) through a local web administration. YDB never fails over by itself. The Bridge API is `draft`.

## Model

- A **pile** is a named part of one cluster (usually a DC), not a separate cluster. Exactly one pile is stored `PRIMARY`. **Generation** counts cluster-state commits (including no-op updates, YDB follow-ups); it does not version membership details.
- **Writes need every participating pile**; piles do not vote. Config commits (distconf) need quorum inside every config-quorum pile. A failed participating pile stalls the cluster until an external actor disconnects it. Failed piles must be disconnected **together in one request**, because intermediate states still need the other failed piles' quorum.
- **Split brain is possible** if each side disconnects the other. Exactly one active controller must exist, placed in a third failure domain reaching all piles.

### Pile states

| State | Data writes | Config commits | Notes |
| --- | --- | --- | --- |
| `PRIMARY` | yes | yes | stored primary |
| `PROMOTED` | yes | yes | effective placement target for tablets/BSC before YDB commits the stored `PRIMARY`; the follow-up commit needs its quorum, so a failed `PROMOTED` pile stays stuck |
| `SYNCHRONIZED` | yes | yes | may become primary |
| `NOT_SYNCHRONIZED` | stage 2 only, per group sync stage | stage 2 only | hides two internal stages; stage 1 = no quorums and no gRPC listener; stage 2 = both quorums, so its failure stalls config commits and can stall writes. YDB moves it to `SYNCHRONIZED` itself |
| `SUSPENDED` | no | yes | planned shutdown; public update cannot touch it; a failed one cannot be disconnected via the public API |
| `DISCONNECTED` | no | no | rejoin or RemovePile; gRPC listener stopped (expected) |
| `INACTIVE` | no | no | not yet added / removed |

Only a synchronized pile (`SYNCHRONIZED`, `PROMOTED`, `PRIMARY`) can become primary; the public API cannot promote an unsynchronized pile.

StateStorage, SchemeBoard and Board have different per-pile quorum rules; never model them as one shared all-pile quorum.

### Operations (`UpdateClusterState` unless noted)

| Operation | Request |
| --- | --- |
| Failover | failed piles → `DISCONNECTED` in one request; if primary failed, also a synchronized survivor → `PRIMARY` |
| Switchover | target → `PROMOTED`; YDB later makes it `PRIMARY` and old primary `SYNCHRONIZED` |
| Takedown | non-primary → `SUSPENDED` (primary needs switchover first; one-step is rejected) |
| Rejoin | `DISCONNECTED` → `NOT_SYNCHRONIZED` |
| Add / Remove / Convert | `AddPile` (`INACTIVE`→`DISCONNECTED`), `RemovePile` (`DISCONNECTED`→`INACTIVE`, **deletes pile data**), `ConvertToBridge` |

Skipper's Auto mode performs failover only. Manual mode plans failover, switchover, take-offline and rejoin with the same guards (reviewed plan, then execute). Add, Remove and Convert are never sent by skipper.

## Bridge API contract (`Ydb.Bridge.V1.BridgeService`)

**`GetClusterState`**
- Answers from the receiving node's local copy, which may lag. Query several nodes; keep the highest generation within a coherent history. A numeric max is not a quorum read.
- Same generation with different states/roles for the same pile = conflict. A higher generation with the same public vector is legitimate (hidden stage change, no-op update). Do not infer internal stage or commit cause from a generation bump.
- `conversion_in_progress` and `pending_pile_operation` may change without a generation change. Removing an `INACTIVE` pile can change the pile list without one. Match piles by name.
- Opt-in `include_pile_connectivity` returns a per-reporter report (`reporter_node_id`, `reporter_is_root`, `binding_in_progress`, own `generation`, per pile: `static_nodes`, `connected_static_nodes`, `has_node_quorum`, `in_config_quorum`, `in_data_quorum`). It is connectivity of one distconf binding component, not disk health, not a failover vote, with no timestamp/freshness. It is a separate snapshot from the public state: reconcile generation and pile names, never match by position. Missing cross-pile connectivity for `DISCONNECTED`/`INACTIVE` piles is expected. A failed optional query can fail the whole RPC (older nodes); skipper therefore issues it as a separate call so the plain view survives.
- Errors: `UNSUPPORTED` (self-management off), `NOT_FOUND` (not bridged), `UNAVAILABLE` (no bridge config on that node; try another).

**`UpdateClusterState`**: `updates` = list of `{pile_name, state}`; `quorum_piles` is validated but ignored (send empty); set optional `expected_generation` to the decision generation.
- It is an **overlay**: unlisted piles keep their exact internal state. Explicit `NOT_SYNCHRONIZED` stores stage 1; repeating it in stage 2 sends the pile back to stage 1 and resets sync; a synchronized pile cannot go directly to it. Never use rejoin as a status refresh.
- Result must have exactly one primary and at most one promoted pile. Naming a new `PRIMARY` requires explicitly moving the old one (`DISCONNECTED` or `SYNCHRONIZED`); a different pending `PROMOTED` pile must be set explicitly too, or the promotion later overrides the choice.
- New primary/promoted must already be synchronized. Setting `SYNCHRONIZED` requires an already synchronized pile; it can clear a role or explicitly keep an existing `SYNCHRONIZED` state.
- Rejected: targeting `SUSPENDED`/`INACTIVE` piles, setting `INACTIVE`, an actual state change on a pile with pending Add/Remove.
- Only one stored-state change per request, except batch where **all** are `→ DISCONNECTED`. Role changes do not count as stored-state changes.
- **Generation compare-and-set is implemented; no lease or fencing.** With `expected_generation=G`, the receiving node rejects a newer local generation with `ABORTED` and an older one with `UNAVAILABLE`. Distconf checks G again before applying the overlay; a mismatch returns `ABORTED`, and a successful commit has generation G+1. A greater generation within the same coherent history rules out a later commit of an unresolved guarded request. `ABORTED` proves this invocation did not apply, not that every observer is newer than G: the distconf root can lag. Older nodes may ignore the field; require support on every receiving/forwarding node.
- Without the guard, the receiving node stamps generation+1 from its own snapshot. A request delayed before that snapshot can apply a stale overlay to newer state. Only unguarded requests can get synthesized success after a forwarding-hop disconnect by matching the observed state. Guarded requests take the error path instead; matching state never proves invocation identity. A timeout may precede a late commit, and a follow-up may commit before the response arrives.
- Status codes: gRPC-layer validation → `BAD_REQUEST`, no admin rights → `UNAUTHORIZED`, guard mismatch → `ABORTED`, other distconf failures (validation, forwarding race and lost quorum alike) → `INTERNAL_ERROR`. A node without cluster state returns `PRECONDITION_FAILED`; absent bridge config or a local snapshot older than G returns `UNAVAILABLE`. Operation-level `UNAVAILABLE` here is pre-distconf rejection, distinct from a transport failure.
- Distconf re-checks the connected node quorum of every surviving config-quorum pile before every proposition (`StartPropositionImpl` → `HasConnectedNodeQuorum`); a disconnect that leaves a dead participating pile out of the update fails with `INTERNAL_ERROR` rather than committing.
- Send it to a node in a pile that stays in the config quorum after the change (normally the intended primary pile).

**`AddPile` / `RemovePile` / `ConvertToBridge`**: one Add/Remove pending at a time, none during conversion. Add/Remove return when BSC finishes, `GENERIC_ERROR` if BSC errors (YDB keeps retrying). `RemovePile` on a pending Add cancels it. `ConvertToBridge` returns before background BSC conversion ends (watch `conversion_in_progress`); with `skip_storage_pool_conversion` (needs `enable_non_uniform_storage`) pools stay non-bridged, so consumers must allow mixed bridged/non-bridged groups and differing pile membership. Error mapping: `NO_QUORUM`→`UNAVAILABLE`, `RACE`→`ABORTED`, others→`GENERIC_ERROR` (differs from `UpdateClusterState`).

**Reachability**: YDB stops the gRPC listener on `DISCONNECTED`, `INACTIVE` and stage-1 `NOT_SYNCHRONIZED` piles. For those a missing listener is expected. For `PRIMARY`/`PROMOTED`/`SYNCHRONIZED`/stage-2 piles it is not explained by lifecycle. Send rejoin/Add/Remove through a node in a config-quorum pile.

**Auth**: mutating RPCs check `security_config.administration_allowed_sids` (empty list passes everyone who reaches the check). New login tokens need SchemeShard and can fail during a stall; use client-certificate auth (`client_certificate_authorization` mapped to an admin SID) and test it before an emergency. Skipper supports a token file (re-read before every update and after `UNAUTHORIZED`) and client certificate/key/CA (read once; change needs a restart); it has no login/password path.

**Inventory**: `ConfigService/FetchConfig` YAML (`hosts[].location.bridge_pile_name`, `bridge_config.piles[].name`, includes `INACTIVE`). In a converted cluster hosts may lack `bridge_pile_name`: they belong to the implicit pile from the stored pile registry (not an empty name, not the first pile); verify via the node's own SelfCheck `location.pile.name`. `Discovery/ListEndpoints` is database-scoped and omits `INACTIVE` piles; it is not a storage inventory. When implementing discovery, refresh inventory and reconcile with `GetClusterState`; current skipper uses static configured endpoints (policy below) and never calls either RPC.

## SelfCheck evidence semantics (`MonitoringService.SelfCheck`)

Request: `return_verbose_status=false`, `merge_records=false`, `do_not_cache=true`, no filters, empty database (whole cluster), explicit operation timeout. Current skipper reads `issue_log` and responder `location`; verbose mode adds `database_status` and is optional for diagnostics. The timeout is also the server budget: BSC gets half, whiteboards all of it (default 20 s). Short timeouts make fallback mode and `EMERGENCY` more likely under load. Bound every call also with a client deadline (skipper: operation timeout + 2 s).

- **Single source.** Normal-mode storage state comes from BSC, a single tablet in the effective primary pile. Agreeing replies from many nodes are one source, not independent probes. Replies can still differ by snapshot timing and local cluster-state filtering. SelfCheck has no generation, so a reply cannot be tied to a cluster state.
- **Issues that matter**: `BRIDGE_GROUP` identifies a pile's part of a bridged group, at `location.storage.pool.group.pile.name`. `STORAGE_GROUP` is a logical group verdict, or a static-group part in fallback (same pile-name field). `PILE_STATE_STORAGE`/`PILE_SCHEME_BOARD`/`PILE_BOARD` (`location.compute.state_storage.pile.name`) measure ring-node whiteboard availability, not service or quorum health. `BRIDGE_PILE` (`location.compute.pile.name`) concerns compute; `STORAGE` with "System tablet BSC didn't provide information" marks fallback. `HEALTHCHECK_STATUS` warns of size or truncation; its presence alone does not mean truncation. Issue types/messages are not a versioned contract: pin and test parsers per release.
- **Pile-part coverage.** `BRIDGE_GROUP` covers synchronized and internal stage-2 parts; stage 1, `SUSPENDED`, `DISCONNECTED`, `INACTIVE` are excluded. Logical group: all synchronized parts RED → RED; some RED → at least ORANGE; stage-2 degradation raises it only to ORANGE and never counts as a usable copy. A missing `BRIDGE_GROUP` issue is not a failure report and not a health proof.
- **Lost BSC connection to a node** marks that node's VDisks `ERROR` (RED after the next ~5 s sysview publication).
- **BSC restart**: a VDisk without a status is reported GREEN; BSC turns it `ERROR` only after ~15 s (15–20 s with the 5 s cycle, not a hard bound). Nothing in the reply shows BSC initialization is incomplete, so BSC-backed replies right after BSC returns (after a primary change or after the fallback issue disappears) are not evidence of health.
- **Fallback (BSC silent for half the timeout)**: only static groups, from the whiteboards of nodes the responder reaches; incomplete and responder-dependent, so different piles may legitimately differ during a partition. A missing group record omits the part entirely. Pile state is not filtered. Per static disk: answered and listed → evaluated; answered but absent → RED. Observed undelivery/session loss → RED even while retries remain; an unreachable PDisk also emits RED `Storage node is not available`. A received reply of that request kind takes precedence; otherwise a shared node-level failure marker also affects missing replies of the other disk kind. No reply and no observed transport failure by final timeout → **GREY "has no data"**, except a missing VDisk with known RED PDisk state is RED. A group with only unknown bad disks has no RED group issue; it gets GREY `Group has disks with no data`. Pool/storage aggregates can still be RED because they account pessimistically for unknown disks.
  - Treat GREY `... no data` (with or without pile name) as **unknown**: neither healthy nor failed, never a basis to promote.
  - RED `BSC didn't provide information` is not a pile failure.
  - A silent loss can yield "no data" if no disconnect/undelivered was observed before the deadline. Missing replies alone cannot establish primary loss; use qualifying connectivity evidence.
  - **Server-side scope rule for skipper changes to `health_check.cpp`**: the unknown-vs-failed distinction exists only at the STORAGE_GROUP/VDISK level, which skipper reads. Pool, storage and node statuses keep their pre-existing pessimistic behavior (a pool counts no-data disks as failed; a node whose whiteboard request was undelivered is RED). When touching the fallback path, change only group-level issues and add pool assertions (`CheckStaticPool` in `health_check_ut.cpp`) to new whiteboard tests.
- **Replication**: `REPLICATING` VDisks are BLUE and count toward a group's failed-disk threshold, so a group can go RED during replication. Keep the VDisk reasons behind a RED group; distinguish replication from demonstrated unavailability.
- **Large replies**: the server attempts to trim issues BLUE→YELLOW→ORANGE→RED near 50 MiB; GREY issues are retained, so trimming does not guarantee a bounded result. `HEALTHCHECK_STATUS` warns YELLOW above 30 MiB, ORANGE above 40 MiB, RED at the truncation threshold. Treat a truncated reply as incomplete.
- RED group thresholds: `block-4-2` RED with more than 2 failed disks; `mirror-3-dc` with failures in all three realms or more than one failed disk in each of two realms. A single RED group in a pile does not by itself define a policy of disconnecting the whole pile; that must be an explicit decision. Skipper's current policy: any RED group part attributed to a pile in every fresh BSC-mode reply, held for `confirm_seconds`, makes the whole pile Failed; one fresh reply suffices. The docs do not yet state this explicitly (open decision D5 in the 003 plan).

## Current skipper policy and review boundaries

These describe the C++ controller at the snapshots cited above, not guarantees supplied by YDB. Preserve the distinction between raw evidence, a policy verdict and qualification on a real cluster. Defaults: state poll 1 s, read timeout 1 s, round 1 s, SelfCheck operation timeout 4 s (client 6 s), evidence TTL 8 s, confirm 2 s, BSC warm-up 30 s (minimum 20), mutation operation timeout 25 s (client 27 s), 2 health endpoints per pile. These defaults target a committed steady-state failover within 20 s when failure evidence and a surviving commit quorum permit it; blockers and the post-role-change warm-up never expire into authorization. Explicit timing overrides retain their values and can exceed that target.

1. **Freshness and pile attribution.** Use monotonic request-send timestamps and TTL, never batch completion time. Health and connectivity evidence require verified pile attribution and a current endpoint view; `VERIFIED` does not establish remote cluster identity. A successful SelfCheck without a responder pile keeps the prior pile-attribution state and cached pile-named reply, with its original send time and TTL, and reports `ENDPOINT_PILE_UNVERIFIED`. It neither adds fresh evidence nor extends cache lifetime. Named fallback/truncation replies still replace the cache; a named mismatch (`ENDPOINT_PILE_MISMATCH`) excludes the endpoint from views, evidence and routing until a matching reply. Select the highest fresh compatible generation, block equal-generation state conflicts (`VIEW_CONFLICT`) and regression below the persisted high-water mark (`STALE_HISTORY`). Matching public views do not prove a globally coherent history.
2. **Confirmation.** All Down (`Failed` or `Lost`) piles must be confirmed before one batch disconnect. Confirmation spans supporting evidence send times, not `down_since`. A primary/promoted role change clears all confirmations; otherwise a generation change clears only changed pile states. Unchanged states can retain ordinary BSC/Lost confirmation; the plan built afterwards always carries the new generation. Fallback failure confirmation restarts on every observed generation change and on every switch between ordinary, generic fallback and storage-failure evidence.
3. **Health.** Verdict precedence is Failed, Lost, Replicating, Healthy, Unknown; Replicating is never Down. Failed requires every usable fresh BSC-mode reply to attribute a RED group part to the pile, after separating replication-only and incomplete reasons. Healthy requires a continuous clean BSC window of `bsc_warmup_seconds`. Reset that window on role changes, unclean evidence, fallback from the BSC-host pile (PROMOTED, else PRIMARY), fallback→BSC return, or an excessive evidence gap. After an observed primary/promoted role change, only clean evidence sent at or after its monotonic observation time can seed or advance the replacement window. Fresh earlier evidence remains usable for negative verdicts; initial role establishment retains request-send timing. BSC replies share one source; fallback/GREY/truncation do not prove health, and a missing group issue alone proves nothing. With no fresh BSC reply anywhere, only the BSC-host pile (PROMOTED, else PRIMARY) can become Failed from fallback: every current outside fallback reply must attribute a RED static STORAGE_GROUP part with complete unambiguous VDISK reasons, at least one actual RED, no GREY/unknown reason and no truncation; an own node-quorum claim vetoes generic fallback failure. It does not veto the separate storage proof: every current outside fallback reply must name a RED static group whose complete unique reason graph consists only of RED VDisks caused by explicitly reported same-node, same-pile PDisk `DeviceIoError`. Reject mixed transport/replication reasons, missing or ambiguous IDs, wrong locations and truncation; a generic RED issue or silent I/O hang does not establish this proof. Admit only sends after the observed generation and, on role change, its observation plus BSC warm-up. Confirmation spans `confirm_seconds` within that generation. Missing, GREY and replication-only parts cannot establish failure. The aggregate `fallback_red` flag remains a RED/GREY/incomplete candidate veto, not failure proof by itself.
4. **Connectivity.** Lost requires settled outside reports that all show config-quorum participation without node quorum, and no self report claiming node quorum. Binding reports remain usable for positive participation, self-quorum and survivor-visibility checks, not negative loss claims. This is controller policy, not a freshness guarantee from distconf. Persistently binding reports can prevent automatic detection of silent loss (measurement M1 open). Mutation routing retains the queried URI and requires that receiving endpoint's own valid report to show node quorum for every surviving config-quorum pile. A different endpoint in the same pile, or the forwarded reporter node ID, cannot substitute for that provenance. Known gap: a `NOT_SYNCHRONIZED` pile whose participation is unknown is treated as participating by the decision but is not a required survivor in the receiver check (`domain/mutation.cpp:107`); the server rejects such a partial disconnect, so the cost is delayed failover, not a wrong commit (open decision D4).
5. **Participation and candidates.** Assess `PRIMARY`, `PROMOTED`, `SYNCHRONIZED` and stage-2 `NOT_SYNCHRONIZED`; stage 2 is inferred from `in_config_quorum` in any valid report or from a fresh BSC part (`in_data_quorum` is decoded but unused). Unknown participation yields verdict Unknown and, when nothing is Down, decision UNKNOWN; it does not hold back a batch for other confirmed-Down piles. Keep a primary that is not Down, regardless of its verdict (open decision D1 versus the historical "evidence shows it is healthy"). If it is Down, prefer an eligible `PROMOTED`, then the name-ordered eligible `SYNCHRONIZED` pile. Eligibility is Healthy, or, with no fresh BSC-mode reply from a verified current endpoint anywhere, self quorum (binding report allowed), its own fresh non-truncated fallback reply, and no fallback RED/GREY group part attributed to the candidate by any current responder. A missing own reply blocks eligibility; there is no additional candidate confirmation window. This is an explicit policy assumption, not proof of full disk health; real-cluster qualification (M3) remains open. With BSC available, candidate fallback evidence is not a separate veto. `SUSPENDED` piles get a verdict but never participate; a Lost `SUSPENDED` pile is the first-checked blocker `SUSPENDED_PILE_LOST`.
6. **Scheduling.** Bound every RPC with operation and client deadlines. Schedule state, connectivity and SelfCheck independently; a pending call must not block other observations. An endpoint/method slot remains occupied until its future settles, even after its deadline; there is no actor watchdog. Config validation enforces `state_poll + read_timeout < evidence_ttl` and `selfcheck_op + 2 + round_interval < evidence_ttl`.
7. **Guarded mutations.** Persist the pending update before sending; a state-file write failure blocks all dispatch (`STATE_WRITE_FAILED`). At generation G, allow only the identical guarded update or a replacement retaining every pending entry and adding only `DISCONNECTED` targets. Reevaluate before resending; identical retries after an ambiguous result back off exponentially (`mutation client timeout · 2ⁿ`), capped at five minutes. A permitted superset replacement resets resend state and does not inherit that delay. A pre-distconf `NotAppliedHere` result (`UNAVAILABLE`, `PRECONDITION_FAILED`) permits trying another endpoint at once. Never change the pending primary at G or treat matching state as invocation proof. A newer coherent generation resolves the old guard; SUCCESS and ABORTED both raise the high-water mark to G+1. A Rejected result (`BAD_REQUEST`, `UNAUTHORIZED`) retains the durable pending record because earlier attempts may still commit, and stops Auto at that generation in the current process (process-local latch). Restart preserves the same-generation overlay restriction and resends the identical record once. Token files are re-read before updates and after UNAUTHORIZED replies, so ordinary rotation needs no restart. Rotation does not clear a rejected mutation's Auto stop: fix the rejection's cause and restart, or observe a newer generation, retaining the pending overlay restriction. Every other status, including `INTERNAL_ERROR`, is Ambiguous; the server's error text is logged only, never parsed. No guard provides fencing across divergent histories.
8. **Single controller.** Exclusive mutation authority and placement in a third failure domain remain operational requirements. The local state-directory lock (`skipper.lock`) does not exclude another host or administrator. YDB's promotion, synchronization and suspension follow-ups are expected (`ExplainTransition` whitelist: promotion completing, `NOT_SYNCHRONIZED`→`SYNCHRONIZED`, `SUSPENDED`→`DISCONNECTED`, absent==`INACTIVE`, own update); unexplained transitions are logged at WARN, counted (`skipper_unexplained_state_change_total`) and alerted, not automatically blocked. Operator Add/Remove completion, CLI switchover and rejoin outside skipper count as unexplained.
9. **Inventory.** Current skipper uses configured single-node endpoints keyed by pile; SelfCheck verifies only the configured pile name. Independently verify that all endpoints belong to the intended cluster. `cluster_id` is a local configuration/state-directory label, not an identifier read from YDB; matching pile names do not establish cluster identity. Unknown endpoints' views can raise the durable high-water mark before SelfCheck returns, and correcting inventory does not lower it. Skipper does not call FetchConfig/ListEndpoints; membership changes require a configuration change and restart. Configured piles absent from the view are warned about and skipped; view piles without endpoints are assessed from other piles' evidence. See the inventory API contract above when implementing discovery (decision D7).
10. **Manual mode, lifecycle plans and blockers.** Manual and Auto derive the same failover `Decision`; mode only gates dispatch. Manual lifecycle plans (`PlanLifecycle`): switchover needs a Healthy `SYNCHRONIZED` target and demotes any other `PROMOTED`; take-offline accepts only a `SYNCHRONIZED` non-primary (the primary needs a switchover first); rejoin accepts only `DISCONNECTED`. All lifecycle plans are refused while a failover is Ready or Confirming, while a `SUSPENDED` pile is Lost, or while the target has a pending Add/Remove or conversion is in progress. Lifecycle mutations are dispatched only through an endpoint whose pile stays in the final config quorum (the take-offline target's endpoints are excluded explicitly, and a rejoin target gets no rank because it is `NOT_SYNCHRONIZED` in the update). Pending Add/Remove information is displayed and gates lifecycle on that pile, but is not a blanket failover blocker: the server rejects an actual state change on the affected pile. Auto never dispatches lifecycle operations. Plans are reviewed (`POST /api/plans`, 120 s TTL, bound to `snapshot_revision`) and executed (`POST /api/operations` with `request_id` receipts and the per-process `boot_id`); mode changes go through `POST /api/mode` with `expected_boot_id`/`expected_mode_revision`, and Auto additionally needs a reviewed snapshot revision. `--clear-pending-mutation` forces Observe.
11. **Dispatch freshness.** Pending history does not authorize a new RPC by itself. Each launch has an ephemeral inclusive `ValidUntil`, the minimum admitted view, health and connectivity send time plus evidence TTL. Recheck it after synchronous actor writes and, in the SDK adapter, after token reload immediately before launch. Local expiry publishes `EVIDENCE_EXPIRED` without an RPC, completion, sent bookkeeping or retained update slot. Preserve pending history; fresh evidence may authorize a later attempt without treating local expiry as server rejection or an ambiguous RPC.
12. **Conservative ABORTED floor.** Skipper classifies ABORTED as GenerationMoved, clears pending and persists a high-water mark of at least G+1. A lagging root can return ABORTED while coherent history remains at G, so Auto and generated Manual plans can remain blocked indefinitely (`STALE_HISTORY`). Restart and `--clear-pending-mutation` do not lower this floor; only deleting `state.json` does, which the runbook labels split-brain-prone. Check actual generation/history through independently trusted cluster endpoints; do not lower the floor or remove the guard to force an old plan. Follow the existing recovery constraints in `ydb/apps/bridge_skipper/docs/operations.md` (decision D6).

For Auto qualification, use the real-response recordings (10 cases, stored as `domain/ut/fixtures/real_<case>.pbtxt`) and loaded-cluster measurements M1–M4 in `ydb/apps/bridge_skipper/README.md`. Synthetic fixtures, unit tests, `ydbd_mock` and acceptance passes do not close them.

## Reviewing a skipper commit

Check each of these against the diff:

- Does a decision rest on a single sample, a stale reply, a batch timestamp, or one shared-BSC source counted as several?
