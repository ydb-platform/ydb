## 1.2 История YDB

Решение о создании собственной СУБД было продиктовано потребностью
в масштабируемости и высокой доступности. Эти свойства критически важны
для инфраструктуры крупной интернет-компании, где каждый сервис должен быть способен
обслуживать многомиллионную аудиторию и работать непрерывно.

В 2008 году перед нами стояла задача построить
базу данных, предназначенную для веб-робота, кроулера. Эта база
используется для построения индекса, необходимого для обработки
поисковых запросов.

Тогда мы считали, что у нас достаточно надёжное оборудование --- около
20 машин, которые редко выходили из строя. Сохранность данных на
дисках обеспечивал обычный RAID. Мы использовали псевдошардированную
базу данных, написанную на C++, --- достаточно эффективную, с основным
алгоритмом sort-merge.

Большинство задач обработки данных в этой базе выполнялось локально на
конкретной машине. Однако иногда возникали более сложные запросы,
например посчитать page rank. Для их решения требовалось, чтобы все
машины были доступны одновременно и могли обмениваться данными.
Механизмы распределённого консенсуса и распределённых транзакций
в этой системе не использовались.

Интернет рос, вместе с ним должна была расти и наша база, нам
приходилось все время добавлять ресурсы. Мы были вынуждены шардировать
данные, к чему зачастую готовились по нескольку месяцев, ведь для этого
нужно было написать новую программу. При каждом шардировании схема 
раскладки данных менялась,
предыдущая программа устаревала, и её приходилось дописывать или
писать заново.

Для решения проблем устойчивости и масштабируемости в 2011 году
была создана новая система KIWI. Она использовала key-value-подход
и consistent hashing для распределения данных по хеш-рингу, что
позволяло масштабировать базу горизонтально в кросс-ДЦ-конфигурации.

Ряд архитектурных решений KIWI был специфичен для задачи веб-робота.
Например, репликация и обработка данных выполнялись во время
background-процесса мерджа. Основной объём данных хранился на дисках в
виде отсортированных по ключу последовательностей записей. А новые
данные или информация об изменении старых, то есть дельта, хранились
отдельно, тоже отсортированные по ключу. И когда их накапливалось
определённое количество, начинался мердж, все данные перечитывались и
записывались в качестве новой «основной базы», отсортированные по ключу.
В процессе мерджа данные полностью перечитывались и переписывались, что 
позволяло одновременно выполнять их обработку, считать статистику и
выполнять другие вычисления. Это позволяло экономить IOPS и
эффективно утилизировать ресурсы. Удаление данных происходило через
политики хранения, фактически по TTL: мы помечали, что данные можно
удалить из базы, если они не обновлялись.

После запуска в продакшн кластер KIWI составлял порядка 600 нод ---
на тот момент это превышало крупнейшую публичную инсталляцию Cassandra
примерно вдвое.

По мере активной эксплуатации стали проявляться аномалии, вызванные
eventual consistency. Например, для анализа данных требовался
консистентный срез, но получить его в этой системе было сложно.
Каждую конкретную проблему приходилось решать на стороне прикладного
разработчика.

Периодически обнаруживались новые возможные варианты
раскладки данных, которые необходимо было предусматривать в прикладном
коде. Сложность инфраструктуры транслировалась в сложность приложений,
которые и без того были непростыми.

Параллельно рос спектр задач, связанных с хранением и обработкой
данных: хранение временных рядов для мониторинга, персистентные очереди
для доставки логов, решения для обработки данных в реальном времени.
Требовались и классический key-value store, и масштабируемая
реляционная NewSQL база данных.

Было принято решение создать единую платформу, которая решала бы
общие для всех этих систем проблемы: распределённый консенсус,
репликацию данных для отказоустойчивости, распределённые транзакции.
В каждой из существовавших систем низкоуровневый слой был реализован
по-своему, и репликацию приходилось делать разными способами и с различным 
качеством.

Важной целью было обеспечить поддержку класса интерактивных приложений
(internet scale applications) --- приложений, которые должны быть
постоянно доступны и отвечать пользователям за приемлемое время.
Платформа должна была позволить строить поверх неё высокодоступные,
отказоустойчивые и масштабируемые приложения.

Результатом стала YDB --- геораспределённая NewSQL база данных,
предоставляющая надёжное хранение данных с автоматической репликацией,
распределённые ACID-транзакции со строгой консистентностью, высокую
пропускную способность при малом времени отклика, автоматическое
восстановление после сбоев и горизонтальную масштабируемость на тысячи
и десятки тысяч нод, позволяющая формулировать запросы при помощи
декларативного языка запросов YQL.

Для конечного пользователя YDB предоставляет ряд абстракций. Прежде
всего это понятие таблицы. Она представляет
собой набор строк, соответствующий схеме данных. Строка содержит
значения колонок определённых типов. Некоторые из колонок должны
составлять primary key, по которому происходит сортировка. Таблица
шардируется горизонтально, нарезается на шарды --- так обеспечивается
масштабируемость, и мы можем хранить таблицы произвольного размера. Их в
базе данных может быть несколько.

Рассмотрим ключевые свойства YDB подробнее. Автоматический split-merge
шардов работает в режиме реального времени: когда шард таблицы
накапливает слишком много данных или, наоборот, становится слишком
маленьким, система без участия администратора разделяет его на
несколько или объединяет соседние шарды для снижения накладных расходов.

Автоматическое восстановление после сбоев происходит за время,
сопоставимое со временем обнаружения отказа. На практике обнаружение
сбоя зачастую занимает больше времени, чем собственно восстановление ---
перезапуск упавших компонентов на других нодах кластера.

Синхронная репликация данных работает в том числе в геораспределённой
конфигурации. Если запись в систему завершилась успешно, данные
гарантированно сохранены --- даже если сразу после подтверждения записи
происходит отказ дата-центра. Данные не «доедут позднее»: они надёжно
зафиксированы в момент получения подтверждения и доступны для чтения.

YDB обеспечивает serializable-транзакции по умолчанию --- уровень
изоляции, который не предоставляют многие даже нераспределённые СУБД.

Первоначально YDB проектировалась в первую очередь для обработки
OLTP-нагрузок. Система
оптимизирована для большого количества транзакций в единицу времени,
каждая из которых затрагивает относительно небольшой объём данных.
Однако также реализована поддержка колоночных таблиц для
OLAP-запросов, работающих с большими объёмами данных для аналитики.

YDB прошла долгий путь развития: от key-value хранилища до полноценной
NewSQL базы данных с сильными гарантиями консистентности и поддержкой
распределённых ACID-транзакций. Сегодня YDB активно используется в
самых разных компаниях, решая задачи высоконагруженных
интерактивных приложений, требующих одновременно высокой доступности,
масштабируемости и строгой консистентности данных.

В следующих разделах мы подробно рассмотрим архитектуру YDB и поймем,
какие технические решения позволили получить все перечисленные
свойства системы.
