## 1.4 Устройство системы YDB

### Акторная система

В основе YDB лежит акторная система, позволяющая строить YDB из акторов, обменивающихся сообщениями.
Для обмена сообщениями между акторами, работающими на разных узлах, используется подсистема интерконнект,
осуществляющая сериализацию сообщений и их передачу по TCP между узлами.

### Распределённое хранилище

Все данные хранятся в отказоустойчивом распределённом хранилище. YDB работает с блочными устройствами напрямую,
соответственно, роль, аналогичную роли файловой системы, выполняет PDisk. PDisk делит блочное устройство на
нумерованные чанки по 128 мегабайт; можно рассматривать чанки как аналог файлов.

Поверх каждой «файловой системы» PDisk работает порядка 8 VDisk, каждый из которых можно рассматривать как
базу ключ-значение данных, хранящую блобы (двоичные строки размером от 1 байта до 10 мегабайт) по LogoBlobID
(короткому двоичному ключу специального вида).

Блобы иммутабельны, то есть они могут быть записаны, после этого многократно прочитаны и затем удалены. Ключи
блобов не могут быть переиспользованы. VDisk сохраняет блобы в чанках PDisk и во время работы держит в памяти полный
индекс всех хранимых блобов.

VDisk может быстро писать блобы небольшого размера, но не может эффективно хранить много таких блобов длительное время.
В VDisk применяется LSM-дерево (Log-Structured Merge Tree).

VDisk объединяются в группы из 8-9 штук для обеспечения отказоустойчивости. В зависимости от режима избыточности
хранения, используемого в группе, на несколько VDisk группы записываются либо реплики блоба, либо полученные
в результате erasure-кодирования части блоба.

VDisk группы обмениваются peer-to-peer метаданными о хранимых блобах, и при потере данных на множестве VDisk группы,
не превышающем модель отказа, VDisk выявляют потерю и восстанавливают избыточность хранения.

Конфигурацией распределённого хранилища управляет BS_Controller. BS_Controller может создавать группы и
заменять входящий в состав группы VDisk на новый. Автоматическая замена не работающих длительное время
(1 час) VDisk называется Self Heal.

На каждом узле работает актор NodeWarden, который подключается к BS_Controller и получает актуальную конфигурацию.
NodeWarden запускает все PDisk и VDisk, которые должны быть запущены на узле в соответствии с конфигурацией.

### Таблетки

Пользователи распределённого хранилища — таблетки (от Tablet, табличка) — реплицированные конечные автоматы,
работающие поверх общего лога (RSM over shared log). Таблетки взаимодействуют с группой хранения через
актора DSProxy этой группы, который порождает актор-запрос, выполняющий erasure-кодирование данных и
реализующий сложные протоколы для того, чтобы таблетка получила необходимые гарантии от распределённого хранилища.

Так, гарантируется, что если DSProxy отвечает на запись OK, то блоб был надёжно сохранен с необходимой избыточностью
на энергонезависимых носителях и не будет потерян, если не будет превышена модель отказа. При чтении записанного
ранее и ещё не удалённого блоба гарантируется, что блоб либо будет успешно прочитан, либо будет возвращена ошибка,
говорящая о временной недоступности части системы.

Важным свойством распределённого хранилища является наличие специальной операции Block, позволяющей
реализовать таблетки поверх распределённого хранилища. Block принимает идентификатор таблетки и блокируемый
номер поколения и завершается успехом только в случае, если кворум VDisk ответит OK. VDisk отвечает OK на
Block, только если ранее не выполнялась блокировка для такого же или большего поколения этой таблетки и
VDisk надёжно сохранил на PDisk (в энергонезависимую память) информацию о блокировке.

В состав LogoBlobID входит идентификатор пишущей его таблетки и номер её поколения, что позволяет VDisk
отвечать ошибкой при попытке записи блоба из старых (меньших) поколений таблетки. В результате не более чем
один экземпляр таблетки может успешно выполнить блокировку и далее успешно выполнять запись блобов в группу.
Если другой экземпляр заблокирует группу, старый экземпляр не сможет выполнить запись блоба с необходимой избыточностью
и получит ошибку.

Распределённое хранилище является единственным источником гарантий единственности способного писать экземпляра таблетки.

Таблетки изменяют состояние транзакционно и хранят лог операций в виде блобов в распределённом хранилище (характерный размер записи — 100 байт).
Когда накапливается большое количество записей лога, таблетка записывает снимок состояния в компактном виде (один или несколько
блобов по 8 мегабайт) и удаляет старую часть лога.

Таблетка имеет «локальную базу» — одну или несколько таблиц, состоящих из типизированных колонок. Характерный размер локальной базы — до 2 гигабайт.
Операции с локальной базой — транзакции — написаны на C++ и могут читать, писать и удалять данные в таблицах. Локальная база хранится в виде
блобов построчно.

Таблетка может хранить часть данных не в локальной базе, а непосредственно в виде блобов с двоичными данными произвольного формата в распределённом хранилище.

### Инфраструктура

Запуск системных таблеток, таких как BS_Controller, выполняют специальные акторы Bootstrapper. Запуск большинства таблеток выполняет
специальная таблетка Hive, которая выполняет роль оракула для назначения поколений таблеткам. В результате большинство таблеток успешно
запускаются без гонки за блокировку распределённого хранилища.

Таблетка Hive хранит информацию о конфигурации запускаемых ею таблеток и управляет тем, какие таблетки запускаются на каких узлах.
Для этого на каждом узле работает актор Local, который подключается к Hive и запускает или останавливает таблетки по команде от Hive.

Hive взаимодействует с BS_Controller для получения информации о группах хранения и назначения групп хранения, используемых конкретной таблеткой.

Для того чтобы найти таблетку по её идентификатору TabletID, используется распределённая система in-memory хранения метаданных о таблетках — StateStorage.
При запуске таблетки специальный актор StateStorage Guardian записывает информацию о том, где запущена таблетка, на кворум реплик StateStorage.

При необходимости отправить сообщение таблетке её поиск выполняется путем запроса в StateStorage. Для удобства взаимодействия с
таблеткой существует специальный актор TabletPipe, выполняющий поиск таблетки и обеспечивающий упорядоченную доставку таблетке передаваемых ему сообщений.

Большие таблицы базы данных могут состоять из одной или множества таблеток DataShard, хранящих часть строк этой таблицы.

Таблетка SchemeShard хранит информацию о том, какие таблетки соответствуют каким частям каких таблиц.
Для распространения информации о схеме используется распределённая in-memory система хранения SchemeBoard.

### Транзакции и запросы

Специальные таблетки Coordinator и Mediator, а также TxAllocator взаимодействуют между собой и с таблетками SchemeShard, DataShard и другими для
обеспечения возможности выполнения детерминированных распределённых транзакций, примерно так, как это сделано в Calvin.

Пользователи YDB могут писать запросы на языке YQL — SQL с дополнительными операциями, позволяющими более эффективно использовать базу данных.

Компиляцией запросов на языке YQL управляет сервис CompileService.
Для компиляции запроса создаётся отдельный актор, который запускает
YQL-конвейер и получает результаты его асинхронных этапов через future.
В конвейере выполняется парсинг запроса, строится AST и последовательно
применяются оптимизирующие преобразования. Результат — физический план
выполнения запроса, представленный ориентированным ациклическим графом
(DAG): он описывает вычисления и обмен данными между ними.
Полученный план исполняет KQP, организуя работу вычислительных акторов
и обращения к шардам.
