## 5.2 Канал к таблетке

Канал к таблетке, или пайп (tablet pipe), позволяет актору обращаться
к таблетке по её идентификатору. Пайп находит ноду, на которой работает
таблетка, устанавливает соединение с её пайп-сервером и сообщает
владельцу о результате подключения и завершении соединения. Так
обнаружение таблетки и отслеживание её перезапусков, переездов между
нодами и разрывов связи сосредоточены в одном механизме.

Сообщения, передаваемые таблетке по одному пайпу, сохраняют порядок
отправки. При разрыве соединения доставленная последовательность
образует префикс отправленной. Если актор отправил сообщения 1, 2, 3,
таблетка может получить все три сообщения, только 1 и 2, только 1 или
ни одного. Получить 1 и 3, пропустив 2, она не может. Прикладной протокол
учитывает неопределённость результата запроса, оставшегося без ответа:
таблетка могла выполнить операцию до разрыва связи.

Параметр RetryPolicy задаёт повторные попытки первоначального подключения.
До завершения подключения пайп накапливает отправленные ему сообщения;
после установления соединения начинает передавать их таблетке. Владелец
клиентской стороны пайпа (Owner) получает TEvClientConnected: поле Status
сообщает, удалось ли подключение. При завершении уже установленного
соединения владелец получает TEvClientDestroyed. Для дальнейшего общения
с таблеткой он создаёт новый пайп и определяет по прикладному протоколу,
какие запросы нужно повторить.

Ответы таблетки идут непосредственно прикладному отправителю через
акторную систему. Для удалённого отправителя ответ следует направлять
через ту interconnect-сессию, по которой пришёл запрос. Её ActorId записан
в поле InterconnectSession полученного IEventHandle. В хендле ответа
с помощью Rewrite указывают тип TEvInterconnect::EvForward и адрес
этого актора сессии, затем отправляют хендл через акторную систему.
Для локального сообщения поле InterconnectSession пусто и ответ
отправляют непосредственно актору.

Так ответ остаётся связан с сессией исходного запроса. В пределах
одного канала этой сессии ответы сохраняют порядок отправки, а при
разрыве доставленная последовательность образует префикс отправленной.
Если указать только адрес удалённого актора, interconnect proxy
выберет текущую сессию,
которая к этому моменту уже могла смениться. Сообщения новой сессии могут
обогнать сообщения старой, а ответ может прийти после закрытия пайпа.
Отправка через конкретную сессию позволяет прикладному протоколу явно
обрабатывать завершение этого взаимодействия.

Классическая TCP-реализация интерконнекта может восстановить оборванное
соединение внутри прежней interconnect-сессии и продолжить
передачу сообщений с сохранением порядка в каждом канале. Если сессия
завершается, закрывается и использующий её пайп. Подробнее это поведение
рассмотрено в разделе 12.4.

На стороне таблетки события TEvServerConnected и TEvServerDisconnected
сообщают о подключении и отключении пайп-сервера. В поле ServerId
передаётся его ActorId, а TEvServerConnected также содержит
InterconnectSession. Пайп-сервер сам отслеживает завершение этой сессии.
Таблетка может хранить состояние взаимодействия, например подписки
клиента на уведомления, по ServerId и освобождать его при получении
TEvServerDisconnected.

Если актор самостоятельно продолжает взаимодействие через
interconnect-сессию и ему нужно отслеживать её завершение, он
подписывается непосредственно на её актора и обрабатывает
TEvNodeDisconnected. Так подписка относится к сессии исходного запроса.
При подписке через interconnect proxy за это время может быть выбрана
уже новая сессия. Когда подписка больше не нужна, от неё следует
отписаться.

Для такой связи используются поля IEventHandle входящего сообщения.
Sender содержит адрес прикладного отправителя, Recipient --- адрес
пайп-сервера, а GetRecipientRewrite() возвращает фактического адресата
в таблетке. Поэтому пайп, по которому пришло сообщение, определяется
по Recipient.

При передаче клиентская сторона упаковывает прикладное сообщение для
пайп-сервера. Сервер извлекает его содержимое и создаёт новый IEventHandle,
сохраняя прикладного отправителя и указывая себя в Recipient. Затем
с помощью Rewrite он направляет сообщение фактическому адресату
в таблетке. Метод GetRecipientRewrite() возвращает адрес после такого
перенаправления; исходный Recipient сохраняется в хендле. Аналогично
поле Type хранит исходный тип события, а GetTypeRewrite() возвращает
тип, по которому событие обрабатывается после Rewrite.
