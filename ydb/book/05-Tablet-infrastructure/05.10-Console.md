## 5.10 Console

В консоли есть конфиги, в частности описанные в виде протобуфа.
Это те же самые конфиги, что и appconfig, с небольшой поправкой ---
динамически поддерживается только часть из них.

Консоль нужна для конфигурирования YDB в рантайме. Она поддерживает
переконфигурацию некоторых параметров.

Например, Net classifier config можно переконфигурировать на лету --- он
никогда и не конфигурируется руками, а только самой системой. Он
используется для митеринга. В конфиге net classifier хранятся записи обо
всех используемых подсетях.

Кроме того, акторная система тоже умеет конфигурироваться --- но только с
рестартом.

Динамически конфигурируются логи, сентинель, отдельные параметры CMS.

Config dispatcher --- прокси к таблетке-консоли. Это локальный сервис на
каждой ноде, работающий по модели подписок. Запрос «я хочу получать
обновление такого-то конфига» попадает в config dispatcher, который
создаёт подписку в таблетке консоли и оттуда начинает загружать все необходимые данные. Предусмотрено сообщение-подтверждение, что конфиг дошел и
т. п. Сам локальный сервис при старте просто ходит в таблетку консоли
по пайпу и сообщает, что нужны новые конфиги. Если есть дифф,
присылаются новые. На базовом уровне все просто: если новые конфиги
отличаются от того, что есть сейчас, то присылаются, если нет --- ничего
не присылается. Причем присылается только дифф.

Подразумевается, что конфиг хранится где-то в системе контроля версий и
изменяется девопсами. Для быстрого изменения настроек туда-сюда
предусмотрены волатильные конфиги. Волатильный конфиг используется в
случае, когда нужно что-нибудь отладить, например включить логи
акторной системы на уровень повыше, чтобы посмотреть, что идёт не так. Yaml-конфиг отправляется на сервер. Он подклеивается к
основному конфигу и применяется. Yaml-конфиги можно удалять независимо.
Для волатильных YAML-конфигураций TTL не предусмотрен: автоматически
по истечении заданного времени они не удаляются. После завершения
отладки ненужные временные настройки следует удалить явно.

Yaml-конфиг имеет систему, подобную кубернетисовским лейблам. Она
позволяет определённой группе нод применять дополнительные конфиги.
Система индексов и диффов также включает в себя многослойные протобуфы.
Речь идёт о том, что есть одна версия, на неё накладывается
вторая и т. д. с разными способами мерджа. Люди путались, поэтому от
такого подхода отказались.

Консоль --- самостоятельная таблетка, которая реализует совсем другой
API. Публичная же часть этого API называется CMS API. В нём заключается
только одна из функций таблетки консоли --- управление базами данных,
тенантами. Её вторая функция --- управление конфигурацией кластера.

Таблетка консоли --- точка входа для создания, расширения и удаления
тенанта. Для создания тенанта пользователь в первую очередь идёт в
control plane (раздел 9.3), который генерирует запросы CMS API, идущие в таблетку консоли. В
таблетке консоли запоминается, что нужно создать тенанта и выделить ему
определённое количество групп хранения и компьют-ресурсов. С появлением
полноценного control plane в консоли не хранится ничего о
компьют-ресурсах, только информация о сторадж-ресурсах. Причина
заключается в том, что выделением компьют-ресурсов занимается control plane.

Консоль --- большой оркестратор, который общается с остальными
системными таблетками для того, чтобы создать и запустить все части
тенанта. В частности, консоль идёт в scheme shard, создаёт субдомен,
настраивает согласно запросу. Затем идёт в blob storage controller и
создаёт там blob storage пулы. В схем-шард консоль сообщает, что у
тенанта будут сторадж пулы, созданные в блоб-сторадже, и трекает весь
этот процесс. При сбоях Console выполняет повторные попытки, доводя
процесс до конца либо сообщая об ошибке.

Изменение конфигурации тенанта тоже происходит через консоль, как и
удаление. Консоли известно, что это за тенанты, какого они типа,
dedicated tenant, serverless tenant или shared tenant. В зависимости
от типа тенанта консоль по-разному работает со scheme shard,
BS_Controller и т. д. Например, для serverless она не будет создавать
storage pool, а будет использовать storage pool общего (shared) тенанта.

Вторая функция --- хранение и распространение конфигов. У таблетки
консоли есть локальная табличка, в которой она хранит все конфиг-айтемы,
когда-либо залитые и ещё не удалённые. На запрос «дай мне конфиги»
таблетка консоли отдаёт их по-разному --- например, generic config для
всего кластера либо для определённого тенанта или ноды. При входе в
кластер нода по внешнему API запрашивает конфиги из консоли и, получив
их, поднимается с ними дальше.

Есть кластер, у кластера есть ноды, есть 2 типа конфигурации ---
статическая, которая подкладывается к каждой ноде, и динамическая.
Динамическая хранится в таблетке консоли, описывается yaml и
распространяется по кластеру, по динамическим нодам. Когда динамическая
нода стартует, она идёт в нод-брокер и в таблетку консоли за
конфигурацией и выкачивает полный слепок текущей конфигурации
загруженной в консоль. Потом она, если у неё есть текстовые конфиги,
берёт их, у них приоритет, иначе она берёт то, что приехало из консоли.
Резолвит их.

У каждой ноды есть лейблы. Есть неявные
лейблы: node ID, полученный из нод-брокера, branch, то есть ветка на
которой она собрана, номер ревизии, тип ноды --- динамическая или нет. И
есть явные лейблы, они просто передаются через параметры командной
строки при запуске. Запускаешь бинарь ydbd \--label key=value, после
этого лейбл key будет равен value.

Конфиг состоит из ряда секций. Есть базовая секция, которая применяется
по умолчанию, а поверх неё могут быть наложены некоторые патчи,
описанные в конфиге секции, называемые селекторами. То, какой список
патчей накладывается, определяется набором правил в селекторе. Правила
--- просто то, на какие лейблы этот селектор накатывать, а на какие --- не
накатывать. Это позволяет при помощи селекторов выбирать группы нод на
которых есть эти лейблы и резолвить конфиг. В документации это
достаточно подробно описано.

К примеру, control plane указывает для нод, запущенных с разным количеством ядер
и памяти, лейбл flavor, а в конфиге для каждого flavor
отдельно выставлен подходящий конфиг акторной системы и shared cache, это
делается как раз при помощи селектора.

Файл конфига в yaml удовлетворяет стандарту, его можно редактировать
всякими редакторами с подсветкой. Но при этом мы используем расширение
стандарта --- merge case и теги. Некоторые парсеры требуют явно
определять с какими тегами как работать, а без этого ничего не
отображает.

Итак, нода при старте резолвит конфиг, то есть берёт исходный и
накладывает на него все нужные патчи, и записывает это в памяти в
AppConfig. Это место, в котором лежат все конфиги и разные компоненты
могут их использовать. Кроме того, что конфигурация может применяться на
старте, есть ряд настроек, которые могут применяться без рестарта ноды.
Для этого каждая нода имеет сервис config dispatcher который
подписывается на конфиги в консоли, получает их и резолвит. Но в
рантайме могут применяться только те конфиги, для которых явно написан
соответствующий код, то есть компонент должен обратиться при старте в
config dispatcher и подписаться на кусочек конфига. Тогда ему придёт
нотификация при обновлении конфига.

При помощи команды ydb admin config fetch можно получить конфиг кластера,
указав endpoint и корневой домен кластера. После получения конфиг можно
отредактировать. Далее его можно залить при помощи ydb cli admin
config replace имя-конфига. В конфиге есть пара защитных механизмов:

Есть защита от конкурентной заливки двух разных версий конфига,
затирающих одна вторую. При fetch конфига в нём проставляется новый
номер версии и при последующем replace конфиг одной версии может быть
залит только один раз. Соответственно, только один участник сможет
залить измененный конфиг, а второй получит ошибку и должен повторить
fetch, модификацию и replace.

Второй важный сценарий --- если совершена случайная ошибка и предпринята
попытка залить конфиг не на тот кластер. В конфиге есть поле cluster
name, в нём указывается то же имя которое было использовано при запуске
storage нод. Для успешной заливки конфига имя должно совпадать.

Есть command-line инструмент для резолва конфига. Можно порезолвить
конфиг либо для всех лейблов, либо для конкретного набора лейблов, либо
для лейблов присутствующих у заданной ноды.

Есть web-инструменты для того же самого. В разделе cluster management
system есть несколько кнопок, их безопасно нажимать, от этого ничего не
сломается. Можно выполнить прямо в интерфейсе резолвинг, посмотреть на
примеры конфигов, перейти на интерфейс config dispatcher и посмотреть на
текущие лейблы ноды на которой вы находитесь, посмотреть какой конфиг
приехал, что из него порезолвилось, в какой protobuf этот конфиг
преобразовался. В том числе показывается и конфиг который был получен на
старте.

Dynamic nameservice config и naming config на момент написания этих
строк используют другой механизм конфигурирования, это связано с тем, что
конфигурируется это не человеком, а машиной, это большое количество
записей, которые могут с большой частотой изменяться. Основной конфиг мы
стараемся сохранять в состоянии когда его пишут и модифицируют люди, а
не машины. Для машин используется другой механизм конфигурирования,
config registry. Там конфиг можно посмотреть и при необходимости даже
поправить. По задумке настройки из config registry не пересекаются с
настройками из основного yaml конфига.

Раздельные конфиги для людей и роботов --- конфиг для людей
должен быть в виде, написанном человеком и редактируемом человеком, а
машинно-сгенерированные конфиги, обновляемые например каждые пять минут
роботом, не должны смешиваться с редактируемым человеком конфигом.
Конфиг из config registry тоже можно посмотреть и поправить, но обычно
это должно быть не нужно, этот конфиг не перекрывается с yaml, по
задумке там настраиваются другие параметры.

Статическая нода после старта получает конфиг из файла и запускается с
ним. После этого нода пойдёт в console и получит новый конфиг. И из него
применится только то что умеет динамически применяться.

Динамическая нода может пойти либо по сценарию статической ноды если у
неё есть под ногами конфиг, либо она пойдёт в node-broker, получит себе
node ID, лизу и попытается подгрузить CMS-ный конфиг, его можно получить
по gRPC. Нода с ним запустится и после этого пойдёт в CMS получать более
свежий конфиг если он там есть.
