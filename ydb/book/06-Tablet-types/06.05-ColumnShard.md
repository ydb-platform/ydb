## 6.5 ColumnShard

ColumnShard --- таблетка, обслуживающая колоночные таблицы. Данные в них
организованы так, чтобы при аналитическом запросе читать нужные колонки,
обрабатывать сразу множество строк и по возможности пропускать участки,
которые не подходят под условие запроса. Это полезно как для полного
сканирования таблицы, так и для выборок с фильтрами, в том числе по диапазону
первичного ключа.

### Хранение данных и метаданных

Основная единица организации данных внутри ColumnShard --- порция
(*portion*). Она содержит набор строк, представленных отдельными колонками,
и метаданные: сведения о схеме, границах ключей, версиях данных, размещении
блобов и индексах. Колонки разбиваются на фрагменты, сериализуются и
сохраняются в блобах. Порция не обязана соответствовать одному блобу.

Для обработки колоночных данных используется Apache Arrow. При этом схема
YDB не исчезает: ColumnShard сохраняет информацию о типах, первичном ключе
и версиях схемы и использует её при проверке записей, преобразовании данных
и чтении порций, созданных с разными версиями схемы.

Основной объём данных порций хранится в блобах. В локальной базе таблетки
сохраняются метаданные и состояние операций, необходимые для восстановления
после рестарта. При запуске ColumnShard читает их и восстанавливает свои
структуры. Во время работы используются структуры в памяти и механизмы
загрузки и кэширования метаданных.

Запись подготавливает колоночные пакеты, формирует порции и сохраняет их
блобы. При транзакционной записи данные становятся видимыми другим
транзакциям после коммита. Фоновый компакшн объединяет и переорганизует
порции, создавая новые блобы и заменяя набор используемых порций. Удаление старых данных согласовано
с сохранением версий, необходимых активным чтениям. Этот компакшн относится
к колоночному движку и управляется отдельно от компакшна локальной базы
таблетки.

### Чтение и выполнение вычислений на шарде

План чтения определяет снапшот, диапазоны первичного ключа и необходимые
колонки. По метаданным и индексам ColumnShard исключает неподходящие порции
и фрагменты. Помимо границ первичного ключа, для этого могут использоваться
дополнительные индексы, например min--max и Bloom-фильтры. Их наличие
и применение зависят от схемы и условий запроса. Они помогают пропускать
данные, а окончательную проверку условия выполняет фильтр.

KQP может передать на ColumnShard часть вычислений в виде SSA-программы.
SSA (*static single assignment*) означает, что каждому промежуточному
результату присваивается значение один раз; при колоночной обработке такой
результат обычно представляет целую колонку значений. Программа позволяет
выполнять фильтры, вычислять выражения, выбирать колонки и, когда это
предусмотрено планом, выполнять агрегации. Какие вычисления будут перенесены
на шард, определяют оптимизатор, поддерживаемые операции и настройки.
Это уменьшает объём данных, передаваемых следующим стадиям запроса.

Для сканирования создаётся отдельный актор. Он получает описание чтения
и доступ к необходимым метаданным и загружает данные через подсистему
хранения ColumnShard. Таблетка учитывает активное чтение, чтобы фоновая
обработка не освободила нужные ему данные раньше времени. После завершения
чтения соответствующие удержания освобождаются.

Снапшот задаёт версию данных для чтения. ColumnShard сохраняет историю,
которая позволяет читать согласованный срез за недавнее прошлое.
Для локального механизма контроля снапшотов ориентир задаёт настройка
`MaxReadStaleness_ms`: по умолчанию 300000 мс, то есть 5 минут.
Она участвует в вычислении нижней границы снапшотов для новых чтений
относительно продвинувшегося шага; учитывается и уже выполненная очистка.
При включённом `EnableSnapshotsLocking` граница определяется с участием
общего реестра снапшотов.

Уже используемые снапшоты удерживаются отдельно, позволяя продолжать
начатое чтение и за пределами этого пятиминутного окна. Возможность
продолжения зависит от сохранения нужного снапшота и ограничений времени
жизни запроса или транзакции.

### Запросы, транзакции и пакетная загрузка

Колоночные таблицы доступны через Query Service: через него можно читать
данные и выполнять SQL-операции записи, включая `INSERT`, `UPSERT`,
`REPLACE` и `DELETE`. Для чтения также существует scan query в Table Service,
а для пакетной загрузки --- отдельный вызов `BulkUpsert`. У этих способов
доступа разные транзакционные свойства; устройство клиентских API описано
в разделе 8.6.

Транзакции Query Service могут включать несколько запросов и несколько
ColumnShard. Поддерживаются чтение в режиме `Snapshot Read-Only`,
транзакции `Serializable Read-Write` и `Snapshot Read-Write`. При
сериализуемом выполнении чтение по снапшоту сочетается с контролем
конфликтов: ColumnShard учитывает транзакционные зависимости,
а конфликт может привести к отмене транзакции. Режимы `Online Read-Only`
и `Stale Read-Only` для колоночных таблиц не поддерживаются.

Одна транзакция может обращаться и к строковым, и к колоночным таблицам,
в том числе записывать в оба вида таблиц. Возможность таких смешанных
транзакций с записью управляется настройкой `EnableHtapTx`, которая
по умолчанию включена. Запись в колоночные таблицы через механизм выходов
вычислительного графа (*sinks*) управляется `EnableOlapSink`, также
включённой по умолчанию. Для записи через `ExecuteDataQuery` в Table
Service нужна отдельная настройка `AllowOlapDataQuery`, по умолчанию
выключенная. Режим `Snapshot Read-Write` отдельно управляется
настройкой `EnableSnapshotIsolationRW`, по умолчанию включённой.

`BulkUpsert` предназначен для пакетной загрузки и не включается в
пользовательскую SQL-транзакцию. Входной пакет разбивается на запросы
к шардам; каждый такой запрос записывается независимо. Успех возвращается
после успешного завершения всех частей, но общей атомарности всего вызова
нет: при ошибке часть данных уже может быть записана. Эта гарантия
относится и к колоночным таблицам. Для атомарного изменения данных на
нескольких шардах используется транзакционный путь Query Service.

У нетранзакционной загрузки есть и отдельное ограничение взаимодействия
со снапшотными чтениями: в реализации ColumnShard такие записи могут
становиться видимыми уже начатым чтениям. Это нужно учитывать при
совмещении снапшотных чтений с загрузкой через `BulkUpsert`.

### Шардирование

Колоночная таблица распределяется между ColumnShard по ключу шардирования.
Он может отличаться от полного первичного ключа, но его колонки должны
входить в первичный ключ. Тогда одинаковые значения первичного ключа
имеют одинаковый ключ шардирования и направляются на один шард.
Первичный ключ при этом используется для организации данных внутри шарда
и различения строк.

`HASH_FUNCTION_CONSISTENCY_64` используется для новых таблиц
по умолчанию и распределяет пространство 64-битных хешей между шардами
по интервалам. Вариант `HASH_FUNCTION_MODULO_N` выбирает шард
по остатку от деления хеша на число шардов.

Для колоночных таблиц внутри table store реализовано перешардирование
с увеличением или уменьшением числа шардов в два раза. Оно включает
изменение распределения записей и чтений и передачу данных между шардами.
Механизм управляется флагом `EnableAlterShardingInColumnShard`, который
по умолчанию выключен: без него SchemeShard отклоняет операцию.
Перед включением следует проверить работу перешардирования
на используемой конфигурации и нагрузке.

### TTL и внешние уровни хранения

TTL удаляет данные порциями. Для выбора порции используется максимальное
значение TTL-колонки: удаление становится возможным, когда истекли данные
всей порции. Решение принимается по метаданным: для удаления целой порции
не требуется читать её строки и создавать новые блобы с оставшимися
данными. Это позволяет удалять устаревшие данные без построчного
сканирования и перезаписи.

Нужное значение берётся из метаданных границы первой колонки первичного
ключа либо из подходящего индекса максимума или min--max. Наличие такого
индекса проверяется при настройке TTL. Сам по себе целочисленный тип
колонки не означает наличия min--max индекса.

Тот же механизм выбора порций по возрасту используется для тиринга ---
переноса данных на внешний уровень хранения, например в S3-совместимое
хранилище. В отличие от удаления, перенос требует чтения и записи данных
и изменения метаданных их размещения. Настройка переноса во внешнее
хранилище разрешается флагом `EnableTieringInColumnShard`, который
по умолчанию выключен.

При чтении размещение данных определяет используемый оператор хранилища.
Для Blob Storage применяется путь чтения через blob cache; для внешнего
уровня оператор выполняет запрос к объектному хранилищу. Кэширование
и перенос между уровнями --- отдельные механизмы: чтение из S3 само
по себе не означает сохранения постоянной копии в Blob Storage.
