## 8.6 Клиентские библиотеки и API

Клиентские библиотеки YDB берут на себя работу с эндпоинтами, создание
и переиспользование сессий, отправку запросов, обработку результатов
и повторные попытки. Приложение выбирает нужный сервис и режим выполнения,
а SDK реализует взаимодействие с сервером через gRPC.

Набор сервисов и удобных обёрток различается между SDK. Например,
в C++ есть отдельные клиенты `NQuery::TQueryClient` и
`NTable::TTableClient`. Драйверы для JDBC и `database/sql` предоставляют
привычный для соответствующей экосистемы интерфейс поверх взаимодействия
с YDB. Поддерживаемые возможности API и отображение транзакционных
режимов зависят от конкретного драйвера.

### Разделение API на сервисы

Публичный API описан protobuf-сообщениями и gRPC-сервисами. Среди них:

- **Discovery Service** --- получение списка доступных эндпоинтов
  базы данных и сведений о них;
- **Query Service** --- выполнение SQL-запросов, управление транзакциями
  и выполнение скриптов;
- **Table Service** --- операции со схемой таблиц, data query,
  подготовленные запросы, scan query, чтение таблиц и пакетная загрузка;
- **Scheme Service** --- работа с пространством имён и правами доступа;
- **Topic Service**, **Coordination Service** и **Rate Limiter Service** ---
  работа с топиками, координацией и ограничением скорости;
- сервисы аутентификации, операций, экспорта и мониторинга.

Query Service предоставляет `ExecuteQuery` с потоком частей результата.
В зависимости от режима запрос может содержать операции чтения, изменения
данных и схемы. Транзакцией можно управлять в параметрах выполнения:
начать её, продолжить по идентификатору и завершить коммитом. Есть также
отдельные вызовы `BeginTransaction`, `CommitTransaction`
и `RollbackTransaction`. `ExecuteScript` запускает выполнение скрипта
как операцию; результаты затем запрашиваются через `FetchScriptResults`.
Допустимое сочетание операторов определяется режимом выполнения.

В Table Service сохранены отдельные методы для data query и scheme query,
подготовки запросов и управления транзакциями. `StreamExecuteScanQuery`
возвращает результаты аналитического чтения потоком, а `BulkUpsert`
загружает пакет данных вне пользовательской SQL-транзакции. У каждого
метода свои ограничения и гарантии.

В частности, Query Service выполняет транзакционные запросы к строковым
и колоночным таблицам, в том числе смешанные транзакции при разрешающей
настройке. Подробнее об устройстве колоночных таблиц и транзакционных
свойствах способов доступа к ним сказано в разделе 6.5.

### Сессии и соединения

Сессия --- серверный контекст работы с запросами и транзакциями,
размещённый на конкретной ноде. Она отличается от TCP-соединения и
gRPC-канала: транспорт переносит запросы, а сессия хранит состояние
их выполнения. Повторное установление соединения само по себе
не восстанавливает потерянную сессию или транзакцию.

Запросы внутри одной сессии выполняются последовательно. Попытка начать
следующий запрос, пока предыдущий ещё не завершён, может получить
`SESSION_BUSY`. Для параллельной работы с явно созданными сессиями
используются разные сессии из пула. Они могут оказаться на одной или
на разных нодах.

Сессия содержит контексты активных транзакций и связанное с запросами
состояние. В Table Service есть явная подготовка запроса с получением
идентификатора для последующего выполнения. Подготовка запросов и
переиспользование скомпилированных планов связаны с работой KQP,
описанной в разделе 8.3.

В Table Service сессия явно создаётся через `CreateSession`, а для
поддержания неактивной сессии используется `KeepAlive`. Однако не все
методы Table Service требуют сессию: например, запросы `BulkUpsert`
и `StreamExecuteScanQuery` не содержат её идентификатора.

Для явно созданной сессии Query Service после `CreateSession` клиент
открывает долгоживущий поток
`AttachSession`, через который отслеживается состояние сессии. Завершение
этого потока приводит к закрытию сессии на сервере. В C++ SDK создание,
подключение и возврат таких сессий в пул выполняются клиентской
библиотекой. При потоковом чтении сессия остаётся связана с выполняемым
запросом до его завершения.

Для самостоятельного запроса есть и путь без явно созданной клиентской
сессии. Например, C++ `TQueryClient::ExecuteQuery` может отправить запрос
без `session_id`; KQP создаёт для него временный серверный контекст.
Транзакция в этом случае должна завершаться в рамках вызова. Для
интерактивной транзакции, продолжаемой несколькими вызовами клиента,
нужна явная сессия.

Сессии не являются долговечным состоянием базы. При потере сессии SDK
исключает её из повторного использования и при необходимости получает
новую. Продолжать в новой сессии прежнюю незавершённую транзакцию нельзя.

### Ошибки и повторные попытки

Клиенту приходится различать три уровня ошибок:

- транспортный --- gRPC не смог доставить запрос или получить ответ;
- серверный --- получен ответ YDB с кодом ошибки и пояснениями;
- клиентский --- например, SDK не смог получить сессию из пула
  за отведённое время.

После получения ответа gRPC нужно проверить статус YDB.
При потоковом выполнении нужно также дождаться завершения всего потока
и проверить его итоговый статус, даже если первые строки уже получены.

Повторные попытки зависят от кода ошибки, оставшегося времени и свойств
операции. Например, после конфликта с отменой транзакции (`ABORTED`)
повторяется вся транзакция. При перегрузке повтор откладывается, чтобы
не усиливать нагрузку. Потерянную сессию исключают из повторного
использования и заменяют.

Особый случай --- неизвестный результат выполнения. Если соединение
разорвалось после отправки запроса, сервер мог успеть выполнить коммит,
а клиент --- не получить подтверждение. Поэтому повтор неидемпотентной
операции может применить её эффект ещё раз. Например, повтор увеличения
счётчика способен увеличить его дважды. В C++ SDK решение о повторе
для `UNDETERMINED` и `TRANSPORT_UNAVAILABLE` учитывает признак
идемпотентности. Retry-обёртка может повторно вызвать переданную ей
функцию, и это нужно учитывать для любых внешних действий внутри неё.

### Discovery и клиентская балансировка

Обычная схема подключения начинается с заданного приложением эндпоинта.
Через `ListEndpoints` SDK получает список эндпоинтов выбранной базы
и использует его для выбора адресов и обновления своего представления
о доступных нодах. Discovery сообщает доступные адреса, а решение о выборе
конкретного соединения и его переиспользовании принимает клиентская
реализация с учётом настроек.

При создании сессий нагрузку можно распределять по нодам. Последующие
запросы существующей сессии выгодно направлять на ноду, где она находится:
это позволяет избежать дополнительной пересылки через interconnect.
Например, C++ Query Client использует идентификатор ноды из идентификатора
сессии при выборе предпочтительного эндпоинта.

Список обнаруженных нод, пул сессий и набор транспортных соединений ---
разные вещи. SDK не обязан немедленно устанавливать отдельное соединение
с каждой обнаруженной нодой. Количество соединений, момент их открытия
и политика выбора адресов зависят от библиотеки и конфигурации.

При ленивом установлении соединений первое обращение к выбранному
эндпоинту может дополнительно ждать подключения, включая TLS-handshake
при использовании TLS. Повторное использование готового соединения
позволяет не платить эту цену при каждом запросе. Поэтому при оценке
задержек полезно отдельно учитывать первое обращение и работу по уже
установленным соединениям. Например, C++ SDK переиспользует gRPC-каналы
через пул. После разрыва связи к задержке запроса может добавиться
время восстановления транспортного соединения.

Начальный адрес также может вести на балансировщик, а одно DNS-имя ---
разрешаться в несколько IP-адресов.
