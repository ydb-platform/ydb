## 8.7 Типы и функции PostgreSQL в YDB

YDB использует типы данных и функции PostgreSQL в выражениях YQL и
поддерживает хранение PG-значений в строковых таблицах. Для этого часть
кода PostgreSQL встроена в библиотеку YQL и адаптирована к выполнению
вычислений в MiniKQL.

В YQL PG-типы обозначаются именами с префиксом `Pg`, например `PgInt4`,
`PgText` и `PgNumeric`; имена типов массивов начинаются с `_Pg`.
Для создания значений доступны конструкторы типов и специальные
суффиксы литералов. Функции PostgreSQL вызываются
через пространство имён `Pg::` или встроенную функцию `PgCall`, а
приведение между PG-типами выполняется через `PgCast`. Такие выражения
становятся частью графа вычислений YQL и исполняются вместе с остальными
операциями запроса.

Создание PG-колонок в строковых таблицах управляется флагом
`EnableTablePgTypes`, по умолчанию выключенным. PG-значения в выражениях
YQL можно использовать и без хранения PG-колонок в таблице.
Колоночные таблицы PG-типы не поддерживают.

Для работы с типами используется PG-каталог. Он строится из описаний
PostgreSQL, в том числе файлов `.dat`, и содержит сведения о типах,
функциях, операторах, агрегатах и преобразованиях типов. По этим
описаниям YQL выбирает подходящую операцию и проверяет типы аргументов.
Для использования функции в запросе требуется также её включение
в список разрешённых функций.

Вызов реализованной на Си функции PostgreSQL использует соглашения
function manager: обёртка подготавливает описание функции и её
аргументы, вызывает реализацию и получает результат. Представление
значения во время вычисления определяется соответствующим PG-типом.

Для локальной базы на основе того же каталога создаются дескрипторы
типов. Дескриптор содержит сведения о размере значения, функциях
сравнения и хеширования, преобразовании текстового и бинарного
представлений. В `TTypeInfo` хранится идентификатор типа и, для PG-типа,
указатель на такой дескриптор. В обычной 64-битной сборке `TTypeInfo`
занимает 16 байт: 2 байта идентификатора, выравнивание и 8-байтное поле
дескриптора. Указатель даёт прямой доступ к описанию PG-типа без нового
поиска по каталогу при каждом обращении.

В ячейке локальной базы PG-значение хранится в бинарном представлении,
которое формирует функция PostgreSQL `send` для данного типа. Обратное
преобразование в представление для вычислений выполняет `receive`.
Это тот же формат отдельного значения, который используется при
бинарном обмене PostgreSQL. Например, целочисленные PG-типы
сериализуются в сетевом порядке байтов, поэтому бинарное представление
`PgInt8` отличается от внутреннего представления обычного `Int64` в
YDB на little-endian платформе.

Порядок значений задаётся функцией сравнения типа. При сравнении
сохранённых PG-значений обёртка восстанавливает их через `receive` и
вызывает соответствующую PG-функцию. Аналогично выполняется
хеширование. Для включения PG-колонки в первичный ключ у типа должна
быть функция сравнения; SchemeShard проверяет это при создании
таблицы.

Параметры типа, например ограничение длины строки или точность числа,
передаются отдельно от базового типа в виде модификатора --- `typemod`.
В метаданных колонки он хранится как строка. Table API позволяет задать
его в поле `type_modifier` описания PG-типа. При обращении к функциям
PostgreSQL строковый модификатор преобразуется в их внутренний числовой
формат.

При записи модификатор колонки доходит из схемы таблицы до построителя
строки `TRowBuilder`. Для PG-значения, отличного от `NULL`, если
модификатор задан и тип требует приведения с учётом параметров,
выполняется coercion.
Результат сериализуется для сохранения в ячейке; ошибка приведения
прерывает запись. Этот механизм используется в пути записи KQP, в том
числе для YQL `INSERT`. Применение модификаторов реализовано и в
`BULK UPSERT`.

Модификаторы используются также при явном приведении внутри выражения:
`PgCast` принимает параметры целевого типа. Поэтому базовый тип и его
модификатор имеют разные роли: тип определяет представление значения
и доступные операции, а модификатор задаёт дополнительные условия
конкретного приведения или записи в колонку.

Обёртки согласуют окружение PostgreSQL с управлением памятью и потоками
в YQL. Они выполняют инициализацию состояния для потока, устанавливают
нужные контексты памяти при входе в вычисления и восстанавливают
предыдущее состояние при выходе. Для завершения потока предусмотрена
очистка связанных с PostgreSQL ресурсов.

Обработка ошибок также требует адаптации. В коде PostgreSQL используются
макросы `PG_TRY` и `PG_CATCH`, основанные на `setjmp` и `longjmp`.
В обёртках есть преобразование ошибок в механизм MiniKQL, включая
обработчики, выбрасывающие C++-исключения. При таком исключении работают
обычные средства освобождения ресурсов C++, в том числе `Y_DEFER`.
Переход через область C++ с помощью `longjmp` не обеспечивает вызова
деструкторов, поэтому на границе этих механизмов очистка ресурсов
должна быть организована явно.
