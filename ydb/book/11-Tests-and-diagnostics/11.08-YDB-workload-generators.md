## 11.8 Генераторы нагрузки YDB workload

В составе `ydb cli` (см. раздел 10.2) поставляется встроенный фреймворк для генерации нагрузки и бенчмаркинга YDB — `ydb workload`. Это основной инструмент для performance-тестирования кластера «снаружи», то есть со стороны клиентского приложения.

### Принцип работы

`ydb workload` работает как обычное клиентское приложение. Оно подключается к кластеру через gRPC API (используя C++ SDK) и выполняет запросы к базе данных, эмулируя работу реальных сервисов.

Работа с нагрузочным тестом обычно состоит из трех этапов:

1.  **Init** (`ydb workload ... init`) — Создание схемы данных (таблиц, индексов) и, опционально, начальное наполнение данными.
2.  **Run** (`ydb workload ... run`) — Непосредственно подача нагрузки. На этом этапе запускается множество клиентских потоков, которые выполняют заданные операции (чтение, запись) в цикле в течение заданного времени или количества итераций. В процессе работы выводится промежуточная статистика (RPS, Latency), а в конце — итоговый отчет.
3.  **Clean** (`ydb workload ... clean`) — Удаление созданных таблиц и освобождение ресурсов.

### Основные виды нагрузок

Фреймворк поддерживает несколько встроенных сценариев (workload types), каждый из которых нацелен на тестирование определённых аспектов системы.

#### 1. Stock (Склад)
Эмулирует работу интернет-магазина или складской системы. Это классический OLTP-тест.

*   **Схема**: Множество таблиц (`stock`, `orders`, `order_lines` и т.д.).
*   **Операции**: Создание заказа с транзакционным обновлением остатков на складе. Тестирует производительность распределённых транзакций, затрагивающих несколько шардов.

#### 2. KV (Key-Value)
Простой сценарий для тестирования «сырой» производительности операций Point Read и Point Write.

*   **Схема**: Одна таблица `kv` с первичным ключом и полезной нагрузкой.
*   **Операции**: `upsert` (вставка/обновление) и `select` (чтение по ключу).
*   Полезен для оценки максимального RPS, который может выдать кластер (или отдельная нода) на простых запросах, а также для измерения минимальной задержки (latency).

#### 3. ClickBench
Сценарий для тестирования аналитической производительности (OLAP). Основан на популярном бенчмарке ClickBench (хиты веб-сервиса).

*   **Схема**: Одна широкая таблица с аналитическими данными (обычно используется Column-store).
*   **Операции**: Выполнение набора из 43 аналитических SQL-запросов (агрегации, фильтрации, группировки).
*   Полезен для тестирования колоночных таблиц и оптимизатора запросов.

#### 4. Topic
Сценарий для тестирования подсистемы топиков (YDB Topics) — аналога Apache Kafka.

*   Тестирует скорость записи (write) и чтения (read) сообщений в топики.
*   Позволяет проверить пропускную способность брокера сообщений.

### Особенности запуска

*   **Параллелизм**: Флаг `--threads` (или `-t`) управляет количеством параллельных потоков, генерирующих нагрузку. Увеличение числа потоков позволяет загрузить кластер, но при чрезмерном увеличении может вырасти задержка.
*   **Ограничение нагрузки**: Флаг `--rate` позволяет ограничить частоту запросов (RPS), что полезно для поиска точки насыщения системы.
*   **Период сбора статистики**: Флаг `--window` задает окно усреднения статистики при выводе на экран.

Пример полного цикла тестирования KV:
```bash
# Создать таблицу с 1000 партициями (min-partitions)
ydb workload kv init --min-partitions 1000

# Запустить нагрузку на запись (100 потоков, 60 секунд)
ydb workload kv run upsert --threads 100 --seconds 60

# Запустить нагрузку на чтение
ydb workload kv run select --threads 100 --seconds 60

# Удалить таблицу
ydb workload kv clean
```
