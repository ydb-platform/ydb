# Distconf: модель совместимого протокола

[distconf.pml](distconf.pml) описывает текущий кандидат и старые правила для
проверки наката/отката. Промежуточных ревизий протокола нет.
[check.py](check.py) сохраняет все 36 сценариев: 22 основных, 7 переходов версий
и 7 проверок нового Replace поверх старого конфликта.

## Запуск

Нужны Python 3, SPIN и C-компилятор. Команды выполняются из корня репозитория:

```bash
# Все сценарии и контрольные истории полностью старого кластера.
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check.py --suite all --decompose --timeout 300

# Отрицательный контроль: отключённое исправление старого конфликта должно блокировать сходимость.
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check.py --suite legacy --scenario 30 31 32 --check liveness --legacy-repair 0

# Отдельные наборы и выбранные гонки.
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check.py
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check.py --suite compatibility
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check.py --scenario 19 20
```

Runner печатает каталог со снимком модели, командами, полными результатами и
трассами. Отчёты сохраняются в каталоге артефактов и не входят в исходники модели.
Код возврата: `0` — ожидаемые результаты; `1` — нарушение свойства или регрессия;
`2` — ошибка инструмента либо незавершённый поиск. Таймаут не считается PASS.

`--decompose` проверяет закрытость итогового состояния, затем его достижение при
weak process fairness для сценариев 30–33. Для вывода о стабильной сходимости
должны пройти обе проверки. Остальные сценарии проверяются обычным способом.

## Свойства и правила

- Последний конфиг, записанный на committed-кворум, должен устойчиво стать
  committed всех нод после прекращения запросов и отказов, даже если ответ клиенту потерян.
- Последний успешный Replace должен победить незавершённую докатку предыдущего.
  После неуспешного запроса ноды должны сойтись к одному ненулевому конфигу.
- Два разных содержимых одного поколения не могут оба получить `OK`.
  Применение разных содержимых одного поколения на одной ноде считается ошибкой.
- Пустая нода сначала получает конфиг; она не участвует в ненулевом чтении/голосовании.
  Кворум остаётся `Q=2`, а объединение выключенных и пустых нод не превышает `f=1`.

Новый root подтверждает `OK` после committed-кворума. Перед записью он читает
конфиги, выбирает поколение выше всех наблюдавшихся и восстанавливает максимальный
опубликованный конфиг. Повторные публикации доводят его до отставших нод.

Root сохраняет максимум известных applied-метаданных до смены root. Старое тело
не публикуется поверх этого максимума; для восстановления требуется совпадающий
committed/proposed из чтения. Единственный неопубликованный proposed не блокирует recovery.

Пустая новая реплика после обычной ненулевой публикации запрашивает свежий конфиг
через родителя. Ответ относится к текущей связи и жизни root. Ответ старого root
без признака свежести разрешает только сохранённую обычную публикацию;
локальное тело QueryConfig из такого ответа не применяется.

Явный Replace может заменить старый конфликт одного поколения новым конфигом,
если собран stateful read quorum, текущее тело root присутствует на дисках у максимального
восстановимого поколения и applied-максимум не новее. Новое поколение должно быть выше
всех увиденных; обычные кворумы и проверка актуальности операции сохраняются.
Автоматическое recovery и Fresh Query не выбирают произвольно спорное старое тело.

## Совместимость

Каждый из семи сценариев перехода сравнивается с той же историей при `ALL_OLD=1`.
Старый root сохраняет прежние правила ответа, выбора поколения и восстановления.
Проверяется дополнительная проблема от наката/отката; прежний баг старого root
после отката не считается новой регрессией.

Только известные циклы восстановления в сценариях 8 и 29 принимаются как
унаследованное поведение, когда воспроизведены и в полностью старой истории.
Другие совпадающие отрицательные результаты требуют разбора и дают ошибку runner.
`LEGACY_REPAIR=0` сохраняет отрицательный контроль исправления конфликта.

## Границы модели

Модель ограничена `N=3/Q=2`, одним диском на ноду и неизменным составом. Основные
сценарии начинают с согласованного ненулевого конфига; сценарии 30–36 намеренно
начинают со старого конфликта. Запись, ACK, публикация, чтение диска и ответ чтения —
разные переходы; записи полных committed/proposed-метаданных упорядочены FIFO.
Префиксы отказов заданы явно, в сценариях 11 и 19–20 перебираются ограниченные разрезы.
После префикса работают независимые disk/network workers и координатор с weak fairness.

Метаданные applied в сценарии 24 задерживаются явно. Сценарий 25 допускает
нежелательное старое тело от промежуточной ноды как расширение входов модели;
это не доказанная история cookies/session C++. Полной реализации дерева и
перекрывающихся root здесь нет. Bootstrap поколения 0, bridge, изменение состава,
геометрия static-групп и произвольные цепочки форматирований не доказаны.
Проверки переходов моделируют правила участников, а не разные исполняемые бинарники.

## Дерево связей

[three_node_convergence.pml](../three_node_convergence.pml) и
[run_three_node.py](../run_three_node.py) сохраняют исходные проверки дерева
(`CONFIG_VERSIONS=0`), наборы `baseline`, `quorum` и `bootstrap`. У bootstrap остаются
известные циклы; наличие набора не означает, что он целиком проходит.

Тот же файл при `CONFIG_VERSIONS=1` объединяет дерево, recovery, дисковое IO,
scatter/gather, MAIN Replace и Fresh refill. Runner — [check_tree.py](check_tree.py):

```bash
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check_tree.py --decompose --timeout 90
python3 ydb/core/blobstorage/nodewarden/spin/config_versions/check_tree.py --case samegen_later_ok_witness --check safety --timeout 90
```

Точные завершённые проверки покрывают стабильную цепочку, докатку `A2/B2/C1`,
заполнение `A2/Bempty/C1` и достижимость следующего успешного Replace после гонки.
Последняя проверка является witness, а не перебором всех исходов гонки.

Полные поиски гонок, разрыва цепочки и MAIN Replace с API transport остаются
`INCOMPLETE`. Это ограниченная трёхнодовая модель с FIFO mailbox, конечными очередями,
фиксированным составом и начальным форматированием. Она не доказывает все три свойства
для произвольного дерева и не является полным refinement-доказательством C++.
