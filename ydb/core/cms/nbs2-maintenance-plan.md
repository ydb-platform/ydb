# Учёт NBS2 при выдаче CMS-локов на ноды

## Цель и договорённости

CMS перед выдачей разрешений на отключение нод дополнительно проверяет безопасность
NBS2 через DBSController. Модель отказа остаётся в DBSController. В первую версию
не входят eviction, управление размещением и операции над отдельными дисками.

- Проверка включается только при `NbsConfig.Enabled = true` и новом флаге
  `EnableCmsNbs2MaintenanceChecks` (по умолчанию `false`). Иначе CMS работает как раньше.
- `InfoCollector` не меняется. Запрос в DBSController выполняется асинхронно
  при обработке CMS-запроса, до принятия и сохранения новых permissions.
- В DBSController отправляются все ноды исходного запроса на блокировку
  (для refresh — оставшихся действий), включая отложенные локальными лимитами CMS,
  вместе с нодами с применимыми действующими ограничениями CMS. Идентификаторы уникальны.
- Одна пакетная проверка на попытку обработки, общий `ALLOW/DENY`.
  Подбор подмножеств и отдельные проверки каждой ноды не выполняются.
- После `ALLOW` сохраняются обычные проверки CMS, включая частичные разрешения,
  приоритеты и `MaxInflightActions`. `DENY` запрещает выдачу новых разрешений
  проверяемого запроса, но не отзывает ранее выданные.
- Пустая карта DBSController не является дополнительной причиной отказа:
  принимаем его текущий `ALLOW`. Недоступность контроллера — временная ошибка без новых локов.
- Force и ручное одобрение не обходят проверку NBS2.
- Локи хранятся только в CMS. Уведомления об их установке/снятии и резервирование
  в DBSController не добавляются. Контракт ответа и модель отказа DBSC не меняются.

## Подзадачи

Реализуем по порядку в текущей ветке; следующую начинаем после проверки предыдущей.
Для пункта 1 отдельные тесты не добавляем по договорённости. Прямые тесты сборщика
из пункта 2 удалены вместе с тестовым friend-доступом: его покрытие переносим на
интеграционные сценарии через публичный API CMS после подключения полного пути.
Код пункта 3 и три комплексных теста реализованы. По результатам запуска пользователем
исправлены линковка вывода enum и доставка событий в тестах; итог повторного запуска
пока не подтверждён. Для пункта 4 добавлены общий механизм ожидания и четыре
комплексных интеграционных теста. В пункте 5 подключены permission/create и добавлены
ещё два комплексных теста. По запуску пользователя три интеграционных теста прошли,
два ожидаемо упали на ещё не подключённых обработчиках; ошибка cookie в тесте
публичного create исправлена, повторный запуск пока не подтверждён.
В пункте 6 подключён refresh и добавлен комплексный тест его жизненного цикла;

одобрение и добавлены интеграционные сценарии; сборка и тесты не запускались.
Из пункта 8 добавлены тесты с реальными CMS и DBSController; результаты и исправление
их первого запуска описаны ниже, повторный запуск оставлен пользователю.

Выделить подготовку полного набора `NodeIds`: разрешение hostname/tenant,

**Статус:** подготовлен `TCms::CollectNbs2MaintenanceNodes`, использующий существующий
`TClusterInfo::FindLockedItems`. Отдельный resolver удалён. Прямые unit-тесты и
`TCmsNbs2TestAccess` удалены по договорённости; тесты не запускались.
Сборка `core/cms` в `relwithdebinfo`
после перехода на `FindLockedItems` прошла успешно.
Вызов сборщика и обращение к DBSController подключены для permission/create в пункте 5
и refresh в пункте 6; ручное одобрение подключено в пункте 7.

- Учитываются `SHUTDOWN_HOST`, `REBOOT_HOST` и `RESTART_SERVICES`
  по существующим правилам `FindLockedItems`. Операции над отдельными дисками,
  drain и cordon не входят в набор.
- Раскрытие tenant остаётся в существующем обработчике CMS: сборщик принимает уже
  нормализованный запрос с host actions, но ещё до отбора действий по локальным проверкам
  и квотам. Повторного раскрытия tenant в сборщике нет.
- Цели действий берутся из `FindLockedItems`, без отдельной проверки host/services.
  Существующие `CheckActionRestartServices`, `CheckActionShutdownHost` и маршрутизация
  в `CheckAction` оставлены без изменений. Объединение обычных обработчиков отложено
  в отдельный PR, чтобы не смешивать с интеграцией NBS2.
  Числовой `Host` обозначает конкретный NodeId. Итоговый набор отсортирован и не содержит дублей.
- Наследуется семантика `NodePtrs`/`MakeServices`: для числового NodeId фильтр сервисов
  не применяется; неизвестные сервисы игнорируются при определении целей. Обычный
  `CheckAction` по-прежнему проверяет корректность действия перед выдачей permission.
- Ноды с уже наложенными permissions включаются независимо от приоритета и физического
  состояния, в том числе permissions той же задачи при refresh: ранее выданное разрешение
  уже может использоваться для отключения ноды.
- Уведомления учитываются при пересечении с интервалом проверки; scheduled actions —
  только при строго более высоком приоритете. Учитываются и временные локи снимка.
  Общий интервал берётся по самой длительной проверке исходного набора действий.
- Сбор не изменяет `ClusterInfo`, не симулирует локальные разрешения и не применяет квоты.
  Неизвестный hostname даёт пустой набор целей для действия, а не общий отказ сборщика.
  Если не найдено ни одной целевой ноды, результат пустой: старые ограничения сами по себе
  не инициируют проверку NBS2. Успешный сбор не означает, что действия валидны или разрешены.

**Критерий готовности:** интеграционные тесты подтверждают точный состав запроса в DBSC,
включая уже заблокированную, но физически работающую ноду и действия за пределами
текущей квоты CMS. Покрытие добавляем после подключения полного пути, без доступа
тестов к приватным методам CMS.

### 3. Асинхронный клиент DBSController

Добавить actor-helper для одной пакетной проверки через tablet pipe:
отправка запроса, обработка ответа, ограниченный таймаут и ошибка соединения.
Передавать результат в CMS внутренним событием с идентификатором попытки.
Подключить контракт событий/protobuf без ненужных зависимостей от реализации DBSC.

**Статус:** добавлен `CreateNbs2MaintenanceChecker` в `nbs2_maintenance.{h,cpp}`.
Добавлены три комплексных теста в `ut/nbs2_maintenance_ut.cpp`; после исправлений
по результатам запуска пользователем успешный повторный прогон пока не подтверждён.
Общий механизм ожидания и обработчик результата добавлены в пункте 4;
permission/create подключены в пункте 5, refresh — в пункте 6, manual approve — в пункте 7.

- Отдельный actor и tablet pipe на одну попытку. Весь набор `NodeIds` отправляется
  одним `TEvNodeMaintenancePermissionRequest` в `MakeDbsControllerID()`, без повторной
  отправки внутри попытки. Конечный положительный таймаут передаётся при создании
  actor и покрывает подключение и ожидание ответа.
- `TEvNbs2MaintenanceResult` содержит `AttemptId`, статус CMS, причину и
  `BlockingPartitionIds`: `ALLOW`, `DISALLOW_TEMP` для `DENY`, `ERROR_TEMP` при ошибке
  DBSC, неизвестном решении, ошибке подключения, разрыве pipe или таймауте.
- Успешный proto3-ответ может не содержать `Error` и `Decision`: это штатный `ALLOW`,
  в том числе при пустой карте DBSC. Ошибка определяется штатным `HasError` NBS.
- Идентификатор попытки передаётся также через cookie запроса; ответы с другим
  cookie игнорируются. После единственного результата actor завершает работу и
  закрывает pipe. `TEvPoisonPill` отменяет попытку без ответа.
- CMS должен дополнительно сверять `AttemptId` с актуальным ожидающим запросом
  и отменять ненужный helper — это пункт 4. Сам клиент не выдаёт и не меняет локи.
- Используются существующий контракт `TEvDbsControllerPrivate`, protobuf и общие
  библиотеки NBS; зависимость от библиотеки реализации DBSController не добавлена.

**Критерий готовности:** проверены `ALLOW`, `DENY`, ошибка и таймаут; нет блокирующего ожидания,
повторного завершения или обработки запоздалого ответа как актуального.
Интеграционные тесты permission/create добавлены в пунктах 4–5, но ещё не запускались.

### 4. Незавершённый запрос и управление очередью CMS

Добавить контекст ожидания и приостановку продвижения очереди разрешений.
До ответа не фиксировать новые локи и не оставлять глобальные временные изменения
локальных проверок. Изменение значимых ограничений, конфигурации или удаление задачи
во время ожидания должно приводить к перепроверке либо безопасному завершению
с ошибкой. Учесть пути изменения состояния вне `ProcessQueue`.

**Статус:** общий механизм реализован; по запуску пользователя прошли
`QueueAndCompletion` и `StaleResultsAndRestart`.
`StartNbs2MaintenanceCheck` подключён к permission/create в пункте 5 и refresh в пункте 6;
manual approve подключён в пункте 7.
Добавлены четыре комплексных теста `TCmsNbs2MaintenanceIntegrationTest`
в `ut/nbs2_maintenance_cms_ut.cpp`. По договорённости с пользователем тесты
написаны заранее: неподключённые обработчики пока дают падение с диагностикой,
что CMS ответил без обращения в DBSC. Ожидания ограничены; тесты не пропускаются.

- Контекст владеет исходным событием (включая sender/cookie), копией нормализованного
  permission request, набором нод, `AttemptId`, helper actor и продолжением обработки.
  Для refresh/manual approve также сохраняются `RequestId`, копия исходного
  `TRequestInfo` из `State` и связь с maintenance task. Исходный scheduled request
  хранится отдельно от эффективного запроса с переопределёнными параметрами попытки.
  Ссылки и итераторы на изменяемые задачи не сохраняются.
- После начала проверки `ProcessQueue` не продвигает очередь, а `StartCollecting`
  не запускает следующий сбор. Текущий элемент извлекается и учитывается в статистике
  один раз; новые запросы остаются в `NextQueue`.
- Ответ принимается только от ожидаемого helper и с актуальным `AttemptId`.
  Продолжение вызывается один раз, синхронно; затем `ResumeQueue` возобновляет
  обработку или запускает сбор для следующей очереди. Порядок установки локов
  в памяти и их сохранения транзакцией остаётся прежним.
- Глобальной инвалидации и вызовов из транзакций нет: актуальность проверяется
  непосредственно при ответе DBSC. Для create повторно проверяется отсутствие
  задачи с указанным `MaintenanceTaskId`. Для refresh/manual approve запрос должен
  существовать с прежним содержимым; связь с maintenance
  task и её существование также проверяются. Удаление и повторное создание задачи
  с тем же uid отличается новым `RequestId`.
- Перед продолжением проверяются включение интеграции и `DisableMaintenance`.
  Ручное одобрение (запрос `TEvManageRequestRequest` с командой `APPROVE`) сохраняет
  существующий обход `DisableMaintenance`, но не проверок NBS2 и актуальности запроса.
  Затем заново собирается набор нод с текущими локами, конфигурацией и временем.
  При изменении запроса или набора возвращается `ERROR_TEMP`; второго запроса в DBSC
  нет. Изменения посторонних задач, markers и нерелевантных настроек сами по себе
  не отменяют результат. Обычные CMS-проверки выполняются на текущем состоянии
  в продолжении обработки. Перед продолжением после `ALLOW` к checkers повторно
  применяются текущие cluster/tenant limits: они могли обновиться во время ожидания
  без изменения набора нод. Новый сбор информации для этого не требуется.
- Запуск проверки должен предшествовать локальным проверкам и временным изменениям
  `ClusterInfo`/`State`. Эффективный запрос для refresh/manual approve готовится
  в отдельной копии. Продолжение обязано обработать статус, пересчитать квоту
  по живой задаче и установить разрешённые локи в памяти до возврата, не откладывая
  эту работу в отдельное событие. Сохранённая до ожидания квота не используется.
- При остановке таблетки helper отменяется через `PoisonPill`, контекст уничтожается
  без продолжения. Незавершённая проверка не сохраняется в БД и не создаёт локов.

**Критерий готовности:** конкурирующие запросы не используют устаревший контекст локов;
очередь возобновляется на всех исходах. После рестарта незавершённая попытка
не создаёт разрешений, а ранее сохранённые локи учитываются при новом запросе.
Проверка полного пути выполняется через публичные события CMS и подставной DBSC,
без friend-доступа или вызова приватных методов. Общий fake DBSC вынесен
в `ut/nbs2_maintenance_helpers.h` и переиспользуется тестами checker.

Тесты пункта 4 (refresh и manual approve подключены, повторный прогон не выполнен):

1. `QueueAndCompletion`: очередь и отсутствие новых локов во время ожидания,
   доступность управляющего API, продолжение после `ALLOW`, `DENY` и таймаута,
   учёт разрешения первого запроса в следующем пакете DBSC, сохранение cookie
   и адресата ответа. Force не обходит проверку NBS2.
2. `RequestFreshness`: удаление проверяемого запроса, попадание будущего уведомления
   в горизонт проверки, удаление постороннего запроса и допустимые переопределения
   параметров refresh. Устаревший `ALLOW` не создаёт локов и не воскрешает запрос;
   очередь возобновляется без повторной проверки той же попытки.
3. `ConfigurationAndManualApproval`: включение `DisableMaintenance` во время
   обычной проверки, ручное одобрение при выключенном maintenance для трёх исходов
   DBSC и отключение feature flag во время ожидания. При отказе ручное одобрение
   сохраняет ожидающие действия; после выключения интеграции новый запрос идёт
   по прежнему пути без DBSC.
4. `StaleResultsAndRestart`: неверные sender/attempt, запоздалые и повторные
   результаты, отмена helper и закрытие pipe при рестарте CMS. Сохранённые локи
   переживают рестарт; ожидающий и стоящий в очереди запросы локов не получают.

### 5. Выдача разрешений и создание maintenance task

Встроить общий асинхронный этап в обработку `TEvPermissionRequest`, используемую
create. `ALLOW` разрешает продолжить существующую выдачу; `DENY` даёт
`DISALLOW_TEMP` с `BlockingPartitionIds`; ошибка связи или таймаут — `ERROR_TEMP`.
На отказе не выдавать новые permissions и сохранять ожидающие действия
по правилам планирования CMS. Dry-run выполняет проверку без создания локов.
После `ALLOW` или пропуска DBSC-проверки при пустом наборе обязательно выполнять штатный
`CheckPermissionRequest`, включая обработку ошибок отдельных host/service и `ALLOW_PARTIAL`.
Невалидное действие может добавить лишние ноды через `FindLockedItems` и привести
к консервативному отказу DBSC; это не новая строгая валидация в сборщике.

**Статус:** код и два комплексных теста добавлены. По запуску пользователя
`PermissionBatchAndLegacyPaths` прошёл. `CreateMaintenanceTaskBatchAndDryRun`
упал из-за неверного ожидания ненулевого cookie: существующие публичные адаптеры
отвечают с cookie `0`. Для публичных Create/Get тест теперь отправляет cookie `0`,
сохраняя проверку ненулевого cookie для прямых CMS-запросов. Повторный запуск
после этой правки не выполнялся.

- `Handle(TEvPermissionRequest)` раскрывает tenant, сортирует действия, проверяет
  условие включения и собирает все ноды до локальных проверок и отбора по квоте.
  Непустой набор передаётся в `StartNbs2MaintenanceCheck` одной попыткой.
  Таймаут берётся из существующего `InfoCollectionTimeout` (по умолчанию 15 секунд).
- Прежнее продолжение обработчика вынесено в `ProcessPermissionRequest`.
  После `ALLOW` или при пропуске интеграции вызываются прежние проверки CMS,
  выдача permissions и транзакция сохранения. Force не обходит DBSC.
- Общая ошибка предварительной проверки передаётся в `CheckPermissionRequest`:
  после подготовки прежних scheduled-метаданных, но до проверки отдельных действий
  она запрещает выдачу любых permissions. При scheduling сохраняются все действия
  и generic issues с причиной и `BlockingPartitionIds`; лимит числа issues сохранён.
  Текст причины также возвращается в legacy `Status.Reason`, выставляется retry deadline.
- Публичный create использует существующий адаптер: `DENY` означает успешно
  созданную задачу с pending actions, `ERROR_TEMP` — `UNAVAILABLE`. В последнем
  случае задача с ожидающими действиями тоже сохраняется, но без локов;
  дальнейшая работа идёт через Get/Refresh, а не повторный Create того же uid.
- Dry-run обращается в DBSC, но не сохраняет tasks, scheduled requests или permissions.
  Для dry-run `DENY` причина возвращается в публичных `Issues`, поскольку pending
  actions не хранятся. Этот дополнительный warning включён только вместе с интеграцией NBS2.
- При занятом uid продолжение после DBSC возвращает временную ошибку без записи
  поверх существующей задачи, в том числе если результат уже признан устаревшим.
- Добавлены `PermissionBatchAndLegacyPaths` и `CreateMaintenanceTaskBatchAndDryRun`:
  полный пакет до квоты, частичное разрешение после `ALLOW`, общий `DENY`/таймаут,
  сохранение ожидающих действий и причин, актуальные лимиты после ожидания,
  выключенная интеграция, штатная валидация пустого набора, настоящий maintenance
  Create API и dry-run для `ALLOW`/`DENY`. Используется реальный CMS и общий fake DBSC.

**Критерий готовности:** протестированы общий отказ без запросов на подмножества, разрешение,
обычный частичный результат CMS после `ALLOW`, force, dry-run и пустая карта DBSC.

### 6. Повторная проверка maintenance task

Подключить тот же этап к `TEvCheckRequest`, используемому refresh. Проверять
все оставшиеся действия вместе с действующими ограничениями, включая ранее
выданные разрешения этой задачи. Сохранить правила квот и завершения действий.

**Статус:** код и один комплексный тест добавлены; сборка и тесты не запускались.

- `Handle(TEvCheckRequest)` готовит копию сохранённого запроса с приоритетом,
  собирает полный набор нод и запускает одну проверку DBSC.
  До ответа сохранённый запрос и квота не изменяются. Выключенная интеграция
  и пустой набор целей идут по прежнему пути.
- `ProcessCheckRequest` продолжает обработку после общей проверки актуальности.
  Режим текущей попытки устанавливается здесь, перед обычными проверками CMS.
  После `ALLOW` квота пересчитывается по текущим permissions задачи: завершение
  действия во время ожидания может освободить место. Затем выполняются штатные
  проверки CMS и сохранение разрешений с привязкой к существующей задаче.
- `DENY` оставляет все неполучившие разрешение действия ожидающими с причиной
  и `BlockingPartitionIds`. Ранее выданные permissions не отзываются.
  `ERROR_TEMP`, включая таймаут и устаревший контекст, возвращается без изменения
  задачи и без новых локов; удалённый или изменённый запрос не восстанавливается
  из сохранённой копии. Публичный Refresh API возвращает `UNAVAILABLE`.
- Dry-run проходит DBSC и локальные проверки, но не меняет сохранённый запрос,
  permissions или время последнего refresh. Если ожидающих действий уже нет,
  публичный Refresh API по-прежнему только возвращает существующие разрешения.
- `RefreshMaintenanceTaskLifecycle` проверяет отказ и последующее разрешение,
  полный пакет при исчерпанной квоте, таймаут без изменения задачи,
  `CompleteAction` во время ожидания, сохранение локов и ожидающих действий после
  рестарта, dry-run и выключенный feature flag. Используются настоящий CMS,
  публичные Refresh/Get/CompleteAction и общий fake DBSC.
  Ранее добавленный `RequestFreshness` проверяет удаление запроса, новое ограничение
  в горизонте проверки, изменения посторонней задачи и переопределение режима refresh.
  Ручное одобрение в `ConfigurationAndManualApproval` подключено в пункте 7.

**Критерий готовности:** refresh корректно обрабатывает `DENY → ALLOW`, новые ограничения,
завершение предыдущих действий, рестарт CMS и исчерпанную квоту.

### 7. Ручное одобрение

**Статус:** код и интеграционные тесты добавлены; сборка и тесты не запускались.

Подключить `ManuallyApproveRequest` к общей проверке. До положительного ответа
не выдавать permissions и не удалять ожидающие действия. При отказе или ошибке
запрос остаётся ожидающим. Остальную семантику ручного одобрения сохранить.
`DisableMaintenance = true` не запрещает ручное одобрение; отказ или ошибка DBSC
по-прежнему запрещают выдачу новых permissions.
Отдельно обеспечить безопасное разрешение целей: этот путь не вызывает `CheckAction`,
а сохранённые scheduled actions могут содержать ещё не проверенные или невалидные действия.

- При включённой интеграции `APPROVE` проходит общую очередь и сбор информации
  о кластере, затем одну проверку DBSC. Это позволяет переиспользовать существующий
  контекст одной незавершённой проверки `PendingNbs2MaintenanceCheck`; проверка
  актуальности результата остаётся отдельной защитой. `GET`, `LIST` и `REJECT`
  остаются немедленными.
  При выключенной интеграции сохраняется прежний путь; если проверка уже выполняется
  в момент выключения флага, одобрение дожидается её завершения в очереди.
- Для пакета используется копия scheduled request с `Min<i32>()`, как в прежних
  проверках ручного одобрения: приоритеты ожидающих запросов обходятся, но действующие
  permissions и уведомления учитываются. Сохранённый запрос до ответа не меняется.
- Для действий над нодами дополнительно проверяются host и сервисы существующими
  `IsActionHostValid` и `ParseServices`; пустой список и отсутствие нужных сервисов
  отвергаются. Обычная модель отказа CMS при этом не запускается.
- После `ALLOW` и общей проверки актуальности выполняется прежнее продолжение
  `ProcessManuallyApproveRequest`: проверка конфликтующих локов, выдача в памяти,
  сохранение транзакцией и ответ с исходным cookie. При `DENY`/ошибке возвращается
  `DISALLOW_TEMP`/`ERROR_TEMP` с причиной, без изменения ожидающего запроса.
- В NBS2-пути длительность разрешения определяется через `GetPermissionDuration`,
  как и горизонт пакета DBSC. Это учитывает duration в действии публичного API,
  вместо уже истёкшего разрешения при отсутствии duration у самого запроса.
- `ManualApprovalWithRealDbsController` проверяет общий отказ из-за действующего
  лока другой задачи, сохранение pending и причины с partition ID, разрешение после
  `CompleteAction` при `DisableMaintenance = true`, deadline и сохранение после рестарта.
  CMS и DBSC настоящие, карта задаётся через API DBSC.
- `ConfigurationAndManualApproval` проверяет `ALLOW`, `DENY`, таймаут, отсутствие
  изменений при отказе и выключенную интеграцию. Новый `ManualApprovalQueueAndTargets`
  проверяет очередь за другой попыткой, включение её выданного лока в пакет,
  удаление ручного запроса во время ожидания и безопасное завершение с продолжением
  очереди; табличные случаи проверяют невалидные host/services без новых разрешений.
  Для управления задержками и ошибками в этих сценариях используется реальный CMS
  и существующий fake DBSC.

**Критерий готовности:** проверены `ALLOW`, `DENY`, таймаут, выключенная интеграция
и ручное одобрение во время другой незавершённой проверки. При `DisableMaintenance = true`
ручное одобрение проходит после `ALLOW`, но не после отказа или ошибки DBSC.

### 8. Диагностика, регрессия и документация

**Статус:** добавлены три теста `TCmsNbs2RealDbsControllerTest`
в `ut/nbs2_maintenance_dbsc_ut.cpp`, включая тест ручного одобрения из пункта 7.
При запуске пользователем первые два упали на
`ResolveTablet` сразу после создания bootstrapper DBSC. Добавлено ограниченное
ожидание успешного подключения tablet pipe при старте и после рестарта контроллера;
повторная сборка и запуск после исправления не выполнялись.
Диагностика, общий регрессионный прогон и документация флага ещё не выполнены.

Обе таблетки настоящие: CMS запускается существующим `TCmsTestEnv`, DBSController —
через `CreateDbsControllerTablet` под штатным tablet ID. Карта дисков передаётся
через `TEvUpdateDDiskMapRequest`, maintenance-запросы проходят через публичные события
CMS и настоящий tablet pipe. Наблюдатели только записывают запросы и ответы;
решения `ALLOW/DENY` не подменяются. Whiteboard и часть источников кластерной
информации остаются тестовыми; реальные NBS partitions и диски не запускаются.
Зависимость от реализации DBSController добавлена только в тестовую цель.

1. `DecisionsFromDiskMap`: пустая карта даёт `ALLOW` для dry-run без сохранения
   задачи и разрешений. Для полной DBG из пяти здоровых нод одна нода разрешается,
   две дают общий `DENY` даже при `FORCE` и `MaxInflightActions = 1`.
   Проверяются точный пакет нод, единственная проверка на попытку, blocking partition ID
   и сохранение всех отклонённых действий как pending с причиной.
2. `ExistingLocksRefreshAndRestart`: разрешение задачи A на первую ноду учитывается

   pending B и отказ на refresh. После `CompleteAction` задачи A refresh B получает
   `ALLOW`; пакет содержит только вторую ноду, новое разрешение сохраняется.

## Принятые ограничения первой версии

- Неполная карта означает неполную защиту NBS2; отдельный протокол готовности не добавляем.
- Общая проверка может отклонить запрос, выполнимый последовательно:
  например, две ноды одной DBG даже при `MaxInflightActions = 1`.
- Общий список со старыми локами может давать консервативный отказ из-за группы,
  не связанной с новыми действиями.
- Ожидание DBSController задерживает следующие запросы очереди CMS;
  задержка ограничивается таймаутом.
