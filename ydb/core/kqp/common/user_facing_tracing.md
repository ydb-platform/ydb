# User-facing tracing: уровни сбора и ограничения

Канал user-facing трейсинга (`user_facing_tracing_config`) независим от dev-канала (`tracing_config`):
свой trace-id, своё сэмплирование, своё дерево. Архитектура — record-then-render: движок только
записывает таймстемпы и компактные статы, всё дерево спанов строится одним рендерером
(`kqp_user_facing_tracing.cpp`) в момент ответа клиенту.

## Что собираем на каком уровне

Уровень сэмплирования (0-15 из конфига) маппится на **внутри-KQP режим сбора статов**
(`UserFacingTraceCollectionMode`, см. `PrepareBaseRequest`):

| Уровень сэмплирования | Режим сбора | Что появляется в трейсе | Стоимость |
|---|---|---|---|
| 1..5 | `STATS_COLLECTION_BASIC` | Корень (verb + таблица, атрибуты RU/rows/cpu), фазы: Queued, Compile, Execute → Prepare (ResolveTables → Metadata/Partitioning, ResolveShards, Snapshot), Run, Commit (+ PrepareShards/Coordinator/ApplyShards). Стейджей и тасков НЕТ — BASIC-экспорт статов их не содержит. | Копеечная: таймстемпы фаз + лёгкие локальные ивенты. |
| 6..15 | `STATS_COLLECTION_FULL` | + спаны стейджей (Join/Aggregate/Read/Write `<таблица>`) с агрегатами параллельности: min/avg/max длительности тасков, start/finish (spread + avg offset), skew, wait, spill, `ydb.tasks_by_node` (распределение тасков по нодам, кап 32), ноды экстремальных тасков (`ydb.slowest/fastest_task_node`) + спаны тасков (top-128 на стейдж, имя = глагол стейджа) + per-shard спаны: `Read from shard …` под тасками (read actor, stream lookup; ≤64 на таск), `Prepare/Commit shard …` под коммитом. | CA собирают FULL-статы; экзекьютер держит выжимку ~100 байт/таск + карту stage→node→count; шардовые записи ≤64×~40Б на таск. |

**PROFILE трейс-каналом не используется вообще**: рендерер не потребляет ничего
PROFILE-эксклюзивного (history, NodeStats, каналы), а профильный сбор облагает налогом все CA
и датащарды запроса. PROFILE остаётся клиентам, явно запросившим статы. Побочный эффект решения:
клиентские FULL-запросы (без трейсинга) тоже собирают шардовые записи в Extra таск-статов
(до ~2.5KB на таск в сообщениях статов) — одинаково для всех, план их игнорирует.

Важно: эскалация режима сбора **не меняет ответ клиенту** — экспорт статов в ответ идёт строго
по клиентскому `StatsMode` (см. `CollectionStatsMode` vs `Request.StatsMode` в экзекьютере).

## Действующие ограничения (капы)

| Ограничение | Значение | Семантика |
|---|---|---|
| Спанов на запрос (глобально) | `MaxUserFacingSpansPerQuery = 5000` | Фазы и стейджи рендерятся всегда; таски допускаются глобальным top-K по длительности (duration cutoff через nth_element по всем экзекьюшенам); шардовые дети едят остаток. Корень получает `ydb.spans_truncated`. |
| Тасков на стейдж | `MaxUserFacingTraceTasksPerStage = 128` | top-N по длительности (вытесняется самый короткий) — стрэгглеры сохраняются. Стейдж-спан получает `ydb.tasks_truncated`. |
| Шардов на таск | `MaxUserFacingShardReadsPerTask = 64` | first-come при экспорте из актора; таск-спан получает `ydb.shards_truncated`. |
| Shard-ack'ов коммита | 64 (та же константа) | first-come при отправке `TEvKqpBuffer::TEvResult`. |
| Память на таск | ~100 байт (`TUserFacingTaskSnapshot`) | Выжимка вместо полного CA-прото; в неё уже включены retries и per-shard записи. |
| Текст запроса | параметризован | Литералы → `?`, комменты выброшены (лексер); sensitive-маркеры (PASSWORD и т.п.) прячут текст целиком; при сбое лексера текст не пишется вовсе. |
| Сообщение об ошибке | 1024 символа | issues одной строкой в status.message корня. |

## Известные пределы на больших запросах (не реализовано, кандидаты)

Худший случай (50 стейджей × 2000 тасков, PROFILE): пер-контейнерные капы сами по себе не
ограничивали суммарное число спанов (потолок ~400k на трейс при деградации Jaeger UI на ~10-50k) —
поэтому введён глобальный бюджет `MaxUserFacingSpansPerQuery`.

Глобальный бюджет спанов уже реализован (см. таблицу капов). Остальные кандидаты (следующие ПР):

1. **[РЕАЛИЗОВАНО] Верхняя ступень = FULL, без PROFILE.** Флаг через dq не понадобился:
   per-shard сбор перевешен с `CollectProfile()` на `CollectFull()` в акторах, маппинг уровней
   упрощён до двух ступеней (BASIC / FULL). Сэмплирование больше не включает history у CA,
   профильную агрегацию экзекьютера и профильный сбор на датащардах.
2. **Свой enum уровней вместо dev-шкалы 0-15.** Сейчас пороги 6/10 взяты из dev-констант
   (`TQueryProcessor::Basic/Detailed`) — чужая семантика, оператор не видит стоимости за числом.
   Предложение: `detail: phases | stages | tasks | shards` в конфиге, с капами, скейлящимися со
   ступенью. Verbosity в TTraceId остаётся деталью кодирования на проводе.
3. **Скан-путь (OLAP) не покрыт per-shard спанами**: канал extra-статов scan fetcher → CA в
   апстриме закомментирован, нужно оживлять отдельно.
4. **[РЕАЛИЗОВАНО] Имена пишущих стейджей**: экзекьютер снимает карту
   `stageId -> (таблица, запись?)` из стейдж-меты TasksGraph (нумерация совпадает со статами);
   sink-стейджи рендерятся как `Write <таблица>` / `Write task N`.

## Карта зависимостей от режима сбора (что включает каждый уровень)

1. **Compute actors** (`GetDqStatsMode` -> `TCollectStatsLevel` в runtime settings таска):
   BASIC — агрегаты по таску (cpu/rows/времена; достаточно для таск-спанов); FULL — + перечисление
   per-source/channel протошек, плюс на этот гейт (`IngressStats.CollectFull()`) посажен наш
   per-shard сбор; PROFILE — + history time series и детальные статы буферов.
2. **Датащарды** (`GetDqStatsModeShard`): NONE глушится «to improve datashard performance»;
   PROFILE включает профильный сбор прямо на шардах — эскалация трогает storage-слой и латентность
   соседних запросов.
3. **Экзекьютер**: `CollectFullStats` — стейдж-агрегаты; `CollectProfileStats` — NodeStats и
   stage extra; `HistorySampleCount` — тайм-серии агрегатов.
4. **Экспорт клиенту**: BASIC — totals; FULL — + стейджи и longest-task ComputeActors, планы со
   статами; PROFILE — + ноды и extra.
5. **Дно**: NONE внутри форсится до BASIC у CA — RU-биллинг и sysview всегда едят totals.

## Прочие зафиксированные трейд-оффы

- Post-hoc рендер: всё-или-ничего — упала сессия, трейса нет; долгий запрос невидим до ответа.
- Traceparent клиента уходит в оба канала (осознанно, см. коммент в `MaybeStartTracing`).
- Окно Compile — штампы сессии вокруг round-trip'а; у мультистейтмент-скриптов только первая
  компиляция.
- `UPDATE` на старом (не-sink) пути записи именуется `UPSERT` — физплан не хранит verb.
- Джойн именуется по ведущей таблице (lookup-сторона не источник в физплане).
- Схема имён/атрибутов спанов — experimental, стабильность пока не гарантируется.
