# Доработки DQ для трассировки KQP

В текущем PR код и тесты `ydb/library/yql/dq` остаются как в базе PR.
Ниже — требования для отдельного изменения DQ. Имена задач, выбор атрибутов
и представление статистики остаются в KQP.

## Завершение compute-спана

Файл: `ydb/library/yql/dq/actors/compute/dq_compute_actor_impl.h`.

- `ReportStats()` не должен завершать спан: это промежуточная отправка
  статистики, после которой задача продолжает работать.
- Завершать спан при фактическом завершении задачи, после записи итоговых
  атрибутов. Сохранять успех, ошибку, отмену и timeout, включая текст ошибки.
- Не завершать спан заранее в обработчике пересылаемого abort-события.
  Нужные поля события следует прочитать до передачи владения им.
- Для checkpoint/streaming-сценариев отдельно определить границы спана:
  завершение вычисления и уничтожение актора могут происходить в разное время.

KQP нужен вызов с итоговой статистикой и результатом операции до закрытия
спана. Существующий `FillExtraStats()` получает
`WithProgressStats || last`: этот аргумент сам по себе не отличает
промежуточный отчёт от итогового. Контракт должен явно различать эти случаи.
Переносить KQP-разметку в базовый DQ-актор для этого не требуется.

## Достоверное время выполнения задач

Файлы: `runtime/dq_tasks_runner.cpp`, `runtime/dq_input_producer.cpp`
и формирование `TDqTaskStats` в `actors/compute` под `ydb/library/yql/dq`.

- Определить и заполнять время начала для программ без входов
  (`ProgramInputsCount == 0`): у них нет поступления первой входной строки,
  которое могло бы установить `StartTs`.
- Заполнять время начала в wide input merge при первой строке либо завершении
  пустого входа; один `Yield` не должен означать начало обработки данных.
- Передавать уже измеренные границы выполнения в итоговой Basic-статистике.
  Не подменять отсутствующий замер временем создания актора или временем
  отправки ответа.
- Различать отсутствующий замер и измеренную нулевую длительность, в том числе
  при округлении timestamp до миллисекунд.

## Spill-счётчики без Full/Profile

Файлы: `runtime/dq_tasks_runner.cpp`,
`actors/compute/dq_compute_actor_stats.cpp` под `ydb/library/yql/dq`.

Нужны готовые `SpillingComputeWriteBytes` и `SpillingChannelWriteBytes`
в итоговом отчёте для диагностики запроса с Basic-статистикой.
В базе PR обновление этих полей task runner и их экспорт в protobuf
ограничены Full/Profile.

- Не повышать режим статистики запроса ради трассировки.
- Получать дешёвый снимок существующих счётчиков только при наличии
  потребителя. Полные временные и операторные профили для этого не нужны.
- Не превращать каждый обычный `GetStats()`, включая запросы без tracing,
  в неявное обновление диагностических полей.
- Желательно явно обозначать доступность счётчика: отсутствие данных
  не должно выглядеть как измеренный ноль.

## Что проверить в отдельном PR

1. Долгая задача отправляет несколько промежуточных отчётов, затем завершается:
   один compute-спан охватывает всю работу и содержит итоговую статистику.
2. Успех, ошибка вычисления, timeout и пересланный abort: спан закрывается
   один раз, с соответствующим результатом; статус запроса не зависит от tracing.
3. Задача без входов и sorted merge с непустым/пустым результатом:
   корректные границы, стабильное время начала, допустимая нулевая длительность.
4. Настоящий spill при Basic и Full, с tracing и без: доступность счётчиков,
   отсутствие автоматического повышения режима и лишнего сбора без потребителя.
5. Query и Table service: отчёты задач согласованы с суммами KQP;
   изменения общего DQ проверены также для его других потребителей.

## Ограничения текущего KQP PR

- Общий DQ пока может закрыть `Task` на промежуточной статистике. Поздние
  атрибуты такого спана могут отсутствовать, а его длительность — быть короче
  выполнения задачи. Нормализация успешного/ошибочного статуса спана также
  остаётся задачей DQ. KQP продолжает отражать результат на Query/Execute plan
  и обрабатывать итоговые отчёты для стадий.
- У части успешных задач нет замера длительности. KQP сохраняет доступные
  данные и выставляет `ydb.task_stats_incomplete`; это не ошибка запроса.
- На Basic значения `ydb.spilled_bytes` строятся из доступного отчёта DQ.
  Нулевое значение пока не доказывает отсутствие spill. Полные счётчики доступны,
  когда Full/Profile явно запросил клиент.
- Атрибуты CPU, строк, ожиданий, узла, retry и доступных временных границ
  добавляются в KQP через существующий `FillExtraStats()`. Нового helper в DQ нет.

Это материал для обсуждения, а не требование повторить прежний способ реализации.
