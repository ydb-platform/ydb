# RFC: `query_metrics_one_hour`

Режим: локальное расширение существующего SysView processor


## Краткое описание

Добавить системное представление `.sys/query_metrics_one_hour`, расширив
существующий pipeline минутных метрик запросов.

Результат намеренно является приблизительным. Сначала количество запросов
ограничивается на каждой ноде, затем processor запрашивает полные метрики
только для конфигурируемого количества глобально выбранных минутных
кандидатов. Источники аппроксимации должны быть документированы и наблюдаемы.

Часовая агрегация не добавляет ещё одного этапа вытеснения: каждый запрос, для
которого были получены полные минутные метрики, сохраняется в персистентном
аккумуляторе текущего часа.

Первая версия сохраняет:

- существующий `QueryTextHash` от сырого текста;
- текущую топологию акторов;
- протокол `summary -> metrics request`;
- один `TSysViewProcessor` на базу.

Нормализованные fingerprint'ы, отдельный словарь текстов запросов, push-модель
сбора и шардирование processor'а выносятся в последующие задачи.

## Мотивация

В processor уже есть большая часть публичной и внутренней инфраструктуры для
`MetricsOneHour`, но в эту таблицу никто не пишет.

Восстанавливать часовую статистику из опубликованного минутного top нельзя:
полные метрики запросов, не выбранных в соответствующую минуту, после закрытия
минутного окна необратимо теряются.

Пример:

- запрос `Q` потребляет 1 CPU-секунду каждую минуту;
- каждую минуту существует 256 других одноразовых запросов по 1.01
  CPU-секунды;
- `Q` стабильно занимает 257-е место и не запрашивается processor'ом;
- за час `Q` потребляет 60 CPU-секунд и может быть настоящим лидером часа;
- каждый из записанных одноразовых запросов потребил только 1.01 CPU-секунды.

При минутном лимите 256 запрос `Q` ни разу не будет запрошен, поэтому его
полную часовую статистику невозможно восстановить задним числом.

Следовательно, нужна персистентная running-агрегация доступных полных минутных
метрик, а не merge уже материализованного минутного результата.

## Текущий pipeline

1. После выполнения запроса KQP отправляет одно событие `TQueryStats`.
2. Локальный `TSysViewService` агрегирует запросы текущей минуты в памяти.
3. `TQueryInterval` оставляет не более 1024 хешей сырого текста, вытесняя
   запись с наименьшим накопленным CPU.
4. Раз в минуту ноды отправляют в `TSysViewProcessor` базы summary из хешей и
   CPU.
5. Processor оставляет не более 1024 различных summary-хешей и выбирает
   глобальный top по CPU. Текущий `TopCountLimit` равен 256.
6. Processor запрашивает полные метрики и текст для выбранных хешей.
7. Результат сохраняется в `MetricsOneMinute` с ключом
   `(IntervalEnd, Rank)`.

Основные точки в коде:

- `ydb/core/kqp/session_actor/kqp_query_stats.cpp` — хеширование сырого текста
  и ограничение текста в 10 KiB;
- `ydb/core/sys_view/service/query_interval.{h,cpp}` — node-side top-1024;
- `ydb/core/sys_view/service/sysview_service.cpp` — волатильные окна
  `Collect/Report` и минутная ротация;
- `ydb/core/sys_view/processor/tx_aggregate.cpp` — выбор кандидатов и запрос
  полных метрик;
- `ydb/core/sys_view/processor/processor_impl.cpp` — сохранение минутного
  результата;
- `ydb/core/sys_view/processor/schema.h` — схема таблиц, включая существующую,
  но неиспользуемую `MetricsOneHour`.

## Цели

- Добавить `.sys/query_metrics_one_hour` с теми же колонками и правилами
  сортировки, что у `.sys/query_metrics_one_minute`.
- Показывать live-снимок текущего календарного часа.
- Хранить закрытые часовые бакеты две недели.
- Переживать рестарт tablet'а SysView processor без потери или повторного
  учёта уже закоммиченных минут.
- Оставить состояние на compute-нодах волатильным. Рестарт ноды может потерять
  только её незакрытое минутное окно.
- Сделать количество кандидатов, для которых запрашиваются полные метрики,
  конфигурируемым в диапазоне `1..1024`, default `256`.
- Не добавлять дополнительное вытеснение внутри часовой агрегации.
- Сохранить совместимость существующего протокола при rolling restart.
- Ограничить потребление памяти и персистентного хранилища.

## Не входит в задачу

- Точный глобальный часовой top среди всех выполненных запросов.
- Удаление существующих лимитов в 1024 записи на ноде и в processor summaries.
- Нормализация текста или изменение семантики `QueryTextHash`.
- Новый actor, новый тип tablet'а или новый wire-протокол.
- Шардирование SysView processor.
- Персистентное хранение query statistics на compute-нодах.
- Скользящее окно «последние 60 минут».
- Исправление уже финализированного бакета произвольно поздними данными.

`query_metrics_one_hour` использует непересекающиеся часовые бакеты по UTC.

## Пользовательская семантика

`query_metrics_one_hour` содержит до 256 запросов для каждого календарного
часа. Строки отсортированы по убыванию наблюдаемого `CpuTimeUs.Sum`.

Бакет текущего часа является live-снимком и обновляется после каждой успешно
собранной минуты. После пересечения границы часа последний снимок старого часа
остаётся в истории, а накопление начинается для нового часа.

Метрики строки точны для тех вкладов, которые удалось собрать. Сам сбор
является best effort. Запрос может отсутствовать или иметь заниженные значения,
если:

- он был вытеснен из минутного node-side top-1024;
- он не попал в глобальный минутный top `QueryMetricsRequestLimit` processor'а;
- нода перезапустилась до отправки закрытой минуты;
- summary или metrics response не уложились в существующий deadline;
- нода или pipe завершились ошибкой во время сбора.

Поэтому представление не гарантирует наличие настоящего глобального часового
top. Увеличение `QueryMetricsRequestLimit` одновременно улучшает recall и
увеличивает сетевую и tablet-нагрузку.

В документации пользовательское представление должно называться приблизительным
диагностическим инструментом, а не источником данных для биллинга или строгого
учёта ресурсов.

Часовой слой не добавляет собственного sampling: если полные метрики запроса за
минуту дошли до processor, они сохраняются до финализации часа.

## Конфигурация

Добавить секцию в `TQueryServiceConfig` из
`ydb/core/protos/config.proto`. Номер поля 27 сейчас свободен:

```proto
message TQueryServiceConfig {
    message TQueryMetricsConfig {
        optional uint32 MetricsRequestLimit = 1 [default = 256];
    }

    optional TQueryMetricsConfig QueryMetrics = 27;
}
```

Эффективное значение должно находиться в диапазоне `1..1024`.

- Если поле отсутствует, используется `256`.
- Некорректная статическая конфигурация отклоняется валидатором.
- В runtime значение дополнительно ограничивается диапазоном `1..1024`.
  При срабатывании защиты пишется error log и увеличивается счётчик.
- Некорректная конфигурация не должна приводить к падению tablet'а.
- Старые бинарники игнорируют новое optional-поле и продолжают использовать
  скомпилированный лимит 256.

Настройка управляет только количеством хешей, для которых processor запрашивает
полные метрики. Она не изменяет:

- node admission limit, равный 1024;
- processor summary limit, равный 1024;
- публичный result limit, равный 256.

Эти три ограничения должны оставаться независимыми: они управляют разными
ресурсами и разными этапами потери точности.

В первой версии processor читает
`AppData()->QueryServiceConfig` при старте. Hot reload не требуется. Новое
значение применяется после рестарта или миграции tablet'а.

## Внутреннее хранение

Добавить в schema processor внутреннюю таблицу со следующим свободным локальным
ID — `Table<22>`:

```text
IntervalMetricsOneHour
    HourEnd   Timestamp  key
    QueryHash Uint64     key
    Data      String     serialized TQueryMetrics
```

Таблица хранит только метрики, без текста запроса.

Зеркало текущего часа в памяти:

```text
unordered_map<QueryHash, TQueryMetrics> CurrentHourMetrics
```

В accumulator хранится только активный час. `HourEnd` в ключе не позволяет
смешать соседние часы при восстановлении или очистке.

Максимальное количество различных записей:

```text
60 * QueryMetricsRequestLimit
```

Получается:

- не более 15 360 записей при default `256`;
- не более 61 440 записей при максимуме `1024`.

В реальной нагрузке число меньше, потому что хеши повторяются между минутами.

В accumulator не применяется top-1024. Такой лимит добавил бы ещё один
history-dependent eviction и дополнительный bias, экономя сравнительно немного
metrics-only состояния.

Исторические часовые результаты продолжают храниться в существующей
`MetricsOneHour` с ключом `(IntervalEnd, Rank)`. Retention остаётся равным 336
часовым бакетам, то есть двум неделям. Для закрытого часа сохраняется только
финальный top-256.

## Хранение текста запроса

Сохранять текст размером до 10 KiB для каждого элемента accumulator нельзя:
при максимальном лимите это даёт слишком большой worst case. Поэтому
`IntervalMetricsOneHour` не содержит текст.

При построении нового live top-256 текст ищется в следующем порядке:

1. текст, полученный вместе с метриками текущей минуты;
2. текст из предыдущего live-снимка этого часа по `QueryTextHash`;
3. пустой текст, если все запросы текста к нодам завершились неуспешно.

Этого достаточно для ограниченного top, потому что все агрегируемые значения
внутри часа монотонно растут. Неизменившийся запрос, отсутствовавший в прошлом
top-256, не может самостоятельно войти в новый top-256. Новый участник обязан
получить вклад в текущей минуте, в которой processor также запрашивает его
текст. Запрос, оставшийся в top, может использовать текст прошлого снимка.

Отдельный query-text dictionary устранит эту зависимость и дублирование текста,
но он не входит в первую реализацию.

## Алгоритм записи

Часовая обработка добавляется в существующую LocalDB-транзакцию `TTxCollect`.
Минутный результат, обновление accumulator, live-снимок часа, stage и reset
коммитятся атомарно.

Для каждой завершённой минуты:

1. Построить существующий минутный результат, отсортированный по CPU.
2. Сохранить публичный минутный top как сейчас.
3. Вычислить `hourEnd = EndOfHourInterval(IntervalEnd)`.
4. Для каждой полученной записи с полными метриками:
   - найти или создать `CurrentHourMetrics[QueryHash]`;
   - объединить `Count`, `Sum`, `Min`, `Max` и lock counters существующей
     функцией `Aggregate(TQueryMetrics&, const TQueryMetrics&)`;
   - сделать upsert `(hourEnd, queryHash)` в `IntervalMetricsOneHour`.
5. Выбрать top-256 accumulator по `CpuTimeUs.Sum`.
6. Для одинакового CPU использовать `QueryHash` как tie-breaker, чтобы снимки
   были детерминированными.
7. Полностью обновить live-строки `MetricsOneHour` с ключами `(hourEnd, rank)` и
   удалить оставшийся хвост старых rank'ов.
8. Выполнить существующий reset минутного интервала в той же транзакции.

При пересечении границы часа:

1. Последняя минута добавляется в старый час.
2. Снимок старого часа сохраняется и становится неизменяемой историей.
3. Записи старого часа удаляются из `IntervalMetricsOneHour`.
4. Для нового `hourEnd` начинается пустой accumulator.

Необходимо использовать тот же расчёт границы часа, который уже применяется в
`top_queries_*_one_hour`, чтобы бакеты разных представлений совпадали.

## Восстановление и идемпотентность

Accumulator загружается из LocalDB в `TTxInit` рядом с существующими минутными
и часовыми result maps.

Персистентного состояния на нодах не добавляется. Во время rolling restart нода
может потерять незавершённую минуту, но ранее закоммиченное состояние processor
остаётся доступным.

Отдельная таблица дедупликации минут не требуется: merge accumulator и переход
processor к следующему интервалу коммитятся одной LocalDB-транзакцией.
Транзакция либо сохраняет и метрики, и новое состояние интервала, либо не
сохраняет ничего.

Тесты восстановления должны покрывать рестарт:

- после сохранения summaries;
- при наличии незавершённых metrics requests;
- после сохранения части metrics responses;
- сразу после commit `TTxCollect`;
- непосредственно до и после границы часа.

## Исправление failure path

Текущий обработчик неуспешного metrics request удаляет ноду только из
in-memory набора in-flight запросов. Если последним завершается ошибочный
запрос, уже полученные частичные `QueryMetrics` могут не сохраниться, а
персистентная запись запроса может остаться в LocalDB.

Увеличение `MetricsRequestLimit` повышает вероятность попадания в этот путь,
поэтому исправление входит в текущую задачу.

Завершение ошибочного запроса должно выполняться транзакционно:

- удалить ноду из персистентного `NodesToRequest`;
- сохранить метрики, уже полученные от остальных нод;
- вызвать `PersistQueryResults`, когда последний запрос завершился успехом или
  ошибкой;
- считать отсутствующий вклад ошибочной ноды допустимой best-effort потерей.

## Публичное представление и read path

Для `.sys/query_metrics_one_hour` необходимо добавить:

- `EQueryMetricsOneHour = 47` в `sys_view_types.proto`;
- запись registry с существующей схемой `Schema::QueryMetrics`;
- dispatch в `scan.cpp`;
- выбор `METRICS_ONE_HOUR` в `query_metrics.cpp` вместо жёстко заданного
  `METRICS_ONE_MINUTE`;
- cluster-state visibility;
- canonical tenant schemas;
- тесты и пользовательскую документацию.

Публичная схема полностью совпадает с `query_metrics_one_minute`. Отличаются
только размер бакета, retention и запрашиваемый `EStatsType`.

## Rolling upgrade

Wire-сообщения между node service и processor не изменяются. Старые и новые
node service могут участвовать в сборе одной минуты. Во время mixed-version
rollout качество определяется существующим summary cap 1024 и версией
processor, на которой в данный момент запущен tablet.

Публичному пути системного представления нужен отдельный rollout barrier.
Старый SchemeShard не знает новую запись registry и может удалить уже созданный
путь как неизвестный.

Порядок включения:

1. Раскатить бинарник с внутренней схемой и новым публичным типом, но оставить
   создание представления выключенным.
2. Дождаться обновления всех нод, способных запускать SchemeShard.
3. Включить создание и видимость нового системного представления.
4. После шага 3 не откатываться на SchemeShard без поддержки нового типа без
   предварительного отключения или удаления представления поддерживаемым
   способом.

Общее изменение SchemeShard «сохранять неизвестные системные представления
будущих версий» выносится отдельно: оно полезно для всех будущих sys-view и
требует самостоятельного review.

Неизвестные внутренние LocalDB-таблицы processor сохраняются старыми
бинарниками, поэтому таблица accumulator не требует отдельного wire-механизма
совместимости.

## Оценка ресурсов

### Память ноды

Не изменяется: не более двух окон метрик по 1024 хеша на каждую активную базу
на ноде. Текст одного запроса ограничен 10 KiB.

### Сеть и CPU processor

Размер summary не изменяется. Объём полных метрик приблизительно растёт
пропорционально `MetricsRequestLimit`:

- `256` — текущий объём;
- `512` — до 2x текущего объёма;
- `1024` — до 4x текущего объёма.

Сохраняются существующие jitter отправки и ограничение количества in-flight
requests.

### Состояние processor

Metrics-only accumulator текущего часа содержит не более 61 440 различных
хешей при максимальной конфигурации. Каждую минуту записываются только
изменившиеся хеши; вся таблица целиком не перезаписывается.

Публичная часовая история добавляет не более:

```text
336 * 256 = 86 016 строк на базу
```

Как и сейчас, result history зеркалируется в RAM processor. При тексте 10 KiB
теоретический вклад только текстов достигает примерно 840 MiB на базу. Реальные
тексты обычно значительно короче, но это известное ограничение. Для первой
версии нужны memory counters, а затем — text dictionary и изменение read path.

## Наблюдаемость

Минимально необходимые счётчики:

- configured и effective `MetricsRequestLimit`;
- число различных summary-хешей, увиденных processor;
- число хешей, вытесненных processor summary limit 1024;
- число запросов полных метрик за интервал;
- число успешных, ошибочных и просроченных node responses;
- число хешей, добавленных в час за минуту;
- количество записей и сериализованный размер hour accumulator;
- количество строк live и финального часового снимка;
- число интервалов, отброшенных существующим deadline;
- число применений защитного fallback для некорректного конфига.

Если это можно сделать без изменения протокола, следует также добавить
node-side eviction counter.

Для cluster-wide процента покрытого CPU нужны новые поля summary. Это остаётся
последующей задачей.

## Тестирование

Интеграционные тесты используют FAST-режим processor.

Обязательные сценарии:

1. Результат минуты появляется одновременно в минутном и текущем часовом
   представлениях.
2. Один хеш правильно объединяется между несколькими минутами: проверяются
   count, sum, min, max и lock counters.
3. При изменении rank live-снимок часа переписывается без старых хвостовых
   строк.
4. Запрос, остающийся в top, сохраняет текст, даже если в следующую минуту не
   получил нового вклада.
5. Новый участник top получает текст текущей минуты.
6. Рестарт processor в середине часа сохраняет accumulator и не приводит к
   повторному учёту закоммиченных минут.
7. Последняя минута перед границей часа попадает в старый бакет, следующая — в
   новый.
8. Закрытый час переживает рестарт processor и удаляется после 336 бакетов.
9. Ошибка последнего node request сохраняет частичный успешный результат и
   очищает персистентное состояние запроса.
10. Работают лимиты 1, 256 и 1024; значения вне диапазона отклоняются или
    защитно ограничиваются.
11. Запрос на 257-м месте отсутствует при лимите 256 и становится доступным
    при лимите не меньше 257.
12. Публичный scan использует `METRICS_ONE_HOUR`; проверяются tenant canondata и
    доступ через `.sys/query_metrics_one_hour`.

## Рассмотренные варианты

### Объединять опубликованный минутный top-256

Отклонено. Реализация простая и ограниченная по ресурсам, но полные метрики
невыбранных запросов уже потеряны. На допустимой нагрузке recall настоящего
часового top-256 может быть равен нулю.

### Ограничить часовой accumulator 1024 хешами

Отклонено для первой версии. Вытеснение добавляет новый слой аппроксимации и
делает результат зависимым от порядка прихода минут. Хранение до 61 440
metrics-only записей одного активного часа предпочтительнее хранения текстов
или полной истории всех кандидатов.

### Держать часовое окно на каждой ноде

Отклонено. Состояние ноды волатильно, поэтому rolling restart делает результат
зависимым от порядка обновления кластера. Вариант также увеличивает память всех
нод и создаёт mixed-version семантику.

### Строить час только после его закрытия

Отклонено как основной вариант. Такой подход не показывает текущий live-час и
не восстанавливает метрики, которые не были запрошены в соответствующую минуту.
Он может остаться аварийным fallback для уже сохранённых минутных результатов.

### Сохранять каждое выполнение запроса

Отклонено для встроенного sys-view. ClickHouse-подобный execution log даёт
точную и гибкую агрегацию постфактум, но требует значительно большего write
volume, хранилища, сложной политики retention, защиты чувствительных текстов и
распределённого чтения.

### Нормализованные fingerprint'ы и шардированный stats store

Это предпочтительная целевая архитектура, но она меняет идентичность запросов,
transport, storage layout и tablet topology. В двухнедельную задачу она не
помещается.

## Опыт других систем

- [PostgreSQL `pg_stat_statements`](https://www.postgresql.org/docs/17/pgstatstatements.html)
  использует нормализованную идентичность, конфигурируемый лимит записей,
  статистику вытеснений и отдельное хранение текста. В дальнейшем стоит взять
  нормализованный fingerprint, словарь текстов и явные counters потерь.
- [CockroachDB statement statistics](https://www.cockroachlabs.com/docs/stable/ui-statements-page)
  использует statement fingerprint, часовую агрегацию, периодический durable
  flush и retention по общему числу строк. Это наиболее близкая к целевой YDB
  модель.
- [ClickHouse `system.query_log`](https://clickhouse.com/docs/reference/system-tables/query_log)
  сохраняет отдельные выполнения локально и требует чтения всех реплик для
  полной картины кластера. Для встроенного YDB sys-view эта модель отклоняется
  из-за стоимости записи и хранения.

## План реализации

1. Добавить внутреннюю таблицу accumulator и её загрузку.
2. Реализовать merge минутных метрик и live-материализацию часа.
3. Реализовать очистку на границе часа и восстановление после рестарта.
4. Добавить и валидировать конфигурируемый `MetricsRequestLimit`.
5. Исправить завершение неуспешных node requests.
6. Добавить публичный enum, registry, scan routing и документацию.
7. Добавить unit-, FAST-, boundary- и restart-тесты.
8. Выполнить сфокусированные сборки и тесты SysView, обновить canondata.

Этот объём укладывается в 10 рабочих дней. Нормализация fingerprint, новый
transport и изменение топологии явно исключены из оценки.
