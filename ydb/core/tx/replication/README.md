# Async replication

## Acknowledged source-topic retention

New base-table replication streams using ROW or GLOBAL consistency can opt into private acknowledged retention. Set the destination `ReplicationConfig.SourceTopicRetentionPolicy` to `SOURCE_TOPIC_RETENTION_ACKNOWLEDGED` and enable `EnableReplicationTopicAcknowledgedRetention` on the source. The destination enum requests the mode; the source flag permits creation. Both default to STANDARD/off. The destination does not need the source flag enabled. Index and transfer targets keep ordinary retention. A disabled or older source falls back to the existing separate consumer-creation path.

Source CDC creation requires `TopicsAreFirstClassCitizen`, as ordinary CDC creation already does. ACK activation additionally requires the existing source `EnableTopicDiskSubDomainQuota` flag; with quotas disabled, new streams retain STANDARD policy and ordinary consumer creation. The source creates the required Important consumer atomically with the CDC topic, before the initial scan starts. It persists the ACK policy and canonical consumer identity in the topic's private configuration. Existing topics are not migrated. Disabling the creation flag later does not turn an ACK topic back into an ordinary TTL topic. Altering unrelated topic settings preserves the policy; dropping, recreating, demoting or otherwise invalidating the required consumer is rejected.

PQ removes complete physical blobs whose records are below the required consumer's durable committed offset, while honoring other Important consumers. Reading a record or acknowledging a source write does not authorize deletion. A commit inside a multipart record or Kafka batch cannot remove unacknowledged records; the last physical blob remains. Idle topics receive cleanup opportunities, so another source write is unnecessary. Missing or inconsistent required-consumer state blocks deletion, including TTL/storage-limit deletion of unread data. Ordinary topics retain their existing TTL and storage-limit behavior.

For GLOBAL consistency, a source acknowledgement follows durable destination staging and source-offset deduplication, and can precede global row visibility. The controller must recover its write-transaction assignments and complete the global commit from durable destination state after the acknowledged source prefix is gone.

This mode does not provide a source storage budget or write admission control. A stalled replication can accumulate unread data until source storage fills. Operators must monitor backlog and storage and restore consumer progress or explicitly remove the replication when appropriate. The ordinary retention period remains configured for compatibility; it is not permission to discard unread ACK data.

Roll out the source schema/API and PQ support before requesting ACK streams from destination controllers. Old PQ interpretation retains the Important consumer and falls back to ordinary retention; current-binary configuration tests alone do not certify an older binary. Dedicated actual-binary restart, rolling downgrade/re-upgrade, ordinary old-API alter and unread-data protection tests are included, but their historical retention executions and final compatibility review are still pending. N/N−1 compatibility is not yet certified. Older source APIs do not enforce the new immutable-consumer guards; destructive administrative removal has the older API's existing semantics. Keep disk-subdomain quotas enabled for ordinary Important-consumer alterations through older source APIs. The creation flag is an activation gate, not a mechanism for reversing the persisted topic contract.
