# Async replication

## Acknowledged source-topic retention

New base-table replication streams using ROW or GLOBAL consistency can opt into private acknowledged retention. Set the destination `ReplicationConfig.SourceTopicRetentionPolicy` to `SOURCE_TOPIC_RETENTION_ACKNOWLEDGED` and enable `EnableReplicationTopicAcknowledgedRetention` on the source. The destination enum requests the mode; the source flag permits creation. Both default to STANDARD/off. Creation also requires `EnableTopicDiskSubDomainQuota`, whose existing default is true. The destination does not need the source flag enabled. Index and transfer targets keep ordinary retention. A disabled or older source, or a source with disk-subdomain quotas disabled, falls back to STANDARD and the existing separate consumer-creation path.

Source CDC creation requires `TopicsAreFirstClassCitizen`, as ordinary CDC creation already does. The source creates the required Important consumer atomically with the CDC topic, before the initial scan starts. It persists the ACK policy and canonical consumer identity in the topic's private configuration. Existing topics are not migrated. Disabling the creation flag later does not turn an ACK topic back into an ordinary TTL topic. The current source API preserves the policy when altering unrelated topic settings and rejects dropping, recreating, demoting or otherwise invalidating the required consumer.

PQ removes complete physical blobs whose records are below the required consumer's durable committed offset, while honoring other Important consumers. Reading a record or acknowledging a source write does not authorize deletion. A commit inside a multipart record or Kafka batch cannot remove unacknowledged records; the last physical blob remains. Idle topics receive cleanup opportunities, so another source write is unnecessary. Missing or inconsistent required-consumer state blocks deletion, including TTL/storage-limit deletion of unread data. Ordinary topics retain their existing TTL and storage-limit behavior.

For GLOBAL consistency, a source acknowledgement follows durable destination staging and source-offset deduplication, and can precede global row visibility. The controller must recover its write-transaction assignments and complete the global commit from durable destination state after the acknowledged source prefix is gone.

This mode does not provide a source storage budget or write admission control. A stalled replication can accumulate unread data until source storage fills. Operators must monitor backlog and storage and restore consumer progress or explicitly remove the replication when appropriate. The ordinary retention period remains configured for compatibility; it is not permission to discard unread ACK data.

Roll out source schema/API and PQ support before requesting ACK streams from destination controllers. Actual-binary compatibility tests passed against `stable-26-4-1` (commit `c7e4ce6c7ff3bc86e1f9368ed43cf686911cfa8c`, executable SHA-256 `07d66274f2aa9ffd5fb30e9f5b5fea1da7d804758934dd242a6ddffce855bb94`). ROW and GLOBAL tests cover independent source/destination rollback and re-upgrade on existing topics; a three-node source test covers mixed-node rolling downgrade and re-upgrade. These tests preserve exact rows, durable consumer offsets, unread message bodies and offsets, topic/consumer identity, persisted ACK configuration and the unchanged 86400-second lifetime. The current source resumes prompt reclamation after re-upgrade without repairing the topic. Separate controls verify STANDARD fallback and old-binary Important protection of unread data when ordinary TTL cleanup actually expires a STANDARD topic.

Keep `EnableTopicDiskSubDomainQuota=true` through these transitions. Old PQ retains the Important consumer, which protects unread data, but may retain acknowledged data until ordinary TTL cleanup. Normal old API topic alterations, ordinary consumer changes and duplicate consumer-creation replay are covered. The old API does not enforce the new immutable required-consumer guards: explicitly deleting or changing that consumer can still invalidate replication. The current API rejects those mutations again after re-upgrade. Disabling quotas while rolling an active ACK topic back recreates an existing old API limitation and is outside this supported configuration. The creation flags govern activation and do not reverse a persisted topic contract.

These tests cover existing replicated schemas. Fresh schema alterations applied by the old destination remain subject to its preexisting schema serialization oneof defect described below; this result does not certify that separate operation or every historical release.
