## 1. Контракт и границы работ

Заменить публичный `freeze` в `CmsService.AlterDatabase` двумя независимыми optional-полями `freeze_schema` и `freeze_datashards`. Все четыре пары допустимы:

| Режим | Schema | DataShard | Поведение после SUCCESS |
| --- | --- | --- | --- |
| OPEN | false | false | Ограничения данного механизма сняты |
| SCHEMA_FROZEN | true | false | DDL обычных пользователей закрыты с исключениями EnableClientModifications; запись/TTL/автопартиционирование работают |
| DATA_FROZEN | false | true | Записи остановлены и CDC drain завершён; разрешён только проверенный безопасный DDL |
| FULLY_FROZEN | true | true | Схемный запрет с выбранными исключениями и подтверждённый data freeze |

Отсутствующий параметр сохраняет последнее принятое целевое значение. Два параметра можно менять одним запросом. Отсутствие обоих сохраняет обычный AlterDatabase. Наличие любого из них запрещает совмещать запрос с другими изменениями базы; разрешены path, generation, idempotency_key и operation_params.

Старый API `freeze` и SDK-настройку `Freeze(bool)` не сохранять. Пользователь разрешил несовместимое изменение именно этого API; поэтому стандартное правило SDK о сохранении публичной совместимости не требует слоя алиасов в этой задаче. Остальные публичные контракты без необходимости не менять.

Максимально сохранить:

- Историю и OperationId Console, текущую таблицу DatabaseFreezeOperations, индекс ключей и привязку к DomainId.
- Состояние домена в SchemeShard, обход затрагиваемых путей и HasDatabaseFreezeSchemaWork.
- Pipe/retry/ACK и стадии существующего TDatabaseFreezeWorker.
- DataShard wire-протокол, AcceptedTxIds, локальные счётчики, обработку индексов, initial scan, финальных resolved и доставки CDC.
- Независимый старый потабличный Freeze: новые команды его не снимают.

В задачу не входят динамическое подключение участников при действующем data fence, новый сервис/SQL, глобальный счётчик запросов, новый журнал операций, изменение EnableClientModifications, остановка физических compaction/GC и ожидание применения данных получателем. Чтения, отправка CDC и commit существующего CDC-консюмера продолжаются при соблюдении остальных прав и настроек.

## 3. Модель состояния: определить до изменения переходов

В существующих сериализованных записях добавить две цели. В SchemeShard дополнительно различать физически установленный пользовательский запрет, завершение его drain и состояние data-подпротокола.

Предлагаемая минимальная модель фаз, с окончательным выбором имён при реализации:

| Область | Фазы | Назначение |
| --- | --- | --- |
| Пользовательская схема | UNKNOWN, OPEN, DRAINING, FROZEN | Установлен ли общий запрет и завершено ли ожидание принятой работы |
| Данные | UNKNOWN, OPEN, PREPARING, DRAINING, FROZEN, OPENING | Есть ли подготовка, подтверждённый data freeze или обязательства по снятию fence |

Стадии FENCE_WRITES/DRAIN_INDEXES/DRAIN_CDC остаются стадиями прежнего worker/DataShard; отдельный второй набор генераторов эпох не вводится. Ошибку можно хранить в результате текущей операции, оставляя последнюю физическую фазу; специальный enum ERROR не обязан дублировать это состояние. UNKNOWN трактуется консервативно.

Сохранить текущие Shards и ParticipantsFixed. Последний означает только фиксацию участников data-протокола: он не заменяет SchemaDrained и не должен выставляться для чистого schema-only.

Обязательные правила:

- Целевые bool описывают принятое намерение, а не уже применённое состояние. Из false нельзя делать вывод об отсутствии прежнего fence.
- Общие Ready/Status относятся к текущему запросу, физические фазы — к сохраняющимся ограничениям. Изменение схемной цели не обнуляет подтверждённый data freeze.
- Новая управляющая эпоха сама по себе не требует новой команды в DataShard. Если data-цель уже подтверждена и меняется только схема, DataShard не опрашиваются заново.
- Для новой попытки незавершённого data-протокола допустимо перезапустить прежний worker с новой эпохой, сохранив участников и ограничения. Продолжать один worker сквозь разные управляющие эпохи не требуется.
- Повтор достигнутого режима с новым ключом может завершить новую управляющую операцию без повторного физического применения. Новая эпоха не обещает отдельной новой временной CDC-границы.
- Если data-фаза PREPARING и участников ещё не фиксировали, DS-команды ещё не могли быть отправлены: отмена такой подготовки не требует OPEN во все шарды базы.
- Если участники уже зафиксированы и fence мог быть отправлен, сохранять весь набор до более нового подтверждённого OPEN. Это касается ошибок, замещения и перезагрузки.
- Пустой набор участников не означает data OPEN: пустая база может быть DATA_FROZEN, и создание первого пишущего DataShard остаётся запрещено.

Частичные цели применять в безопасном порядке: техническую защиту установить до снятия прежнего общего схемного запрета; при полном thaw снимать её после OPEN ACK. Терминальная ошибка не снимает уже установленные ограничения автоматически.

Изменение proto и всех зависимых обращений к нему выполнять согласованно. Это логический порядок работ, а не предложение оставить промежуточную некомпилируемую версию для использования.

## 5. Шаг 2 — разделить проверки SchemeShard

Основные файлы:

- `schemeshard__operation.cpp`.
- `index/build_index__create.cpp`, `schemeshard_import__create.cpp`, `schemeshard_export__create.cpp`, `schemeshard_set_column_constraint__create.cpp` и аналогичные отдельные входы.
- `schemeshard__conditional_erase.cpp`.
- `schemeshard__table_stats.cpp`, `schemeshard__table_stats_histogram.cpp`, `schemeshard__operation_split_merge.cpp`, `schemeshard__operation_alter_pq.cpp`.

Выделить причины отказа, переиспользуя обход целевых путей/доменов:

1. Общий пользовательский запрет DDL — по установленному схемному барьеру.
2. Подготовительная пауза нового приёма — на конечный этап схемного/data drain.
3. Несовместимость схемной операции с data fence — до подтверждённого OPEN.
4. Запрет новой физической топологии — при подготовке schema-only временно, при data freeze до OPEN.
5. Запрет запуска новых фоновых записей — по data-фазе, а не по общему Ready/Status.

Операция должна пройти каждый применимый барьер. Допуск безопасного DDL к data freeze не обходит пользовательский запрет схемы, а служебный replication-допуск не обходит data-барьер.

Минимальный проверенный список DDL для устойчивого DATA_FROZEN: MkDir и удаление пустого каталога при обычных проверках путей и прав. Неизвестные типы отклонять. Проверять точный OperationType и отсутствие посторонних изменяющих payload; наличие GetReady или признака безопасной операции не должно разрешать другую фабричную операцию. Не расширять список на view/ACL/атрибуты без отдельной проверки побочных действий.

Разрешённые продолжения:

- Ранее принятая работа завершается во время нужной фазы drain; сохранённые записи import/index/export используют существующую проверку связи с родительским процессом.
- Старое условие `Internal && !ParticipantsFixed` заменить явной фазой. Не допускать произвольные Internal навсегда из-за отсутствия участников у schema-only.
- Автоматический row split/merge и внутренний AlterPersQueueGroup для физического разбиения разрешать в устойчивом schema-only, но закрывать при активной data-защите.
- Сохранить узкую финализацию CDC scan с проверкой типа операции. Для пользовательского schema freeze использовать те же исключения, что у EnableClientModifications: администраторы, системные пользователи, отсутствие токена и распознанное обслуживание CDC репликации. Исключения не обходят техническую защиту data freeze.

В начальной минимальной реализации сохранять общий запрет новых DDL во время подготовки, чтобы HasDatabaseFreezeSchemaWork мог закончить конечный набор. Безопасные DDL при data-only открываются после успешного drain. Предварительно переписывать общий учёт TxDependencies/Operations не нужно; конкретную принятую работу, отсутствующую в drain, исправлять при её обнаружении.

## 6. Шаг 3 — переходы и worker SchemeShard

Использовать существующие TTxDatabaseFreeze, TTxDatabaseFreezeDone и TDatabaseFreezeWorker. Основная переделка — выбор действия и сохранение состояний, а не отправка новых типов событий.

### 6.1. Установка schema-only

Установить пользовательский запрет, временно закрыть новые автоматические смены топологии, закончить HasDatabaseFreezeSchemaWork, подтвердить схемную фазу. Не фиксировать Shards и не запускать DS-worker. TTL, записи, CDC и периодические resolved продолжаются. После успеха возобновить топологию при сохранённом запрете пользовательских DDL.

### 6.2. Установка data freeze

Независимо от схемного флага:

1. Проверить поддержку участников, включая запрет ColumnShard, до установки новых ограничений. Schema-only колонночные таблицы не запрещает.
2. Сохранить data PREPARING и техническую защиту; закрыть новые несовместимые DDL, split/merge, служебные изменения CDC и запуск TTL.
3. Дождаться актуальной принятой схемной работы по существующему helper.
4. Собрать активные Tables/Partitions, включая приватные индексы; не включать выведенные источники split только потому, что они ещё есть в ShardInfos.
5. Сохранить участников и data DRAINING, затем запустить прежние FENCE_WRITES → DRAIN_INDEXES → DRAIN_CDC.
6. После успеха сохранить data FROZEN. При schema=false снять лишь общую подготовительную паузу DDL, оставив техническую защиту участников/CDC.

После успешного schema-only пользовательский запрет уже установлен и старые пользовательские DDL закончились. Повторяются шаги подготовки текущей служебной работы, остановки TTL/топологии, нового снимка участников и data-протокола. Нельзя ограничиться фиксацией участников или считать прежний SchemaDrained вечным отсутствием схемной работы.

До первого FENCE не ждать отдельно все пользовательские DML, уже отправленные TTL и весь CDC scan в SchemeShard. Их учитывают прежние стадии DataShard. Не закрывать доставку асинхронных индексов слишком рано: она нужна для завершения drain. Периодические resolved и initial scan сохраняют текущую стадиальную логику.

### 6.3. Снятие data freeze

При любых схемных целях, если fence мог быть отправлен, открыть всех сохранённых участников новой эпохой. До OPEN ACK не менять их топологию и защищённые назначения. После ACK сохранить data OPEN, снять технические ограничения, возобновить TTL и отложенное партиционирование. Схемный барьер оставить только при соответствующей цели.

Перенести условие ScheduleSplitMergeRevisit с нынешнего «успешный Freeze=false» на переход топологической защиты в открытое состояние. TTL сохранить в штатном периодическом ScheduleConditionalEraseRun: ACK отдельного первого TTL-запуска для успеха thaw не нужен.

### 6.4. Все направленные переходы

| Из | В | Действия и ожидаемые DS-команды |
| --- | --- | --- |
| OPEN | SCHEMA_FROZEN | Схемный запрет и drain; DS-команд нет |
| SCHEMA_FROZEN | OPEN | Снять только схемный запрет; DS-команд нет при отсутствии прежних data-обязательств |
| OPEN | DATA_FROZEN | Техническая подготовка, участники, три стадии; schema-цель остаётся false |
| DATA_FROZEN | OPEN | OPEN сохранённым участникам, затем снять техническую защиту |
| OPEN | FULLY_FROZEN | Установить оба барьера, общий подготовительный drain и три стадии |
| FULLY_FROZEN | OPEN | OPEN ACK, затем снять оба вида защиты |
| SCHEMA_FROZEN | FULLY_FROZEN | Сохранить пользовательский запрет, новая data-подготовка и три стадии |
| FULLY_FROZEN | SCHEMA_FROZEN | OPEN ACK; пользовательский запрет оставить, TTL/топологию разрешить |
| DATA_FROZEN | FULLY_FROZEN | Установить схемный запрет и дождаться принятого безопасного DDL; подтверждённую data-фазу сохранить, DS-команд нет |
| FULLY_FROZEN | DATA_FROZEN | Снять общий схемный запрет; OPEN не отправлять, техническую защиту оставить |
| SCHEMA_FROZEN | DATA_FROZEN | Сначала техническая защита и data freeze, затем оставить только её |
| DATA_FROZEN | SCHEMA_FROZEN | Сначала общий схемный запрет и его drain, затем OPEN ACK и снятие технической защиты |

Для запросов без изменения режима проверить отдельный быстрый путь без фиктивной рассылки OPEN. После ошибки повтор не должен использовать терминальный результат старой попытки вместо выполнения новой управляющей эпохи.

## 7. Шаг 4 — Console: patch, идемпотентность, восстановление

Файлы: `core/cms/console/console__freeze_tenant.cpp`, `console_tenants_manager.{h,cpp}`, `console__alter_tenant.cpp`, `console__remove_tenant.cpp`, существующая схема хранения.

Порядок приёма:

1. Сохранить административную авторизацию и базовую валидацию формы запроса.
2. При ключе найти старую freeze-операцию по DomainId и ключу, сравнить исходную маску/явные значения и вернуть её до проверки нового generation и дополнения текущими флагами.
3. Для нового запроса дополнить отсутствующие флаги из последней принятой цели того же экземпляра базы; до первой операции — false/false.
4. Проверить generation, взаимоисключение с остальными изменениями и поддержанные OperationParams.
5. Применить нынешнюю политику конкуренции к полной паре и атомарно сохранить результат приёма.

Политика:

- Тот же ключ и тот же исходный patch — исходная операция даже после смены режима; другой patch — BAD_REQUEST.
- Без ключа и с той же незавершённой целью — присоединение к текущей операции.
- Новый ключ с той же незавершённой целью — UNAVAILABLE; отклонённый ключ не резервируется.
- Другая цель — новая эпоха с сохранённым CANCELLED для прежнего запроса; это не означает автоматический физический rollback.
- После завершения новый ключ создаёт новую управляющую эпоху; прежний ключ остаётся привязанным к прежнему результату.

Восстановление: сохранить нынешние NextDatabaseFreezeEpoch, индекс ключей, FreezeEpoch и DomainId. Не возвращать TenantTxId. При создании новой базы по тому же пути история не должна считаться её текущим состоянием. При рестарте восстановить полные пары и маски, затем возобновить незавершённые операции; transient progress может временно отсутствовать.

Проверки обычного Alter/Remove учитывать при любом активном режиме или незавершённом/ошибочном восстановлении. Сохранить ранний возврат прежнего обычного Alter по AlterIdempotencyKey после авторизации. Пока не расширять список обычных CMS-настроек, разрешённых при заморозке.

## 8. Шаг 5 — gRPC, статус, SDK и CLI

### gRPC и публичный статус

В `core/grpc_services/rpc_cms.cpp` проверки присутствия freeze заменить на наличие любого нового поля. Сохранить ASYNC, SYNC и подписки на прежнюю операцию. Таймаут/разрыв RPC не отменяет принятую цель. Не расширять эту задачу исправлением ранее обсуждавшейся очистки SYNC-подписчиков.

GetOperation возвращает сохранённую цель/результат, а metadata — best-effort фазу и причины ожидания. В GetDatabaseStatus показать последнюю цель и операцию отдельно от существующего состояния конфигурации. Pending/ошибка не выдаются за подтверждённое применение; технический data-барьер не превращается в публичный schema=true.

### C++ SDK

Файлы: `public/sdk/cpp/include/ydb-cpp-sdk/client/cms/cms.h`, `public/sdk/cpp/src/client/cms/cms.cpp`.

- Заменить Freeze на optional FreezeSchema и FreezeDataShards, сохранив copy/reset и наличие false.
- Адаптировать SerializeTo и пред-RPC валидацию; data-only допускается без схемного флага.
- Сохранить TAsyncStatus, существующий SYNC/RunDeferred и deadline/OperationTimeout для любого из двух полей.
- Расширить TGetDatabaseStatusResult без доступа к private SDK-типам из публичного заголовка.
- Проверить все места старой CMS-настройки по репозиторию; не трогать одноимённый потабличный API.
- Обновить комментарии и changelog по правилам SDK. Новый метод с возвратом объекта операции не является обязательным объёмом; ключи/generation пока можно задавать через сырой gRPC.

### CLI

Файлы: `public/lib/ydb_cli/commands/ydb_admin.{h,cpp}` и существующий `commands/ut/database_freeze_ut.cpp`.

Добавить выбор --schema/--datashards: без выбора передаются оба поля, с одним — только оно. freeze ставит true, unfreeze — false. Оба флага области вместе допустимы и дают один RPC. Сохранить ожидание TAsyncStatus и вывод ошибки, запретить лишние аргументы, не добавлять зависимостей CLI от core. Проверить справку/completion и необходимость записи в `apps/ydb/CHANGELOG.md` по видимости команд.

## 9. Шаг 6 — подготовка репликации под схемным запретом

Этот этап не требуется для data-only, но нужен для полного сценария «сначала schema-only, затем запуск ещё не подготовленной репликации».

Схемный запрет использует существующие исключения EnableClientModifications без отдельной настройки доверенных SID:

1. Отсутствие UserToken, системный пользователь и администратор определяются общим helper. Штатная семантика AdministrationAllowedSIDs сохраняется: пустой список считает всех администраторами.
2. Для TModifyScheme обе проверки используют один результат классификации запроса. Обслуживание CDC репликации определяется прежним IsAsyncReplicationOperation по типу операции и маркеру `__async_replication`; исключение должно подходить всему пакету транзакций. Дополнительное доказательство сервисной identity не требуется. Обычная авторизация сохраняется.
3. На отдельных входах index build, constraints, import/export передаются UserSID и UserGroupSIDs из авторизованного контекста gRPC/KQP. Исходные credentials не передаются. Старый запрос с UserSID без групп остаётся запросом идентифицированного пользователя, а не запросом без токена.
4. Общий пользовательский схемный барьер можно обойти этими исключениями, технические data-барьеры и UNKNOWN — нельзя. Подготовка и ожидание старой работы сохраняются. Финализация CDC scan остаётся узким отдельным исключением.

Schema-only допускает новые схемные операции привилегированных пользователей и обслуживание помеченных CDC обычными учётными записями с необходимыми ACL. Поэтому он не обещает абсолютной неизменности схемы для всех субъектов. Включение data freeze закрывает несовместимые операции независимо от этих исключений.

Тесты дополнять вместе с соответствующими изменениями, а не создавать параллельные fixtures для одной и той же истории. Новые проверки добавлены в эти fixtures; запуск отложен по требованию пользователя.

| DataShard regression | `core/tx/datashard/datashard_ut_database_freeze.cpp` / `core/tx/datashard/ut_database_freeze` | Прежний wire-протокол, write paths, индексы, CDC/resolved, рестарты и потабличный Freeze |

Ключевые сценарии SchemeShard:

- Schema-only не отправляет FENCE/OPEN, не останавливает TTL, записи, CDC и resolved; после начальной подготовки снова работает автоматический split/merge.
- DATA_FROZEN при schema=false даёт ту же write/CDC-гарантию, что FULLY_FROZEN. MkDir проходит только в первом; CreateTable, изменение защищённой таблицы, split и удаление CDC отклоняются в обоих.
- После schema-only начать автоматический split, задержать `TEvSplitPartitioningChangedAck`, запросить data freeze. Пока операция не закончена, ParticipantsFixed=false и FENCE не рассылается; после завершения в наборе новые участники, а выведенный источник исключён.
- Удержать in-flight TTL/пишущую работу: не требовать её завершения на этапе схемной подготовки; DS drain не должен успешно закончиться раньше необходимых commit/CDC ACK.
- FULLY_FROZEN → DATA_FROZEN не отправляет OPEN; обратный переход при подтверждённом data freeze также не перезапускает DS-протокол.
- FULLY_FROZEN → SCHEMA_FROZEN ждёт OPEN всех участников, затем возобновляет TTL и отложенные split/merge при всё ещё запрещённом пользовательском DDL.
- Пустая DATA_FROZEN-база остаётся защищённой от создания первой строковой таблицы; thaw это снимает.
- ColumnTable допускается для schema-only; data freeze при любом schema-флаге UNSUPPORTED до нового data-барьера.
- Два домена одного SchemeShard изолированы. Неизвестная фаза не становится OPEN.

Восстановление и конкуренция:

- Рестарт Console и SchemeShard в подготовке, между фиксацией участников и рассылкой, между DS-стадиями, после частичного OPEN и в каждом устойчивом режиме.
- Частично разосланный FENCE → замещение thaw → запоздалые старые FENCE/ACK. Список не теряется, а общий успех возможен только после нужного более нового OPEN.
- Изменение только схемной цели при подтверждённом FROZEN сохраняет data-фазу. При незавершённой data-попытке новая эпоха может перезапустить её без открытия записи.
- Ошибка чистого схемного перехода не останавливает TTL через общий Ready/Status. Ошибка data freeze не превращает пользовательскую schema-цель в true.
- Варьировать presence и значения обоих полей; повтор старого ключа после иных переходов возвращает прежний OperationId до generation/дополнения текущими значениями.
- Сохранить кейс failed remove → freeze → Console restart → повтор ключа и кейс удаления/создания новой базы по тому же пути: используется DomainId.
- Новый ключ при той же pending-цели не резервируется после UNAVAILABLE; замещение не уничтожает историю старого результата.

Сохранить прежние положительные тесты CDC GetReady и отрицательные decorated CreateTable. Для ранее удалённого CDC сохранить текущую границу: cleanup может оставаться незавершённым при FENCE_WRITES, но нужные транзакции удаления должны закончиться до общего SUCCESS; не требовать доставки в удалённый поток.

Не переписывать DataShard-тесты ради появления двух CMS-флагов и не добавлять проверку новой управляющей эпохи как обязательное изменение DataShard epoch при чистом схемном переходе.

## 12. Перепроверка плана и критерии готовности

План повторно сопоставлен с текущими функциями, proto и существующими ya.make. Основные риски и решения:

| Риск | Решение в плане |
| --- | --- |
| Скрытая зависимость data=true от schema=true | Все 4 пары, data-only тестируется из OPEN; пользовательский флаг не выставляется техническим барьером |
| Непрерывный поток DDL мешает drain | Новые обычные DDL закрыты, принятые работы учитывает HasDatabaseFreezeSchemaWork; привилегированные исключения могут продлевать ожидание schema-only |
| Старый общий Ready/Status продолжает подавлять TTL | Раздельные физические фазы и специализированные predicates |
| Снимок участников устарел после schema-only | Участники собираются только после новой data-подготовки |
| Новая эпоха или смена схемного флага теряет частичный fence | Сохранение участников/обязательств вместо полного state.Clear |
| Снятие schema отправляет OPEN и разрешает запись | Отдельный переход FULLY_FROZEN → DATA_FROZEN без DS-команд |
| Pure schema-only ждёт недоступный DataShard | Нет фиктивного DS-worker при отсутствии data-обязательств |
| Слишком ранняя остановка индексов/scan ломает drain | Сохранить текущую стадиальную логику DataShard |
| Безопасный payload обходит другой OperationType | Явная классификация и отсутствие посторонних изменяющих частей |
| Replication-маркер превращается в универсальный обход | Прежняя классификация операций репликации, проверка целевого CDC/топика и обычные ACL; без обхода data-барьера |
| После thaw остаются остановлены TTL/отложенные split | Возобновление по data/topology-фазе, а не по единому Freeze=false |

Критерии последующей динамической проверки: пройти тесты четырёх режимов и всех 12 переходов, рестартов, ошибок, идемпотентности, прежних CDC-гарантий и table Freeze. Отдельно проверить подготовку CDC/консюмера через replication controller с обычными source credentials.
