# YDB Essential Metrics 2.0

Обзор состояния YDB и активности выбранной базы с подробными графиками.
Язык дашборда — русский. Источник — штатные метрики YDB в Prometheus.
Дополнительные плагины Grafana, exporters и recording rules не нужны.

Это отдельный дашборд с UID `ydb-essential-2-0`. Он не заменяет штатный
**YDB Essential Metrics** с UID `ydb-essentials`.

## Установка

1. Настроить сбор метрик по [штатному шаблону YDB](https://github.com/ydb-platform/ydb/tree/main/ydb/deploy/prometheus).
2. Добавить Prometheus в Grafana как datasource.
3. Открыть **Dashboards → New → Import**, загрузить
   [ydb-essential-2.0.json](dashboards/ydb-essential-2.0.json) и нажать **Load → Import**.
4. В дашборде выбрать Prometheus, базу и пулы хранения.

Один datasource должен представлять один кластер. Имя и UID источника могут
быть любыми: они не зашиты в JSON. Сохранённых адресов, выбранных баз и пулов нет.

При одном пуле он выбирается автоматически; при нескольких сначала показано
`! Выберите пул`. Можно выбрать несколько пулов. Пулы выбираются отдельно
от базы: смена базы не определяет автоматически её пулы хранения.

Повторный импорт с тем же UID обновляет этот дашборд. Для независимой копии
измените UID в форме импорта. Ссылки на подробные графики остаются внутри копии
и сохраняют период и выбранные переменные.

## Совместимость и сбор метрик

Используются встроенные Canvas, Bar gauge, Stat, Table, Time series, Math
и Dashboard data source. Импорт, сохранение и работу виджетов проверяли
на Grafana 11.2.0 и 13.2.4 с Prometheus 3.15.1 и YDB 26.3.1.ent.3.
Это проверенные версии, а не ограничение совместимости версией YDB.

Основной проверяемый вариант — штатный bare-metal/VM шаблон Prometheus,
используемый также YDB Ansible. Для него важны:

- префиксы имён метрик из `metric_relabel_configs`;
- роли `container="ydb-static"` / `"ydb-storage"` и `"ydb-dynamic"`;
- метки `instance`, `database`, `storagePool`, `group`, `orderNumber`;
- идентификаторы процессов `host`, `slot` и `pod`, когда они присутствуют
  в соответствующих метриках; обязательного добавления `pod` для VM нет;
- scrape jobs вида `ydb/utils`, `ydb/ydb`, `ydb/kqp`, `ydb/tablets`,
  `ydb/pdisks`, `ydb/vdisks`, `ydb/interconnect` и другие из шаблона.

Для проверок полноты сбора поддерживаются штатные форматы jobs:
`ydb/<counter>`, `ydb/<name>/counter/<counter>` и
`ydb/<namespace>/<name>/counter/<counter>`. Например, для `utils` используется
селектор `job=~"ydb/(.+/counter/)?utils"`. Расчёты самих показателей используют
метрики и ролевые labels, как остальные дашборды репозитория.

Различные форматы jobs и идентификация VM-процессов/Kubernetes pods проверены
локальными PromQL-регрессиями. Живая Helm/Operator-установка пока не проверена;
для неё также необходимы корректные значения ролевой метки `container`.
Неверная маркировка Storage как Compute не исправляется по имени job.

Для попроцессной проверки каждый endpoint должен иметь различимый набор
labels у `up`. Дашборд сохраняет исходный `instance` и учитывает `pod`,
когда он есть. Если сбор объединяет несколько портов в одинаковый набор
labels, восстановить потерянную идентификацию процессов из него нельзя.

Для меж-ЦОД трафика всем Interconnect targets нужны `dc` с логическим ЦОД.
Имя `instance` должно сопоставляться с именем peer YDB; при другом имени
можно добавить `ic_host` с коротким именем узла. Пример file-SD:

```yaml
- targets: [node-a.example.com:8765]
  labels:
    container: ydb-static
    dc: zone-a
```

Такая же разметка ЦОД нужна вычислительным процессам. Без неё общий трафик
работает, а меж-ЦОД разрез показывает отсутствие данных.
Для точного состояния VDisk нужны расширенные счётчики
`ReplUnreplicatedVDisks`; при их отсутствии полноценное состояние не вычисляется.
Для расчётной загрузки дисков используются штатные `UserDiskCost`,
`InternalDiskCost`, `CompactionDiskCost`, `DefragDiskCost`, `ScrubDiskCost`
и `DiskTimeAvailable` либо `DiskTimeAvailableCtr` в группе VDisk.
Нужна исходная метка `pdisk`; дополнительно размечать физические диски не нужно.
Если расширенные счётчики отключены или измерений недостаточно, загрузка
показывает «Нет данных».

## Разделы

| Раздел | Что показывает |
|---|---|
| Индикаторы кластера и ресурсов | Узлы, таблетки, группы хранения, диски, CPU, память, сеть, место и дисковые операции |
| Индикаторы работы БД | SQL, транзакции, API, компиляции, чтение, запись, удаление, компакшены и TTL |
| Вычислительные ресурсы | CPU, четыре actor-пула по процессам, память и её состав |
| Хранение и сеть | Место, состояния дисков и групп, дисковые задержки, Interconnect |
| Запросы и транзакции | Частоты, p50/p95, статусы API, сессии, компиляции, даташарды и перегрузка |
| Операции с данными | Чтение, Scan API, обычная запись, BulkUpsert и удаление |
| Фоновые операции | Компакшены, TTL, экспорт и импорт |
| Стабильность узлов | Количество процессов, uptime, расхождение часов и сбои таблеток |
| Диагностика сбора метрик | Последний результат опросов Prometheus и адреса без метрик |

Два обзорных раздела раскрыты при открытии; остальные свёрнуты.
Всего 79 виджетов в девяти штатных Row.

В разделе «Хранение и сеть» под историей состояний находятся таблицы
«Проблемные PDisk» и «Проблемные VDisk»: узлы, идентификаторы объектов и их
состояние на конец выбранного периода. Переходы есть из карточки «PDisk и VDisk»
и графиков состояний. Таблицы относятся ко всему кластеру, без фильтра по БД
или пулу; исправные объекты не перечисляются. При неполном сборе появляется
предупреждение, а известные проблемы на доступных узлах сохраняются.

Карточка «PDisk и VDisk» показывает пары «в норме / всего», максимальную
расчётную загрузку физического диска и число перегруженных PDisk. Загрузка
учитывает все VDisk каждого физического диска, включая фоновые операции,
и не ограничивается выбранными БД и пулами. Это оценка по модели YDB.
Она вычисляется на конец периода за то же скользящее окно, что скорости
дисковых операций. Пороги максимума: ниже 80% — зелёный, 80–100% — жёлтый,
от 100% — красный. Перегруженным считается PDisk с загрузкой от 100%.
Показатели чтения, записи и задержек в карточке «Дисковые операции» сохранены.

## Период и интерпретация

- В восьми карточках работы БД частоты — средние за выбранный период;
  события — оценка количества за этот период; p95 — по наблюдениям того же периода.
- Текущие значения вычисляются на конец выбранного периода. Это относится
  и к прошлому периоду, не только к диапазонам, заканчивающимся сейчас.
- Подробные графики показывают историю; окно скорости или событий указано
  в описании соответствующего виджета.
- SQL-выполнения, транзакции и вызовы API — разные уровни учёта.
  Их частоты и задержки не обязаны совпадать. p50/p95 — перцентили
  объединённых гистограмм, не среднее перцентилей отдельных узлов.
- Операции чтения и изменения данных отражают счётчики движка. Внутренние
  проверки ключей при INSERT не обязательно входят в показатели чтения.
- `increase` учитывает сбросы счётчиков и экстраполирует края интервала:
  оценка числа событий может быть дробной и округляется при отображении.

Пороговые цвета объяснены в подсказках каждого виджета. Они служат ориентиром
для эксплуатации, а не готовой политикой оповещений или SLA.
Нулевое число даташардов намеренно жёлтое.

«Ёмкость и заполнение» объединяет объёмы и проценты в одной Canvas-карточке.
Верхний ряд: занято в БД, квота и процент заполнения. Нижний: занято на дисках
кластера, полная ёмкость и процент заполнения. Значения расположены над подписями;
проценты показаны числами без прогресс-баров. Типографика общая с остальными
Canvas-карточками. Цвет занятого объёма соответствует проценту заполнения.
Для байтов используется штатная автоматическая точность Grafana; проценты
показаны с одним десятичным знаком.

## Отсутствие данных и ограничения

`Нет данных` / `—` означают отсутствие обязательных измерений или неполный
сбор. Они не заменяются здоровым нулём. `Нет SQL`, `Нет транз.`, `Нет обращений`,
`Нет TTL` означают наблюдаемый период без соответствующих операций или настроек.
Зелёные прочерки в полях «БД: квота» и «БД: %» означают измеренный нулевой
лимит: квота не задана. Недостаток измерений в этой карточке показан жёлтым
«Н/Д» (нет данных).

Полнота проверяется относительно настроенных targets. Узлы, полностью
удалённые из service discovery, требуют отдельного инфраструктурного контроля.
Успешный scrape не подтверждает наличие каждого лениво создаваемого счётчика.
Диагностика сбора — это состояние опросов, не самостоятельная проверка доступности YDB.

CPU и память агрегируются с весами ёмкости, а не усреднением процентов узлов.
Кластерная память относится к процессам YDB, не ко всем процессам ОС.
Группы с ошибками, синхронизацией и дефицитом места могут пересекаться;
их нельзя складывать. Статусы дисков не являются вычислением кворума.

Счётчики API могут создаваться при первом событии; оценка прироста не является
аудиторским журналом всех ответов приложения. Для расследования используются
также логи и трассировки.

Счётчики экспорта/импорта создаются при работе операций. Их потоки показывают
обрабатываемые данные и этапы, не реестр операций и не процент готовности.
Реальная проверка экспорта/импорта S3 пока не выполнена.

Карточки SQL и API используют общий расчёт в карточке «Ошибки API» (id 112).
«SQL и активность» (id 110) получает готовые результаты через штатный Dashboard
data source. При ручном изменении SQL-выражений редактировать нужно источник 112;
при удалении этого источника связь необходимо обновить. Большие периоды
увеличивают стоимость расчёта; отдельная SQL-карточка ждёт общий результат API.

## Происхождение

Разработан как отдельный вариант на основе штатного
[YDB Essential Metrics](https://github.com/ydb-platform/ydb/blob/main/ydb/deploy/helm/ydb-prometheus/dashboards/ydb-essentials.json).
Изменены состав и группировка панелей, описания, расчёты, проверки полноты
данных и визуализация. Исходный дашборд сохраняется без изменений.
При включении в YDB применяется лицензия [Apache-2.0 репозитория YDB](https://github.com/ydb-platform/ydb/blob/main/LICENSE).
