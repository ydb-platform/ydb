# Оптимизация аналитических запросов

Аналитический запрос в {{ ydb-short-name }} чаще всего упирается в объём прочитанных данных и в то, насколько схема таблицы совпадает с типичными фильтрами и группировками. Ниже приведены три группы решений: первичный ключ, схема таблицы и формулировка запроса.

## Первичный ключ

Первичный ключ задаёт физический порядок данных и границы, по которым {{ ydb-short-name }} отсекает лишние диапазоны при чтении.

На что смотреть:

* колонки из `WHERE` и из условий соединения в составе ключа;
* порядок колонок в составном ключе: сначала равенства, затем диапазоны по дате или идентификатору;
* согласованность выбора ключа с паттерном нагрузки, а не только с уникальностью строк.

Подробнее о колоночных таблицах см. [выбор первичного ключа для колоночных таблиц](../dev/primary-key/column-oriented.md).

## Схема данных

Схема определяет, сколько данных попадёт в сканирование при типичном отчёте или агрегате.

На что смотреть:

* [колоночное хранение](../concepts/datamodel/table.md#column-oriented-tables) для таблиц под аналитику;
* типы колонок без избыточной точности и длины строк, если это не нужно для отчётности;
* [партиционирование колоночной таблицы](../concepts/datamodel/table.md#olap-tables-partitioning) для таблиц объёмом более 2 ГБ.

Параллельная запись в одни и те же ключи из нескольких задач может упираться в ограничения транзакций. Это описано в разделе [Ограничения](limitations.md).

## Запросы

Даже удачная схема не спасёт запрос, который тянет лишние колонки или не сужает период.

На что смотреть:

* состав `SELECT`: только колонки, нужные для результата или агрегата;
* [вторичные индексы](../concepts/query_execution/secondary_indexes.md) при фильтрации по колонкам вне префикса первичного ключа;
* предикаты, опирающиеся на ключ, партицию или индекс, а не на полное сканирование без необходимости.
