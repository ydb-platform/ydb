# Группы хранения block-8-2

Схема `block-8-2` кодирует блоб в восемь частей данных и две части чётности. Группа содержит двенадцать VDisk: десять основных позиций и две handoff-позиции. Каждый VDisk занимает отдельный домен отказа в одной области отказа. Минимум — двенадцать независимых доменов; дополнительные резервные домены и свободные слоты выбираются с учётом требований конкретного развёртывания к восстановлению. Универсальной рекомендации использовать тринадцать или четырнадцать доменов нет.

При недоступности любых двух доменов группа продолжает чтение и запись. При трёх отказах доступность не гарантируется. Идеальная избыточность кодирования составляет 1.25 (10/8); handoff-копии, метаданные, фрагментация и временные доноры требуют дополнительного места.

## Конфигурация и версии

Все процессы хранения, контроллера и баз данных должны использовать сборку с поддержкой `block-8-2` (числовой идентификатор 19). Выберите и закрепите такую сборку до создания кластера или пула. Автоматическое согласование смешанных версий и откат на сборки без поддержки схемы не предусмотрены.

Для нового кластера задайте `erasure: block-8-2` в основной конфигурации, используйте стойки как домены отказа и укажите не менее двенадцати независимо размещённых узлов хранения. Пример из той же версии исходников: `ydb/deploy/yaml_config_examples/block-8-2.yaml`. Состав StateStorage настраивается независимо от группы хранения из двенадцати VDisk.

Схему и геометрию существующей статической группы нельзя изменить на месте. У динамических пулов есть собственное поле `erasure_species`: пулы `block-4-2` и `block-8-2` могут сосуществовать без изменения схемы статической группы. Редактирование erasure существующей группы не преобразует её данные. Блобы Block82 используют формат без заголовка; общая настройка добавления заголовков не меняет формат этой схемы.

## Обслуживание и статусы

При одном недоступном VDisk группа получает статус PARTIAL, при двух — DEGRADED, при трёх — DISINTEGRATED. Health check и Viewer отображают соответственно жёлтый, оранжевый и красный статусы; единственный запускающийся или реплицирующийся VDisk может давать синий статус. Нарушения размещения и нехватка места отдельно повышают статус проблемы.

Режим максимальной доступности CMS допускает не более одного недоступного или заблокированного VDisk в каждой затронутой группе. Режим сохранения доступности допускает не более двух. Уже недоступные VDisk учитываются в этом ограничении. Получайте разрешения CMS перед обслуживанием и дожидайтесь восстановления перед следующей операцией. Перенос и self-heal статической группы выполняются через distconf; обычная балансировка кластера и sanitizer динамических групп не обслуживают статическую группу.

`ydb-dstool group list --include-static` показывает static groups вместе с динамическими пулами. Метаданные static group и `ViewerState` берутся из Viewer; `OperatingStatus` остаётся статусом динамических групп из BSC.

## Метаданные ёмкости

BSC публикует два безразмерных gauge-счётчика под `counters=storage_pool_stat,subsystem=erasureMapping`:

- `GroupErasureInfo{group,storagePool,erasureSpecies}=1` для каждой материализованной группы. Значение `group` — десятичный ID шириной не менее девяти цифр, как у `DskUsedBytes`. Статическая группа 0 имеет `group="000000000",storagePool="static"` без вымышленного ID динамического пула.
- `StoragePoolErasureInfo{storagePoolId,storagePool,erasureSpecies}=1` для каждого настроенного пула, в том числе без материализованных групп. Значение `storagePoolId` имеет вид `boxId:poolId`.

На группу приходится одно соответствие; переименование или удаление пула/группы удаляет старые серии. Неизвестные или противоречивые метаданные не публикуются. Потребитель должен отклонять отсутствующее или неоднозначное соответствие, а не подставлять `block-4-2`.

`DskUsedBytes` по-прежнему отражает физические байты, занятые VDisk на PDisk, включая накладные расходы; метка erasure к нему не добавляется. Агрегируйте использование по `(group, storagePool)` и присоединяйте отдельное соответствие перед применением модели ёмкости для конкретной схемы. Умножение физических байтов на 8/10 не даёт точного объёма SQL-данных. Оценка ресурсов группы в BSC использует коэффициент на слот `12 * 8 / 10 = 9.6`; он и идеальная избыточность блоба описывают разные величины.

Локальный стенд `ydb/deploy/local/block-8-2` проверяет статическую группу Block82 и отдельные пулы баз данных Block42 и Block82. Внешние средства развёртывания и правила промышленного запуска требуют отдельной проверки.
