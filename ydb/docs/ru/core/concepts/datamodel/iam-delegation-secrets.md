# Секреты с делегированием IAM

{% note info %}

Секреты с делегированием IAM доступны только в базах данных {{ ydb-short-name }}, развёрнутых в {{ yandex-cloud }}: они опираются на механизм делегирования сервисных аккаунтов сервиса IAM.

{% endnote %}

Когда запрос {{ ydb-short-name }} обращается к внешней системе — топику другой базы {{ ydb-short-name }}, бакету Object Storage, метрикам Monium — он аутентифицируется во внешней системе от имени [сервисного аккаунта](https://yandex.cloud/ru/docs/iam/concepts/users/service-accounts) {{ yandex-cloud }}. Обычный [секрет](secrets.md) хранит для этого либо IAM-токен, который истекает через 12 часов, либо авторизованный ключ сервисного аккаунта, который не истекает никогда и потому требует ручной ротации. Ни то, ни другое не подходит для долгоживущих запросов: [потоковый запрос](../streaming-query/index.md) работает неделями, а федеративный запрос по большому бакету — часами.

Секрет с делегированием IAM (`TYPE = "IAM_DELEGATION"`) не хранит ни токена, ни ключа. При его создании {{ ydb-short-name }} просит IAM разрешить ей действовать от имени указанного сервисного аккаунта — **от имени пользователя, выполняющего запрос**. Дальше {{ ydb-short-name }} сама получает короткоживущие IAM-токены этого аккаунта и обновляет их до истечения срока действия, а при удалении секрета просит IAM отозвать делегирование.

Для всего, что читает секреты, такой секрет ничем не отличается от обычного: его значением всегда является действующий IAM-токен делегированного сервисного аккаунта. Любой объект, который принимает секрет с токеном, например [внешний источник данных](external_data_source.md) с `AUTH_METHOD = "TOKEN"`, работает с секретом с делегированием без изменений.

## Как это работает {#how-it-works}

1. **`CREATE SECRET`**. {{ ydb-short-name }} обращается к IAM и просит настроить делегирование сервисного аккаунта на себя. IAM проверяет, что пользователь, выполняющий запрос, имеет право использовать этот сервисный аккаунт (роль `iam.serviceAccounts.user`). Если права нет или IAM недоступен, секрет не создаётся, а пользователь получает ошибку IAM. В самом секрете сохраняются только идентификатор сервисного аккаунта, идентификатор облака и идентификатор делегирования.
2. **Чтение секрета**. При первом чтении секрета на узле {{ ydb-short-name }} получает IAM-токен делегированного аккаунта через сервис токенов IAM, аутентифицируясь собственным системным сервисным аккаунтом. Токен пользователя, создавшего секрет, при этом не используется и нигде не хранится. Затем узел обновляет токен в фоне до истечения срока его действия, поэтому запрос всегда получает действующий токен, как бы долго он ни работал. При временной недоступности IAM используется последний полученный токен, пока он действителен.
3. **`ALTER SECRET`**. Новое делегирование настраивается до отзыва старого, поэтому работающие запросы переключаются на другой сервисный аккаунт без перезапуска.
4. **`DROP SECRET`**. Объект удаляется, после чего {{ ydb-short-name }} просит IAM отозвать делегирование. С этого момента получить новые токены сервисного аккаунта через этот секрет нельзя; уже выданные токены действуют до истечения их срока, так как IAM не отзывает выданные токены.

## Требования {#requirements}

* Команды `CREATE SECRET`, `ALTER SECRET` и `DROP SECRET` для секрета с делегированием может выполнять только субъект {{ yandex-cloud }}: пользователь, федеративный пользователь или сервисный аккаунт, аутентифицированный через IAM. Локальным пользователям базы данных эти команды недоступны.
* Пользователь должен иметь роль `iam.serviceAccounts.user` на делегируемый сервисный аккаунт. Владельцам, администраторам и редакторам каталога она выдана по умолчанию.
* Сервис {{ ydb-short-name }} должен быть включён в облаке, которому принадлежит сервисный аккаунт.
* Команды выполняются через сервис запросов (Query Service): в {{ ydb-short-name }} CLI это команда `ydb sql`.
* На сам секрет действуют [обычные права](secrets.md#secret_access) схемных объектов: для создания нужно право `CREATE TABLE` на директорию, для чтения — `SELECT ROW` на секрет.

## Создание {#create}

```yql
CREATE SECRET `events_sa` WITH (
    type = "IAM_DELEGATION",
    service_account_id = "aje8k2vqp3n1rd7cmf4t"
);
```

Опции:

* `type` — `IAM_DELEGATION`. Без опции `type` создаётся [обычный секрет](secrets.md) со значением.
* `service_account_id` — идентификатор сервисного аккаунта, от имени которого будет действовать {{ ydb-short-name }}. Обязательная опция.
* `resource` — идентификатор облака, в котором регистрируется делегирование. Это облако, которому принадлежит сервисный аккаунт. Необязательная опция: если она не указана, {{ ydb-short-name }} определяет облако по сервисному аккаунту с правами пользователя, а если это не удаётся (например, у пользователя нет роли `iam.serviceAccounts.get`), использует облако текущей базы данных и сообщает об этом предупреждением в ответе на запрос.

Полное описание команды — в разделе [CREATE SECRET](../../yql/reference/syntax/create-secret.md).

## Использование {#usage}

Секрет с делегированием указывается там же, где указывается обычный секрет с токеном. Пример потокового запроса, который читает топик другой базы {{ ydb-short-name }} и пишет метрику в Monium от имени одного и того же сервисного аккаунта:

```yql
-- Источник: топик в другой базе данных.
CREATE EXTERNAL DATA SOURCE `events_db` WITH (
    SOURCE_TYPE = "Ydb",
    LOCATION = "ydb.serverless.yandexcloud.net:2135",
    DATABASE_NAME = "/ru-central1/b1gxxxxxxxxx/etnyyyyyyyyy",
    USE_TLS = "TRUE",
    AUTH_METHOD = "TOKEN",
    TOKEN_SECRET_PATH = "events_sa"
);

-- Приёмник: проект Monium, тот же секрет.
CREATE EXTERNAL DATA SOURCE `metrics` WITH (
    SOURCE_TYPE = "Monium.Metrics",
    LOCATION = "monitoring.api.cloud.yandex.net",
    PROJECT = "events-monitoring",
    AUTH_METHOD = "TOKEN",
    TOKEN_SECRET_PATH = "events_sa"
);

-- Запрос работает, пока его не удалят.
CREATE STREAMING QUERY `events_to_metrics` AS
DO BEGIN
    INSERT INTO `metrics`.`events`
    SELECT "events" AS sensor, COUNT(*) AS value, HOP_END() AS ts
    FROM `events_db`.`events` WITH (
        FORMAT = "json_each_row",
        SCHEMA (event_time Timestamp NOT NULL, kind String NOT NULL)
    )
    GROUP BY HOP(event_time, "PT1M", "PT1M", "PT1M")
END DO;
```

Секрет с делегированием подходит только для способов аутентификации, значением секрета для которых является токен. Для `AUTH_METHOD = "SERVICE_ACCOUNT"` (ключ сервисного аккаунта) и `AUTH_METHOD = "BASIC"` (пароль) он не подходит; попытка создать такой объект над секретом с делегированием завершится ошибкой.

## Пошаговый пример: чтение метрик Monium {#example}

Ниже описано, как с помощью секрета с делегированием читать метрики проекта Monium от имени отдельного сервисного аккаунта, не вводя в {{ ydb-short-name }} ни ключа, ни токена.

1. Создайте сервисный аккаунт, который будет читать метрики:

    ```bash
    yc iam service-account create --name metrics-reader
    SA_ID=$(yc iam service-account get metrics-reader --format json | jq -r .id)
    ```

1. Выдайте ему роль на чтение метрик в каталоге, которому принадлежит проект Monium:

    ```bash
    yc resource-manager folder add-access-binding <folder-id> \
      --role monitoring.viewer \
      --subject serviceAccount:$SA_ID
    ```

1. Убедитесь, что у вас есть право использовать этот аккаунт. Владельцам, администраторам и редакторам каталога оно выдано по умолчанию; иначе:

    ```bash
    yc iam service-account add-access-binding $SA_ID \
      --role iam.serviceAccounts.user \
      --subject userAccount:<your-user-id>
    ```

1. Подключитесь к базе данных от своего имени (не по ключу сервисного аккаунта) и создайте секрет:

    ```yql
    CREATE SECRET `metrics_reader` WITH (
        type = "IAM_DELEGATION",
        service_account_id = "<SA_ID>"
    );
    ```

    Если IAM отказывает, в ошибке указана причина: например, что у вас нет права на сервисный аккаунт или что сервисный аккаунт принадлежит другому облаку. В последнем случае укажите облако явно опцией `resource`.

1. Создайте внешний источник данных и прочитайте метрики:

    ```yql
    CREATE EXTERNAL DATA SOURCE `monium` WITH (
        SOURCE_TYPE = "Monium.Metrics",
        LOCATION = "monitoring.api.cloud.yandex.net",
        PROJECT = "<project-id>",
        AUTH_METHOD = "TOKEN",
        TOKEN_SECRET_PATH = "metrics_reader"
    );

    SELECT * FROM `monium`.`<service>` WITH (
        selectors = @@{name = "cpu_usage"}@@,
        from = "2026-09-01T00:00:00Z",
        to = "2026-09-02T00:00:00Z"
    );
    ```

1. Чтобы сменить сервисный аккаунт, выполните `ALTER SECRET metrics_reader WITH (service_account_id = "<другой SA_ID>")`: источник данных и запросы менять не нужно. Чтобы отозвать доступ, удалите секрет: `DROP SECRET metrics_reader`.

## Ограничения {#limitations}

* Тип секрета нельзя изменить: `ALTER SECRET` и `CREATE OR REPLACE SECRET` не превращают обычный секрет в секрет с делегированием и наоборот.
* Секрет с делегированием нельзя удалить командой `DROP SECRET`, выполненной вне сервиса запросов (например, через `ydb yql`): удаление и отзыв делегирования выполняются вместе, и такая команда завершается ошибкой.
* Если отзыв делегирования при `DROP SECRET` не удался (например, IAM недоступен), секрет всё равно удаляется, а команда завершается с предупреждением, содержащим идентификатор делегирования; по нему делегирование можно отозвать через поддержку {{ yandex-cloud }}.
* [Асинхронная репликация](../async-replication.md) и [трансфер данных](../transfer.md) не используют секреты с делегированием: для них по-прежнему применяются описанные в их документации способы аутентификации.
