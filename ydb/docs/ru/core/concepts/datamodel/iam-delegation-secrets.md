# Секреты с делегированием IAM

{% note info %}

Секреты с делегированием IAM доступны только в базах данных {{ ydb-short-name }}, развёрнутых в {{ yandex-cloud }}: они опираются на механизм делегирования сервисных аккаунтов сервиса IAM.

{% endnote %}

Обращаясь к внешней системе — [топику](topic.md) другой базы {{ ydb-short-name }}, бакету Object Storage, метрикам Monium, — запрос аутентифицируется в ней от имени [сервисного аккаунта](https://yandex.cloud/ru/docs/iam/concepts/users/service-accounts) {{ yandex-cloud }}. Обычный [секрет](secrets.md) хранит для этого либо IAM-токен, который истекает через 12 часов, либо авторизованный ключ сервисного аккаунта, который не истекает никогда и потому требует ручной ротации. Ни то, ни другое не подходит для долгоживущих запросов: [потоковый запрос](../streaming-query/index.md) работает неделями, а [федеративный запрос](../query_execution/federated_query/index.md) по большому бакету — часами.

Секрет с делегированием IAM не хранит ни токена, ни ключа. При его создании {{ ydb-short-name }} просит IAM разрешить ей действовать от имени указанного сервисного аккаунта — от имени пользователя, выполняющего запрос. После этого {{ ydb-short-name }} сама получает короткоживущие IAM-токены этого аккаунта и обновляет их до истечения срока действия, а при удалении секрета просит IAM отозвать делегирование.

Для объектов, использующих секреты, такой секрет ничем не отличается от обычного: его значением всегда является действующий IAM-токен делегированного сервисного аккаунта. Любой объект, принимающий секрет с токеном, например [внешний источник данных](external_data_source.md) с `AUTH_METHOD="TOKEN"`, работает с секретом с делегированием без изменений.

## Принцип работы {#how-it-works}

* **Создание.** При выполнении [CREATE SECRET](../../yql/reference/syntax/create-secret.md) {{ ydb-short-name }} сначала проверяет права пользователя на создание объекта в директории: без них команда завершается ошибкой, и обращения к IAM не происходит. Затем {{ ydb-short-name }} обращается к IAM и просит настроить делегирование сервисного аккаунта на себя. IAM проверяет, что пользователь, выполняющий запрос, имеет право использовать этот сервисный аккаунт (роль `iam.serviceAccounts.user`). Если права нет или IAM недоступен, секрет не создаётся, а пользователь получает ошибку IAM. В секрете сохраняются только идентификатор сервисного аккаунта, идентификатор облака и идентификатор делегирования.
* **Чтение.** При первом чтении секрета на узле {{ ydb-short-name }} получает IAM-токен делегированного аккаунта через сервис токенов IAM, аутентифицируясь собственным системным сервисным аккаунтом. Токен пользователя, создавшего секрет, при этом не используется и не хранится. Затем узел обновляет токен в фоне до истечения срока его действия, поэтому запрос всегда получает действующий токен, как бы долго он ни работал. При временной недоступности IAM используется последний полученный токен, пока он действителен.
* **Изменение.** При выполнении [ALTER SECRET](../../yql/reference/syntax/alter-secret.md) новое делегирование настраивается до отзыва старого, поэтому работающие запросы переключаются на другой сервисный аккаунт без перезапуска.
* **Удаление.** При выполнении [DROP SECRET](../../yql/reference/syntax/drop-secret.md) доступ к секрету прекращается сразу: чтение секрета больше невозможно. Затем {{ ydb-short-name }} просит IAM отозвать делегирование и повторяет попытки, пока отзыв не будет принят, в том числе после сбоев и перезапусков. С момента отзыва новые токены сервисного аккаунта через этот секрет не выпускаются. Уже выданные токены действуют до истечения их срока, так как IAM не отзывает выданные токены.

## Требования {#requirements}

* Создавать, изменять и удалять секрет с делегированием может только субъект {{ yandex-cloud }} — пользователь, федеративный пользователь или сервисный аккаунт, аутентифицированный через IAM. Локальным пользователям базы данных эти команды недоступны.
* Пользователь должен иметь роль `iam.serviceAccounts.user` на делегируемый сервисный аккаунт. Владельцам, администраторам и редакторам каталога она выдана по умолчанию.
* Сервис {{ ydb-short-name }} должен быть включён в облаке, которому принадлежит сервисный аккаунт, — см. [Управление доступом сервисов к ресурсам](https://yandex.cloud/ru/docs/iam/concepts/service-control) и [Включение и отключение сервиса](https://yandex.cloud/ru/docs/iam/operations/service-control/enable-disable) в документации IAM, а также [ниже](#enable-service).
* На секрет действуют [обычные права](secrets.md#secret_access) схемных объектов: для создания нужно право `CREATE TABLE` на директорию, для использования в запросе — `SELECT ROW` на секрет.

### Включение сервиса в облаке {#enable-service}

Делегирование регистрируется в облаке сервисного аккаунта, и IAM выполняет его от имени [сервисного агента](https://yandex.cloud/ru/docs/iam/concepts/service-control) {{ ydb-short-name }} в этом облаке. Агент существует, если сервис `ydb` в облаке имеет статус `ENABLED` или `DEFAULT`; со статусом `DISABLED` команда `CREATE SECRET` завершается ошибкой IAM с указанием, что сервис не включён в облаке. Чтобы [проверить](https://yandex.cloud/ru/docs/iam/operations/service-control/list-get) и при необходимости [включить](https://yandex.cloud/ru/docs/iam/operations/service-control/enable-disable) сервис:

1. Узнайте статус сервиса `ydb` в облаке, которому принадлежит сервисный аккаунт:

    ```bash
    yc iam service-control get ydb --cloud-id <идентификатор_облака>
    ```

    Статусы `ENABLED` и `DEFAULT` означают, что делать ничего не нужно: в состоянии `DEFAULT` сервисные агенты создаются автоматически при первом делегировании.

1. Если статус `DISABLED`, включите сервис. Для этого нужна роль администратора или владельца облака:

    ```bash
    yc iam service-control enable ydb --cloud-id <идентификатор_облака>
    ```

    После включения статус сервиса меняется на `ENABLED`, и в облаке создаются сервисные агенты {{ ydb-short-name }} с необходимыми правами.

Отключение сервиса командой `yc iam service-control disable ydb` лишает {{ ydb-short-name }} возможности действовать от имени всех сервисных аккаунтов этого облака: секреты с делегированием, зарегистрированные в нём, перестают выдавать токены.

## Синтаксис {#syntax}

Секрет с делегированием создаётся командой [CREATE SECRET](../../yql/reference/syntax/create-secret.md) с параметром `SOURCE="IAM_DELEGATION"`:

```yql
CREATE SECRET events_sa WITH (
    SOURCE="IAM_DELEGATION",
    SERVICE_ACCOUNT_ID="aje8k2vqp3n1rd7cmf4t"
);
```

* `SOURCE` — `IAM_DELEGATION`: секрет является [внешним](secrets.md#types), его значение {{ ydb-short-name }} получает через IAM. Без параметра `SOURCE` создаётся [обычный секрет](secrets.md) со значением.
* `SERVICE_ACCOUNT_ID` — идентификатор сервисного аккаунта, от имени которого будет действовать {{ ydb-short-name }}. Обязательный параметр.
* `RESOURCE` — идентификатор облака, в котором регистрируется делегирование: облако, которому принадлежит сервисный аккаунт. Необязательный параметр. Если он не указан, {{ ydb-short-name }} определяет облако по сервисному аккаунту с правами пользователя, а если это не удаётся (например, у пользователя нет роли `iam.serviceAccounts.get`), использует облако текущей базы данных и сообщает об этом предупреждением в ответе на запрос.

Сервисный аккаунт и облако можно изменить командой [ALTER SECRET](../../yql/reference/syntax/alter-secret.md); источник секрета изменить нельзя. Удаляется секрет командой [DROP SECRET](../../yql/reference/syntax/drop-secret.md).

## Использование {#usage}

Секрет с делегированием указывается там же, где указывается обычный секрет с токеном. В примере ниже потоковый запрос читает топик другой базы {{ ydb-short-name }} и записывает метрику в Monium от имени одного и того же сервисного аккаунта:

```yql
CREATE SECRET events_sa WITH (
    SOURCE="IAM_DELEGATION",
    SERVICE_ACCOUNT_ID="aje8k2vqp3n1rd7cmf4t"
);

CREATE EXTERNAL DATA SOURCE events_db WITH (
    SOURCE_TYPE="Ydb",
    LOCATION="ydb.serverless.yandexcloud.net:2135",
    DATABASE_NAME="/ru-central1/b1gxxxxxxxxx/etnyyyyyyyyy",
    USE_TLS="TRUE",
    AUTH_METHOD="TOKEN",
    TOKEN_SECRET_PATH="events_sa"
);

CREATE EXTERNAL DATA SOURCE metrics WITH (
    SOURCE_TYPE="Monium.Metrics",
    LOCATION="monitoring.api.cloud.yandex.net",
    PROJECT="events-monitoring",
    AUTH_METHOD="TOKEN",
    TOKEN_SECRET_PATH="events_sa"
);

CREATE STREAMING QUERY events_to_metrics AS
DO BEGIN
    INSERT INTO metrics.`events`
    SELECT "events" AS sensor, COUNT(*) AS value, HOP_END() AS ts
    FROM events_db.`events` WITH (
        FORMAT="json_each_row",
        SCHEMA (event_time Timestamp NOT NULL, kind String NOT NULL)
    )
    GROUP BY HOP(event_time, "PT1M", "PT1M", "PT1M")
END DO;
```

Запрос работает, пока его не удалят, и на всём протяжении работы использует действующий токен сервисного аккаунта. Команда `ALTER SECRET events_sa WITH (SERVICE_ACCOUNT_ID="aje6h0sbq9wl2xn5tdg7")` переключает его на другой сервисный аккаунт, не затрагивая источники данных и сам запрос; команда `DROP SECRET events_sa` отзывает доступ.

## Ограничения {#restrictions}

* Секрет с делегированием подходит только для способов аутентификации, значением секрета для которых является токен. Для `AUTH_METHOD="SERVICE_ACCOUNT"` (ключ сервисного аккаунта) и `AUTH_METHOD="BASIC"` (пароль) он не подходит; попытка создать такой объект над секретом с делегированием завершится ошибкой.
* Источник секрета нельзя изменить: `ALTER SECRET` и `CREATE OR REPLACE SECRET` не превращают обычный секрет в секрет с делегированием и наоборот.
* Если получить токен невозможно — делегирование отозвано в IAM, сервис {{ ydb-short-name }} отключён в облаке или IAM недоступен после истечения последнего полученного токена, — секрет остаётся действительным объектом схемы. Создание объектов, которые на него ссылаются, например внешнего источника данных, выполняется успешно, так как значение секрета при этом не читается. Ошибка IAM возвращается запросу, который использует секрет.
* Описание секрета показывает его источник и параметры, но не то, можно ли сейчас получить его значение: состояние токена у каждого узла базы данных своё.
* Если отзыв делегирования при `DROP SECRET` не удался (например, IAM недоступен), секрет всё равно удаляется, команда завершается с предупреждением, а {{ ydb-short-name }} повторяет отзыв автоматически.
* [Асинхронная репликация](../async-replication.md) и [трансфер данных](../transfer.md) не используют секреты с делегированием: для них применяются способы аутентификации, описанные в их документации.
