# Прогрев кэша компиляции

{{ ydb-short-name }} хранит скомпилированные планы запросов в памяти [узлов базы данных](../glossary.md#database-node). Повторное использование плана позволяет обслужить запрос без новой компиляции. При перезапуске узла его кэш теряется.

Прогрев кэша компиляции заранее подготавливает планы [популярных запросов](#query-selection) при запуске узла. Узел получает тексты запросов из кэшей узлов той же базы данных и компилирует их локально. Это сокращает задержки первых запросов после перезапуска или добавления узла. Во время прогрева запросы подготавливаются, но не выполняются и не изменяют данные базы.

## Как проходит прогрев

1. Узел обнаруживает узлы той же базы данных и читает их кэши через системное представление [`.sys/compile_cache_queries`](../../dev/system-views.md#compile-cache-queries).
2. Из полученных записей выбираются наиболее часто используемые запросы. Количество запрашиваемых узлов, выбранных запросов и одновременно выполняющихся компиляций ограничено [настройками прогрева](../../reference/configuration/table_service_config.md#compile-cache-warmup).
3. Выбранные запросы компилируются с учётом пользователя, типа запроса, синтаксиса и типов параметров. Готовые планы сохраняются в локальном кэше.
4. После завершения прогрева узел появляется в списке доступных [эндпоинтов](../connect.md#endpoint) базы данных и начинает обслуживать клиентские запросы. До этого прямое обращение к узлу может возвращать `UNAVAILABLE` с сообщением о прогреве кэша.

### Выбор запросов {#query-selection}

Популярность определяется по `AccessCount` в `.sys/compile_cache_queries` — количеству обращений к результату компиляции за время его хранения в кэше. Записи с одинаковыми текстом запроса, пользователем, типом запроса и синтаксисом объединяются, а их `AccessCount` суммируется по выбранным узлам. Для прогрева выбираются запросы с наибольшими суммарными значениями. Это накопленный показатель, без ограничения на последние минуты или часы.

В прогрев не включаются записи с усечённым текстом, нулевым `AccessCount` или без информации о типе запроса. Пропускаются и запросы, предыдущая компиляция которых заняла не меньше половины мягкого лимита времени прогрева. Например, при мягком лимите 10 секунд выбираются запросы с длительностью компиляции меньше 5 секунд.

Из выбранных запросов сначала компилируются те, которые ранее требовали больше времени. Прогрев поддерживает запросы через Table API и Query API, в том числе параметризованные запросы.

## Рестарты и ошибки

Прогрев полезен при последовательном перезапуске узлов: работающие узлы сохраняют кэши и предоставляют запросы запускаемому узлу. На одноузловой базе данных прогрев пропускается, поскольку нет других узлов, из которых можно получить запросы.

Кэш не сохраняется на диске. После одновременного перезапуска всех узлов прогрев может не найти запросов для подготовки. В этом случае кэш заполняется обычным образом при поступлении клиентских запросов.

Прогрев ограничен двумя сроками: после мягкого лимита новые компиляции не запускаются, а уже начатые могут завершиться; по достижении жёсткого лимита прогрев завершается. Ошибка получения кэша или компиляции отдельных запросов не блокирует запуск узла навсегда. Уже подготовленные планы остаются в кэше и могут использоваться клиентами.

Прогрев не гарантирует, что каждый последующий запрос найдёт готовый план: запрос мог не попасть в выбранную часть кэша, не успеть скомпилироваться или отличаться по контексту выполнения. Планы также могут быть вытеснены из кэша или потребовать повторной компиляции после изменения схемы.

На системных узлах корневого домена прогрев не запускается. Для serverless-баз данных получение кэша через `.sys/compile_cache_queries` недоступно.

## Настройка

В секции `table_service_config.compile_cache_warmup_config` можно настроить объём прогрева, параллелизм и время ожидания готовности узла:

* `soft_deadline_seconds` — мягкий лимит времени получения запросов и компиляции, в секундах. После его истечения новые компиляции не запускаются, а уже начатые могут завершиться в пределах жёсткого лимита. Также от этого значения зависит выборка: предыдущая компиляция запроса должна занимать меньше половины мягкого лимита.
* `hard_deadline_seconds` — предельное время прогрева, в секундах. При его достижении прогрев завершается, и узел становится доступен клиентам, даже если не все выбранные запросы подготовлены. Значение должно быть не меньше `soft_deadline_seconds`.
* `max_concurrent_compilations` — максимальное количество одновременно выполняющихся компиляций на запускаемом узле. Позволяет ограничить нагрузку прогрева на CPU и память.
* `max_queries_to_load` — максимальное количество популярных запросов, выбираемых для прогрева. Дополнительно ограничивается размером кэша `compile_query_cache_size`. Большее значение позволяет подготовить больше планов, если хватает времени на их компиляцию.
* `max_nodes_to_request` — максимальное количество узлов базы данных, из кэшей которых выбираются запросы. Позволяет ограничить объём обращений к работающим узлам.

По умолчанию мягкий лимит составляет 10 секунд, жёсткий — 20 секунд. Одновременно выполняется не более 5 компиляций; для прогрева выбирается до 1000 запросов из кэшей не более 5 узлов.

Настройки применяются при запуске узла. Пример конфигурации и правила обработки нулевых значений приведены в разделе [{#T}](../../reference/configuration/table_service_config.md#compile-cache-warmup).

## Проверка результата

Содержимое кэша можно посмотреть в [`.sys/compile_cache_queries`](../../dev/system-views.md#compile-cache-queries), отфильтровав записи по `NodeId` запускавшегося узла.
