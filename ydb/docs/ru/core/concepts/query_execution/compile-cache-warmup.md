# Прогрев кеша компиляции

После перезапуска [узла базы данных](../glossary.md#database-node) первые запросы могут выполняться дольше. Узлу нужно заново определить, какие операции потребуются для каждого запроса и в каком порядке их выполнить. Такая подготовка называется компиляцией, а её результат — планом выполнения запроса. Узел хранит готовые планы в оперативной памяти и использует их повторно. При перезапуске этот кеш теряется.

Прогрев кеша компиляции сокращает задержку первых запросов. {{ ydb-short-name }} заранее готовит планы [часто используемых запросов](#query-selection), пока узел ещё не обслуживает клиентов. Это полезно при последовательном перезапуске узлов или добавлении узла в работающую базу данных.

По умолчанию прогрев запускается автоматически. Администратор может [ограничить время прогрева и количество запросов](../../reference/configuration/table_service_config.md#compile-cache-warmup). Во время прогрева узел только компилирует запросы. Данные в базе не меняются.

## Как проходит прогрев

1. Узел получает сведения о запросах из кешей других узлов той же базы данных через системное представление [`.sys/compile_cache_queries`](../../dev/system-views.md#compile-cache-queries).
2. Из полученных записей выбираются наиболее часто используемые запросы. Количество опрашиваемых узлов, выбранных запросов и одновременно выполняющихся компиляций ограничено [настройками прогрева](../../reference/configuration/table_service_config.md#compile-cache-warmup).
3. Выбранные запросы компилируются с учётом пользователя, типа запроса, синтаксиса и типов параметров. Готовые планы сохраняются в локальном кеше.
4. После завершения прогрева узел появляется в списке доступных [сетевых адресов для подключения](../connect.md#endpoint) к базе данных и начинает обслуживать клиентские запросы. До этого прямое обращение к узлу может вернуть `UNAVAILABLE` с сообщением о прогреве кеша.

Чтобы посмотреть, какие запросы сейчас хранятся в кеше узла, отфильтруйте строки `.sys/compile_cache_queries` по его `NodeId`. В выборку попадут в том числе запросы, скомпилированные при обслуживании клиентов. См. [примеры запросов к представлению](../../dev/system-views.md#compile-cache-queries-examples).

### Выбор запросов {#query-selection}

Для прогрева выбираются часто используемые запросы из кешей работающих узлов. При отборе учитываются статистика обращений и время, необходимое для компиляции. Объём работы ограничен настройками прогрева, поэтому часть запросов может не попасть в выборку.

Прогрев поддерживает запросы через Table Service и Query Service, в том числе параметризованные запросы.

## Перезапуски и ошибки

При последовательном перезапуске работающие узлы сохраняют кеши, из которых запускаемый узел получает запросы для прогрева. В базе данных с одним узлом прогрев пропускается, поскольку получить запросы с других узлов невозможно.

Кеш не сохраняется на диске. После одновременного перезапуска всех узлов прогрев может не найти запросов для подготовки. В этом случае кеш заполняется обычным образом при поступлении клиентских запросов.

По достижении мягкого лимита времени узел прекращает запускать новые компиляции и ждёт завершения уже начатых. По достижении жёсткого лимита прогрев завершается. Даже если узлу не удалось получить содержимое кеша или скомпилировать отдельные запросы, он может начать обслуживать клиентов. Уже подготовленные планы остаются доступны в кеше.

Клиентскому запросу может потребоваться компиляция, если он не попал в выборку, не успел скомпилироваться или если изменились пользователь, тип запроса, синтаксис или типы параметров. Планы также могут быть вытеснены из кеша или потребовать повторной компиляции после изменения схемы.

На системных узлах корневого домена прогрев не запускается. Для serverless-баз данных получение кеша через `.sys/compile_cache_queries` недоступно.
