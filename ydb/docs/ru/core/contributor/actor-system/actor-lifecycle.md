# Жизненный цикл актора

Актор — C++-объект, которым владеет среда выполнения и чьё состояние изменяется во время последовательных циклов обработки событий почтового ящика. Эта страница описывает создание, регистрацию, диспетчеризацию, сервисы и пулы исполнения. Начните с инвариантов в [руководстве по акторной системе](index.md); переход к завершению описан в разделе [Сбои и завершение работы](failure-and-shutdown.md).

## Минимальный актор

```cpp
#include <ydb/library/actors/core/actor_bootstrapped.h>
#include <ydb/library/actors/core/event_local.h>
#include <ydb/library/actors/core/events.h>
#include <ydb/library/actors/core/hfunc.h>

using namespace NActors;

enum EEv {
    EvRequest = EventSpaceBegin(TEvents::ES_PRIVATE),
    EvResponse,
};

struct TEvRequest : TEventLocal<TEvRequest, EvRequest> {
    TString Value;
    explicit TEvRequest(TString value)
        : Value(std::move(value))
    {}
};

struct TEvResponse : TEventLocal<TEvResponse, EvResponse> {
    TString Value;
    explicit TEvResponse(TString value)
        : Value(std::move(value))
    {}
};

class TExampleActor final : public TActorBootstrapped<TExampleActor> {
public:
    void Bootstrap() {
        Become(&TThis::StateWork);
    }

    void Handle(TEvRequest::TPtr& ev) {
        Send(ev->Sender, new TEvResponse(ev->Get()->Value), 0, ev->Cookie);
    }

    void BeginShutdown() {
        Become(&TThis::StateDying);
        PassAway();
    }

    STRICT_STFUNC(StateWork,
        hFunc(TEvRequest, Handle);
        cFunc(TEvents::TEvPoison::EventType, BeginShutdown);
    )

    STFUNC(StateDying) {
        Y_UNUSED(ev); // PassAway may be waiting for coroutine tasks.
    }
};
```

В этом примере TEvRequest и TEvResponse предназначены только для локальной передачи.
Для сообщения, которое может пересекать границу узла, используйте сериализуемое событие.

## Создание, Bootstrap и диспетчеризация состояний

`TActor<TDerived>` принимает начальную функцию состояния и начинает ожидать события.
`TActorBootstrapped<TDerived>` устанавливает состояние начальной загрузки; при регистрации
в очередь добавляется событие Bootstrap, которое вызывает одну из поддерживаемых перегрузок Bootstrap.

Конструктор также сохраняет тип активности, используемый в счётчиках мониторинга.
Значение по умолчанию выбирается в таком порядке: TDerived::ActorName (статическая строка),
затем TDerived::ActorActivityType() (перечисление), затем имя C++-типа. Можно передать
строку или перечисление в конструктор либо вызвать SetActivityType, но только до
Register: SetActivityType выбрасывает исключение, если у актора уже есть ActorId.

Bootstrap должен установить состояние для последующих событий. В синхронном Bootstrap
вызовите Become до возврата. В Bootstrap на корутине вызовите Become до первой
приостановки: в этот момент управление возвращается вызывающему коду.

Сигнатура функции состояния:

```cpp
void State(TAutoPtr<IEventHandle>& ev);
```

Become меняет текущее состояние всего актора, а не только текущего запроса или корутины.
Поэтому обработчики на корутинах, чьё выполнение пересекается во времени, могут наблюдать
результаты вызовов Become друг друга.

Макросы диспетчеризации из hfunc.h упрощают описание веток switch:

| Макрос | Сигнатура вызываемого обработчика |
|---|---|
| hFunc(TEv, Handle) | Handle(TEv::TPtr&) |
| HFunc(TEv, Handle) | Handle(TEv::TPtr&, const TActorContext&) |
| sFunc / SFunc | Handle() / Handle(ctx), без использования полезной нагрузки |
| cFunc / CFunc | Диспетчеризация по числовому типу события, без типизированного указателя |
| fFunc / FFunc | Handle(ev) / Handle(ev, ctx), с исходной оболочкой события |
| IgnoreFunc(TEv) | Отбросить событие этого типа |

STRICT_STFUNC диагностирует неизвестный тип через Y_DEBUG_ABORT_UNLESS в отладочных
сборках. Это средство отладки, а не гарантия протокола в сборке release. Обычный STFUNC
позволяет задать собственное поведение по умолчанию. Для диспетчеризации используйте
GetTypeRewrite, как это делают макросы: перенаправление и Interconnect могут изменять
эффективный тип события и получателя.

### У обработчиков на корутинах другая сигнатура

Корутина верхнего уровня без собственного стека — нестатический метод IActor,
возвращающий void. Все явные аргументы должны передаваться **по значению**:

```cpp
void HandleAsync(TEvRequest::TPtr ev) {
    // ...
    co_await Something();
}

STRICT_STFUNC(StateWork,
    hFunc(TEvRequest, HandleAsync);
)
```

hFunc передаёт lvalue TAutoPtr, чья операция, похожая на копирование, передаёт владение
параметру корутины, принятому по значению. Ссылочный параметр не позволяет выбрать
promise акторной корутины и приводит к ошибке компиляции.
Полный контракт описан в разделе [Акторы на корутинах](coroutine-actors.md).

## Регистрация и владение

Из цикла выполнения актора:

```cpp
TActorId child = Register(new TChild);
TActorId other = Register(
    new TChild,
    TMailboxType::HTSwap,
    AppData()->UserPoolId);
TActorId colocated = RegisterWithSameMailbox(new THelper);
```

Из кода, располагающего указателем TActorSystem:

```cpp
TActorId id = actorSystem->Register(
    new TExampleActor,
    TMailboxType::HTSwap,
    poolId);
```

Регистрация немедленно передаёт владение актором. После неё нельзя разыменовывать
исходный указатель. Среда выполнения прикрепляет актор к почтовому ящику, назначает
ActorId и вызывает Registered. Реализация Registered по умолчанию вызывает AfterRegister
и отправляет возвращённую им оболочку события — так актор с начальной загрузкой получает
Bootstrap. Переопределение Registered без вызова базовой реализации пропускает оба действия.
Эти обратные вызовы регистрации не должны исходить из того, что выполняются в активации
нового актора; работу, зависящую от активации, выполняйте в Bootstrap или при обработке следующего события.

RegisterWithSameMailbox допустим в активации актора. После этого акторы выполняются
последовательно в одном почтовом ящике и могут намеренно использовать общее состояние,
но не могут работать параллельно. IActor::InvokeOtherActor временно меняет идентичность
актора в контексте активации для прямого вызова в рамках одного почтового ящика.
Такой вызов должен быть полностью синхронным: он не должен пересекать co_await;
никогда не вызывайте асинхронный метод другого актора через обычный указатель.

Аргумент типа почтового ящика сохранён в API для совместимости. Текущий путь регистрации
встроенного исполнителя использует интрузивный почтовый ящик без блокировок и не выбирает
между историческими значениями TMailboxType. Не подбирайте Simple/HTSwap/ReadAsFilled
и другие значения, не проверив используемую реализацию исполнителя.

## ActorId и сервисы

TActorId — 16-байтовое значение, содержащее локальный идентификатор, подсказку (hint)
и закодированные биты узла и пула. Обычный идентификатор назначается при регистрации
и действителен только для данного экземпляра актора. NodeId указывает узел-владелец;
нулевой узел в идентификаторе сервиса означает локальный узел.

ToString и Out предназначены для отладки. Они опускают биты пула, поэтому разбор строки
в общем случае не позволяет восстановить исходный идентификатор. Не сохраняйте такую
строку как адрес или устойчивый ключ базы данных.

Идентификатор сервиса хранит имя длиной до 12 байт и сопоставляется с актором локально:

```cpp
const TActorId serviceId = TActorId(nodeId, "myservice");
actorSystem->RegisterLocalService(serviceId, actorId);
actorSystem->RegisterLocalService(serviceId, TActorId()); // clear
```

Маршрутизация выполняет один поиск соответствия между сервисом и актором. Не рассчитывайте
на цепочки псевдонимов сервисов. Имя сервиса стабильно лишь потому, что прикладной код
поддерживает это соответствие; при переключении после сбоя нужно установить новое.

## Почтовые ящики, пулы и поведение исполнителя

Гарантируется последовательное выполнение почтового ящика, а не конкретный алгоритм очереди.
Текущая встроенная среда выполнения использует интрузивный почтовый ящик без блокировок.
При регистрации почтовый ящик назначается логическому пулу исполнителей.

Исполнитель обрабатывает события, пока не исчерпан настроенный квант времени или числа событий,
не опустел почтовый ящик, Tail не передал выполнение либо не произошло мягкое вытеснение
рабочего потока общего пула. Эти ограничения проверяются между событиями, но никогда
внутри обработчика. Значения по умолчанию и производственная конфигурация {{ ydb-short-name }}
различаются, поэтому корректность не должна зависеть от конкретной длительности или числа событий.

Логические пулы определяют планирование нагрузки и учёт ресурсов. В некоторых конфигурациях
общие или объединённые рабочие потоки исполнителей могут временно предоставляться пулам
или переключаться между ними. Поэтому утверждение «пулу A принадлежит отдельный набор потоков ОС»
не является универсальным инвариантом. Имена User/System также не подразумевают фиксированный
бюджет времени для обработчика.

В узле {{ ydb-short-name }} TAppData предоставляет идентификаторы пулов нагрузки процесса
(SystemPoolId, UserPoolId, IOPoolId, BatchPoolId). Передавайте их в Register;
не задавайте числовые идентификаторы пулов в коде.

Блокирующую работу нужно выносить из обработчиков System/User:

- InvokeIoCallback(callback, AppData()->IOPoolId, activity) отправляет TEvInvokeQuery
  локальному сервису IoDispatcher (MakeIoDispatcherActorId). Выделенные потоки ОС
  («kikimr IO») выполняют callback. Этот обратный вызов не является циклом выполнения актора:
  передавайте уведомление о завершении через TActorSystem::Send. Если диспетчер
  не зарегистрирован, Send завершается неудачей и вспомогательная функция использует актор
  ExecuteLater в переданном poolId, который *занимает* рабочий поток исполнителя.
- CreateInvokeActor(callback, complete, activity) вместе с Register в IOPoolId
  выполняет callback в короткоживущем акторе пула IO, затем отправляет
  TEvInvokeResult родителю. Обрабатывайте это событие через Process() или шаблонный
  `GetResult<TCallback>`(). Рабочий поток пула IO всё равно занят на всё время выполнения callback.
- Регистрация долгоживущего актора в IOPoolId предназначена для акторов, чьи обработчики
  сами выполняют блокирующую работу. Другие почтовые ящики этого пула всё равно могут оставаться
  без обслуживания, пока он выполняется.

Акторы одного почтового ящика всегда выполняются последовательно, даже если в пуле много
рабочих потоков. Разные почтовые ящики могут выполняться параллельно. Заблокированный
рабочий поток уменьшает доступные ресурсы пула; достаточное число заблокированных потоков
останавливает все почтовые ящики, которым нужны эти ресурсы.

## Потоки вне акторной системы

Внешний поток может использовать указатель TActorSystem с гарантированным временем жизни
для Send или Ask. Он не должен вызывать IActor::Send, SelfId().Send, методы доступа
TActivationContext, объекты ожидания с привязкой к актору или напрямую работать с объектами акторов.
Определите владельца указателя TActorSystem и убедитесь, что ни один отправитель не использует
его после завершения системы.

Для асинхронных внешних API передавайте уведомление о завершении обратно как событие
или используйте описанный потокобезопасный мост ожидания для корутин без собственного стека.
Никогда не возобновляйте акторную корутину напрямую во внешнем потоке.
