# Акторы на корутинах

Этот раздел описывает библиотеку NActors async для корутин без собственного стека в текущем дереве исходного кода YDB. Он сочетает руководство по использованию с кратким контрактом корректности. Устаревший API TActorCoro для корутин с собственным стеком использует другой механизм и здесь не рассматривается.

Основные заголовки находятся в `ydb/library/actors/async/`:

- [async.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/async.h);
- [wait_for_event.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/wait_for_event.h);
- [continuation.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/continuation.h);
- [event.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/event.h);
- [sleep.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/sleep.h) и [yield.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/yield.h);
- [timeout.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/timeout.h);
- [cancellation.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/cancellation.h);
- [task_group.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/task_group.h);
- [low_priority.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/async/low_priority.h).

Подключайте async.h в единице трансляции, где определяется метод-корутина актора. Этот заголовок предоставляет специализацию coroutine_traits, которая превращает метод актора, возвращающий void, в задачу актора верхнего уровня.

Описание API ожидания приведено в разделе [«Примитивы корутин»](coroutine-primitives.md), завершения из внешнего контекста и типовых приёмов — в разделе [«Интеграция корутин»](coroutine-integration.md), а отмены и поведения RAII — в разделе [«Сбои и завершение работы»](failure-and-shutdown.md). Эти правила опираются на [руководство по системе акторов](index.md).

## Краткий контракт

1. **Корутины не добавляют потоки.** Код актора по-прежнему выполняется последовательно через почтовый ящик. Несколько кадров могут быть приостановлены, но одновременно выполняется только один цикл обработки события или одно продолжение.

2. **У двух видов кадров разные владельцы.** Корутина актора, возвращающая void, — задача верхнего уровня, зарегистрированная в акторе. `async<T>` — ленивый дочерний кадр, которым владеет ожидающее его выражение.

3. **Параметры верхнего уровня передаются по значению.** Каждый явный параметр корутины актора, возвращающей void, должен иметь нессылочный тип. В частности, асинхронный обработчик hFunc принимает TEv::TPtr ev, а не TEv::TPtr&.

4. **Вызов задачи верхнего уровня выполняется немедленно и не создаёт структурированной связи.** Он работает синхронно до первой фактической приостановки и не возвращает дескриптор задачи. Вызов другой корутины, возвращающей void, не делает её дочерней; если важны порядок выполнения и владение, используйте `async<T>` и co_await.

5. **Вызов `async<T>` ленивый.** Он создаёт приостановленный кадр; тело начинает выполняться только при непосредственном ожидании. Если объект отбрасывается, ещё не запущенный кадр уничтожается.

6. **Каждая возможная приостановка — точка чередования выполнения.** До возобновления этого кадра другое событие или задача верхнего уровня может изменить состояние актора. Последовательная обработка почтового ящика предотвращает гонки данных, но не устаревшие ссылки и логические ошибки.

7. **Отмена — кооперативная передача управления, а не исключение.** Код после отменённой приостановки обычно пропускается; живые объекты кадра уничтожаются, поэтому RAII выполняется. catch (...) не перехватывает отмену.

8. **PassAway запрашивает отмену и может вернуть управление.** Актор остаётся зарегистрированным, пока все задачи верхнего уровня не завершат отмену. Ожидание, не поддерживающее отмену, может отложить завершение актора на неопределённое время.

9. **Примитивы, учитывающие контекст актора, локальны для актора.** Resume/Throw/уничтожение продолжения, Notify/уничтожение TAsyncEvent, Cancel области отмены и планирование runnable требуют активации нужного актора. Внешний поток отправляет событие или завершает универсальный объект ожидания через мост.

10. **Тайм-аут не задаёт жёсткий крайний срок.** Он запрашивает отмену дочерней операции и ждёт подтверждения. Обычное завершение всё ещё может опередить отмену после истечения срока.

11. **Освобождение ресурсов через RAII должно выдерживать принудительное уничтожение.** Принудительная очистка почтового ящика уничтожает кадры без возобновления их тел и может выполняться без пригодного TLS актора. Деструкторы должны освобождать память и связи, не полагаясь на Send или TActorContext.

12. **Ожидайте временные объекты непосредственно.** Неперемещаемые объекты ожидания библиотеки с атрибутом nodiscard предназначены для использования как непосредственные операнды co_await. Если сохранить обёртку или отделить вызов лямбды-корутины от её ожидания, ленивый кадр может сохранить ссылку на уже уничтоженное замыкание.

## Два вида кадров

| Свойство | Корутина актора верхнего уровня | Вложенная `async<T>` |
|---|---|---|
| Сигнатура | Нестатический метод IActor, возвращающий void | Функция, метод или лямбда, возвращающие `async<T>` |
| Запуск | Немедленный, initial_suspend — suspend_never | Ленивый, initial_suspend — suspend_always |
| Возвращаемый объект | Нет | Некопируемый и обычно неперемещаемый `async<T>` |
| Владелец | Список TActorTask актора | Непосредственное выражение co_await / декоратор |
| Время жизни актора | PassAway ждёт эту задачу | Живёт внутри ожидающей её задачи верхнего уровня |
| Результат | Нет | T или void; исключение повторно выбрасывается в co_await |
| Отмена | Корневой источник отмены | Наследуется от ожидающего родителя |

### Жизненный цикл кадра верхнего уровня

Вызов корутины актора, возвращающей void, логически выполняет следующие действия:

1. выделяет кадр корутины и копирует или перемещает в него все явные параметры, переданные по значению;
2. создаёт TActorAsyncHandlerPromise, который регистрирует себя в акторе как TActorTask;
3. немедленно выполняет тело, поскольку initial_suspend никогда не приостанавливает выполнение;
4. при фактической приостановке в co_await оставляет кадр в ожидании и возвращает void вызывающему коду;
5. при нормальном завершении уничтожает локальные объекты тела, достигает final suspend, уничтожает кадр и снимает регистрацию задачи в деструкторе promise-объекта;
6. при подтверждённой отмене уничтожает приостановленный кадр, а вместе с ним — все живые локальные объекты, объекты ожидания (awaiter), параметры и promise-объект;
7. при принудительной очистке почтового ящика DestroyActorTasks напрямую вызывает coroutine_handle::destroy: объекты C++ уничтожаются так же, но код тела больше не выполняется.

Если тело фактически ни разу не приостанавливается, регистрация, выполнение, завершение и уничтожение кадра происходят до возврата из вызова.

Вызывающий код не получает дескриптор задачи. Это подходит для точки входа обработки события или намеренно независимого фонового цикла актора. Вызов другой корутины, возвращающей void, из обработчика не ждёт её завершения, а запускает отдельную задачу того же верхнего уровня:

```cpp
void Handle(TEvRequest::TPtr ev) {
    ChildRoot();              // sibling TActorTask; Handle does not wait
    co_await SomethingElse();
}

void ChildRoot() {            // also a top-level void coroutine
    co_await Work();
}
```

Предпочитайте вложенную `async<T>`, которую Handle ожидает через co_await:

```cpp
void Handle(TEvRequest::TPtr ev) {
    co_await Child();
}

async<void> Child() {
    co_await Work();
}
```

### Жизненный цикл вложенного кадра

Вызов функции `async<T>`:

1. создаёт её кадр и сохраняет копии параметров или ссылки на них;
2. останавливается на initial_suspend до выполнения тела;
3. возвращает объект `async<T>`, владеющий дескриптором кадра.

Затем происходит одно из двух:

- если объект async отбрасывается, его деструктор уничтожает кадр; локальные объекты тела ещё не создавались, а тело никогда не выполняется;
- при непосредственном ожидании выражение await устанавливает актор, источник отмены и продолжение родителя, затем передаёт выполнение дочерней корутине.

После завершения дочерней корутины final suspend возвращает выполнение родителю. Promise-объект сохраняет значение или исключение, пока await_resume не извлечёт его. В конце полного выражения co_await владеющий объект async уничтожает дочерний кадр. Исключение, сохранённое вложенной корутиной, повторно выбрасывается в родителе в точке co_await.

`async<T>` намеренно не является универсальным future или задачей, которую можно отделить от владельца. Не используйте UnsafeMove в обычном прикладном коде: он предназначен для библиотечных комбинаторов.

## Параметры, захваты и данные кадра

Специализация верхнего уровня выбирается только для:

```cpp
template<IsActorSubClassType T, IsNonReferenceType... Args>
struct std::coroutine_traits<void, T&, Args...>;
```

Поэтому все явные аргументы должны передаваться по значению:

```cpp
void Handle(TEvRequest::TPtr ev) { // correct: event ownership enters frame
    co_await Process();
}

void Handle(TEvRequest::TPtr& ev) { // not a stackless actor coroutine promise
    co_await Process();             // compile-time failure
}
```

hFunc передаёт свой TAutoPtr lvalue в обработчик с параметром по значению, передавая владение событием. Неявная ссылка this ожидаема и не входит в Args. Перегрузки Bootstrap для корутин также должны принимать явные параметры по значению. Для корутины предпочитайте `Bootstrap()` или `Bootstrap(TActorId parent)`. Копирование `TActorContext` не продлевает жизнь активации, на которую он ссылается; никогда не используйте этот контекст после приостановки. Установите Become до первой приостановки Bootstrap.

Вложенные функции `async<T>` могут иметь ссылочные параметры, но это обычные заимствования:

```cpp
async<void> Use(const TString& value); // caller must keep value alive
```

Дескриптор события, переданный в корутину верхнего уровня по значению, остаётся безопасным с точки зрения памяти после приостановки, поскольку им владеет кадр. Однако так можно надолго удержать большой объём данных. Извлеките нужные небольшие поля и вызовите ev.Reset() перед длительным ожиданием.

У лямбд-корутин есть дополнительная ловушка времени жизни: их кадры обычно заимствуют замыкание лямбды через её указатель this. Следующие варианты безопасны:

```cpp
auto operation = [value]() -> async<void> {
    co_await Use(value);
};
co_await operation(); // named closure outlives the await

co_await WithTimeout(TDuration::Seconds(1), [value]() -> async<void> {
    co_await Use(value);
}); // closure temporary lives through this co_await full-expression
```

Не создавайте и не сохраняйте возвращённый ленивый async или декоратор в одном полном выражении, чтобы затем ожидать его в другом. TTaskGroup::Add устроен иначе: он хранит копии функции обратного вызова и аргументов с типами после decay до завершения дочерней задачи.

В целом по возможности избегайте лямбд-корутин.

## Минимальный актор с запросом и ответом

Определения событий опущены; существенны параметры по значению, уникальные cookie, вложенная вспомогательная функция, обработка тайм-аута, диспетчеризация устаревших ответов и состояние завершения.

```cpp
#include <ydb/library/actors/async/async.h>
#include <ydb/library/actors/async/timeout.h>
#include <ydb/library/actors/async/wait_for_event.h>
#include <ydb/library/actors/core/actor_bootstrapped.h>
#include <ydb/library/actors/core/hfunc.h>

using namespace NActors;

class TClient final : public TActorBootstrapped<TClient> {
public:
    explicit TClient(TActorId backend)
        : Backend(backend)
    {}

    void Bootstrap() {
        Become(&TThis::StateWork);
    }

    void Handle(TEvStart::TPtr ev) {
        const TActorId replyTo = ev->Sender;
        const ui64 replyCookie = ev->Cookie;
        TString payload = ev->Get()->Payload;
        ev.Reset(); // do not retain the incoming envelope while waiting

        auto value = co_await WithTimeout(
            TDuration::Seconds(5),
            RoundTrip(std::move(payload)));

        if (value) {
            Send(replyTo, new TEvDone(*value), 0, replyCookie);
        } else {
            Send(replyTo, new TEvFailed("timeout"), 0, replyCookie);
        }
    }

    async<int> RoundTrip(TString payload) {
        const ui64 cookie = ++NextCookie;
        Send(Backend, new TEvBackendRequest(std::move(payload)), 0, cookie);
        auto reply = co_await ActorWaitForEvent<TEvBackendReply>(cookie);
        co_return reply->Get()->Value;
    }

    void BeginShutdown() {
        Become(&TThis::StateDying);
        PassAway();
    }

    STRICT_STFUNC(StateWork,
        hFunc(TEvStart, Handle);
        IgnoreFunc(TEvBackendReply); // late reply after timeout/cancellation
        cFunc(TEvents::TEvPoison::EventType, BeginShutdown);
    )

    STFUNC(StateDying) {
        Y_UNUSED(ev);
    }

private:
    const TActorId Backend;
    ui64 NextCookie = 0;
};
```

Каждый TEvStart запускает независимую задачу верхнего уровня. Эти задачи могут одновременно находиться в ожидании, но никогда не исполняются одновременно. ActorWaitForEvent быстро отменяется, поэтому именно этот тайм-аут может завершиться кооперативно. Другой дочерний объект ожидания может не обладать таким свойством.

ActorWaitForEvent сопоставляет только тип и cookie, но не Sender. В примере предполагается, что только Backend использует эти cookie ответов. Если требуется проверять отправителя, направляйте ответы через StateFunc или специальный поток протокола, который выполняет такую проверку.

## Выполнение и возобновление

Обработчик верхнего уровня начинает работу внутри вызова StateFunc или Bootstrap и выполняется синхронно до приостановки. Пока он ждёт, Receive продолжает обрабатывать события почтового ящика:

| Поступившая работа | Что происходит |
|---|---|
| Событие, соответствующее ActorWaitForEvent | Объект ожидания поглощает его и возобновляет корутину непосредственно внутри Receive. |
| Несовпадающее пользовательское событие | Оно попадает в текущий StateFunc и может запустить другую корневую задачу. |
| Запланированный runnable актора | Он выполняется при обработке текущей очереди runnable. |
| Системное событие TEvResumeRunnable | Возобновление происходит при обработке этого более позднего события почтового ящика. |

TActorRunnableQueue устанавливается для каждого Receive. Такие примитивы, как TAsyncContinuation и TAsyncEvent, планируют runnable, чтобы не возобновлять другой кадр рекурсивно из Resume/Notify. Очередь обрабатывается до завершения Receive. ActorWaitForEvent намеренно устроен иначе: совпавшее событие возобновляет ожидающую корутину непосредственно и никогда не достигает StateFunc.

AsyncSleep, AsyncYield, конечные таймеры и универсальные мосты к внешним потокам используют переход через почтовый ящик с TEvResumeRunnable. Они не исполняют код актора в потоке планировщика или внешнем потоке. Вызовы Send в библиотеке передают TEvResumeRunnable::EventFlags (FlagSystemMessage). Если такое событие уничтожается необработанным и его Item всё ещё активен, ~TEvResumeRunnable вызывает Item->Run(nullptr). Если для деактивации события Item был установлен в nullptr, уничтожение ничего не делает. Библиотека может таким образом деактивировать ожидающие события, локальные для актора; события, принадлежащие планировщику, требуют отдельного моста, поскольку их уничтожение может происходить одновременно с выполнением актора.

### Правила чередования выполнения

Каждый co_await, который может приостановить выполнение, рассматривайте как следующую последовательность:

```text
сохранить состояние кадра
допустить произвольные последующие циклы выполнения актора
возобновить выполнение через почтовый ящик
перепроверить предположения
```

В частности:

- Become действует на весь актор; другой обработчик может изменить функцию состояния;
- запись в словаре, указатель, итератор, контекст транзакции или поколение могут быть удалены или заменены, пока этот кадр ждёт;
- ссылка на данные входящего события безопасна, только пока кадр владеет этим событием; сброс или пересылка дескриптора делает её недействительной;
- TActorContext никогда не безопасен после приостановки: он ссылается на активацию и рабочий поток предыдущего цикла выполнения;
- никогда не удерживайте мьютекс или guard транзакции/БД через приостановку;
- указатель this актора остаётся действительным, пока его задача верхнего уровня зарегистрирована, но у сырого указателя на другой актор такой защиты нет.

Надёжный приём для рабочего кода — хранить в кадре идентификатор запроса или поколение и после каждой приостановки заново искать принадлежащее актору состояние. Последовательная обработка почтового ящика не делает ранее сохранённый указатель логически действительным.
