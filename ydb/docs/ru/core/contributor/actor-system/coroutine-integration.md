# Интеграция корутин

Внешние обратные вызовы и операции с ключами требуют явного управления владением между циклами выполнения актора. Эта статья описывает взаимодействие с другими потоками, собственные объекты ожидания и фоновую работу на основе контрактов из статей [Акторы на корутинах](coroutine-actors.md) и [Примитивы корутин](coroutine-primitives.md).

## Завершение из внешнего потока

Поддерживаются две модели. Выберите один путь завершения.

### Отправка акторного события

Это наиболее понятный вариант, если у потока ввода-вывода или обработки
завершений уже есть TActorSystem* и целевой ActorId:

```cpp
// Actor:
const ui64 cookie = ++NextCookie;
StartIo(SelfId(), cookie);
auto done = co_await ActorWaitForEvent<TEvIoDone>(cookie);

// Foreign thread:
actorSystem->Send(
    new IEventHandle(actorId, senderId, new TEvIoDone(status), 0, cookie));
```

Во внешнем потоке используйте TActorSystem::Send, а не IActor::Send,
SelfId().Send или TActivationContext::Send. Последним API нужен акторный
контекст в локальном хранилище потока (TLS). Событие завершения — обычное событие
почтового ящика; оно может прийти поздно, уже после отмены, поэтому StateFunc
должен допускать такой ответ.

Чтобы уведомить несколько ожидающих, отправьте из внешнего потока одно событие
через Send. В обработчике этого события обновите состояние актора и вызовите
continuation.Resume или TAsyncEvent::NotifyAll.

### Ожидание обычного awaitable-объекта C++

Объект ожидания без IsActorAwareAwaiter оборачивается в потокобезопасный
прокси-объект. При приостановке библиотека создаёт адаптер, содержащий актор,
ActorId, почтовый ящик и ActorSystem*. Внешняя операция получает дескриптор
корутины-адаптера, а не кадра актора.

При возобновлении этого дескриптора:

- в той же активации почтового ящика адаптер ставит действие в очередь выполнения;
- в остальных случаях, в том числе во внешнем потоке, адаптер использует
  ActorSystem::Send для отправки TEvResumeRunnable;
- код актора возобновляется только тогда, когда целевой почтовый ящик
  обрабатывает эту работу.

NThreading::TFuture — обычный awaitable-объект. Подключите
library/cpp/threading/future/core/coroutine_traits.h: одного future.h
недостаточно для operator co_await. Future может завершиться в другом потоке,
но акторную отмену он не поддерживает. Поэтому PassAway обычно ждёт завершения
future; future, который никогда не завершится, может навсегда задержать
уничтожение актора.

Обязанности обычного объекта ожидания:

- завершиться ровно один раз;
- для одного адаптера ровно один раз возобновить или уничтожить его; если
  протокол с поддержкой отмены предоставляет отдельные адаптеры нормального
  завершения и отмены, завершить ровно один из них и никогда не обращаться к обоим;
- не отправлять через Send второе пробуждение для того же ожидания;
- обеспечить последующее завершение или отмену, чтобы адаптеры не утекали;
- гарантировать, что захваченный TActorSystem ещё существует, когда позднее
  завершение из другого потока пытается поставить возобновление в очередь.

После принудительной очистки актора поздний TEvResumeRunnable обычно уничтожается
без обработки: ~TEvResumeRunnable вызывает Item->Run(nullptr), который не должен
возобновлять уничтоженный кадр актора. В момент отправки отправителю всё ещё
нужен живой TActorSystem. Остановите внешние источники завершений до уничтожения
акторной системы.

### Операции, локальные для актора

Следующие операции нельзя завершать или выполнять из внешнего потока:

- Resume, Throw, присваивание или уничтожение активного TAsyncContinuation;
- Notify или уничтожение TAsyncEvent с ожидающими;
- Cancel для TAsyncCancellationScope с активными приёмниками отмены;
- TActorRunnableQueue::Schedule;
- обращение к дескрипторам продолжения объектов ожидания, учитывающих акторный контекст;
- IActor::Send, SelfId().Send и API TActivationContext.

Помечайте собственный объект ожидания как IsActorAwareAwaiter, только если все
действия по возобновлению, отмене и уничтожению сериализованы в правильном
акторе и почтовом ящике. Если пометить так объект ожидания, который завершается
в другом потоке, он обойдёт адаптер и сможет запустить код актора в неверном
потоке.

## Собственный объект ожидания

Предпочитайте библиотечные примитивы. Если собственный объект ожидания всё же
необходим, сначала определите, какой контракт он реализует.

### Объект ожидания с поддержкой акторного контекста

Объявляйте IsActorAwareAwaiter = true только для пробуждения внутри актора.
Такой объект может использовать TActorRunnableQueue::Schedule во время Receive,
чтобы избежать рекурсивного возобновления. ActorWaitForEvent — исключение:
он возобновляет выполнение непосредственно внутри обработки события.

Для кооперативной отмены объект ожидания может реализовать:

- await_cancel(cancellationHandle), вызываемый во время активной приостановки;
- await_cancelled(cancellationHandle), необязательный метод для случая, когда
  отмена уже зафиксирована до приостановки.

await_cancel может вернуть void/false для отложенной отмены, true для
немедленной раскрутки кадра или дескриптор корутины, выполняющей отмену.
В итоге должен сработать ровно один путь: нормальное продолжение или
подтверждение отмены. Никогда не возобновляйте оба.

Если отмена уже зафиксирована, await_ready всё равно имеет приоритет, когда
возвращает true. Для неготового объекта ожидания с поддержкой отмены этот
случай обрабатывает await_cancelled. Если await_cancel существует, а
await_cancelled нет, библиотека пропускает обычный await_suspend и сразу
начинает раскрутку кадра. Объект ожидания без обоих методов отмены всё ещё
может приостановиться обычным образом.

Деструктор объекта ожидания должен удалить все внешние указатели на
продолжение: принудительное завершение может уничтожить кадр без нормального
завершения операции. Не уничтожайте дескриптор подтверждения акторной отмены;
возобновляйте его согласно протоколу.

### Обычный объект ожидания

Не объявляйте IsActorAwareAwaiter. await_suspend получает дескриптор адаптера,
который можно безопасно завершить из другого потока. Внешняя операция обязана
ровно один раз возобновить или уничтожить его. По возможности объект ожидания
всё же должен предоставлять работающий механизм отмены; иначе PassAway
останется в ожидании нормального завершения.

Проверьте как минимум следующие случаи:

- готовность без приостановки;
- нормальное отложенное завершение;
- отмена до приостановки и во время неё;
- гонка нормального завершения с отменой;
- исключение из await_ready/await_suspend/await_resume;
- вызов PassAway, пока актор ожидает;
- принудительное завершение акторной системы и последующее позднее внешнее завершение;
- отсутствие двойного возобновления и утечек адаптера или кадра.

## Типовые приёмы проектирования

### Множество одновременных запросов

Каждый входящий запрос имеет собственную корутину `Handle` верхнего уровня.
Несколько таких корутин могут одновременно ожидать, но выполняются они
по-прежнему по одной. Это обычная модель: не переносите незавершённые запросы
в написанный вручную автомат состояний без необходимости.

Если другое событие должно отменять конкретный запрос, храните отображение
идентификатора запроса в область отмены, подключённую к этому обработчику.
Следующий фрагмент отклоняет повторные активные идентификаторы ответом
`TEvBusy`, определённым в приложении. Отмена не освобождает идентификатор,
пока старый кадр действительно не завершит раскрутку.

```cpp
struct TInFlight {
    TAsyncCancellationScope Scope;
};
THashMap<ui64, TInFlight> InFlight;

void Handle(TEvRequest::TPtr ev) {
    const ui64 id = ev->Get()->RequestId;
    const TActorId replyTo = ev->Sender;
    const ui64 replyCookie = ev->Cookie;
    TString payload = std::move(ev->Get()->Payload);
    ev.Reset();

    if (auto it = InFlight.find(id); it != InFlight.end()) {
        Send(replyTo, new TEvBusy, 0, replyCookie);
        co_return;
    }

    auto& slot = InFlight[id];
    slot.Scope = co_await TAsyncCancellationScope::WithCurrentHandler();
    Y_DEFER { InFlight.erase(id); };

    const ui64 cookie = ++NextCookie; // actor member; fresh for every attempt
    Send(Backend, new TEvWork(std::move(payload)), 0, cookie);
    auto done = co_await ActorWaitForEvent<TEvWorkDone>(cookie);
    Send(replyTo, new TEvDone(done->Get()->Value), 0, replyCookie);
}

void Handle(TEvCancel::TPtr ev) {
    if (auto it = InFlight.find(ev->Get()->RequestId); it != InFlight.end()) {
        it->second.Scope.Cancel();
    }
}
```

Храните в кадре идентификаторы и владеющие значения, а не указатели на элементы
`InFlight`. После каждого ожидания заново находите элемент, если он ещё нужен.
Протокол замены может отменить старый запрос и дождаться явного уведомления о
завершении перед повторным использованием ключа. Никогда не перезаписывайте
его область сразу после `Cancel`: отложенная очистка может удалить состояние
замещающего запроса. Для каждой попытки используйте новый cookie протокола,
чтобы поздний старый ответ не завершил замещающий запрос. StateFunc должен
допускать ответы, ожидание которых уже закончилось.

### Один фоновый цикл на ключ

**Обработчик запроса** запускается, ожидает, отвечает и завершается.
**Фоновый цикл** — корутина `void`, которая не ожидает отдельный клиентский
запрос: она поддерживает подписку, повторные попытки, переподключение или
наблюдение за ресурсом до отмены.

«Ключ» — любой объект, для которого нельзя допустить дублирования: идентификатор
таблетки, удалённый ActorId или идентификатор потока данных. Если цикл для этого
ключа уже работает, не запускайте ещё один.

Здесь `Handle` — обычный обработчик, не корутина: в нём нет `co_await`, поэтому
он может принимать `TEv::TPtr&`. `WatchLoop` — акторная корутина **void**:
`co_await` в методе с возвращаемым типом `void` создаёт вторую задачу верхнего
уровня `TActorTask`. Вызов `WatchLoop(id)` запускает её до первой фактической
приостановки, после чего `Handle` возвращает управление. Именно это и требуется:
если бы `WatchLoop` возвращал `async<T>`, обработчику `Handle` пришлось бы
вызвать его через `co_await` и ждать всё время существования подписки.

Не пишите `co_await WatchLoop(id)`.

```cpp
struct TWatch {
    TAsyncCancellationScope Scope;
    ui32 Refs = 0;
};
THashMap<ui64, TWatch> Watches; // key = resource id

void Handle(TEvWatch::TPtr& ev) {          // sync handler: TPtr&
    const ui64 id = ev->Get()->Id;
    if (auto it = Watches.find(id); it != Watches.end() && !it->second.Refs) {
        // Application-defined reply: retry after the old loop has unwound.
        Send(ev->Sender, new TEvWatchRetry, 0, ev->Cookie);
        return;
    }
    auto& w = Watches[id];
    ++w.Refs;
    if (w.Refs == 1) {
        WatchLoop(id);                     // starts a sibling root task
    }
}

void Handle(TEvUnwatch::TPtr& ev) {         // sync handler
    auto it = Watches.find(ev->Get()->Id);
    if (it != Watches.end() && it->second.Refs && --it->second.Refs == 0) {
        it->second.Scope.Cancel();
    }
}

void WatchLoop(ui64 id) {                   // void + co_await => TActorTask
    Y_DEFER { Watches.erase(id); };
    auto it = Watches.find(id);
    Y_ABORT_UNLESS(it != Watches.end());
    it->second.Scope = co_await TAsyncCancellationScope::WithCurrentHandler();

    const ui64 cookie = ++NextCookie; // fresh for this subscription incarnation
    for (;;) {
        Send(Source, new TEvSubscribe(id), IEventHandle::FlagTrackDelivery, cookie);
        auto ev = co_await ActorWaitForEvent<IEventHandle>(cookie);
        ApplyUpdate(id, ev);               // re-find Watches[id] if needed
    }
}
```

`Y_DEFER` удаляет ключ при раскрутке кадра цикла. `Scope.Cancel()` из
`TEvUnwatch` служит сигналом остановки; пока отмена не завершилась, новые
запросы наблюдения должны повторяться позже. `ApplyUpdate` зависит от протокола:
он должен отличать обновления от `TEvUndelivered`, проверять отправителя и
реализовывать политику повторных попыток или выхода. Само по себе получение
уведомления о недоставке не отменяет корутину. Так устроен механизм разрешения
таблеток: один `TabletStateSubscriptionLoop` на подписавшийся актор,
запускаемый из `SubscribeTabletState`, только если записи в отображении ещё нет.

Не пишите `co_await WatchLoop(id)`: цикл `void` не является `async<T>`. Не
удерживайте указатель или итератор на элемент отображения через ожидание.

### Несколько задач с ограниченным временем жизни

Используйте WithTaskGroup, когда родитель не должен завершаться, пока все
дочерние задачи не завершатся нормально либо с раскруткой кадров. Не имитируйте
независимые дочерние задачи вызовом нескольких методов void: так создаются
несвязанные корневые задачи.

### API внешних обратных вызовов

- Если завершение callback гарантированно происходит в этом акторе,
  адаптируйте его с помощью WithAsyncContinuation.
- Если завершение возможно в другом потоке, отправляйте событие через Send
  или предоставьте обычный объект ожидания.
- Если одно завершение будит много ожидающих в акторе, отправьте одно событие
  через Send и уведомите их через продолжения или TAsyncEvent внутри StateFunc.
