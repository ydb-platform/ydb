# Примитивы корутин

Библиотека акторных корутин без собственного стека предоставляет ожидания, уведомления, сроки завершения, области отмены и группы задач. Их выполнение возобновляется в почтовом ящике актора-владельца. Этот справочник предполагает знакомство с правилами работы с кадрами и временем жизни из статьи [Акторы на корутинах](coroutine-actors.md). Завершение операций из другого потока описано в статье [Интеграция корутин](coroutine-integration.md).

## Выбор примитива ожидания

| Задача | Примитив |
|---|---|
| Дождаться одного ответа протокола с заданными типом и cookie | ActorWaitForEvent |
| Приостановиться, пока код этого же актора не вызовет Resume | WithAsyncContinuation |
| Разбудить одного или всех ожидающих в этом акторе, не сохраняя сигнал | TAsyncEvent |
| Дождаться заданного момента времени | AsyncSleepFor / AsyncSleepUntil |
| Однократно уступить выполнение, отправив собственное событие самому себе | AsyncYield / AsyncSleepFor(0) |
| Задать кооперативный срок завершения дочерней операции | WithTimeout / WithDeadline |
| Отменить часть работы | TAsyncCancellationScope |
| Структурированно запустить несколько задач и собрать их результаты | WithTaskGroup |
| Уступать выполнение из множества задач без переполнения почтового ящика событиями | TAsyncLowPriorityQueue |
| Завершить операцию из внешнего потока | Адаптер обычного awaitable-объекта либо ActorSystem::Send вместе с ActorWaitForEvent |

## ActorWaitForEvent

```cpp
const ui64 cookie = ++NextCookie;
Send(peer, new TEvRequest, 0, cookie);
auto ev = co_await ActorWaitForEvent<TEvReply>(cookie);
```

Контракт:

- сопоставляет GetTypeRewrite и Cookie; Sender не проверяется;
- `ActorWaitForEvent<IEventHandle>` принимает любое несистемное пользовательское
  событие с этим cookie;
- сопоставление происходит до StateFunc и передаёт ожидающей корутине весь
  дескриптор события;
- выполнение возобновляется непосредственно внутри Receive, принявшего событие;
- отмена или уничтожение снимает регистрацию ожидания;
- событие с другим типом или cookie передаётся другим ожидающим, а затем в StateFunc.

Cookie должен быть уникален среди всех активных ожиданий, которые могут принять
один и тот же тип ответа. По умолчанию Send использует cookie 0; не оставляйте
несколько одновременных ожиданий с cookie 0. Если тип и cookie совпадают у
нескольких ожидающих, событие разбудит первого зарегистрированного из них;
такой код не выражает однозначного намерения.

Отправлять запрос непосредственно перед ожиданием безопасно в пределах одного
цикла выполнения актора: почтовый ящик не сможет обработать ответ, пока этот код не приостановится.
Ответ, который уже был обработан до запускающего события, восстановить нельзя.

После отмены или тайм-аута поздний ответ больше не перехватывается и попадает в
StateFunc. Актор с STRICT_STFUNC должен явно обрабатывать или игнорировать типы
устаревших ответов. Проверки поколения по-прежнему нужны, поскольку cookie со
временем может использоваться повторно.

## AsyncSleep и AsyncYield

```cpp
co_await AsyncYield();
co_await AsyncSleepFor(TDuration::MilliSeconds(10));
co_await AsyncSleepUntil(monotonicDeadline);
```

- Sleep всегда приостанавливает выполнение.
- Нулевая длительность отправляет самому актору TEvResumeRunnable, поэтому
  выполнение возобновится при обработке более позднего события почтового ящика.
  AsyncYield — это такое ожидание нулевой длительности.
- Бесконечная длительность или срок не планирует событие и ждёт только отмены
  либо принудительного уничтожения.
- Конечное ненулевое ожидание использует событие планировщика и объект-адаптер
  со счётчиком ссылок.
- Отмена деактивирует адаптер, но не может удалить элемент планировщика;
  отменённое длительное ожидание удерживает небольшой объём выделенной памяти
  до истечения срока или завершения работы системы.

Для сроков, отсчитываемых по прошедшему времени, предпочитайте TMonotonic.
Sleep учитывает акторный контекст и должен запускаться из акторной корутины.

## WithAsyncContinuation

Используйте этот примитив, когда корутина должна дождаться работы, которую уже
выполняет **этот же актор**, но её завершение нельзя перехватить как событие
почтового ящика: `Execute`/`Complete` транзакции таблетки, список ожидающих,
который заполняет последующий `Handle`, или кеш, вызывающий обработчик после
заполнения. Вы сохраняете `TAsyncContinuation<T>`, а в одном из последующих
циклов выполнения **этого же** актора вызываете `Resume`.

**Не** используйте его для следующих задач:

- ответ другого актора — для этого есть `ActorWaitForEvent`, поскольку само
  событие и есть сигнал пробуждения;
- несколько ожидающих изменения флага без возвращаемого значения — для этого
  есть `TAsyncEvent`;
- завершение в другом потоке — отправьте событие через `Send` или используйте
  `co_await` с обычным `TFuture`. `Resume` не является потокобезопасным.

Лямбда настройки выполняется синхронно внутри `await_suspend`. Она должна
только принять продолжение и подключить его к существующему механизму обратного
вызова. Пример по образцу рабочего кода DataShard для ожидания блокировки строк
или идентификатора транзакции:

```cpp
void Handle(TEvNeedTx::TPtr ev) {
    const TActorId replyTo = ev->Sender;
    const ui64 replyCookie = ev->Cookie;
    ev.Reset();

    ui64 txId = co_await WaitForTxId();
    Send(replyTo, new TEvTxId(txId), 0, replyCookie);
}

async<ui64> WaitForTxId() {
    if (!TxIdCache.empty()) {
        ui64 id = TxIdCache.back();
        TxIdCache.pop_back();
        co_return id;
    }
    co_return co_await WithAsyncContinuation<ui64>(
        [this](TAsyncContinuation<ui64> c) {
            TxIdWaiters.push_back(std::move(c));
            // This example's allocator returns one ID per request, so each
            // cache miss needs its own allocation request.
            Send(TxAllocator, new TEvAllocateTxId);
        });
}

void Handle(TEvAllocateTxIdResult::TPtr ev) {
    ui64 txId = ev->Get()->TxId;
    // Still this actor. Resume parked waiters; check bool after cancel.
    while (!TxIdWaiters.empty()) {
        auto c = std::move(TxIdWaiters.front());
        TxIdWaiters.pop_front();
        if (c) {
            c.Resume(txId);
            return;
        }
    }
    TxIdCache.push_back(txId);
}
```

`TTxLockRows` использует тот же подход без пользовательского события:
запускается транзакция, которая хранит `TAsyncContinuation<void>` и вызывает
`Resume()` из `Execute` или `Complete`.

Продолжение можно только перемещать, а завершить — только один раз:

- `Resume(value)` завершает ожидание нормально; для типа `void` используется
  `Resume()`;
- `Throw(exception_ptr)` заставляет `await_resume` выбросить исключение;
- уничтожение активного продолжения или присваивание поверх него завершает
  ожидание с `logic_error("continuation object was destroyed")`;
- `Resume`/`Throw` для пустого продолжения выбрасывает `logic_error`.

Вызов `Resume` внутри лямбды настройки завершает ожидание без приостановки.
Последующий `Resume`/`Throw` или уничтожение ставит действие в очередь выполнения;
ожидающая корутина не запускается рекурсивно до возврата из `Resume`.

Если ожидающую корутину отменяют, сохранённое продолжение отсоединяется и
преобразуется в false. Проверяйте его перед последующим завершением. Все операции
с активным продолжением, включая уничтожение, требуют очереди выполнения
этого актора.

## TAsyncEvent

TAsyncEvent — локальная для актора очередь уведомлений, которая не сохраняет
сигнал при отсутствии ожидающих:

```cpp
bool notified = co_await Changed.Wait();
Changed.NotifyOne();
Changed.NotifyAll();
```

- NotifyOne будит ожидающего, который первым встал в очередь; NotifyAll будит
  всех, кто ожидает в данный момент.
- Notify при отсутствии ожидающих теряется. Событие не запоминает сигнал и
  не хранит счётчик.
- При уведомлении Wait возвращает true.
- Уничтожение события отсоединяет текущих ожидающих, и они возвращают false;
  это нормальное завершение, а не отмена.
- Отмена ожидающего, пока он ещё в очереди, удаляет его из очереди и запускает
  раскрутку его кадра вместо возврата false.
- Когда действие уведомления или отсоединения уже поставлено в очередь
  выполнения, последующая отмена обычно не срабатывает и Wait завершается нормально.

Notify и уничтожение события с ожидающими требуют активации актора-владельца.
Не используйте один TAsyncEvent в несвязанных акторах или почтовых ящиках и не
обращайтесь к нему из внешнего потока.

Wait(callback) сначала регистрирует объект ожидания, а затем синхронно вызывает
callback. Это удобно для счётчиков и логики запуска: между регистрацией и
вызовом callback уведомление не потеряется.

## WithTimeout и WithDeadline

```cpp
bool completed = co_await WithTimeout(
    TDuration::Seconds(1),
    DoVoidWork());

std::optional<int> value = co_await WithDeadline(
    deadline,
    DoValueWork());
```

Для дочерней операции `async<void>` результат имеет тип bool, для `async<T>` —
`optional<T>`. true или значение означает нормальное завершение. false/nullopt
означает, что отмена по тайм-ауту была подтверждена.

Последовательность обработки срока:

1. запустить таймер и ленивую дочернюю операцию;
2. если таймер сработал первым, запросить отмену дочерней операции;
3. дождаться подтверждения раскрутки её кадра;
4. только после этого вернуть false/nullopt.

Поэтому срок не задаёт жёсткую границу по реальному времени:

- объект ожидания дочерней операции, не поддерживающий отмену, может отложить
  возврат навсегда;
- после запроса отмены дочерняя операция может завершиться нормально — тогда
  возвращается её успешный результат;
- немедленно готовая операция может завершиться раньше нулевого тайм-аута;
- отмена вызывающей корутины, в том числе при PassAway, распространяется
  дальше как отмена и не приводит к возврату false;
- бесконечный тайм-аут не добавляет обёртку.

Гарантированно удалить запланированный таймер нельзя, поэтому деактивированный
длительный тайм-аут удерживает небольшой объект-адаптер до истечения срока или
завершения работы системы. Если внешний эффект операции может пережить локальный
тайм-аут, задайте в протоколе правила проверки поколения и идемпотентности.

WithTimeout/WithDeadline вместе с их callback или аргументом async должны
оставаться непосредственным операндом одного и того же co_await.

## Области отмены

TAsyncCancellationScope отменяет выбранные дочерние операции независимо от
корневой отмены актора.

**Его деструктор не отменяет работу.** Вызывайте Cancel явно. Область запоминает
отмену; повторный Cancel идемпотентен. Приёмник отмены (sink), подключённый после
отмены, отменяется сразу. Cancel и операции с активными приёмниками выполняются
локально в акторе.

### Wrap

```cpp
TAsyncCancellationScope Scope; // actor member; outlives wrapped work

void Handle(TEvStart::TPtr ev) {
    bool completed = co_await Scope.Wrap([this]() -> async<void> {
        co_await WaitForWork();
    });
    // Inspect completed here if this handler itself was not cancelled.
}

void Handle(TEvCancel::TPtr& ev) {
    Scope.Cancel(); // another turn can run while the first handler waits
}
```

`Wrap<void>` возвращает bool, а `Wrap<T>` — `optional<T>`. false/nullopt
означает, что отмена области подтверждена. Нормальное завершение может опередить
запрос отмены — тогда возвращается успех. Отмена вызывающей корутины или
корневой задачи обычно раскручивает кадр за пределы Wrap вместо возврата false.

Уже отменённая область всё равно запускает ленивое тело. Его синхронная
начальная часть может выполниться, после чего корутина должна начать раскрутку
кадра при первой приостановке, поддерживающей отмену.

### Подключение всего корневого обработчика

Допустимо только внутри обработчика верхнего уровня с возвращаемым типом void:

```cpp
Request.Scope =
    co_await TAsyncCancellationScope::WithCurrentHandler();
```

Возвращённая область содержит этот корневой обработчик как приёмник отмены.
Последующий Request.Scope.Cancel() запрашивает отмену всего обработчика.
Используйте вызов непосредственно в корневом обработчике: он опирается на
специальный await_transform его объекта promise.

Это удобно для запросов с ключами, которыми владеет актор: храните область рядом
с состоянием запроса, отменяйте её при дубликате или явной отмене и используйте
RAII-объект для удаления состояния и уведомления о завершении. Поскольку отмена
отложенная, перед повторным использованием ключа замещающему запросу может
потребоваться дождаться явного уведомления через Finished TAsyncEvent.

### WrapShielded и InterceptCancellation

WrapShielded не пропускает отмену вызывающей корутины в обёрнутую дочернюю
операцию до её завершения. Он не сбрасывает уже зафиксированную отмену
вызывающей корутины, а явный scope.Cancel по-прежнему отменяет дочернюю операцию.
Такая защита может отложить PassAway навсегда; используйте её только для очистки,
которая действительно обязана завершиться.

InterceptCancellation(body, onCancel) — низкоуровневый механизм очистки,
которую нужно выполнить при отмене вызывающей корутины. onCancel может вернуть:

- void или true, чтобы распространить отмену;
- false, чтобы отклонить её распространение;
- `async<void>` или `async<bool>`, чтобы дождаться обработки отмены.

Исключение из onCancel выбрасывается повторно после внутренней очистки.
Предпочитайте обычный RAII, если не требуется асинхронная обработка отмены или
возможность отклонить её.

## Группы задач

WithTaskGroup предоставляет структурированный кооперативный запуск нескольких
задач. Дочерние задачи — это кадры `async<T>` в том же акторе, а не потоки.

```cpp
int total = co_await WithTaskGroup<int>(
    [&](TTaskGroup<int>& group) -> async<int> {
        group.Add([this]() -> async<int> {
            co_return co_await Fetch(1);
        });
        group.Add([this]() -> async<int> {
            co_return co_await Fetch(2);
        });

        int sum = 0;
        while (group.Running() || group.Ready()) {
            sum += co_await group.Next();
        }
        co_return sum;
    });
```

Семантика и особые случаи:

- Add возвращает монотонно назначаемый индекс дочерней задачи.
- Add хранит копии callback и аргументов после преобразования decay и планирует
  запуск через очередь выполнения; callback не вызывается рекурсивно.
- Если тело группы возвращает управление до запуска запланированной дочерней
  задачи, её callback может вообще не выполниться.
- Результаты попадают в очередь в порядке завершения.
- Next забирает значение и повторно выбрасывает исключение дочерней задачи.
- NextResult возвращает `TTaskGroupResult<T>` с GetIndex и значением либо
  исключением; используйте HasValue/HasException и ExtractValue/ExtractException.
- WhenReady ожидает результат, не забирая его.
- У группы может быть только один ожидающий. Ожидание при отсутствии готовых
  результатов и незавершённых задач выбрасывает исключение.
- operator bool и Running учитывают только незавершённые задачи. Готовые,
  но ещё не забранные результаты не учитываются, поэтому для полного сбора
  результатов проверяйте Running() || Ready().

Когда тело группы возвращает управление, выбрасывает исключение или подтверждает
отмену, обёртка отменяет все незавершённые дочерние задачи. Она возвращает
управление внешней вызывающей корутине только после завершения их кооперативной
раскрутки. Дочерние задачи не продолжают работу отдельно от группы.

Особенность RAII: автоматические локальные переменные корутины тела группы
уничтожаются при выходе из этого тела, до того как обработка final-suspend
начнёт отменять оставшиеся дочерние задачи. Дочерняя задача не должна заимствовать
эти переменные, если тело может завершиться раньше неё. Сначала дождитесь таких
задач либо захватывайте владеющее состояние, время жизни которого охватывает
внешнее ожидание WithTaskGroup.

При отмене актора тело группы должно сначала раскрутить свой кадр или вернуть
управление, и только затем группа начнёт отменять дочерние задачи. Ожидание без
поддержки отмены в теле группы или дочерней задаче может задержать выход из
группы и уничтожение актора.

## TAsyncLowPriorityQueue

Используйте этот примитив, когда корутинам нужно **дать почтовому ящику обработать
другие события**, чтобы продолжать обслуживать клиентов, но не отправлять
отдельный `TEvResumeRunnable` от каждого ожидающего.

`AsyncYield` / `AsyncSleepFor(0)` отправляет по одному событию самому актору на
каждого ожидающего. Пятьдесят обработчиков, одновременно уступающих выполнение,
поставят в очередь пятьдесят событий; одна активация может обработать их пачкой
и задержать входящую работу до конца кванта.

`TAsyncLowPriorityQueue` — общий член актора: одновременно в пути находится
не более одного события возобновления. `co_await Idle.Next()` приостанавливает
корутину до **следующего цикла почтового ящика**, а затем возобновляет
**одного** ожидающего. Обрабатывая это событие возобновления, очередь сразу
отправляет следующее. Оно будет обработано в более позднем цикле после
пользовательских событий, уже стоящих в очереди. Ожидающие, которые присоединились
после отправки текущего события, попадают в следующее поколение и не могут
возобновиться в текущем цикле, даже если исходный ожидающий был отменён.

Типичный сценарий — разбить ресурсоёмкую работу на элементы, уступать выполнение
после каждого из них и использовать одну очередь для нескольких обработчиков:

```cpp
TAsyncLowPriorityQueue Idle; // actor member, one per actor

void Handle(TEvCompact::TPtr ev) {
    TVector<TKey> keys = std::move(ev->Get()->Keys);
    ev.Reset();
    co_await CompactKeys(std::move(keys));
}

async<void> CompactKeys(TVector<TKey> keys) {
    for (const TKey& key : keys) {
        CompactOne(key);     // keep this bounded
        co_await Idle.Next(); // other Handles run before the next key
    }
}

void Handle(TEvClient::TPtr ev) {
    // still served between CompactOne slices
    Send(ev->Sender, new TEvClientAck, 0, ev->Cookie);
}
```

Одного `co_await AsyncYield()` достаточно, если уступить выполнение нужно
только одному кадру и общая политика не важна.

Все ожидающие должны принадлежать одному актору. Очередь должна жить дольше них;
её уничтожение при наличии ожидающих аварийно завершает процесс. Отмена
отсоединяет ожидающего и может деактивировать либо повторно использовать
отправленное самому актору событие.
