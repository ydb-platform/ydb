# События и обмен сообщениями

Сообщение актора состоит из полезной нагрузки, которой оно владеет, и конверта со сведениями для маршрутизации и сопоставления запросов с ответами. Эта страница объясняет локальную и удалённую доставку, пересылку, таймеры и время жизни полезной нагрузки. Инварианты почтового ящика описаны в [руководстве по акторной системе](index.md), а освобождение ресурсов — в разделе [«Сбои и завершение работы»](failure-and-shutdown.md).

## События и конверты

IEventHandle содержит:

- исходные и переписанные тип и получателя;
- ActorId отправителя Sender и получателя Recipient;
- 64-битный Cookie;
- флаги и 12-битный номер канала Interconnect;
- внутрипроцессный IEventBase или сериализованные данные;
- трассировку и, для принятых удалённых событий, ActorId сессии InterconnectSession.

Среда выполнения не интерпретирует Cookie, кроме случаев, когда отдельный
вспомогательный механизм документирует иное. Распространённое соглашение
запрос/ответ — копировать ev->Cookie в ответ, но это часть протокола, а не
автоматическое поведение. Аргумент cookie у Send по умолчанию равен 0.
Считайте 0 источником коллизий, если несколько незавершённых ожиданий могут
использовать один тип: ActorWaitForEvent и уведомления TrackDelivery
сопоставляются по cookie, поэтому каждому активному ожиданию назначайте
уникальное ненулевое значение.

Номера типов событий разделены на пространства по 65 536 значений. Для
протокола компонента выделяйте уникальный диапазон в соответствующем
назначенном пространстве событий. TEvents::ES_PRIVATE намеренно повторно
используется приватными и локальными протоколами акторов и тестами; оно не
уникально глобально, поэтому значения, способные попасть в один диспетчер,
всё равно должны быть однозначными.

### Классы полезной нагрузки

- `TEventLocal<T, Type>` — внутрипроцессная полезная нагрузка C++, которая не сериализуется.
- `TEventPB<T, Proto, Type>` — обычное сетевое событие на основе protobuf.
  Бинарные блобы, которым не место в protobuf, передаются рядом с ним:
  AddPayload(TRope) возвращает индекс; сохраните его в proto; получатель
  читает GetPayload(i) / GetPayloadCount(). Не помещайте TRcBuf в поля bytes
  protobuf, если нужна передача без копирования. Сетевое кодирование — деталь
  реализации: сейчас это маркер 0x06, размеры полезной нагрузки, блобы, затем
  proto; 0x07 — устаревшая схема, поддерживаемая только при разборе.
- `TEventSimpleNonLocal<T, Type>` сериализуется, но не передаёт поля производного
  класса. Добавление полей в производный класс не включает их в сетевое
  представление. TEvPoison использует этот класс и может отправляться на другой узел.
- API событий Flat/rope предназначены для специализированных форматов без копирования.

Не отправляйте локальное событие на другой узел по ошибке. Максимальный
размер сериализованного события Interconnect по умолчанию — 140 МиБ с учётом
накладных расходов сериализации; конфигурация может изменить или уменьшить
этот предел. Слишком большое сетевое событие завершает всю сессию, а не просто
отбрасывается само. Для больших данных предпочитайте протоколы с разбиением
на части или блобовые протоколы.

### Флаги отправки

Чаще всего нужны следующие младшие биты:

| Флаг | Контракт |
|---|---|
| FlagTrackDelivery | Запрашивает у маршрутизации уведомления о поддерживаемых случаях недоставки. Это не подтверждение доставки. |
| FlagForwardOnNondelivery | При локальной недоставке направляет событие получателю пересылки из конверта; для специальных сценариев. |
| FlagSubscribeOnSession | При удалённой отправке подписывает Sender на текущий экземпляр сессии. |
| FlagGenerateUnsureUndelivered | Вместе с FlagTrackDelivery также сообщает о событиях Interconnect с неопределённым результатом доставки, устанавливая Unsure; сам по себе не действует. |
| FlagDebugTrackReceive | Средство для отладки. |
| FlagDisablePayloadChecksums | Специальная настройка компромисса для IC/XDC/RDMA; не используйте без необходимости. |

Верхние 12 бит флагов кодируют канал Interconnect через
IEventHandle::MakeFlags. FlagExtendedFormat — метаданные сериализации среды
выполнения, а не прикладной флаг. FlagSystemMessage также не является
прикладным флагом: Receive поглощает любое событие с этим битом до StateFunc
и до ActorWaitForEvent. Места отправки в библиотеке передают
TEvResumeRunnable::EventFlags или TEvCheckActorLiveness::RequestFlags;
конструктор конверта не выводит этот бит из типа события C++. Если установить
его на собственном событии, полезная нагрузка будет проигнорирована.
В текущем дереве исходного кода FlagFailFastWhenDisconnected и
FlagUseSubChannel не предоставляют пригодного прикладного контракта;
не стройте на них протокол.

FlagForwardOnNondelivery имеет приоритет над TrackDelivery: он передаёт
исходную полезную нагрузку настроенному резервному получателю вместо
создания TEvUndelivered. Сформированное TEvUndelivered содержит исходные
тип и cookie, а Sender его конверта — получатель, которому не удалось
доставить событие. Само это уведомление также может оказаться недоставленным.

## Отправка, пересылка и планирование

Внутри активации:

```cpp
Send(recipient, new TEvRequest("x"), flags, cookie);
SelfId().Send(recipient, new TEvRequest("x"), flags, cookie);
TActivationContext::Send(
    new IEventHandle(recipient, SelfId(), new TEvRequest("x"),
                     flags, cookie));
```

Вне выполнения актора:

```cpp
actorSystem->Send(
    new IEventHandle(recipient, sender, new TEvRequest("x"),
                     flags, cookie));
```

Не используйте API Send, зависящие от TLS, из произвольных потоков. Если
вызывающей стороне вне актора нужен результат, ActorSystem::Ask создаёт
временный ожидающий актор и возвращает future. Используйте конечный тайм-аут:
по умолчанию он может быть бесконечным. Ask принимает первое полученное
событие, каким бы оно ни было: совпадающий тип или отсутствие ограничения
на тип приводит к успешному завершению future, любой другой тип — к
исключению. Ask не проверяет подлинность Sender и не продолжает ждать после
постороннего события, поэтому там, где это существенно, используйте
выделенный адрес или дополнительное сопоставление на уровне протокола.

Сокращённая перегрузка ActorSystem::Send(recipient, event) использует
синтетический сервисный идентификатор акторной системы в качестве Sender.
Этот адрес не предназначен для ответов.

Forward переносит полезную нагрузку в новый конверт, адресованный новому
получателю. Он сохраняет основные сведения об отправителе, флагах и cookie,
но не все поля происхождения, сессии, переписывания и недоставки. Если
протоколу нужен явный контракт конверта, создание нового события понятнее.

### Отправка Common, Lazy и Tail

Common обычным образом активирует неработающий почтовый ящик получателя.
Lazy и Tail — локальные оптимизации планирования:

- Lazy может позволить текущему рабочему потоку захватить неработающий
  почтовый ящик получателя и отложить его активацию до завершения обработки
  текущего ящика. Это может улучшить локальность, но добавить задержку за
  долгой текущей активацией;
- Tail завершает обработку текущего почтового ящика после этого события
  и передаёт оставшийся квант захваченному получателю, если исполнитель
  может это сделать.

Если оптимизация недоступна, например из стороннего потока или при
неподходящем соотношении пулов, используется обычная отправка. Эти режимы
не меняют семантику доставки, владения или порядка; применяйте их только
после измерений.

### Таймеры

```cpp
Schedule(TDuration::Seconds(1), new TEvWakeup);
Schedule(deadlineMonotonic, new TEvWakeup);
```

Удобная перегрузка IActor создаёт конверт, адресованный самому актору,
с пустым Sender и нулевым Cookie события. Если нужен логический
идентификатор таймера, передавайте его в полезной нагрузке или явно
создайте IEventHandle.

ISchedulerCookie координирует отмену в планировщике и не является
IEventHandle::Cookie. Сразу при планировании используйте двусторонний
держатель cookie. Его отсоединение может предотвратить доставку только
в том случае, если выиграет гонку с планировщиком; после передачи события
в почтовый ящик оно всё ещё может прийти. Таймеры не удаляются автоматически
при смерти актора, а их полезная нагрузка не продлевает его жизнь.
Делайте обработчики таймеров идемпотентными и проверяйте поколение или
монотонный срок. Для логики прошедшего времени предпочитайте
TMonotonic/TDuration: системные часы могут скачкообразно изменяться.

### Проверка существования актора

SendActorLivenessCheck — локальная проверка маршрутизации. Живой локальный
ActorId даёт TEvActorAlive, а неизвестный локальный ActorId — TEvActorDead.
Удалённая цель даёт TEvActorLivenessUnsure; это не распределённая проверка
работоспособности, и она ничего не говорит о продвижении прикладной работы.

## Локальная доставка

Для обычного локального Send:

- если ActorId зарегистрирован в почтовом ящике, конверт ставится в очередь;
- если он неизвестен или уже отсоединён, событие уничтожается;
- с FlagTrackDelivery поддерживаемая локальная недоставка создаёт
  TEvUndelivered с ReasonActorUnknown.

После принятия события в Receive задача TrackDelivery выполнена.
Он не сообщает о том, что обработчик выбросил исключение, проигнорировал
событие, завершил работу до ответа или не выполнил прикладную операцию.

Poison — обычное событие. События, уже стоящие перед ним, выполнятся первыми.
События за ним не исчезают автоматически: после немедленного отсоединения
актора они отбрасываются как адресованные неизвестному получателю, но если
PassAway ждёт задачи корутин, они могут дойти до StateFunc завершающегося
актора. Конкурирующий Send после постановки Poison в очередь всё ещё
успешен; позднее событие просто оказывается за Poison в порядке FIFO.

## Interconnect

Отправка на ActorId с другим NodeId маршрутизируется через прокси
Interconnect этого узла. Через эту границу могут проходить только
сериализуемые события. Трафик разделён на каналы; общего прикладного
порядка между каналами нет.

Контракт сбоев, на который безопасно опираться:

- экземпляр сессии может установить соединение и позднее завершиться;
- часть сообщений могла быть доставлена, тогда как результат других
  незавершённых передач остаётся неопределённым;
- классические сессии могут продолжаться после некоторых переподключений
  TCP, тогда как IC v2 намеренно не поддерживает такое продолжение;
- заменяющая сессия задаёт новую границу порядка и подписок.

Поэтому прикладным протоколам всё равно нужны тайм-ауты ответов,
устойчивость к дубликатам или идемпотентность и восстановление после
смены сессии.

### TrackDelivery через Interconnect

При сбое классической сессии:

- отслеживаемое событие, ещё находящееся в неотправленной Queue канала,
  получает определённое уведомление TEvUndelivered;
- сериализованное, но ещё не подтверждённое событие получает
  TEvUndelivered только при установленном вместе с FlagTrackDelivery
  флаге FlagGenerateUnsureUndelivered; уведомление содержит Unsure=true,
  поскольку получатель мог уже принять событие;
- без флага unsure события с неопределённым результатом могут не породить
  уведомления;
- IC v2 даёт ещё меньше гарантий: отслеживаемые события, уже переданные
  его движку, при завершении могут быть отброшены вообще без уведомления.

Эти уведомления о сбое сессии создаются локально на узле отправителя.
Только обратное уведомление ReasonActorUnknown от удалённого узла
пересекает сеть и само может потеряться; уведомления Unsure локальны
и не сериализуются. Это полезная диагностика и быстрое оповещение
об ошибках, а не протокол «ровно один раз».

### Подписка на сессию

FlagSubscribeOnSession в удалённом событии подписывает его Sender на
этот экземпляр сессии. TEvNodeConnected указывает установленную сессию;
TEvNodeDisconnected означает, что **эта сессия завершилась**, а не обязательно
что узел недоступен. Исправная неиспользуемая сессия может закрыться.
Более позднее соединение — другой экземпляр.

Явно отправляйте TEvUnsubscribe, когда связь больше не нужна. Текущая среда
выполнения также периодически проверяет существование умерших локальных
подписчиков, но ожидание такой медленной проверки излишне удерживает
состояние сессии. Сессия хранит одну подписку на ActorId отправителя;
более поздние сведения о подписке этого отправителя могут заменить
предыдущую запись.

Если на запрос нужно ответить именно через ту сессию, которая его
доставила, используйте ev->InterconnectSession:

```cpp
auto reply = MakeHolder<IEventHandle>(
    ev->Sender, SelfId(), new TEvResponse("ok"), 0, ev->Cookie);
if (ev->InterconnectSession) {
    reply->Rewrite(TEvInterconnect::EvForward, ev->InterconnectSession);
}
TActivationContext::Send(reply.Release());
```

Это не позволяет ответу незаметно перейти на заменяющую сессию.
Но такой приём не делает доставку устойчивой к потере сессии.

## Время жизни данных и большие буферы

TRope и API событий с разделяемыми буферами позволяют дёшево создавать
срезы и передавать владение. Используйте их, если тип события это
поддерживает; не собирайте данные в непрерывный буфер только ради отправки.
При этом сохранение конверта события или rope на время долгого ожидания
удерживает все лежащие в его основе блоки памяти. Извлекайте небольшие поля
и освобождайте большие полезные нагрузки как можно раньше.

Никогда не сохраняйте сырой указатель, возвращённый ev->Get, после
уничтожения конверта, пересылки, передачи владения или ленивого
преобразования из сериализованного представления.
