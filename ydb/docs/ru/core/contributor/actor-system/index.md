# Руководство по акторной системе

Акторная система NActors выполняет C++-объекты, доставляя сообщения в их почтовые ящики (mailbox). Это руководство описывает контракты, на которых строится реализация акторов во всех компонентах {{ ydb-short-name }}, включая таблетки. Персистентное хранение данных таблеток, транзакции и восстановление добавляют к этим акторным контрактам правила конкретного компонента.

## Основные понятия

| Объект | Значение |
|---|---|
| Актор | C++-объект, унаследованный от IActor, с собственным состоянием и одной текущей функцией StateFunc. |
| ActorId | Адрес, назначаемый актору при регистрации. |
| Событие | Полезная нагрузка IEventBase, которой владеет оболочка IEventHandle. |
| Почтовый ящик (mailbox) | Очередь событий с несколькими отправителями, обеспечивающая последовательное выполнение прикреплённых к ней акторов. |
| Пул исполнителей (executor pool) | Ресурсы процессора и механизм планирования для выполнения активаций почтовых ящиков. |
| Активация | Запрос рабочему потоку обработать часть очереди почтового ящика. |
| ServiceId | Стабильное локальное имя, сопоставленное с текущим ActorId. |
| Сессия Interconnect | Один экземпляр соединения между двумя узлами. |

Один цикл обработки события устроен так:

1. Отправитель передаёт оболочку события акторной системе.
2. Акторная система активирует почтовый ящик получателя.
3. Один рабочий поток находит актор-получатель и вызывает IActor::Receive.
4. Receive выбирает обработчик в следующем порядке:
   - если установлен FlagSystemMessage, используется внутренняя диспетчеризация среды выполнения (TEvResumeRunnable,
     TEvCheckActorLiveness); любой другой тип с этим флагом игнорируется и никогда
     не попадает в пользовательский код;
   - иначе, если ожидающий ActorWaitForEvent корутины без собственного стека соответствует cookie и типу события,
     он получает это событие;
   - иначе вызывается текущая StateFunc.
5. Затем деструктор TActorRunnableQueue в Receive выполняет задачи (runnables), запланированные
   в течение этого цикла, без дополнительного события в почтовом ящике. Только после этого почтовый ящик может
   обработать следующее событие. TEvResumeRunnable используется для возобновления через отдельное событие
   в почтовом ящике, если возобновление происходит не в рамках текущей активации.

## Инварианты, которые нужно учитывать при проектировании

1. **Почтовый ящик выполняется последовательно.** Два обработчика, прикреплённые к одному
   почтовому ящику, никогда не выполняются одновременно. В разное время этот ящик могут
   обслуживать разные рабочие потоки. Акторы в разных почтовых ящиках могут выполняться параллельно.

2. **Последовательное выполнение не задаёт глобальный порядок.** Почтовый ящик обрабатывает события
   в порядке своей очереди, но для конкурирующих отправок от разных источников нет полезной гарантии
   взаимного порядка. Не выводите причинно-следственные связи из сообщений независимых отправителей.
   Каналы Interconnect и смена сессий создают дополнительные границы гарантий порядка.

3. **Планирование кооперативное.** Выполняющийся обработчик не вытесняется по истечении
   кванта исполнителя. Проверка кванта происходит между событиями. Долгий или блокирующий
   обработчик занимает один рабочий поток и задерживает все акторы в своём почтовом ящике;
   достаточное число таких обработчиков исчерпывает ресурсы пула. В обработчиках System/User нельзя
   вызывать блокирующий sleep, ожидать в цикле, ждать future, выполнять медленный синхронный ввод-вывод
   или удерживать блокировку, за которую конкурируют потоки.
   Блокирующую работу следует передавать диспетчеру ввода-вывода или актору в пуле IO (см. раздел о пулах).

4. **Собственное состояние актора обычно не требует блокировки.** Изменяйте его только
   во время выполнения этого актора. Общая память безопасна лишь при явно продуманных времени жизни
   и синхронизации; типичный случай совместного использования без блокировок — акторы в одном
   почтовом ящике. Мьютекс не устраняет вред от блокировки рабочего потока исполнителя.

5. **Контекст активации ограничен текущим циклом обработки.** TlsActivationContext, IActor::Send,
   SelfId().Send, методы TActivationContext и большинство асинхронных примитивов с привязкой к актору
   допустимы только во время выполнения акторного кода. Никогда не сохраняйте TActorContext
   после возврата из обработчика или через co_await: он содержит ссылки на рабочий поток
   и почтовый ящик конкретной активации. Поток вне акторной системы должен использовать
   указатель TActorSystem.

6. **Отправка передаёт владение.** После Send, Schedule, Register или Forward считайте
   переданный указатель или оболочку использованными, в том числе при булевом результате false.
   В обработчике ev владеет полезной нагрузкой; указатель, возвращённый ev->Get,
   действителен только пока эта оболочка сохраняет владение. Скопируйте данные, которые нужны
   после текущего цикла, либо явно передайте владение через перемещение, Release или Forward.

7. **Доставка не означает обработку или успех.** Успешный Send означает, что сообщение принято
   для маршрутизации, а не обработано. Даже TEvUndelivered описывает лишь некоторые виды недоставки
   и не доказывает, была ли выполнена прикладная операция.
   Протоколы, которым нужен определённый результат, используют запрос и ответ, срок ожидания
   и, как правило, ключ идемпотентности.

8. **Завершение актора явно и однократно.** Зарегистрированным актором владеет среда выполнения.
   Он вызывает PassAway ровно один раз; никто не удаляет его напрямую.
   PassAway может отложить отсоединение актора, пока отменяются корутины верхнего уровня
   без собственного стека. В этот промежуток последующие события ещё могут попадать в StateFunc.

9. **Родитель при регистрации — это метаданные, а не управление дочерними акторами.** Он передаётся
   в Registered/AfterRegister и указывается отправителем события Bootstrap для актора с начальной
   загрузкой. Время жизни родителя и потомка не связывается автоматически.

10. **ActorId — временный адрес.** Он не является устойчивым идентификатором после
    перезапуска процесса. Его отладочное строковое представление намеренно не позволяет
    восстановить исходное значение без потерь.

11. **Исключения должны останавливаться на явно выбранной границе.** Синхронные исключения
    выходят из Receive, если их не принимает IActorExceptionHandler. Необработанное исключение
    корутины верхнего уровня проходит через тот же обработчик, а если не принято — приводит
    к аварийному завершению. Ожидаемые ошибки перехватывайте внутри протокола.

12. **Сообщения между узлами не являются персистентными и не имеют гарантии «ровно один раз».**
    При сбое сессии результат выполняющейся операции может остаться неопределённым.
    Переподключение и продолжение передачи — оптимизации транспорта, а не прикладные гарантии.
