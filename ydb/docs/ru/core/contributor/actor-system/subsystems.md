# Подсистемы акторной системы

Подсистема — объект `ISubSystem`, которым владеет один `TActorSystem`. Она предоставляет типизированный C++ API и участвует в запуске и остановке системы. Вызов её API — обычный синхронный вызов C++: реестр не предоставляет mailbox, сериализацию доступа или контекст активации актора. Внутри подсистема может создавать акторы для асинхронной работы.

## Доступные реализации

Публичные классы подсистем — абстрактные интерфейсы. Для создания поставляемой реализации используйте фабрику, а для мока реализуйте тот же интерфейс.

| Интерфейс | Подключение и назначение |
|---|---|
| `TActorSystemStatsSubSystem` | Конструктор `TActorSystem` добавляет её автоматически, если под этим типом ещё ничего не зарегистрировано. Предоставляет статистику пулов исполнителей, потоков и harmonizer. Фабрика: `MakeActorSystemStatsSubSystem`. |
| `TCGroupV1StatsSubSystem` | Явная регистрация через `MakeCGroupV1StatsSubSystem(config)`. Читает статистику CPU, памяти, I/O и PID из Linux cgroup v1. |
| `TCGroupV2StatsSubSystem` | Явная регистрация через `MakeCGroupV2StatsSubSystem(config)`. Читает статистику Linux cgroup v2, включая показатели pressure. |
| `TCGroupOomSubSystem` | Явная регистрация через `MakeCGroupOomSubSystem(config)`. Использует поставщиков статистики памяти cgroup для пороговых уведомлений и настраиваемых окон прогноза OOM. |

Автоматически устанавливается только статистика акторной системы. Реализации cgroup находятся в сборочной цели `ydb/library/actors/subsystems`. `ICGroupMemoryStatsProvider` — общий интерфейс статистики памяти для разных версий cgroup, а не ещё одна автоматически устанавливаемая подсистема.

Читатели cgroup выполняют файловый I/O в `config.ExecutorPoolId`; явно выберите существующий I/O-пул. Значение по умолчанию — ноль, но пул с таким ID не обязательно предназначен для I/O. По умолчанию неизменяемые снимки кешируются на одну секунду; нулевой `RefreshPeriod` отключает кеширование. Ответ сохраняет cookie запроса, а нулевой указатель на снимок означает недоступность поставщика или ошибку чтения. Вызовы требуют работающей подсистемы и локального актора-получателя.

Поставляемая реализация OOM предпочитает обоих поставщиков, затем только v2, затем только v1. Без зарегистрированных поставщиков разрешение зависимостей удаляет OOM при запуске. При наличии обоих можно перейти к следующему, если в первой иерархии нет контроллера памяти. Идентификатор cgroup и настройки окон прогноза фиксированы для работающего экземпляра; перенос процесса в другую cgroup прекращает мониторинг. Пороги, подписки и запросы прогноза описаны в [конфигурации и API](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/subsystems/cgroup/cgroup_oom.h).

## Регистрация и получение

Регистрируйте подсистемы при настройке `TActorSystemSetup` или в созданном `TActorSystem` до вызова `Start()`. Например, после настройки пулов исполнителей и планировщика:

```cpp
#include <ydb/library/actors/subsystems/cgroup/cgroup_v2.h>
#include <ydb/library/actors/subsystems/cgroup/cgroup_oom.h>

NActors::TCGroupV2StatsConfig statsConfig;
statsConfig.ExecutorPoolId = ioPoolId;
setup->RegisterSubSystem(NActors::MakeCGroupV2StatsSubSystem(statsConfig));

NActors::TCGroupOomConfig oomConfig;
oomConfig.ExecutorPoolId = systemPoolId;
setup->RegisterSubSystem(NActors::MakeCGroupOomSubSystem(oomConfig));
```

Тип результата фабрики определяет ключ в реестре. При получении нужен тот же тип:

```cpp
auto* stats = actorSystem.GetSubSystem<NActors::TCGroupV2StatsSubSystem>();
if (stats) {
    stats->ReadStats(recipient, cookie); // после возврата из Start()
}
```

`GetSubSystem<T>()` возвращает невладеющий указатель или null, если подсистемы нет. Именованные функции, например `GetActorSystemStats(actorSystem)` и `GetCGroupV2StatsSubSystem(actorSystem)`, аварийно завершают процесс при её отсутствии. Варианты без аргументов требуют текущей активации актора; из других потоков передавайте систему явно.

Каждому типу соответствует один принадлежащий реестру объект. Повторная регистрация под тем же ключом заменяет и уничтожает предыдущий объект. Получение не ищет по иерархии наследования и не создаёт псевдонимы для базовых классов. Идентификаторы типов — индексы внутри процесса; их нельзя сохранять как постоянные идентификаторы или передавать в таком качестве по сети.

## Создание своей подсистемы и мока

Отделите API от реализации. Наследование от `ISubSystem` должно быть публичным, однозначным и невиртуальным: типизированное получение использует статическое приведение от базового указателя. Например:

```cpp
#include <ydb/library/actors/core/actorsystem.h>

class TRequestLimitSubSystem : public NActors::ISubSystem {
public:
    virtual ui32 GetLimit() const = 0;
};

class TFixedRequestLimitSubSystem final : public TRequestLimitSubSystem {
public:
    explicit TFixedRequestLimitSubSystem(ui32 limit)
        : Limit(limit)
    {}

    ui32 GetLimit() const override {
        return Limit;
    }

private:
    const ui32 Limit;
};

class TMockRequestLimitSubSystem final : public TRequestLimitSubSystem {
public:
    ui32 GetLimit() const override {
        return 7;
    }
};
```

При регистрации реализации или мока явно укажите интерфейс в качестве ключа:

```cpp
setup->RegisterSubSystem<TRequestLimitSubSystem>(
    std::make_unique<TFixedRequestLimitSubSystem>(100));

// В тесте заменяем рабочую реализацию до создания акторной системы.
setup->RegisterSubSystem<TRequestLimitSubSystem>(
    std::make_unique<TMockRequestLimitSubSystem>());

NActors::TActorSystem actorSystem(setup);
auto* limits = actorSystem.GetSubSystem<TRequestLimitSubSystem>();
Y_ABORT_UNLESS(limits && limits->GetLimit() == 7);
```

Без `<TRequestLimitSubSystem>` мок зарегистрируется под собственным типом; потребители и зависимости, использующие `TRequestLimitSubSystem`, его не увидят. По тому же правилу мок `TActorSystemStatsSubSystem` заменяет автоматическую статистику: зарегистрируйте его под этим интерфейсом в setup или замените стандартную подсистему в созданной системе до `Start()`.

Мок должен реализовать все чисто виртуальные методы API. Унаследованные от `ISubSystem` lifecycle-хуки по умолчанию ничего не делают, поэтому мок не запускает рабочие акторы и не обращается к настоящему CPU manager или файловой системе cgroup. Асинхронный мок всё равно должен соблюдать контракт API: тип ответного события, получателя, cookie, владение и время жизни данных.

## Зависимости и жизненный цикл

Переопределите `GetDependencies()`, чтобы задать зависимости по их ключам регистрации. Пустой результат означает отсутствие зависимостей. Например:

```cpp
NActors::TSubSystemDependencies GetDependencies() const override {
    return NActors::DependsOn<TRequestLimitSubSystem>() &&
        (NActors::DependsOn<NActors::TCGroupV2StatsSubSystem>() ||
         NActors::DependsOn<NActors::TCGroupV1StatsSubSystem>());
}
```

`&&` требует все перечисленные подсистемы, `||` задаёт альтернативы. При `Start()` разрешение зависимостей удаляет и уничтожает подсистемы с неудовлетворёнными зависимостями, включая транзитивно недоступные. Доступные альтернативы перебираются в порядке объявления до нахождения общего плана без циклов. Неустранимый цикл аварийно завершает запуск. Выражения должны оставаться небольшими: построение аварийно завершается, если развёрнутая дизъюнктивная нормальная форма превысила бы 100 альтернатив.

`OnDependenciesResolved` получает идентификаторы типов и невладеющие указатели на экземпляры выбранной альтернативы в порядке объявления. Только выбранные зависимости определяют порядок lifecycle-хуков: другая зарегистрированная альтернатива может существовать, но не обязана запускаться раньше потребителя. Для независимых подсистем прикладных гарантий порядка нет.

Запуск следует порядку, вычисленному по зависимостям. Оба прохода stop-хуков обходят тот же порядок в обратную сторону, как при раскрутке стека: сначала останавливаются потребители, затем используемые ими подсистемы. Этот порядок задаётся зависимостями, а не временем регистрации. В примере ниже `A` зависит от `B`, а `B` — от `C`.

| Этап | Порядок и состояние среды выполнения |
|---|---|
| `OnDependenciesResolved` | `C → B → A`, до всех стартовых хуков. Все выбранные экземпляры существуют, но ещё не выполняли стартовые хуки. |
| `OnBeforeStart` | `C → B → A`: зависимости раньше потребителей, до подготовки исполнителей и планировщика. Здесь подготавливают синхронное состояние. |
| `OnAfterStart` | `C → B → A`, после запуска исполнителей и планировщика. Здесь подсистемы могут регистрировать внутренние акторы. |
| `OnBeforeStop` | `A → B → C`: потребители раньше зависимостей, пока потоки исполнителей ещё работают; до отложенных pre-stop callbacks. Здесь прекращают приём работы и начинают освобождение ресурсов. |
| `OnAfterStop` | `A → B → C`, после остановки планировщика и потоков исполнителей. Здесь освобождают ресурсы, которым больше не нужно выполнение акторов. |

Каждый хук вызывается отдельным проходом по всем подсистемам. Сначала `OnBeforeStop` выполняется у `A`, затем у `B`, затем у `C`; после этого выполняются отложенные pre-stop callbacks и останавливаются планировщик и исполнители; наконец, `OnAfterStop` выполняется у `A`, затем у `B`, затем у `C`. Поэтому `A` может использовать `B` в своём `OnBeforeStop` до начала stop-хука самой `B`. Этот порядок хуков не гарантирует порядок уничтожения C++-объектов.

Хуки выполняются синхронно в потоке, вызвавшем `Start()` или `Stop()`; контекст активации актора для них не предоставляется. Для операций с акторами используйте переданный `TActorSystem`. Потоки исполнителей могут обрабатывать акторы до завершения всех `OnAfterStart`. Если ранним акторам нужна подсистема, предусмотрите явный протокол готовности. Внешние вызывающие могут дождаться возврата из `Start()`.

## Ограничения и проверка

- Регистрацию нужно сериализовать с запуском и получением подсистем. В реестре нет блокировки; атомарный флаг запуска не делает конкурентную регистрацию безопасной. Регистрация после начала `Start()` аварийно завершает процесс, в том числе после `Stop()`.
- Потокобезопасность вызовов API определяет реализация. Общее состояние подсистемы требует синхронизации или владения внутренним актором; сериализация mailbox не защищает обычные вызовы из разных акторов.
- Невладеющие указатели становятся недействительными при замене, удалении из-за зависимостей или уничтожении акторной системы. Сохранять указатели из setup через разрешение зависимостей можно только при гарантии сохранения подсистемы.
- `Start()` однократный, `Stop()` идемпотентный. Этот API не поддерживает перезапуск или замену подсистемы на ходу. Автоматического отката при ошибке хука нет; учитывайте это при проектировании запуска и остановки.
- `Stop()` не уничтожает объекты подсистем. Порядок зависимостей относится к хукам, а не к C++-деструкторам. Завершайте работу, требующую зависимостей, в stop-хуках; не полагайтесь на порядок деструкторов или actor TLS в них.
- Отправка poison в `OnBeforeStop` не доказывает, что внутренний актор его обработал. Если очистка должна завершиться до остановки исполнителей, необходимо явное подтверждение; см. [Сбои и завершение работы](failure-and-shutdown.md).

Регистрацию по типу, замену, зависимости и жизненный цикл проверяют тесты `ydb/library/actors/core/ut` (`TSubSystemTest`). Тесты реализаций cgroup и их интеграции с моками находятся в `ydb/library/actors/subsystems/ut` (`TCGroupStatsSubSystemTest`). Соблюдайте действующие инструкции сборки из [Тестирования акторов](testing.md).

Контракт реализован в [core/subsystem.h](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/core/subsystem.h), [core/subsystem.cpp](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/core/subsystem.cpp) и [core/actorsystem.cpp](https://github.com/ydb-platform/ydb/blob/main/ydb/library/actors/core/actorsystem.cpp).
