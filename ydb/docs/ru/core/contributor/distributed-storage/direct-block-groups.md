# Группы прямого блочного доступа

Группа прямого блочного доступа (direct block group, DBG) — это принадлежащий таблетке набор выделенных DDisk для данных и PersistentBuffer (PB). Контроллер BlobStorage (BSC) сохраняет сведения об этом наборе и выбирает подходящие слоты. Клиент использует полученную схему размещения для реализации своей политики репликации и восстановления блоков.

Эта страница описывает общие контракты размещения и выделения ресурсов. Политики партиции NBS — основные и резервные роли, кворум записи, чередование регионов и планирование переноса данных из PB — описаны в [руководстве по реализации партиции](https://github.com/ydb-platform/ydb/blob/main/ydb/core/nbs/cloud/blockstore/libs/storage/partition_direct/README.md).

## Три разных вида идентификаторов

| Сущность | Идентификатор и значение |
|---|---|
| Группа пула DDisk в BSC | `TGroupInfo` с `IsDDisk = true`, содержащая слоты, подобранные для пула хранения DDisk. Она предоставляет ресурсы, из которых выделяются логические DBG. |
| Логическая DBG | Запись о закреплённых ресурсах с ключом `(TabletId, DirectBlockGroupId)` в `Schema::DirectBlockGroupClaims`, содержащая упорядоченные списки слотов данных и PB. |
| Сервис DDisk/PB | Сервис по адресу `(NodeId, PDiskId, DDiskSlotId)`. В слоте DDisk работают DDisk и его дочерний PB с разными идентификаторами акторов. |

Между группами пула в BSC и логическими DBG таблетки нет соответствия один к одному. Аллокатор собирает подходящие VSlot из всех групп выбранного пула. Один слот может участвовать в нескольких логических DBG, а его роли для данных и PB учитываются отдельно.

`DirectBlockGroupIndex` в протоколе имеет ещё одно назначение: он выбирает сессию клиента и пространство имён записей PB. PB хранит этот индекс в одном байте, поэтому допустимый диапазон — `0..255`. Это не идентификатор группы BSC, а `DirectBlockGroupId` контроллера не сериализуется автоматически в этот индекс.

## Определение пула и выделение ресурсов

`DefineDDiskPool` создаёт или обновляет пул хранения с флагом DDisk, типом erasure-кодирования `none`, геометрией размещения, фильтрами PDisk и параметром `NumDDiskGroups`. Группы ресурсов и слоты создаёт обычный механизм подбора групп пула. Само определение пула не закрепляет ресурсы DBG за таблеткой.

Затем клиент отправляет `TEvControllerAllocateDDiskBlockGroup` с идентификатором своей таблетки, именем пула данных, именем пула PB и запрошенными операциями. Контроллер сохраняет полученное распределение ресурсов и обновляет два счётчика каждого затронутого VSlot:

- `DDiskNumVChunksClaimed` — суммарное число виртуальных чанков, закреплённых для данных;
- `PersistentBufferRefs` — число ссылок на PB из логических DBG.

В неиспользуемом слоте пула оба счётчика могут быть равны нулю; в одном и том же слоте оба могут быть положительными. Ссылка на PB не резервирует определённый объём данных в PB. Фактическая ёмкость PB определяется локальными настройками выделения ресурсов и допуска запросов.

Закрепление чанков данных также относится к учёту в контроллере. Текущий аллокатор использует для кандидатов верхнюю границу закреплений `Max<ui32>()`; успешное закрепление не гарантирует, что на физическом устройстве уже есть столько свободных чанков. DDisk выделяет ресурсы для данных и контроля целостности по мере необходимости при записи.

## Размещение и сопоставление пар

Размещение данных соблюдает ограничения пула на общую область отказа и разные домены отказа. Порядок закреплений и счётчики размещений используются для распределения выбранных DDisk по узлам, PDisk и слотам.

PB размещаются по геометрии собственного пула. При формировании начального списка PB аллокатор использует DDisk данных с соответствующим индексом как подсказку для совместного размещения. Сначала он пробует узел этого DDisk, затем предпочтительные узлы, если они указаны, затем другие подходящие узлы. Внутри узла он учитывает число ссылок на PB и может предпочесть другой слот, а не указанный слот данных.

Таким образом, `data[k]` и `pb[k]` образуют пару по позиции в списках, но совпадение идентификаторов слотов или узлов не гарантируется. Для переноса данных из PB нужно использовать возвращённый идентификатор PB, а не вычислять его из идентификатора DDisk данных.

Для двух ролей можно выбрать один пул или разные пулы. Один пул не обязывает размещать пару на одном PDisk. Два пула позволяют настраивать наборы кандидатов для каждой роли, но сами по себе не гарантируют разные физические устройства, если фильтры пулов пересекаются.

Число участников также входит в контракт клиента. Совместимый формат запроса выделения ресурсов определяет число участников для каждой роли по геометрии её пула. API явных операций содержит отдельные поля `NumDDisks` и `NumPersistentBuffers`. Фиксированную топологию NBS и поддерживаемое нагрузочным актором NBS-like число хостов нельзя считать универсальными константами протокола DDisk.

## Формы запросов и ответов

Протокол определён в [blobstorage.proto](https://github.com/ydb-platform/ydb/blob/main/ydb/core/protos/blobstorage.proto).

| Форма | Назначение |
|---|---|
| `Queries` | Совместимый формат выделения ресурсов с `DirectBlockGroupId` и `TargetNumVChunks`; контроллер преобразует каждый запрос в операцию определения группы. |
| `DirectBlockGroupOperations` | Явное определение группы, изменение закреплений для отдельных DDisk, переназначение и удаление записей данных/PB. |
| `Responses` | Ответы совместимого формата с `ActualNumVChunks` и индексированными `Nodes`; каждая запись содержит идентификатор данных и, при наличии, идентификатор PB. |
| `DirectBlockGroups` | Ответы на явные операции с отдельными упорядоченными списками данных и PB. |

В одном запросе нельзя смешивать `Queries` и `DirectBlockGroupOperations`. Перед принятием возвращённой топологии клиент должен проверить общий статус ответа. Явные операции могут возвращать списки разного размера, поэтому нельзя предполагать фиксированную парную структуру без проверки требований конкретного клиента.

Повторное определение группы с неизменными закреплениями использует сохранённое распределение ресурсов. Изменение топологии обновляет `DirectBlockGroupClaims` и счётчики затронутых VSlot в транзакции контроллера. Для потребителей сведений о топологии контроллер также поддерживает ревизию топологии каждой таблетки в `DirectBlockGroupTabletState`.

Таблетка должна сохранить успешно полученную схему размещения до создания тракта обработки данных, а после перезапуска заново подключиться к ней. Операции контроллера меняют закрепление ресурсов; они не копируют пользовательские данные и не доказывают, что реплику можно безопасно удалить. Клиент должен согласовать миграцию, завершение сессий, очистку PB и `TEvDeleteTabletChunks` с соответствующим изменением топологии.

## Запуск

Выделенные идентификаторы указывают на сервисы, которыми управляет [NodeWarden](node-warden.md). NodeWarden запускает DDisk для каждого настроенного слота DDisk. Этот DDisk восстанавливает локальное состояние и создаёт дочерний PB независимо от того, какая логическая DBG впоследствии будет ссылаться на каждую из ролей.

Клиенты отдельно подключаются к каждому выбранному сервису DDisk и PB. [Сессии DDisk](ddisk.md#sessions) возвращают непрозрачные токены для обычных запросов данных. Доступность сервиса, успешное установление сессии и завершение восстановления PB на стороне клиента — разные условия готовности.
