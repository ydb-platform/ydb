# NbsDbgLikeLoad

`NbsDbgLikeLoad` измеряет производительность упрощённого пути записи и чтения Network Block Store (NBS) через [группы прямого блочного доступа (DBG)](distributed-storage/direct-block-groups.md). Персистентная нагружающая таблетка владеет DBG и отправляет запросы в [PersistentBuffer (PB)](distributed-storage/persistent-buffer.md) и [DDisk](distributed-storage/ddisk.md). Отдельные нагружающие акторы генерируют запросы и измеряют время их выполнения.

Используйте этот актор для сравнения репликации PB, фонового копирования в DDisk, пакетной обработки и параллельного ввода-вывода. Для проверки пути хранения блобов через DSProxy/VDisk используйте [{#T}](load-actors-storage.md).

## Предварительные требования {#prerequisites}

Используйте тестовый кластер с пулами DDisk и PB, настроенными в BlobStorage Controller (BSC). При выделении ресурсов должно возвращаться число пар DDisk/PB, соответствующее `HostsPerDbg`. Нагружающей таблетке также нужны обычное хранилище для каналов таблетки и работающий Hive; пулы DDisk это хранилище не предоставляют.

Откройте `http://<node>:8765/actors/load?mode=tablet` на узле нужной базы данных. Эта страница позволяет создавать таблетки, просматривать их идентификаторы Hive и размещение, а также запускать нагрузку. Порт мониторинга в вашем кластере может отличаться.

{% note warning %}

Запускайте не более одной нагрузки одновременно на каждой нагружающей таблетке и завершайте её перед удалением таблетки. Во время запуска таблетка остаётся в фазе `Ready` и не обеспечивает исключительный доступ. Следующий запуск перенастраивает те же акторы отдельных DBG.

{% endnote %}

## Автоматизация через dstool {#automation}

Для скриптов и возобновляемых запусков используйте `ydb-dstool cluster workload nbs-dbg-like`. Команда вызывает существующий legacy-метод gRPC `TestShardControl` и не переключается на HTTP. Сначала разверните серверную поддержку: сервис нагрузки на координаторе и узлах генераторов, а также таблетки с версией протокола автоматизации 1. Каждой команде нужны явно указанная база данных (или сохранённый дескриптор с ней) и права администратора. Проверка возможностей отклоняет неподдерживаемые серверы и устаревшие инкарнации координатора.

Legacy-сервис gRPC по умолчанию выключен на TLS-эндпоинтах и при явном списке сервисов, который его не включает. Добавьте `legacy` в `GRpcConfig.ServicesEnabled` в textproto или объедините следующую настройку с серверной конфигурацией YAML:

```yaml
grpc_config:
  services_enabled:
    - legacy
```

Сохраните остальные включённые сервисы и убедитесь, что `legacy` отсутствует в `services_disabled`: этот список имеет приоритет. `test_shard` — отдельный сервис, который не включает данный legacy-RPC. Автоматизация не меняет настройки включения сервисов по умолчанию.

Используйте выделенные таблетки нагрузки. Сериализуйте создание и удаление для каждого индекса владельца в Hive, включая операции через HTTP. Резервируйте разные индексы для баз данных, использующих общий Hive. Одновременные изменения жизненного цикла независимыми контроллерами не поддерживаются. Координатор запрещает известные ему пересекающиеся запуски и удаление таблетки с известной активной нагрузкой; это не блокировка на уровне кластера. Не запускайте нагрузку через другой координатор одновременно на тех же таблетках.

### Конфигурация и команды

Команда gRPC `create` строит `TAllocConfig` из параметров; файл выделения ресурсов не нужен. `--pool-name` задаёт пул для DDisk и persistent buffer, по умолчанию `ddp1`. Значения по умолчанию: `--num-groups` — 32, `--target-num-vchunks` — 1 vChunk на группу, `--vchunk-size-bytes` — 134217728 (128 МиБ), `--hosts-per-dbg` — 5. `TargetNumVChunks` также задаёт запрашиваемое у BSC число vChunk на группу; адресное пространство нагрузки на группу равно `TargetNumVChunks * VChunkSizeBytes`. Используйте пул и геометрию, подходящие вашему кластеру.

Если у базы нет пулов каналов таблетки по умолчанию, повторите `--tablet-storage-pool POOL` в порядке каналов. Для трёх каналов в одном обычном пуле хранения таблеток передайте `--tablet-storage-pool tablet-storage` трижды. Этот параметр отличается от `--pool-name`, который задаёт пулы DDisk/PB. Повторное создание использует существующие ресурсы только при совпадении базы/домена, эффективной конфигурации и фактических упорядоченных привязок; иначе возвращает конфликт. Предварительная проверка не делает создание атомарным относительно другого контроллера. Операция отправляет не более одного запроса создания или удаления; после неоднозначной ошибки транспорта проверьте индекс владельца и сообщённый идентификатор таблетки, прежде чем повторять операцию. Частичная ошибка сопровождается идентификатором таблетки для восстановления. Повторное удаление уже отсутствующей таблетки допустимо.

Команда `run` строит `TEvLoadTestRequest` из параметров; `--config` ей не нужен. Для существующей таблетки укажите `--tablet-id ID`, для нескольких повторите `--target TABLET_ID[@NODE_ID]`. Без цели `run` создаёт выделенную таблетку с теми же параметрами выделения ресурсов, что и `create`, ждёт готовности, выполняет нагрузку и удаляет таблетку после подтверждённого завершения. `--pool-name` задаёт общий пул DDisk/PB; `--ddisk-pool-name` и `--pb-pool-name` позволяют выбрать пулы раздельно, как на странице мониторинга. Без `@NODE_ID` используется текущее размещение Hive; `@0` запускает генератор на координаторе, а ненулевой ID явно задаёт узел. Идентификаторы таблеток должны быть уникальными. По умолчанию каждый запуск или испытание длится 10 секунд. Длительность должна быть положительной и превышать задержку перед измерениями. Для длительности, задержки, inflight и предела LSN CLI использует значения формы мониторинга; остальные пропущенные параметры нагрузки получают значения protobuf по умолчанию.

Без параметров inflight выполняется один запуск со значением 2048 на таблетку. Укажите `--inflight N` для другого одиночного значения или оба параметра `--inflight-from A --inflight-to B` для серии. Значения серии: A, 2A, 4A и так далее, пока значение не превысит B; промежуточное B не добавляется. `--trials` по умолчанию равно 1 и при значении больше 1 должно быть нечётным, как на странице мониторинга. CLI поддерживает те же цели на нескольких таблетках, долю чтений, размер ввода-вывода, префикс DBG, последовательные адреса, предел LSN, контрольные суммы, отключение репликации и выбор медианного испытания по write IOPS. Служебные теги назначаются сервисом.

| Параметр | Поле protobuf | По умолчанию |
| --- | --- | --- |
| `--duration-seconds` | `DurationSeconds` | 10 секунд на запуск или испытание |
| `--delay-before-measurements-seconds` | `DelayBeforeMeasurementsSeconds` | 0 секунд |
| `--num-groups-to-use` | `NumDirectBlockGroupsToUse` | 0 (все группы) |
| `--inflight` или `--inflight-from` / `--inflight-to` | Значения `MaxInFlight` для испытаний | 2048 на таблетку для одиночного запуска |
| `--read-ratio` | `ReadRatio` | 0 чтений на 100 записей |
| `--sequential` | `Sequential` | Случайные адреса |
| `--read-write-size-kib` | `ReadWriteSizeKiB` | 4 КиБ |
| `--stop-on-writes-done-count` | `StopOnWritesDoneCount` | 0 (только длительность) |
| `--max-inflight-lsns` | `TabletConfig.MaxInflightLsns` | 65536 |
| `--flush-batch-size` / `--erase-batch-size` | Размеры пакетов таблетки | 10000 каждый |
| `--sync-requests-batch-size` | `TabletConfig.SyncRequestsBatchSize` | 10 |
| `--pbuffer-reply-timeout-us` | `TabletConfig.PBufferReplyTimeoutMicroseconds` | 50000 мкс |
| `--disable-replication` | `TabletConfig.DisableReplication` | Репликация включена; с этим флагом чтение запрещено |
| `--disable-checksums` | `TabletConfig.EnableChecksums` | Контрольные суммы включены |

`--read-ratio` задаёт число чтений на 100 записей, а не процент всех операций; допустимые значения — от 0 до 100. `--read-write-size-kib` должен быть не меньше 4, кратен 4 и без остатка помещаться в выделенный vChunk. Ненулевое значение `--stop-on-writes-done-count` добавляет условие остановки; длительность по-прежнему ограничивает запуск.

Используйте обычные параметры TLS и аутентификации dstool и явный эндпоинт `grpc://` или `grpcs://`. Замените базу, эндпоинт, индекс владельца и идентификатор таблетки в примерах:

```bash
DSTOOL_ENDPOINT=grpcs://node.example:2135
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like create --database /Root/test --owner-index 1 --pool-name ddp1 --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like list --database /Root/test --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like describe --database /Root/test --owner-index 1 --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like run --database /Root/test --tablet-id 72057594000000001 --duration-seconds 60 --inflight 32 --output-dir ./run-01 --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like results --handle ./run-01 --wait --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like stop --handle ./run-01 --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like run --database /Root/test --duration-seconds 60 --inflight-from 1 --inflight-to 32 --trials 3 --output-dir ./sweep-01 --format jsonl
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like delete --database /Root/test --owner-index 1 --format json
```

`create` ожидает готовности. `run` по умолчанию ожидает завершения; `--no-wait` доступен только для одного запуска на явно заданной таблетке и возвращает дескриптор и путь к артефактам. `results` получает текущее состояние, а `--wait` ожидает конечного результата. `stop` останавливает один запуск и ожидает подтверждения завершения. Для отдельного испытания серии используйте `results` или `stop` с `--database`, `--node-id`, `--incarnation` и `--request-id` из checkpoint вместо `--handle`.

По умолчанию координатором становится принимающий узел; `--node-id` выбирает другой. Перед отправкой клиент фиксирует узел координатора и инкарнацию сервиса. Последующие запросы могут поступать через другой шлюз и перенаправляются координатору. Отсутствие сервиса нагрузки или контекста базы приводит к ошибке. Каждый новый запуск, включая каждое испытание sweep, запрашивает текущее размещение в Hive. Отсутствующий `NodeId` цели размещает генератор рядом с таблеткой; явно заданное ненулевое значение переопределяет размещение, а явный ноль выбирает узел координатора. Принятый запуск сохраняет снимок размещения при повторах и автоматически не переносится и не перезапускается.

Автоматизация ожидает готовности всего запрошенного префикса DBG и подтверждения применения конфигурации его акторами до генерации нагрузки. Она не использует HTTP-подстановку при нулевой готовности и не уменьшает нагрузку молча. Значение `NumDirectBlockGroupsToUse`, превышающее выделенное число DBG, отклоняется. Значения по умолчанию: тайм-аут RPC 90 секунд, бюджет запуска 60 секунд и интервал опроса 2 секунды; параметры — `--rpc-timeout`, `--startup-timeout` и `--poll-interval`. Бюджет запуска — единый срок, отсчитываемый с момента приёма START, который покрывает поиск размещения, проверку возможностей, готовность DBG и подтверждение конфигурации; повторный START его не продлевает, а его максимум составляет 3600 секунд. Тайм-аут RPC также передаётся шлюзу gRPC в поле `RpcTimeoutMs`. Общее ожидание runner по умолчанию равно бюджету запуска + длительности нагрузки + 210 секундам на завершение запросов и ограниченный транспортный запас; его переопределяет `--wait-timeout`. Подтверждённое завершение означает ожидание клиентских запросов, а не фоновых сбросов или удалений. Проверяйте `Run.TerminationConfirmed`: без подтверждения завершения запросов сервис оставляет запуск в `STOPPING` с `ExecutionError`, `TerminationConfirmed: false` и без `FinishedAtMs`, даже если watchdog генератора сообщил об ошибке. Такие неразрешённые запуски продолжают блокировать повторное использование своих таблеток на том же координаторе. Для таких запусков тайм-аут или прерывание клиента возвращает ненулевой код и неразрешённый исход; неуспешный или неподтверждённый исход не должен разрешать следующее испытание.

Один бюджет RPC действует на все попытки через шлюзы и ограничивается остатком общего бюджета операции; остаток передаётся и в gRPC, и в `RpcTimeoutMs`. Бюджет испытания начинается до START или восстановительного GET, ожидания результата — до первого GET, готовности — до DESCRIBE, остановки — до STOP. Поздний конечный ответ сохраняется, но вердикт остаётся тайм-аутом. Отмена получает отдельный ограниченный бюджет.

### Результаты, восстановление и sweep

`--format json` сохраняет машиночитаемый stdout; прогресс и диагностика поступают в stderr. Для серии формат pretty один раз показывает размещение таблеток, затем для каждого испытания выводит `MaxInFlight`, направление, IOPS, p50, p95, p99 в микросекундах, число измеренных ошибок и их процент. Строки чтения показываются, если чтения настроены или измерены. Результаты JSON и JSONL содержат `measured_io_errors` по направлениям: число ошибок и общее число операций строками, процент числом; при неуспешном вердикте добавляется `failure_reason`. Процент равен числу ошибок, делённому на сумму успешных и неуспешных измеренных операций данного направления. Protobuf JSON представляет 64-битные идентификаторы и счётчики строками. Результат CLI содержит `response.Run` и отдельный вердикт `passed` (для незавершённых результатов окончательного вердикта нет). Состояния выполнения: `IN_PROGRESS`, `STOPPING`, `SUCCEEDED`, `FAILED`, `CANCELLED`. `SUCCEEDED` означает завершение нагрузки. Частичные измеренные ошибки остаются видимыми, но не меняют вердикт CLI; направление не проходит проверку только при наличии ошибок и отсутствии успешных измеренных операций (100% ошибок). Ошибка выполнения, отмена, тайм-аут и потерянные/отсутствующие результаты по-прежнему приводят к ненулевому коду выхода. `--allow-io-errors` ослабляет только проверку 100% ошибок.

Типизированный результат содержит ошибки выполнения, эффективную конфигурацию с разрешённым размещением, сведения о сборке, временные метки, длительность измерения в миллисекундах, счётчики, байты, скорости, гистограммы задержек в микросекундах и статистику по таблеткам. Для общей задержки объединяются гистограммы, а не усредняются перцентили. Поля метрик браузера сохраняются как отдельное совместимое представление.

По умолчанию `run` сохраняет артефакты в `./nbs-dbg-like-load-results/<client-generated-uuid>/`. Явно заданный каталог не должен существовать, кроме случая возобновления. Созданный CLI файл `config.json` и атомарно записываемый `checkpoint.json` сохраняют настройки, координатор, идентификаторы запросов, цели и состояния испытаний до отправки. При автоматическом создании таблетки `auto.json` сохраняет индекс владельца и параметры выделения до CREATE. Каждый `result-NNNN.json` сохраняется до отметки о завершении испытания в checkpoint. Учётные данные в артефакты не попадают.

```bash
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like run --resume ./run-01 --format json
ydb-dstool -e "$DSTOOL_ENDPOINT" cluster workload nbs-dbg-like run --resume ./sweep-01 --format jsonl
```

Возобновление использует сохранённые настройки запуска; новые конфликтующие настройки отклоняются. `results --handle` и `stop --handle` также сохраняют конечный результат до отметки о завершении в checkpoint. Они восстанавливают прерванную запись результата и checkpoint и читают сохранённый конечный результат без сети, в том числе после потери истории координатора. Dry-run не изменяет артефакты; незавершённый ответ не помечается завершённым. Возобновление пропускает сохранённые завершённые испытания, запрашивает ранее отправленные и запускает только ещё не отправленные. Полностью завершённый запуск или sweep можно возобновить по сохранённым результатам без работающего координатора. Прерванная отправка неоднозначна: неизвестный или истёкший дескриптор никогда не должен автоматически приводить к новому запуску взамен старого. Принятая ограниченная нагрузка принадлежит сервису и продолжается после отключения клиента. Завершённые результаты и записи дедупликации хранятся в памяти сервера 24 часа; предел координатора — 1024 активные/сохранённые записи, после чего новые запуски отклоняются. Перезапуск координатора теряет историю и меняет инкарнацию. Потеря координатора не доказывает остановку удалённых генераторов; перед новой нагрузкой на те же таблетки выясните их состояние.

Серия сохраняет все значения удвоения inflight и все испытания, меняя только `WorkloadConfig.MaxInFlight`. Испытания последовательны, останавливаются при первом неуспешном вердикте и сохраняют `summary.json` с медианным испытанием по write IOPS. При тайм-ауте или прерывании runner запрашивает отмену конкретного запуска и подтверждает завершение до возможности продолжения; неподтверждённый исход остаётся неразрешённым. Автоматически созданная таблетка удаляется только после сохранения конечных результатов всех отправленных запусков с подтверждённым завершением; иначе её идентификатор остаётся в `auto.json` для восстановления. Существующие таблетки CLI автоматически не удаляет. Глобальный параметр `--dry-run` проверяет и показывает предполагаемые запросы без изменений и вымышленных результатов.

Для работы с агентом используйте специализированный [навык ydb-nbs-dbg-like-load](https://github.com/ydb-platform/ydb/blob/main/ydb/apps/dstool/.agents/skills/ydb-nbs-dbg-like-load/SKILL.md). Остальные разделы описывают совместимый HTTP-сценарий и общие параметры нагрузки.

## Создание таблетки {#create}

Выберите отдельный `owner_idx` для каждой таблетки в выбранном Hive. Hive сопоставляет этот индекс вместе с фиксированным идентификатором владельца сервиса нагрузки с фактическим идентификатором таблетки. Сохраните оба значения: для удаления используется `owner_idx`, а для запуска нагрузки — идентификатор таблетки, назначенный Hive.

Сохраните следующую конфигурацию выделения ресурсов в файл `nbs-dbg-alloc.txt`. Замените имена пулов на настроенные в вашем кластере. Это сообщение `TAllocConfig` без внешнего блока `NbsDbgLikeLoad`.

```proto
DDiskPoolName: "ddp1"
PersistentBufferDDiskPoolName: "ddp1"
NumDirectBlockGroups: 1
TargetNumVChunks: 1
VChunkSizeBytes: 134217728
HostsPerDbg: 5
```

Создайте таблетку через форму на странице или отправьте тот же запрос:

```bash
curl --fail-with-body 'http://<node>:8765/actors/load' \
  -H 'Content-Type: application/x-protobuf-text' \
  --data-urlencode 'mode=tablet_create' \
  --data-urlencode 'owner_idx=1' \
  --data-urlencode 'config@nbs-dbg-alloc.txt'
```

Ответ представляет собой HTML с `TabletId=<id>`. Повторное создание инициализированной таблетки возвращает HTTP 409 с сообщением «Tablet was already initialized»; уже выделенные ресурсы не изменяются.

Чтобы явно задать привязки каналов таблетки, передайте в поле формы `storage_pools` список имён пулов, разделённых переводами строк, — по одному на канал. Например, добавьте `--data-urlencode 'storage_pools@tablet-storage-pools.txt'`. Если привязки не заданы явно, вспомогательный актор использует доступные пулы хранения тенанта для трёх каналов, а при их отсутствии — привязку Hive по умолчанию. HTTP-обработчик читает это отдельное поле формы; одного `TabletStoragePools` в тексте конфигурации выделения ресурсов недостаточно, чтобы задать привязки Hive.

### Параметры выделения ресурсов {#allocation-parameters}

Выделенные ресурсы сохраняются между запусками. Чтобы изменить их конфигурацию, удалите нагружающую таблетку и создайте её заново.

На странице таблетки поле `NumDirectBlockGroups` предварительно заполнено значением `32`. В таблице ниже указаны значения по умолчанию в protobuf, которые применяются, если поле не задано в сообщении конфигурации.

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| `DDiskPoolName` | `"ddp1"` | Пул BSC для данных DDisk. |
| `PersistentBufferDDiskPoolName` | `"ddp1"` | Пул BSC для размещения PB. |
| `NumDirectBlockGroups` | `1` | Число выделяемых логических DBG; должно быть положительным. |
| `TargetNumVChunks` | `1` | Число vChunk на DBG в адресном пространстве нагрузки и запрашиваемое число учитываемых чанков на стороне данных. Используйте положительное значение. |
| `VChunkSizeBytes` | `134217728` | Размер vChunk в байтах; используйте размер чанка, поддерживаемый кластером. Значение должно быть положительным и кратным 4096. |
| `HostsPerDbg` | `5` | Ожидаемое число пар DDisk/PB в каждом ответе на выделение ресурсов — от 3 до 5. Для реплицируемых записей и сброса данных нагрузка использует первые три пары. Поле проверяет ответ, а не настраивает геометрию пула BSC. |
| `TabletId` | Назначается таблеткой | Таблетка перезаписывает это поле собственным идентификатором, назначенным Hive, и использует его как идентификатор владельца хранилища. Не задавайте его во входных данных. |
| `TabletStoragePools` | Пусто | Сохраняемое поле конфигурации. При создании через HTTP передавайте привязки в отдельном поле формы `storage_pools`, как описано выше. |

## Проверка выделенных ресурсов {#summary}

Обновите страницу таблеток или запросите их список:

```bash
curl --fail-with-body 'http://<node>:8765/actors/load?mode=tablet_list'
```

HTML-список объединяет информацию Hive с ответом `TEvNbsLoadTabletGetSummary` каждой таблетки. Он показывает размещение таблеток, пулы и число DBG. Это работает и после создания нескольких таблеток; отдельного сообщения для выделения ресурсов сразу нескольким таблеткам нет.

Сводка протокола акторов содержит число выделенных DBG, геометрию vChunk и `NumReadyDirectBlockGroups` — длину максимального непрерывного начального участка списка DBG, в каждой из которых подключены как минимум три PB. Создание завершается до установки этих соединений. Положительное число готовых DBG ограничивает адресное пространство запуска. Для совместимости текущий прокси нагрузки использует общее число выделенных DBG, если число готовых равно нулю, поэтому запуск сразу после создания всё ещё может приводить к ошибкам «peers not ready». Готовность PB также не гарантирует готовность всех соединений DDisk, необходимых для чтения и сброса данных.

## Запуск нагрузки {#run}

Замените идентификатор таблетки в следующем примере значением, полученным при создании, и сохраните этот полный запрос к сервису нагрузки в файл `nbs-dbg-run.txt`:

```proto
NbsDbgLikeLoad {
  NbsDbgLikeTabletId: 72057594000000001
  WorkloadConfig {
    DurationSeconds: 60
    DelayBeforeMeasurementsSeconds: 15
    MaxInFlight: 32
    ReadRatio: 0
    Sequential: false
    ReadWriteSizeKiB: 4
    TabletConfig {
      MaxInflightLsns: 4096
      FlushBatchSize: 10000
      EraseBatchSize: 10000
      SyncRequestsBatchSize: 10
      PBufferReplyTimeoutMicroseconds: 50000
      EnableChecksums: true
    }
  }
}
```

Вставьте его в общую форму конфигурации нагружающих акторов и запустите на текущем узле или отправьте напрямую:

```bash
curl --fail-with-body 'http://<node>:8765/actors/load' \
  -H 'Content-Type: application/x-protobuf-text' \
  --data-urlencode 'mode=start' \
  --data-urlencode 'config@nbs-dbg-run.txt'
```

Убедитесь, что JSON-ответ содержит `"status": "ok"`, и сохраните назначенные `tag` и `uuid`. Этот обработчик возвращает HTTP 200 даже при ошибках разбора или запуска, поэтому одной проверки `curl --fail-with-body` недостаточно для подтверждения успеха. Ошибки инициализации рабочих акторов могут появиться позже в итоговом результате.

Запрашивайте завершённые результаты по полученному UUID:

```bash
curl --fail-with-body \
  -H 'Accept: application/json' \
  'http://<node>:8765/actors/load?mode=results&uuid=<uuid>'
```

Пустой массив результатов означает, что завершённый результат для этого UUID пока недоступен. Пока нагрузка выполняется, используйте JSON: прокси нагрузки NBS не обрабатывают запросы текущего состояния в HTML. После завершения тот же URL без JSON-заголовка показывает итоговый HTML-отчёт. Завершив запуск, можно начать следующий с другими настройками нагрузки, повторно используя выделенные ресурсы.

### Параметры нагрузки {#workload-parameters}

Эти поля находятся в `NbsDbgLikeLoad.WorkloadConfig`.

На странице таблетки поля `MaxInFlight` и `MaxInflightLsns` предварительно заполнены значениями `2048` и `65536`. HTTP-обработчик `tablet_run` использует те же значения, если параметры не заданы. В таблицах ниже указаны значения по умолчанию в protobuf для сообщений конфигурации.

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| `DurationSeconds` | `0` | Время от старта нагрузки до прекращения генерации запросов, включая прогрев. Задайте положительное значение здесь или в `StopOnWritesDoneCount`. |
| `DelayBeforeMeasurementsSeconds` | `15` | Интервал прогрева, исключаемый из результатов измерения. Должен быть меньше положительного `DurationSeconds`. |
| `MaxInFlight` | `32` | Общий предел одновременно выполняемых записей и чтений на целевую таблетку. Используйте положительное значение. При случайном доступе большие лимиты делятся между рабочими акторами; при последовательном доступе используется один рабочий актор. |
| `ReadRatio` | `0` | Число отправленных чтений на 100 записей, рассчитанное по числу отправленных запросов. `100` означает примерно одно чтение на запись, то есть половину всех запросов. Значения выше `100` допустимы: `200` означает примерно два чтения на запись. Этот параметр не задаёт нагрузку только на чтение. |
| `Sequential` | `false` | Последовательный обход плоского адресного пространства при true; иначе — равномерный случайный выбор. |
| `ReadWriteSizeKiB` | `4` | Фиксированный размер ввода-вывода, не менее 4 КиБ и кратный 4 КиБ. Он не должен превышать размер vChunk и должен делить его без остатка. |
| `NumDirectBlockGroupsToUse` | `0` | Использовать начальную часть списка доступных DBG. Ноль или значение больше числа доступных DBG означает использование всех доступных DBG. |
| `StopOnWritesDoneCount` | `0` | Целевое число успешно завершённых записей, распределяемое между рабочими акторами. Ноль отключает ограничение по числу записей. Также задавайте длительность: в текущей реализации неуспешные записи могут исчерпать лимит отправки до достижения целевого числа успешных записей. |
| `TabletConfig` | См. ниже | Конфигурация, устанавливаемая в акторах отдельных DBG таблетки перед генерацией нагрузки. |

Завершения запросов во время прогрева и ожидания оставшихся ответов учитываются в счётчиках за всё время работы, но исключаются из измеряемых пропускной способности и задержки. Случайное чтение может обращаться к незаписанным адресам, а генератор не сравнивает возвращённые данные с ожидаемым содержимым блока. Для проверки корректности используйте интеграционные тесты.

Когда DBG одной нагружающей таблетки используют общий DDisk для данных, их локальные индексы vChunk могут указывать на одни и те же блоки хранилища. Не считайте, что разные логические диапазоны адресов DBG изолируют сохранённые данные; см. [описание реализации нагрузки](https://github.com/ydb-platform/ydb/blob/main/ydb/core/load_test/rfc/nbs_dbg_like/workload.md).

### Параметры таблетки {#tablet-parameters}

Эти поля находятся в `WorkloadConfig.TabletConfig`.

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| `MaxInflightLsns` | `4096` | Лимит отслеживаемых порядковых номеров записей журнала (LSN). Каждый актор DBG независимо применяет предел `max(1, budget / allocated_DBG_count)`. В делитель входят и неактивные DBG. Ноль запрещает записи; единого общего счётчика для лимита нет. |
| `FlushBatchSize` | `10000` | Максимальное число LSN, включаемых в один пакет сброса для каждого получателя; приводится к значению не менее одного. |
| `EraseBatchSize` | `10000` | Максимальное число LSN, включаемых в один пакет удаления для каждого получателя; приводится к значению не менее одного. |
| `SyncRequestsBatchSize` | `10` | Порог числа готовых LSN в отдельной DBG, необходимого для планирования сброса или удаления. Установите `1`, чтобы остаток очереди обрабатывался без задержки. Проверка порога остаётся включённой после остановки генерации нагрузки. |
| `PBufferReplyTimeoutMicroseconds` | `50000` | Тайм-аут, передаваемый координатору записи в несколько PB. |
| `DisableReplication` | `false` | Записывать только в PB-координатор, возвращать ответ после его подтверждения и удалять запись без копирования в DDisk. Требует `ReadRatio: 0`. |
| `EnableChecksums` | `true` | Вычислять в нагружающем акторе одну контрольную сумму на каждый блок полезной нагрузки размером 4 КиБ и передавать контрольные суммы через нагружающую таблетку в PersistentBuffer. Значение должно соответствовать режиму контрольных сумм DDisk/PersistentBuffer. |

Прокси устанавливает `TabletConfig.IoSizeBytes` из `ReadWriteSizeKiB`, а `TabletConfig.NumDirectBlockGroupsToUse` — из выбранного числа DBG. Настраивайте их через поля нагрузки, а не через внутренние поля таблетки.

Задавайте лимит LSN на DBG со значительным запасом относительно порога синхронизации: LSN остаются под наблюдением на этапах записи, сброса и удаления, и в обеих очередях должно накапливаться достаточно работы для прохождения пороговой проверки.

## Запуск на нескольких таблетках {#multiple-tablets}

Создайте каждую таблетку отдельно с собственным индексом владельца, затем получите их идентификаторы и текущие идентификаторы узлов из списка. Замените идентификаторы в примере:

```proto
NbsDbgLikeLoad {
  Targets { TabletId: 72057594000000001 NodeId: 1 }
  Targets { TabletId: 72057594000000002 NodeId: 2 }
  WorkloadConfig {
    DurationSeconds: 60
    DelayBeforeMeasurementsSeconds: 15
    MaxInFlight: 64
    ReadRatio: 100
    ReadWriteSizeKiB: 4
    TabletConfig { SyncRequestsBatchSize: 1 }
  }
}
```

Отправьте запрос тем же способом с `mode=start`. Непустой список `Targets` включает режим координатора и имеет приоритет над `NbsDbgLikeTabletId`. Каждая целевая таблетка получает полную конфигурацию нагрузки: в этом примере каждой задаётся предел в 64 одновременно выполняемых операции, то есть 128 в сумме. Если задан `StopOnWritesDoneCount`, он также применяется к каждой целевой таблетке отдельно.

`NodeId` выбирает узел для запуска прокси нагрузки соответствующей таблетки. Ноль или отсутствие значения означает узел координатора; актор не запрашивает и не отслеживает размещение в Hive. Используйте узел, на котором сейчас работает таблетка, чтобы генерация нагрузки выполнялась рядом с ней. Сервис нагрузки на целевом узле должен быть доступен. Указывайте каждую таблетку только один раз и запускайте этот координатор на одном узле.

## Результаты и освобождение ресурсов {#results}

Результаты содержат число запросов записи и чтения в секунду, перцентили p50/p95/p99 времени выполнения в микросекундах, заданный `max_in_flight`, общее число успешных запросов (`txs`), пропускную способность (`rps`) и число ошибок в секунду (`errors`). Результаты для нескольких таблеток также содержат массив `tablets`. Координатор объединяет гистограммы задержек, а не усредняет перцентили отдельных таблеток.

Момент завершения записи — получение подтверждения PB, ещё до фонового копирования в DDisk и удаления из PB. Результаты чтения объединяют обращения как к PB, так и к DDisk. Последний HTML-отчёт содержит счётчики, суммарные объёмы в байтах, длительность измерений и перцентили задержки. Счётчики таблетки и отдельных DBG показывают активность записи, сброса, удаления и чтения через сервис счётчиков `load_actor`.

Ограничение длительности, достижение целевого числа записей или [{#T}](load-actors-stop.md) прекращает отправку новых запросов и даёт до 30 секунд на получение оставшихся клиентских ответов. Это ожидание не охватывает все фоновые сбросы и удаления. В частности, порог синхронизации больше одного может оставить небольшой остаток очереди до появления новой работы.

После завершения нагрузки удалите каждую таблетку по индексу владельца, с которым она была создана:

```bash
curl --fail-with-body 'http://<node>:8765/actors/load' \
  -H 'Content-Type: application/x-protobuf-text' \
  --data-urlencode 'mode=tablet_delete' \
  --data-urlencode 'owner_idx=1'
```

Вспомогательный актор запрашивает у таблетки освобождение DBG, а затем удаление из Hive. Эта операция освобождает выделенные ресурсы, но не обеспечивает гарантированного стирания данных. Если выделение или удаление завершается ошибкой, перед повторной попыткой изучите журналы BSC и таблетки: текущая реализация не полностью восстанавливает прерванное выделение ресурсов и может очистить локальное состояние после ошибки освобождения в BSC.
