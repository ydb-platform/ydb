# Структурированное логирование

## Назначение

Структурированное логирование предназначено для того, чтобы в логе (журнале работы {{ydb-short-name}}) отделить текстовое описание событий от параметров этих событий. Например, если произошла ошибка чтения файла, то её описание - это текст вида "Ошибка чтения файла", а параметры - это путь к файлу, код системной ошибки, текстовое описание системной ошибки и т.п.

Разделение описания событий и их параметров впоследствии может быть использовано для эффективного поиска сообщений, сбора статистики, оптимизированного хранения журнала и прочих задач.

## Базовые средства записи сообщений в лог {#simple-logging}

В большинстве случаев при записи сообщений в лог выполняются следующие условия:

1. Исходный код содержится в некотором файле `.cpp` (логирование из заголовочных файлов поддерживается, но [рассматривается далее](#log-in-header-file)).

Пример:

```cpp

#define YDB_LOG_THIS_FILE_COMPONENT NKikimrServices::STATESTORAGE

```

2. В одном файле `.cpp` все сообщения пишутся от имени одного и того же компонента. Поэтому, в начале файла (но после всех директив `#include`) должен быть определён макрос `YDB_LOG_THIS_FILE_COMPONENT`, который задаёт код компонента для всего файла.

3. Логирование происходит в ходе работы актора, и для работы с контекстом (в частности, отправки сообщений актору логирования) доступна переменная `NActors::TlsActivationContext`.

{% note warning %}

Если хотя бы одно из трёх перечисленных условий не выполняется, то следует воспользоваться [расширенными средствами логирования](#extended-logging).

{% endnote %}

Далее в этом файле `.cpp` для логирования сообщений могут использоваться следующие макросы:

|Макрос|Уровень сообщения  |
|--|--|
|`YDB_LOG_EMERG(message, ...values...)`  | Возможен сбой системы (например, отказ кластера).|
|`YDB_LOG_ALERT(message, ...values...)`  | Возможна деградация системы, компоненты системы могут выйти из строя. |
|`YDB_LOG_CRIT(message, ...values...)`  | Критическое состояние.|
|`YDB_LOG_ERROR(message, ...values...)`  | Некритическая ошибка. |
|`YDB_LOG_WARN(message, ...values...)`  | Предупреждение, на которое следует отреагировать и исправить, если оно не временное. |
|`YDB_LOG_NOTICE(message, ...values...)`  | Произошло событие, существенное для системы или пользователя.|
|`YDB_LOG_INFO(message, ...values...)`  | Отладочная информация для сбора статистики. |
|`YDB_LOG_DEBUG(message, ...values...)`  | Отладочная информация для разработчиков. |
|`YDB_LOG_TRACE(message, ...values...)`  | Очень подробная отладочная информация.|

В аргументах вызова перечисленных макросов указываются следующие параметры:

- `message`- текстовое сообщение;

- `...values...`- несколько опциональных параметров (могут отсутствовать вовсе), которые содержат прикрепляемые параметры сообщения и их значения. Каждый параметр указывается в виде пары `{name, value}`, где `name` - текстовая строка с названием параметра, а `value` - значение параметра.

Примеры записи сообщений в журнал:

1. Сообщение без параметров:

```cpp
YDB_LOG_INFO("Module started");
```

2. Сообщение с параметрами:

```cpp
YDB_LOG_ERROR("Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

{% cut "Динамическое определение уровня сообщения:" %}

В некоторых случая уровень сообщения определяется динамически на этапе исполнения. Тогда следует использовать макрос, который принимает уровень сообщения в виде аргумента. Синтаксис макроса:

```cpp
YDB_LOG(prio, message, ...values...);
```

Пример использования:

```cpp
auto prio = PRI_ERROR;
...
YDB_LOG(prio, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

{% endcut %}

## Расширенные средства записи сообщений в лог {#extended-logging}

### Ядро логирования

Наиболее низкоуровневым средством для записи структурированных сообщений в журнал является макрос `YDB_LOG_CTX_COMP`. Он проверяет необходимость логирования (согласно [настройкам](../reference/configuration/log_config.md)), формирует текстовое сообщение, прикрепляет к нему структурированные значения и затем отправляет всю эту информацию актору логирования. Далее, актор логирования обрабатывает полученное сообщение согласно своим текущим настройкам (например, записывает в файл или отправляет в UA Agent).

{% note info %}

Все остальные средства логирования (в том числе и [базовые средства логирования](#simple-logging)) построены на основе этого макроса.

{% endnote %}

Полный синтаксис макроса логирования выглядит следующим образом:

```cpp
YDB_LOG_CTX_COMP(ctx, prio, comp, message, ...values...)
```

В аргументах вызова макроса указываются следующие параметры:

- `ctx` - контекст исполнения актора (необходим для отправки сообщения актору логирования);

- `prio`- уровень логирования сообщения (соответствует [уровням логирования](../reference/configuration/log_config.md#log-levels));

- `comp`- идентификатор компоненты;

- `message`- текстовое сообщение;

- `...values...`- несколько опциональных параметров (могут отсутствовать вовсе), которые содержат прикрепляемые параметры сообщения и их значения.

{% cut "Примеры записи сообщения в журнал:" %}

1. Сообщение без параметров:

```cpp
YDB_LOG_CTX_COMP(env, PRI_INFO, 1, "Module started");
```

В данном примере происходит запись сообщения с текстом `Module started` без прикрепляемых параметров. Для передачи сообщения актору логирования используется контекст исполнения `env`, а в качестве кода компоненты передаётся `1`.

2. Сообщение с параметрами:

```cpp
YDB_LOG_CTX_COMP(env, PRI_ERROR, 1, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

В данном примере происходит запись сообщения с текстом `Unable to open file` и двумя прикреплёнными параметрами: `path` (значение берётся из переменной `filename`) и `errorCode`(значение берётся из переменной `err`). Для передачи сообщения актору логирования используется контекст исполнения `env`, а в качестве кода компоненты передаётся `1`.

{% endcut %}

Макрос `YDB_LOG_CTX_COMP` подразумевает динамическое определение уровня сообщения и его передачу в виде аргумента. По аналогии с базовыми средствами логирования, существует ряд макросов, которые не требют передачи уровня сообщения в виде аргумента.

{% cut "Макросы без указания уровня сообщения в виде аргумента:" %}

|Макрос|Уровень сообщения  |
|--|--|
|`YDB_LOG_EMERG_CTX_COMP`  | Возможен сбой системы (например, отказ кластера).|
|`YDB_LOG_ALERT_CTX_COMP`  | Возможна деградация системы, компоненты системы могут выйти из строя. |
|`YDB_LOG_CRIT_CTX_COMP`  | Критическое состояние.|
|`YDB_LOG_ERROR_CTX_COMP`  | Некритическая ошибка. |
|`YDB_LOG_WARN_CTX_COMP`  | Предупреждение, на которое следует отреагировать и исправить, если оно не временное. |
|`YDB_LOG_NOTICE_CTX_COMP`  | Произошло событие, существенное для системы или пользователя.|
|`YDB_LOG_INFO_CTX_COMP`  | Отладочная информация для сбора статистики. |
|`YDB_LOG_DEBUG_CTX_COMP`  | Отладочная информация для разработчиков. |
|`YDB_LOG_TRACE_CTX_COMP`  | Очень подробная отладочная информация.|

Перечисленные в таблице макросы не требуют указания аргумента `prio`.

Пример:

```cpp
YDB_LOG_ERROR_CTX_COMP(env, 1, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

{% endcut %}

На основе макроса `YDB_LOG_CTX_COMP` работает множество других макросов. Их названия строятся по следующей схеме:

1. Имя макроса всегда начинается с `YDB_LOG`.

2. Если макрос не требует указания уровня сообщения, то к имени макроса через символ подчеркивания добавляется название уровня сообщения.

3. Если макрос требует указания контекста исполнения, то к имени макроса добавляется `_CTX`.

4. Если макрос требует указания контекста исполнения, то к имени макроса добавляется `_COMP`.

### Использование стандартного контекста исполнения

В большинстве случаев для передачи сообщений актору логирования используется контекст исполнения, доступный через глобальную переменную `NActors::TlsActivationContext`. Для того, чтобы исходные тексты не были визуально перегружены обращениями к этой глобальной переменной, введён дополнительный макрос `YDB_LOG_COMP`, который всегда использует `NActors::TlsActivationContext` и не требует указания параметра `CTX`.

Пример:

```cpp
YDB_LOG_COMP(PRI_ERROR, 1, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

В этом примере используется стандартный контекст исполнения, а логирование происходит от имени компонента с кодом `1`.

Макрос `YDB_LOG_COMP` подразумевает динамическое определение уровня сообщения и его передачу в виде аргумента. По аналогии с базовыми средствами логирования, существует ряд макросов, которые не требют передачи уровня сообщения в виде аргумента.

### Использование компонента по умолчанию

Используется тот же механизм, что и в [базовых средствах логирования](#simple-logging):

1. В начале файла (но после всех директив `#include`) должен быть определён макрос `YDB_LOG_THIS_FILE_COMPONENT`. Он задаёт код компонента для всего файла.

2. Далее в файле должны использоваться макросы логирования, не требующие указания кода компонента. Они аналогичны уже рассмотренным ранее, но их имя не содержит в себе строку `_COMP`.

Пример:

```cpp
#define YDB_LOG_THIS_FILE_COMPONENT 1
...
YDB_LOG_CTX(env, PRI_ERROR, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

Макрос `YDB_LOG_CTX` подразумевает динамическое определение уровня сообщения и его передачу в виде аргумента. По аналогии с базовыми средствами логирования, существует ряд макросов, которые не требют передачи уровня сообщения в виде аргумента.

|Макрос|Уровень сообщения  |
|--|--|
|`YDB_LOG_CTX` | Уровень сообщения указывается в аргументах.|
|`YDB_LOG_EMERG_CTX`  | Возможен сбой системы (например, отказ кластера).|
|`YDB_LOG_ALERT_CTX`  | Возможна деградация системы, компоненты системы могут выйти из строя. |

Пример:

### Логирование в заголовочных файлах {#log-in-header-file}

{% note warning %}

Крайне не рекомендуется определять макрос `YDB_LOG_THIS_FILE_COMPONENT` в заголовочных файлах, поскольку это может либо приводить к следующим последствиям:

1. Сложная логика определения кода компонента (не очевидно, из какого заголовочного файла берётся определение `YDB_LOG_THIS_FILE_COMPONENT`).

2. Ошибки при компиляции (в разных файлах макрос `YDB_LOG_THIS_FILE_COMPONENT` может быть определён по-разному).

{% endnote %}

Если в заголовочном файле необходимо логирование, то следует использовать макросы, требующие явного указания кода компонента:

1. `YDB_LOG_CTX_COMP` - макрос из ядра логирования.

2. `YDB_LOG_XXXX_CTX_COMP` - макрос из ядра логирования, не требующий указания уровня сообщения.

3. `YDB_LOG_COMP` - макрос из ядра логирования, использующий стандартный контекст исполнения.

4. `YDB_LOG_XXXX_COMP` - макрос из ядра логирования, использующий стандартный контекст исполнения и не требующий указания уровня сообщения.

## Построение структурированных сообщений

### Переиспользуемые наборы прикрепляемых параметров

Если один и тот же набор параметров прикрепляется к различным сообщениям, то для избежания дублирования кода можно заранее создать этот набор параметров, а затем его переиспользовать при логировании различных событий.



Пример:

```cpp
#define YDB_LOG_THIS_FILE_COMPONENT 1
...
void MyFunction(const std::string& filename) {
    auto context = YDB_LOG_CREATE_MESSAGE(
        {"path", filename});
    ...
    if (err != 0 ) {
        YDB_LOG_ERROR("MyFunction failed",
            context,
            {"errorCode", err});
        return;
    }
    ...
    YDB_LOG_NOTICE("MyFunction successed",
        context);
}
```

Результат вызова макроса `YDB_LOG_CREATE_MESSAGE` является экземпляром класса `TStructuredMessage`. Его можно хранить в локальных и глобальных переменных, копировать, передавать и т.д. Если в процессе работы необходимо изменить ранее созданный набор параметров, то для этого следует использовать специальный макрос или предоставляемые методы.

Пример:

```cpp
// Добавление значения
YDB_LOG_UPDATE_MESSAGE(context,
    {"socket", socketNum});
...
// Удаление значения
values.RemoveValue("socket");
```

Макрос `YDB_LOG_UPDATE_MESSAGE` либо добавляет параметр в набор, либо изменяет уже существующее с таким именем.

### Вложенные наборы

Возможно создание вложенных наборов прикрепляемых параметров.

Пример:

```cpp
#define YDB_LOG_THIS_FILE_COMPONENT 1
...
void MyFunction() {
    auto context = YDB_LOG_CREATE_MESSAGE(
        {"path", filename});
    ...
    if (err != 0 ) {
        YDB_LOG_ERROR("MyFunction failed",
            context,
            {"errorCode", err});
        return l
    }
    ...
    YDB_LOG_NOTICE("MyFunction successed",
        {"details", context});
}
```

В этом примере к сообщению с текстом `MyFunction successed` будет прикреплены параметр `details.path`.

### Контексты логирования

Формирование и переиспользование наборов прикрепляемых параметров неудобно, поскольку эти наборы нужно указывать при логировании каждого сообщения. Для того, чтобы упростить код, можно задать контекст логирования - набор параметров, которые будут автоматически прикрепляться ко всем сообщениям, отправляемым в журнал в данном потоке исполнения.

Пример:

```cpp
#define YDB_LOG_THIS_FILE_COMPONENT 1
...
void MyFunction() {
    YDB_LOG_CREATE_CONTEXT(
        {"path", filename});
    ...
    if (errorCode != 0 ) {
        YDB_LOG_ERROR("MyFunction failed",
            {"error", errorCode});
        return l;
    }
    ...
    YDB_LOG_NOTICE("MyFunction successed");
}
```

В этом примере параметры `path` будет прикрепляться ко всем сообщениям, логируемым в данном потоке исполнения в функции `MyFunction` и вызываемых ею вложенных функциях вплоть до выхода из функции `MyFunction`. В свою очередь, вложенные функции могут пополнять контекст логирования своими параметрами.

## Рекомендации по наполнению логов

### Стиль кодирования

Рекомендуется следующий стиль кодирования при использования макросов `YDB_LOG_...`:

1. Вся обязательная информация (контекст исполнения, компонент, уровень ошибки, текст сообщения) располагается на одной строке.

2. Каждая пара "прикрепляемый параметр-значение" располагается на отдельной строке.

3. Закрывающая скобка может располагаться либо на той же строке, где и отдельный параметр, либо на отдельной строке, но тогда она должна выравниваться по началу макроса `YDB_LOG`.

4. Если есть возможность не указывать какие-либо обязательные параметры (контекст исполнения, код компонента, уровень ошибки), то лучше их не указывать и воспользоваться более коротким маркосом. В идеальном случае, нужно использовать макросы вида `YDB_LOG_<level>`.

5. Запрещается определять макрос `YDB_LOG_THIS_FILE_COMPONENT` в заголовочных файлах.

### Стиль текстовых сообщений

Рекомендуется следующий стиль написания текстовых сообщений:

1. Сообщения являются осмысленными (и желательно корректными) предложениями на английском языке.

2. Текст может содержать имена классов и функций.

3. Сообщения являются фиксированным текстом без динамически формируемых фрагментов.

4. Вся динамическая информация, известная только на момент исполнения, должна помещаться в виде прикрепляемых параметров.

### Согласование текстов сообщений и названий параметров

Существует простое эмпирическое правило:
> Если взять текст сообщения, и к нему добавить значения параметров в виде `название=значение`, то должно получиться осмысленное, законченное, однозначное и понятное человеку описание произошедшего события.

Например, если в исходном тексте сообщение формируется следующим образом:

```cpp
YDB_LOG_ERROR_CTX(env, "Unable to open file",
    {"path", filename},
    {"errorCode", err});
```

Тогда формируемое описание события выглядит так (параметры сообщения перечисляются в алфавитном порядке):

``
Unable to open file. errorCode=<...>, path=<...>.
``

### Именование отдельных параметров

Стиль именования отдельных параметров строится на двух базовых принципах:

1. В контексте конкретного сообщения значение параметра должно интерпретироваться легко и однозначно. Например, если к сообщению `Response timeout elapsed` прикреплён параметр с названием `timeout=100`, то непонятно, в каких единицах задано значение `100`. В данном случае лучше использовать название параметра `timeoutMs` или т.п.;

{% list tabs %}

- Плохо

```cpp
YDB_LOG_ERROR("Response timeout elapsed",
    {"node", hostName},
    {"request", requestNum},
    {"wait", startTime},
    {"timeout", timeout});
```

- Хорошо

```cpp
YDB_LOG_ERROR("Response timeout elapsed",
    {"nodeHostName", hostName},
    {"requestNum", requestNum},
    {"waitAtPosixTime", startTime},
    {"timeoutMs", timeout});
```

{% endlist %}

2. Семантически близкие параметры должны иметь сходные названия. Например, нежелательно в одних сообщениях идентификатор транзакции обозначить как `txId`, а в других - как `transactionId`. Различное именование одних и тех же понятий затрудняет поиск записей в логах.

Далее перечисляются рекомендации, направленные на выполнение двух указанных выше принипов:

1. Названия параметров пишутся в `camelCase`. Такой выбор сделан исходя из следующих соображений:

* как правило, названия параметров являются короткими строками, состоящими из 2-3 слов. В данном случае, использование `snake_case` не добавит наглядности;

* использование `camelCase` согласуется со стилем именования переменных в исходном коде системы;

* для многих сущностей уже есть рекомендованные названия параметров, которые пишутся `camelCase`. Желательно сохранять общую стилистику.

2. Нежелательно в качестве названий параметров использовать отдельные общеупотребимые слова (`id`, `item`, `value`, `path`, `child`, `parent`, `min`, `max`, и т.п.) - это осложняет поиск записей в логах. Например, слово `id` обозначает идентификатор, но при этом совершенно непонятно, к какой сущности он относится, хотя в контексте конкретного сообщения смысл этого параметра может быть предельно ясен.

3. Названия параметров должны состояеть из нескольких слов, причём главным должно быть последнее, а каждое предшествующее слово должно уточнять последующее. Например:

* `actorId` - идентификатор актора;

* `operationId` - идентификатор операции;

* `operationSessionId` - идентификатор сессии, в рамках которой выполняется операция.

4. Правила обозначения отдельных сущностей и коллекций:

* отдельное упоминание имени сущности в единственном числе предполагает, что значение параметра содержит описание этой сущности. Например, `table` - это описание таблицы (в данном случае `tableId` явно указывает, что параметр содержит идентификатор таблицы);

* отдельное упоминание имени сущности во множественном числе предполагает, что значение параметра содержит описание коллекции сущностей. Например,
`tables` - это описание нескольких таблиц (но не их количество);

* отдельное упоминание имени сущности во множественном числе с добавлением `Count` предполагает, что значение параметра содержит описание коллекции сущностей. Например, `tablesCount` - количество таблиц;

* нежелательно для обозначения количества элементов в коллекции к названию параметра вместо `Count` добавлять `Size`. Например, по названию параметра `totalFilesSize` - не понятно, речь идёт о количестве файлов или их суммарном размере.

5. Если в названии параметра используется общепринятая в YDB аббревиатура или термин, то её следует писать в том регистре, в котором принято. Примеры названия таких параметров:

- `VDiskId` - идентификатор VDisk (пишется не как `vdiskId`);

- `PDiskId` - идентификатор PDisk (пишется не как `pdiskId`);

- и т.д.

6. Допустимо использовать популярные сокращения (`idx` вместо `index`, `msg` вместо `message`, `tx` вместо `transaction` и т.д.).

7. Если параметр содержит некоторую числовую величину, то крайне желательно к названию параметра добавлять размерность величины:

- `Id`, если число является идентификатором (но не как `ID`);

- для размеров памяти следует добавлять `Byte`, `KByte`, `MByte`, например, `allocatedBufferSizeMB`;

- для временных интервалов следует добавлять `Ms`, `Sec`, `Min` и т.п., например, `elapsedTimeoutMs`;

- для указания процентных долей чего-либо следует добавлять `Percent`, например, `diskUsagePercent`;

- если используется нестандартная размерность, то имеет смысл использовать предлог 'In', например, `bufferSizeInBlocks`;

- в некоторых случаях полезно к названию параметров добавлять `Str`, чтобы подёркивать, что параметр содержит текстовое опсиание;

- если параметр содержит json, то к его названию следует добавлять `Json`;

- если параметр содержит шестнадцатиричное число, то либо к названию параметра следует добавлять `Hex`, либо само значение должно начинаться с `0x`;

8. Для логических признаков следут в начало названия параметра добавлять `is`, `has` или т.п. Например, `isConnected`, `hasChildren` и т.п.

9. Не следует в названия параметров добавлять слова-глаголы, например, при смене роли пользователя параметр следует называть не `setRoleId`, а `newRoleId`.

10. Существуют общепринятые названия параметров:

- `actorClassName` - название класса, в котором реализован актор;

- `actorStateName` - состояние актора;

- `backtrace` - cтек возникновения исключения (результат функции `TBackTrace::FromCurrentException().PrintToString()`);

- `ev` - описание сообщения, которое обрабатывает актор;

- `evType` - тип сообщения, которое обрабатывает актор;

- `exception` - описание произошедшего исключения C++;

- `selfId` - идентификатор актора, который обрабатывает сообщение;

### Методология обогащения сообщений контекстной информацией

Предлагается следующая методология для обогащения событий, которые пишет в журнал конкретный актор.

**Шаг 1.** Функция создания контекста логирования.
В акторе должна быть функция, которая формирует текущий контекст логирования в виде структурированного сообщения.

Например, если есть некоторый абстрактный актор чтения файла, то функция создания его контекста логирования может быть такой:

```cpp
TStructuredMessage GetLogContext() const {
    return YDB_LOG_CREATE_MESSAGE(
        {"actorClassName", "TFileReader"},
        {"selfId", SelfId()},
        {"path", filename});
}
```

**ЗАМЕЧАНИЯ:**

1. Вместо имени `GetLogContext` может использоваться `GetLogPrefix` или т.п.

2. Это может быть не функция, а поле класса, создаваемое в конструкторе и изменяемое в ходе работы актора.

**Шаг 2.**  Настройка контекстов логирования.
У каждого актора есть небольшой набор функций, которые могут быть вызваны ядром акторной системой. Сюда входят:

1. Функции 'bootsrap'.

2. Функции обработки сообщений (ищутся по макросу `STATEFN` или т.п.).

3. Прочие виртуальные функции, которые перекрывает актор (они легко ищутся по ключевому слову `override`).

Далее в первой строке каждой такой функции с помощью макроса `YDB_LOG_CREATE_CONTEXT` настраивается контекст логирования.

Пример:

```cpp
STATEFN(StateWork) {
    YDB_LOG_CREATE_CONTEXT(GetLogContext());
    switch (ev->GetTypeRewrite()) {
        ....
    }
}
```

**Альтернативным способом** указания контекста логирования является его явное использование в каждом макросе логирования.
 Пример:

```cpp
YDB_LOG_ERROR_CTX(env, "Unable to open file",
    {"context", GetLogContext()},
    {"errorCode", err});
```

Принципиальным отличием данного способа является то, что имена параметров из контекста будут иметь префикс `context.`.
