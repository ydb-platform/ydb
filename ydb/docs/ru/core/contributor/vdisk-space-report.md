# Отчёт об использовании дискового пространства VDisk

Отчёт об использовании дискового пространства [VDisk](../concepts/glossary.md#vdisk) представляет собой внутренний акторный API для оценки объёма и распределения пространства в чанках, выделенных одному VDisk. Чанк представляет собой фиксированную единицу выделения места на [PDisk](../concepts/glossary.md#pdisk).

{% note warning %}

API предоставляет согласованное только в слабом смысле представление для мониторинга. Его нельзя использовать для принятия решений, влияющих на корректность, размещение данных или выполнение операций. Источники статистики и индексы читаются в разные моменты времени, поэтому ненулевой `ReconciliationDeltaBytes` и неклассифицированные байты являются допустимым результатом.

{% endnote %}

## Важные замечания по использованию API {#important-notes}

Построение отчёта рассчитано на минимальное влияние на производительность VDisk, но всё же потребляет ресурсы актор-системы. Чтобы снизить потенциальное влияние на обработку пользовательской нагрузки, рекомендуется одновременно сканировать не более одного VDisk в группе и не более десяти VDisk на одном узле.

## Акторный API {#actor-api}

Запрос и ответ объявлены в [vdisk_events.h](https://github.com/ydb-platform/ydb/blob/main/ydb/core/blobstorage/vdisk/common/vdisk_events.h):

- `TEvGetVDiskSpaceReportRequest` содержит пустое protobuf-сообщение `TGetVDiskSpaceReportRequest`;
- `TEvGetVDiskSpaceReportResponse` содержит protobuf-сообщение `TGetVDiskSpaceReportResponse`;
- схема результата находится в [space_report.proto](https://github.com/ydb-platform/ydb/blob/main/ydb/core/blobstorage/vdisk/protos/space_report.proto).

Запрос отправляется непосредственно на сервисный [ActorId](../concepts/glossary.md#actorid) нужного VDisk.

Сообщение ответа `TEvGetVDiskSpaceReportResponse` содержит следующие поля:

- `Status`: результат выполнения запроса, представленный строковым именем значения `NKikimrProto::EReplyStatus`;
- `Report`: необязательный структурированный отчёт;
- `ErrorReason`: диагностическое сообщение об ошибке.

На одном VDisk одновременно может выполняться только одно сканирование. Параллельный запрос получает статус `TRYLATER` без отчёта. Такой запрос можно повторить с задержкой.

Поле `Report` является необязательным, поэтому проверяйте его наличие отдельно от `Status`. Статус `ERROR` может сопровождаться частичным отчётом. Текст `ErrorReason` предназначен только для диагностики и не является частью контракта.

Запрос не поддерживает отмену, поэтому вызывающая сторона должна устанавливать собственный срок ожидания. После перезапуска VDisk состояние выполнявшегося запроса не восстанавливается. После истечения срока ожидания отправьте новый запрос, когда VDisk снова будет готов.

## Структура отчёта {#report-structure}

`TVDiskSpaceReport` содержит общий баланс и детализацию по подсистемам. Все размеры измеряются в байтах.

### Общий баланс {#top-level-fields}

| Поле | Значение |
|---|---|
| `ChunkSizeBytes` | Размер одного чанка текущего PDisk. |
| `PDiskAllocatedChunks` | Число чанков, выделенных владельцу VDisk по данным PDisk. |
| `PDiskAllocatedBytes` | Произведение `PDiskAllocatedChunks` и `ChunkSizeBytes`. |
| `AccountedBytes` | Сумма всех полей `Total`. |
| `ReconciliationDeltaBytes` | Знаковая разность `PDiskAllocatedBytes` и `AccountedBytes`. В текущей реализации ожидаемое значение равно нулю или меньше нуля. |
| `Total` | Суммарная классификация всех компонентов отчёта. |

Для интерпретации результата используйте следующие равенства:

```text
PDiskAllocatedBytes = PDiskAllocatedChunks * ChunkSizeBytes
AccountedBytes = сумма полей Total
ReconciliationDeltaBytes = PDiskAllocatedBytes - AccountedBytes
AllocatedBytes компонента = ChunkCount компонента * ChunkSizeBytes
```

### Компоненты {#components}

Каждый обычный компонент имеет поля `ChunkCount`, `AllocatedBytes` и `Breakdown`. В таблице ниже [LogoBlob](../concepts/glossary.md#logoblob) означает запись блоба в Hull, [SST](../concepts/glossary.md#sst) (sorted string table) означает неизменяемый отсортированный сегмент индекса, `Huge` означает аллокатор крупных блобов, `SyncLog` означает журнал синхронизации, а `ChunkKeeper` означает владельца чанков вспомогательных подсистем.

| Компонент | Что учитывается |
|---|---|
| `LogoBlobs` | SST и индекс LogoBlob, а также данные, размещённые внутри Hull. Экстенты Huge учитываются отдельно в `Huge`. |
| `Blocks` | SST и индекс записей блокировки поколений таблеток. |
| `Barriers` | SST и индекс барьеров сборки мусора. |
| `Huge` | Чанки Huge-аллокатора, свободный резерв и статистика слотов по классам размера. |
| `SyncLog` | Активные чанки журнала синхронизации. |
| `ChunkKeeper` | Повторяемые записи по идентификаторам подсистем ChunkKeeper. Сейчас известен только объём чанков, поэтому их байты относятся к `UnclassifiedBytes`. |
| `Unattributed` | Остаток чанков PDisk, не сопоставленных ни с одним именованным компонентом. Все такие байты относятся к `UnclassifiedBytes`. |

### Категории байтов {#breakdown}

`TVDiskSpaceBreakdown` разделяет физический объём по семантическому назначению.

На верхнем уровне весь выделенный объём можно разделить на следующие категории:

- Полезные данные: актуальное содержимое блобов, которое не находится за барьером сборки мусора;
- Метаданные: актуальные индексные и структурные метаданные;
- Мусор: данные и метаданные, которые можно освободить при сборке мусора, слиянии или компакции;
- Фрагментация: неиспользуемое место внутри выделенных чанков;
- Системные данные: актуальные данные вспомогательных подсистем, которые сканер может классифицировать; сейчас это занятые байты SyncLog;
- Прочее: свободные резервы и объём без более точной классификации.

| Поле | Значение | Предлагаемая верхнеуровневая категория |
|---|---|---|
| `UsefulBlobDataBytes` | Полезная нагрузка выбранного актуального физического представления блоба. | Полезные данные |
| `LiveMetadataBytes` | Метаданные актуальных записей и структурные метаданные SST. | Метаданные |
| `LiveAuxiliaryDataBytes` | Актуальные служебные данные вне блобов. Сейчас сюда попадают занятые байты SyncLog. | Системные данные |
| `GcDeadBlobDataBytes` | Данные блобов, которые барьеры сборки мусора разрешают удалить. | Мусор |
| `GcDeadMetadataBytes` | Метаданные, которые барьеры сборки мусора разрешают удалить. | Мусор |
| `MergeRedundantBlobDataBytes` | Старые или дублирующие физические данные, не нужные для сохранения логического значения после слияния. | Мусор |
| `MergeRedundantMetadataBytes` | Старые или дублирующие метаданные, не нужные после слияния. | Мусор |
| `WritePaddingBytes` | Дополнение, записанное из-за выравнивания данных внутри Hull или выравнивания Huge-записи на границу блока записи PDisk. | Фрагментация |
| `SlotInternalFragmentationBytes` | Свободный хвост внутри занятого Huge-слота после выровненной записи. | Фрагментация |
| `FreeSlotBytes` | Свободные и незаблокированные Huge-слоты. | Фрагментация |
| `ChunkTailBytes` | Остаток ёмкости внутри выделенных чанков, не занятый другими категориями. Для SyncLog сюда входят сообщённые им свободные байты. | Прочее |
| `FreeChunkReserveBytes` | Свободные чанки, находящиеся в резерве Huge-аллокатора. | Прочее |
| `LockedOrQuarantinedBytes` | Заблокированные свободные Huge-слоты. | Прочее |
| `UnclassifiedBytes` | Байты, для которых безопасная семантическая классификация отсутствует. | Прочее |

### Классы размера Huge {#huge-size-classes}

`Huge.SizeClasses` детализирует Huge-аллокатор. Каждая запись содержит размер слота, число слотов на чанк, число чанков и счётчики актуальных, удаляемых, избыточных и неклассифицированных слотов. Вложенный `Breakdown` распределяет полную ёмкость чанков класса между полезной нагрузкой и метаданными, выравниванием, внутренней фрагментацией, свободными и заблокированными слотами, неклассифицированным объёмом и хвостами чанков.

| Поле | Значение |
|---|---|
| `SlotSizeBytes` | Физический размер одного слота класса. |
| `SlotsPerChunk` | Число слотов класса в одном чанке. |
| `ChunkCount` | Число чанков, назначенных классу. |
| `LiveSlotCount` | Число слотов с выбранным актуальным представлением блоба. |
| `GcDeadSlotCount` | Число слотов с данными, удаляемыми сборкой мусора. |
| `MergeRedundantSlotCount` | Число слотов с избыточными физическими представлениями. |
| `UnclassifiedSlotCount` | Число слотов без безопасной семантической классификации. |
| `Breakdown` | Распределение полной ёмкости чанков класса по категориям байтов. |

`Huge.FreeReserveChunks` показывает текущее число свободных чанков Huge-аллокатора. Эти чанки также входят в `Huge.Total` через `FreeChunkReserveBytes`.

При полных счётчиках сумма `LiveSlotCount`, `GcDeadSlotCount`, `MergeRedundantSlotCount` и `UnclassifiedSlotCount` равна числу занятых слотов. Свободные и заблокированные свободные слоты представлены только байтами в `Breakdown`. Если аллокатор описал не все слоты, пропущенные слоты добавляются в `UnclassifiedSlotCount`. Если проверка класса размера завершается ошибкой, остальные три счётчика обнуляются, а `UnclassifiedSlotCount` содержит число всех слотов класса.

Если счётчики аллокатора и результат классификации противоречат друг другу, весь класс размера попадает в `UnclassifiedBytes`. Такое поведение сохраняет физический объём класса и не выдаёт недостоверное распределение по категориям.

## Как строится отчёт {#scan-algorithm}

Актор-сканер выполняет работу поэтапно, чтобы не удерживать один снапшот Hull и не блокировать поток актор-системы на долгое время.

1. Запрашивает число выделенных чанков у PDisk и компактную статистику у HugeKeeper, SyncLog и ChunkKeeper.
2. Ждёт ответы источников не более 10 секунд. Статистика PDisk обязательна; без неё ответ не содержит отчёт. При тайм-ауте вспомогательного источника сканирование продолжается с частичным результатом.
3. Последовательно обходит метабазы `LogoBlobs`, `Blocks` и `Barriers`. Перед каждым квантом запрашивается новый снапшот Hull.
4. Для каждого ключа просматривает все физические записи, сливает их логическое значение и применяет барьеры сборки мусора. Выбранное физическое представление классифицируется как полезное, удаляемые записи как `GcDead*`, остальные версии как `MergeRedundant*`.
5. После завершения кванта сохраняет позицию обхода, уничтожает снапшот и при необходимости продолжает со следующего кванта.
6. Объединяет результаты Hull со статистикой аллокаторов и вычисляет общий баланс.

Целевой квант сканирования составляет 5 миллисекунд, после него планируется пауза 10 миллисекунд. Время проверяется после обработки полного ключа, поэтому один большой ключ может увеличить длительность кванта. Общая длительность сканирования не ограничена и зависит от размера индексов.

Сканер обходит метабазы в порядке убывания ключей и между квантами продолжает с ключа ниже последнего обработанного. Поэтому ключи, добавленные выше сохранённой границы, не увеличивают длительность текущего сканирования, но не попадают в отчёт и снижают его точность. Ключи, добавленные ниже границы, могут быть учтены.
