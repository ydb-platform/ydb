# Автоматическое партицирование {#automatic-partitioning}

Для строковых таблиц {{ ydb-short-name }} может автоматически **разделять** (split) и **объединять** (merge) партиции, чтобы подстроиться под объём данных и интенсивность запросов. Это задаётся параметрами `AUTO_PARTITIONING_*` в описании таблицы (см. [{#T}](../../../../concepts/datamodel/table.md#partitioning_row_table)).

Типичное время операции разделения или слияния — порядка **500 мс**; в этот интервал данные по затронутой партиции могут быть кратковременно недоступны для чтения и записи (подробности — в [{#T}](../../../../concepts/datamodel/table.md#partitioning_row_table)).

Ограничения автоматического партицирования (лимиты базы и таблицы, очередь split/merge) описаны ниже в разделе [Ограничения автошардирования](#auto-sharding-limits).

## По объёму (size-based) {#auto-by-size}

Режим **`AUTO_PARTITIONING_BY_SIZE`** включает разделение партиции, когда её размер превышает заданный порог **`AUTO_PARTITIONING_PARTITION_SIZE_MB`**, и объединение соседних партиций, когда суммарный размер достаточно мал (см. точные условия в описании параметров в [`AUTO_PARTITIONING_BY_SIZE`](../../../../concepts/datamodel/table.md#auto_partitioning_by_size)).

Практические ориентиры:

* Рекомендуемый диапазон **`AUTO_PARTITIONING_PARTITION_SIZE_MB`** в документации по умолчанию ориентирован на значения порядка **от десятков мегабайт до 2000 MB**; конкретное значение зависит от профиля нагрузки и допустимой частоты split/merge.
* Слишком **большой** порог при неравномерном доступе к ключам приводит к «тяжёлым» партициям и сильнее нагружает один data shard; слишком **маленький** — к частым split/merge.

Независимо от пользовательского порога, в продукте также участвует внутренняя логика, завязанная на ориентир **~2000 MB** для части решений о разделении — см. [{#T}](../../../../concepts/datamodel/table.md#partitioning_row_table).

При изменении порога на **уже большой таблице** избегайте резкого скачка (например, с 2000 MB до 100 MB сразу). Хотя количество одновременных операций split ограничено, резкое изменение создаст **длинную очередь** из задач на разделение. Все операции из этой очереди будут выполняться последовательно с ограниченным параллелизмом, что может затянуть процесс стабилизации таблицы. Рекомендуем снижать порог постепенно и мониторить состояние; см. также [{#T}](../../../../troubleshooting/performance/schemas/splits-merges.md). Подробнее о лимитах на число одновременных операций — в [Ограничениях автошардирования](#auto-sharding-limits).

## По нагрузке (load-based) {#auto-by-load}

Режим **`AUTO_PARTITIONING_BY_LOAD`** позволяет разделять партицию, когда она **перегружена по CPU**, даже если размер партиции ещё не большой. По умолчанию для строковых таблиц этот режим **выключен** (`DISABLED`); для высокой конкурентной записи/чтения по узкому диапазону ключей его обычно имеет смысл **включить** вместе с [`AUTO_PARTITIONING_MIN_PARTITIONS_COUNT`](../../../../concepts/datamodel/table.md#auto_partitioning_min_partitions_count), выставленным исходя из ожидаемого числа партиций, чтобы избежать их излишнего сжатия при спаде нагрузки.

Каноническое описание порогов и алгоритма (сэмпл ключей, учёт реплик, merge при низкой загрузке) — в [`AUTO_PARTITIONING_BY_LOAD`](../../../../concepts/datamodel/table.md#auto_partitioning_by_load).

### Типичные симптомы перегруженной партиции

* высокая загрузка CPU на отдельных партициях при умеренной общей загрузке кластера;
* рост задержек на «горячих» ключах;
* рост числа внутренних ответов **`STATUS_OVERLOADED`**. Начиная с версии 26.2, Query Processor автоматически повторяет такие запросы, поэтому пользователь обычно наблюдает увеличение задержки, а не саму ошибку.

Один data shard использует **не более одного ядра CPU** для операций изменения и чтения данных на партиции: простое добавление CPU на узел не снимает bottleneck с одной партиции — нужны split и/или ключ, лучше способствующий распределению нагрузки по шардам.

## Ограничения автошардирования {#auto-sharding-limits}

«Автошардирование» здесь означает автоматические **split/merge** партиций строковой таблицы. На практику накладываются лимиты уровня **базы данных** и **таблицы**, а также внутренние ограничения алгоритма.

### Лимиты уровня базы данных

* **Максимальное число таблеток в базе** (`MaxShards`) — при достижении лимита автоматическое разделение партиций прекращается. См. [{#T}](../../../../concepts/limits-ydb.md#schema-object).
* **Максимальное число шардов таблицы** (`MaxShardsInPath`) — верхняя граница числа партиций (data shard) на одном пути таблицы, включая индексы.
* **Жёсткий лимит размера партиции на уровне кластера** — по умолчанию **2 ГиБ** (`ForceShardSplitDataSize`). Если размер партиции превышает этот порог, она разделится, даже если пользовательский [`AUTO_PARTITIONING_PARTITION_SIZE_MB`](../../../../concepts/datamodel/table.md#auto_partitioning_partition_size_mb) выше или достигнут [`AUTO_PARTITIONING_MAX_PARTITIONS_COUNT`](../../../../concepts/datamodel/table.md#auto_partitioning_max_partitions_count). Подробнее — в [{#T}](../../../../concepts/datamodel/table.md#partitioning_row_table).

### Параметры таблицы

[`AUTO_PARTITIONING_MIN_PARTITIONS_COUNT`](../../../../concepts/datamodel/table.md#auto_partitioning_min_partitions_count) задаёт нижнюю границу для автоматического объединения партиций, а [`AUTO_PARTITIONING_MAX_PARTITIONS_COUNT`](../../../../concepts/datamodel/table.md#auto_partitioning_max_partitions_count) — верхнюю границу для обычного автоматического разделения. При достижении максимума разделение по размеру или нагрузке останавливается, но превышение жёсткого лимита размера 2 ГиБ всё равно запускает разделение.

**Рекомендуемая разница между min и max:** если разница между минимумом и максимумом **больше ~20%**, при сильно меняющейся во времени нагрузке компонента [Hive](../../../../concepts/glossary.md#hive) возможны лишние циклы split/merge. Подробнее и что делать — в [{#T}](../../../../troubleshooting/performance/schemas/splits-merges.md).

### Скорость адаптации по нагрузке

При включённом [`AUTO_PARTITIONING_BY_LOAD`](#auto-by-load):

* минимальная продолжительность сэмплирования нагрузки перед решением о разделении составляет **две минуты**;
* за одну операцию партиция разделяется **не более чем на две** части.

При значительном или многократном росте нагрузки адаптация партицирования может занимать **единицы и десятки минут**. В течение этого времени перегруженные партиции могут возвращать внутренние ответы `OVERLOADED`, которые начиная с версии 26.2 автоматически обрабатываются повторными попытками в Query Processor. Для пользователя это проявляется прежде всего увеличением задержки.

Разделение и объединение партиций включают **компакшен** данных партиции — дополнительную нагрузку на диск.

После завершения сэмплирования обработка решения о разделении таблетки в [scheme shard](../../../../concepts/glossary.md#scheme-shard) может занимать около **15 секунд** (см. [{#T}](../../../../troubleshooting/performance/schemas/splits-merges.md)).

### Очередь операций split/merge

Одновременно на **таблице** может выполняться ограниченное число операций split — остальные партиции ждут в очереди. Дополнительно Scheme shard ограничивает общее число параллельных split/merge в базе.

### Вторичные индексы

Параметры партиционирования задаются для **таблицы**; индекс имеет свой набор партиций и свои правила по умолчанию — см. [{#T}](../../../../concepts/datamodel/table.md#partitioning_row_table).

{% note warning %}

Колоночные таблицы: автоматическое репартицирование по тем же правилам **не поддерживается** — число партиций задаётся при проектировании таблицы. См. [{#T}](../column-oriented.md).

{% endnote %}
