# Первоначальная синхронизация асинхронной репликации с помощью резервного копирования и восстановления

При этом способе первоначальной синхронизации исходные данные переносятся в приёмник из резервной копии в S3-совместимом хранилище. Затем [асинхронная репликация](../concepts/async-replication.md) применяет накопленные изменения и продолжает синхронизировать базы данных. Во время переноса приложения могут продолжать записывать данные в источник.

Этот способ позволяет использовать серверные операции [резервного копирования](../reference/ydb-cli/export-import/export-s3.md) и [восстановления](../reference/ydb-cli/export-import/import-s3.md) для переноса большого объёма данных. При [первоначальном CDC-сканировании](../concepts/async-replication.md#initial-scan) все исходные данные передаются через потоки изменений, а отдельная резервная копия не требуется. Различия в ресурсных и эксплуатационных затратах приведены в [сравнении способов первоначальной синхронизации](../concepts/async-replication.md#initial-sync-comparison).

## Подготовка {#prerequisites}

В примере таблица `original_table` базы `/Root/source` переносится в таблицу `replica_table` базы `/Root/target`. Экземпляр репликации `my_replication` создаётся в приёмнике. Команды используют [профили {{ ydb-short-name }} CLI](../reference/ydb-cli/profile/index.md) `source` и `target` для подключения к соответствующим базам данных.

Перед началом работы:

- Настройте профили и проверьте подключение к обеим базам с помощью [команды `scheme ls`](../reference/ydb-cli/commands/scheme-ls.md).
- Подготовьте [права для асинхронной репликации](../concepts/async-replication.md#init), экспорта на источнике и импорта в приёмнике. Пользователю, создающему экземпляр репликации, потребуется возможность изменять восстановленные таблицы для подключения их в качестве реплик.
- В приёмнике [создайте секрет](../yql/reference/syntax/create-secret.md) `source_token` с токеном для подключения репликации к источнику.
- Подготовьте бакет `mybucket` и [аутентификацию в S3](../reference/ydb-cli/export-import/auth-s3.md). В примерах используется эндпоинт `storage.yandexcloud.net`, а ключи доступа читаются из переменных окружения или файла `~/.aws/credentials`. Эндпоинт должен быть доступен с серверов обеих баз данных: источник записывает резервную копию, приёмник читает её.
- Выберите свободный префикс `replication-bootstrap` в бакете. Не изменяйте содержимое выгрузки до завершения импорта.
- Убедитесь, что таблица `replica_table` отсутствует в приёмнике. Команда `import s3` создаёт таблицу вместе с данными и не перезаписывает существующие таблицы. Проверить путь можно командой `scheme ls`.

На время первоначальной синхронизации сохраните состав реплицируемых таблиц, их столбцов и индексов. Схемы таблиц в резервной копии должны соответствовать схемам источника при запуске репликации.

{% note warning %}

Записи в [потоках изменений](../concepts/cdc.md) хранятся ограниченное время. Планируйте экспорт, импорт и обработку накопленных изменений так, чтобы репликация успела прочитать записи до их удаления. По умолчанию время хранения составляет 24 часа; фактическое значение нужно проверить после создания потоков. Состояние `PAUSED` не останавливает отсчёт времени хранения.

{% endnote %}

## 1. Создайте репликацию без первоначального сканирования {#create-replication}

Выполните в приёмнике запрос [CREATE ASYNC REPLICATION](../yql/reference/syntax/create-async-replication.md) с параметром `INITIAL_SCAN = FALSE`. YQL-запросы из этого руководства можно выполнить [командой `sql`](../reference/ydb-cli/sql.md) с профилем `target`.

```yql
CREATE ASYNC REPLICATION my_replication
FOR original_table AS replica_table
WITH (
    CONNECTION_STRING = 'grpcs://source.example.com:2135/?database=/Root/source',
    TOKEN_SECRET_PATH = 'source_token',
    INITIAL_SCAN = FALSE
);
```

Адрес `source.example.com:2135` в примере соответствует эндпоинту источника. Параметры `CONNECTION_STRING` и `TOKEN_SECRET_PATH` задают подключение, которое приёмник будет использовать для создания и чтения потоков изменений.

Репликация создаётся в состоянии `PAUSED` и подготавливает потоки изменений на источнике без выгрузки первоначальных данных. Таблица `replica_table` пока не создаётся и не подключается к репликации. Её создаст операция импорта.

## 2. Дождитесь готовности потоков изменений {#wait-for-changefeeds}

Создание потоков выполняется асинхронно. До запуска экспорта проверьте, что они готовы для всех реплицируемых таблиц, включая таблицы реализации индексов, если они входят в репликацию.

Получите [описание репликации](../reference/ydb-cli/commands/scheme-describe.md) в формате JSON:

```bash
{{ ydb-cli }} -p target scheme describe my_replication --format proto-json-base64
```

Проверьте следующие поля:

- `paused`: репликация ожидает запуска после импорта. Наличие этого поля само по себе не подтверждает готовность потоков.
- `items`: перечень объектов с путями `source_path` и `destination_path`. Дождитесь появления всех ожидаемых объектов.
- `source_changefeed_name` у каждого объекта: имя потока изменений. Имя назначается автоматически; не задавайте его вручную.

Для таблицы `original_table` проверьте состояние потока на источнике:

```bash
{{ ydb-cli }} -p source scheme describe original_table --format proto-json-base64
```

В массиве `changefeeds` найдите поток с именем из `source_changefeed_name`. Его поле `state` должно иметь значение `STATE_ENABLED`.

Для элемента, соответствующего синхронному или уникальному индексу, `source_path` указывает на индекс. Его таблица реализации находится по пути `source_path/indexImplTable`. Проверяйте массив `changefeeds` в описании этой таблицы.

Также проверьте [параметры топика потока изменений](../concepts/cdc.md#topic-options): наличие читателя `replicationConsumer` и значение `RetentionPeriod`. Путь к потоку зависит от объекта:

| Объект | Путь к потоку изменений |
| --- | --- |
| Таблица | `source_path/source_changefeed_name` |
| Таблица реализации индекса | `source_path/indexImplTable/source_changefeed_name` |

В этих путях используйте значения полей из описания репликации. Для проверки выполните команду:

```bash
{{ ydb-cli }} -p source scheme describe <changefeed-path>
```

Где:

- `<changefeed-path>`: путь к потоку изменений, например `/Root/source/original_table/stream-name`. Вместо `stream-name` используйте имя из описания репликации.

Повторите проверки для каждого объекта из `items`. Если времени хранения недостаточно, увеличьте его до длительного переноса с помощью [ALTER TOPIC](../yql/reference/syntax/alter-topic.md#alter-topic). Изменение времени хранения не восстанавливает уже удалённые записи.

{% note warning %}

Запускайте экспорт только после готовности всех потоков изменений. Если резервная копия сделана раньше, изменения между её созданием и запуском потоков могут быть потеряны для репликации. Использовать произвольную ранее созданную резервную копию для этой процедуры нельзя.

{% endnote %}

## 3. Экспортируйте исходные данные {#export}

Запустите [экспорт в S3](../reference/ydb-cli/export-import/export-s3.md) с профилем источника:

```bash
{{ ydb-cli }} -p source export s3 \
  --s3-endpoint storage.yandexcloud.net \
  --bucket mybucket \
  --destination-prefix replication-bootstrap \
  --include original_table \
  --include-index-data true
```

Выгрузка таблицы будет размещена под префиксом `replication-bootstrap/original_table`. Параметр `--include-index-data true` сохраняет также данные индексных таблиц, если у исходной таблицы есть индексы. На шаге импорта они будут загружены из резервной копии.

Для нескольких таблиц укажите `--include` для каждой из них в одной операции экспорта: сервер создаёт согласованную копию таблиц. Состав выгрузки должен соответствовать набору объектов репликации.

Команда возвращает идентификатор серверной операции. Дождитесь её успешного завершения с помощью [`operation get`](../reference/ydb-cli/export-import/export-s3.md#status):

```bash
{{ ydb-cli }} -p source operation get <export-operation-id>
```

Где:

- `<export-operation-id>`: идентификатор, полученный при запуске экспорта.

Переходите к импорту только при значениях `ready = true`, `status = SUCCESS` и `progress = Done` в табличном выводе. Успешный запуск команды экспорта ещё не означает завершение выгрузки.

Приложения могут продолжать изменять данные источника. Потоки изменений сохраняют эти изменения, пока репликация находится в состоянии `PAUSED`.

## 4. Импортируйте данные в приёмник {#import}

После успешного экспорта запустите [импорт из S3](../reference/ydb-cli/export-import/import-s3.md) с профилем приёмника:

```bash
{{ ydb-cli }} -p target import s3 \
  --s3-endpoint storage.yandexcloud.net \
  --bucket mybucket \
  --item src=replication-bootstrap/original_table,dst=replica_table \
  --index-population-mode import
```

Параметр `--item` сопоставляет префикс таблицы в резервной копии с целевым путём `replica_table`, указанным в `CREATE ASYNC REPLICATION`. Режим `--index-population-mode import` загружает данные индексов, сохранённые на предыдущем шаге. Для нескольких таблиц укажите отдельный `--item` для каждой пары путей.

Дождитесь успешного завершения операции с помощью [`operation get`](../reference/ydb-cli/export-import/import-s3.md#status):

```bash
{{ ydb-cli }} -p target operation get <import-operation-id>
```

Где:

- `<import-operation-id>`: идентификатор, полученный при запуске импорта.

Убедитесь, что `ready = true`, `status = SUCCESS` и `progress = Done`. Проверьте созданную таблицу:

```bash
{{ ydb-cli }} -p target scheme describe replica_table
```

До запуска репликации восстановленная таблица является обычной таблицей. Не записывайте в неё данные приложения: такие записи не синхронизируются с источником и могут быть перезаписаны при применении изменений.

## 5. Запустите репликацию изменений {#start-replication}

После завершения импорта всех таблиц выполните в приёмнике запрос [ALTER ASYNC REPLICATION](../yql/reference/syntax/alter-async-replication.md):

```yql
ALTER ASYNC REPLICATION my_replication SET (STATE = 'STANDBY');
```

Приёмник проверит соответствие схем восстановленных таблиц источнику и подключит их как объекты-реплики. Проверка включает первичный ключ, столбцы, их типы, семейства столбцов и индексы. Подключённые таблицы становятся доступны только для чтения, а репликация начинает применять накопленные изменения.

Записи читаются из потоков изменений, созданных перед экспортом. Среди них могут быть изменения, уже отражённые в резервной копии. Пока накопленные записи не обработаны, содержимое приёмника может изменяться и ещё не соответствует текущему состоянию источника.

Проверьте состояние и отставание:

```bash
{{ ydb-cli }} -p target scheme describe my_replication --stats
```

После запуска в описании поле `paused` сменяется полем `running`. Статистика содержит отставание репликации и отдельных объектов. Дождитесь обработки накопленных изменений; отсутствие значения отставания не означает, что оно равно нулю.

После этого репликация продолжает переносить новые изменения. Если цель переноса состоит в миграции приложений, выполните отдельную процедуру [завершения асинхронной репликации](../concepts/async-replication.md#done) перед переключением пишущей нагрузки в приёмник.

## Ошибки и повторные попытки {#errors}

- Если экспорт или импорт завершился ошибкой, проверьте статус и описание ошибки через `operation get`. Сохраняйте репликацию в состоянии `PAUSED`, пока импорт всех таблиц не завершится успешно. При повторном импорте учитывайте, что целевые таблицы не должны существовать; ошибка операции не является подтверждением отсутствия созданных объектов.
- Если запуск репликации завершился ошибкой, получите JSON-описание репликации и проверьте поле `error`. В частности, проверьте наличие всех целевых таблиц, соответствие схем и права доступа. Не запускайте импорт поверх таблиц, которые уже подключены как реплики.
- Если нужные CDC-записи удалены из-за истечения срока хранения, продолжение чтения не обеспечит полноту данных. Повторите первоначальную синхронизацию с новыми потоками изменений и новой резервной копией.
- Перезапуск контроллера репликации сохраняет состояние `PAUSED`; он не заменяет явный перевод в `STANDBY`. При прерывании сессии CLI проверяйте ранее запущенные серверные операции по их идентификаторам, прежде чем запускать новые.

Подробнее о временных и критичных ошибках см. в разделе [Обработка ошибок в процессе асинхронной репликации](../concepts/async-replication.md#error-handling).
