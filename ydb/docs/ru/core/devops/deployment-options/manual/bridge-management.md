## Управление кластером в режиме bridge

{% include [feature_enterprise.md](../../../_includes/feature_enterprise.md) %}

Ниже приведены типовые операции по преобразованию кластера в [режим bridge](../../../concepts/bridge.md) и управлению им с использованием [соответствующих команд {{ ydb-short-name }} CLI](../../../reference/ydb-cli/commands/bridge/index.md).

### Преобразовать обычный кластер в bridge с одним pile {#convert}

Преобразование включает режим bridge для системного хранилища и, по умолчанию, для всех существующих пулов хранения баз данных. Существующие данные сохраняются. Операция необратима.

1. Убедитесь, что кластер использует конфигурацию V2 с `self_management_config.enabled: true`, а на каждом статическом и динамическом узле работает сборка с поддержкой преобразования в bridge. Если используется конфигурация V1, сначала выполните [миграцию на V2](../../configuration-management/migration/migration-to-v2.md).

2. Получите текущую конфигурацию через доступный узел:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 admin cluster config fetch > config.yaml
    ```

3. Добавьте ровно один pile в секцию `config.bridge_config` файла `config.yaml`, сохранив `metadata` и остальные настройки:

    ```yaml
    config:
      bridge_config:
        piles:
          - name: pile-a
    ```

    Чтобы оставить существующие пулы баз данных обычными, также установите `bridge_config.enable_non_uniform_storage: true`. Не задавайте этот параметр при преобразовании по умолчанию: если потребуется одновременно использовать обычное хранилище и хранилище в режиме bridge, его можно будет включить после завершения преобразования.

4. Замените конфигурацию и выполните скользящий перезапуск всех статических и динамических узлов. До начала преобразования каждый подключённый узел должен работать с новым `bridge_config`:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 -y admin cluster config replace -f config.yaml
    ```

5. Выберите нужный вариант и выполните только одну команду.

    Для стандартного преобразования системного хранилища и всех существующих пулов баз данных в режим bridge выполните:

    ```bash
    {{ ydb-cli }} -y admin cluster bridge convert
    ```

    Если нужно преобразовать только системное хранилище, а существующие пулы баз данных оставить обычными, выполните вместо этого:

    ```bash
    {{ ydb-cli }} -y admin cluster bridge convert --skip-storage-pool-conversion
    ```

    Второй вариант требует `bridge_config.enable_non_uniform_storage: true`, заданного на шаге 3. Позже каждую существующую базу данных можно отдельно [перевести в режим bridge](#database-mode).

6. С помощью [bridge list](#list) дождитесь завершения преобразования. Пока вывод содержит `Conversion from non-bridged cluster is in progress, piles can't be added yet`, список pile изменять нельзя. После завершения единственный pile находится в состоянии `PRIMARY`.

Преобразование объединяет все существующие узлы в один pile и не создаёт отдельный pile для каждого существующего датацентра. Подробнее о команде см. в [admin cluster bridge convert](../../../reference/ydb-cli/commands/bridge/convert.md).

### Добавить pile {#add-pile}

При добавлении pile выделяются ресурсы хранения и синхронизируются данные в режиме bridge без остановки кластера.

1. Если вы запускали [преобразование обычного кластера](#convert), дождитесь его завершения. Если кластер изначально работал в режиме bridge или преобразование уже завершено, дополнительное ожидание не требуется. В любом случае перед добавлением pile проверьте состояние кластера:

    ```bash
    {{ ydb-cli }} admin cluster bridge list
    ```

    Дождитесь исчезновения сообщения `Conversion from non-bridged cluster is in progress, piles can't be added yet` и любых ожидающих операций `ADD` или `REMOVE`.

2. Если всем существующим узлам уже назначены имена их pile, пропустите этот шаг. Иначе назначьте имена до добавления нового pile в `bridge_config`.

    Получите текущую конфигурацию:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 admin cluster config fetch > config.yaml
    ```

    В секции `config.hosts` найдите запись каждого существующего статического узла и добавьте `location.bridge_pile_name` с именем его текущего pile. Изменяйте существующие записи, не дублируйте их и сохраняйте остальные поля `location`:

    ```yaml
    config:
      hosts:
        - host: node-a1
          host_config_id: 1
          location:
            data_center: dc-a
            rack: rack-a1
            bridge_pile_name: pile-a
        # ... аналогично обновите остальные существующие статические узлы
    ```

    Для каждого существующего динамического узла укажите его текущий pile в параметре командной строки `ydbd server`, например `--bridge-pile-name pile-a`. Динамические узлы не перечисляются в секции `hosts`.

    Примените изменение конфигурации статических узлов:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 -y admin cluster config replace -f config.yaml
    ```

    Выполните [скользящий перезапуск](../../../maintenance/manual/node_restarting.md) всех статических и динамических узлов, настройки которых изменились. Не добавляйте новый pile в `bridge_config`, пока перезапуск не завершён.

3. Получите актуальную конфигурацию ещё раз, чтобы использовать её текущую версию:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 admin cluster config fetch > config.yaml
    ```

    Добавьте новый pile в `bridge_config.piles` и его статические узлы в `hosts`. Для каждого нового узла укажите `location.bridge_pile_name`, как описано в [конфигурации hosts](../../../reference/configuration/hosts.md#hosts-bridge). Если диски новых узлов описывает существующая запись в `host_configs`, используйте её `host_config_id`; иначе добавьте новую типовую конфигурацию.

    Например, следующий фрагмент секции `config` описывает `pile-a` и `pile-b` с одинаковой конфигурацией дисков. Для краткости показано по одному статическому узлу в каждом pile. Добавьте все необходимые узлы и сохраните `metadata`, существующие записи и остальные настройки из `config.yaml`:

    ```yaml
    config:
      bridge_config:
        piles:
          - name: pile-a
          - name: pile-b

      host_configs:
        - host_config_id: 1
          drive:
            - path: /dev/disk/by-partlabel/ydb_disk_ssd_01
              type: SSD

      hosts:
        - host: node-a1
          host_config_id: 1
          location:
            data_center: dc-a
            rack: rack-a1
            bridge_pile_name: pile-a
        # ... остальные статические узлы pile-a
        - host: node-b1
          host_config_id: 1
          location:
            data_center: dc-b
            rack: rack-b1
            bridge_pile_name: pile-b
        # ... остальные статические узлы pile-b
    ```

    Если в `system_tablets` явно перечислены идентификаторы узлов, добавьте туда узлы нового pile, чтобы системные таблетки могли запускаться в нём после switchover или failover.

4. Примените обновлённую конфигурацию через доступный узел:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 -y admin cluster config replace -f config.yaml
    ```

    Запустите статические узлы нового pile и проверьте его состояние:

    ```bash
    {{ ydb-cli }} -e grpc://<node>:2135 admin cluster bridge list
    ```

    Узлы остаются без нагрузки, пока вывод команды показывает pile в состоянии `INACTIVE`.

5. Подготовьте хранилище нового pile:

    ```bash
    {{ ydb-cli }} -y admin cluster bridge provision-pile --pile pile-b
    ```

    Команда запускает операцию `ADD`, которая создаёт части статических групп и групп в режиме bridge для нового pile. Обычные группы не изменяются. С помощью [bridge list](#list) дождитесь завершения операции и перехода pile в состояние `DISCONNECTED`.

6. Подключите подготовленный pile к кластеру:

    ```bash
    {{ ydb-cli }} -y admin cluster bridge join-pile --pile pile-b
    ```

    Pile переходит в состояние `NOT_SYNCHRONIZED`, синхронизируется в фоновом режиме, а затем автоматически становится `SYNCHRONIZED`. Дождитесь этого состояния с помощью [bridge list](#list).

7. Запустите динамические узлы нового pile, добавив к команде `ydbd server` параметр `--bridge-pile-name pile-b` в дополнение к остальным параметрам запуска.

Подробнее о командах см. в [provision-pile](../../../reference/ydb-cli/commands/bridge/provision-pile.md) и [join-pile](../../../reference/ydb-cli/commands/bridge/rejoin.md).

### Удалить pile {#remove-pile}

При удалении pile безвозвратно удаляются его части групп хранения и все данные в них.

1. Если единственные сохранённые копии какой-либо базы данных находятся в удаляемом pile, например после переключения в обычный режим с `--retain-pile pile-b`, сначала [переведите эту базу в режим bridge](#database-mode). Состояния pile при этом могут не измениться. Перед возвратом базы в обычный режим с `--retain-pile pile-a` дождитесь, пока каждая преобразуемая группа хранения получит часть в состоянии `SYNCED` в `pile-a`, как описано в разделе [проверки переключения режима](#verify-database-mode). После переключения в обычный режим избыточные части групп переходят в состояние `BLOCKS` и удаляются в фоновом режиме.

2. Если удаляемый `pile-b` находится в состоянии `PRIMARY`, сначала выполните [switchover](#switchover) на другой синхронизированный pile, например `pile-a`. Затем выполните [плановое отключение](#takedown) удаляемого pile и проверьте его состояние:

    ```bash
    # Только если pile-b — текущий PRIMARY:
    {{ ydb-cli }} admin cluster bridge switchover --new-primary pile-a

    {{ ydb-cli }} admin cluster bridge takedown --pile pile-b
    {{ ydb-cli }} admin cluster bridge list
    ```

    Повторяйте `bridge list`, пока `pile-b` не перейдёт в состояние `DISCONNECTED`, затем остановите все его узлы.

3. Удалите pile:

    ```bash
    {{ ydb-cli }} -y admin cluster bridge destroy-pile --pile pile-b
    ```

    Перед запуском операции `REMOVE` {{ ydb-short-name }} проверяет, что ни одна обычная группа хранения не содержит VDisk в этом pile и ни одна группа в режиме bridge не зависит только от своей части в нём. Если проверка не пройдена, команда возвращает ошибку с идентификатором группы и не начинает удаление. После устранения причины ошибки повторите команду.

    После успешной проверки команда запускает операцию `REMOVE`. С помощью [bridge list](#list) дождитесь завершения операции и перехода pile в состояние `INACTIVE`. Без глобального параметра `-y` команда запрашивает подтверждение перед удалением данных.

4. После перехода pile в `INACTIVE` удалите его запись из `bridge_config.piles`, его хосты из `hosts`, а идентификаторы его узлов из всех явно заданных списков `system_tablets`. Из `host_configs` удаляйте только те конфигурации, на которые больше не ссылается ни один оставшийся хост. В примере выше конфигурацию с `host_config_id: 1` нужно сохранить: её использует `node-a1`.

Подробнее о команде см. в [admin cluster bridge destroy-pile](../../../reference/ydb-cli/commands/bridge/destroy-pile.md).

5. Примените обновлённую конфигурацию:

    ```bash
    {{ ydb-cli }} admin cluster config replace -f config.yaml
    ```

    Выполните [скользящий перезапуск](../../../maintenance/manual/node_restarting.md) оставшихся статических и динамических узлов, как требуется после изменения [bridge_config](../../../reference/configuration/bridge_config.md).

### Переключить базу данных между хранилищем в режиме bridge и обычным хранилищем {#database-mode}

Кластер bridge может одновременно содержать базы данных с хранилищем в режиме bridge и базы данных с обычным хранилищем, если установлено `bridge_config.enable_non_uniform_storage: true`. Преобразование кластера должно быть завершено, а добавление или удаление pile не должно выполняться. Если вы изменили этот параметр конфигурации, перезапустите все статические и динамические узлы перед продолжением.

Выберите одну из двух команд в зависимости от требуемого режима хранения. Это альтернативные операции: не выполняйте их последовательно. Каждая команда изменяет все пулы хранения выбранной базы данных без удаления её существующих данных.

```bash
# Реплицировать базу данных во все подготовленные pile:
{{ ydb-cli }} -y admin cluster bridge set-database-mode bridged --target-database /Root/db1

# Сохранить копии в pile-a и удалить избыточные копии в других pile в фоновом режиме:
{{ ydb-cli }} -y admin cluster bridge set-database-mode ordinary --target-database /Root/db1 --retain-pile pile-a
```

В `--target-database` необходимо указать абсолютный путь к базе данных. Этот параметр не зависит от глобального параметра подключения `--database`. Для serverless-базы данных укажите её коммунальную базу данных: изменение применяется к коммунальной базе и всем её serverless-базам.

При переключении в обычный режим параметр `--retain-pile` выбирает pile, части групп в котором необходимо сохранить. Он не отключает pile и не меняет его роль: можно указать `PRIMARY` или другой pile в состоянии `SYNCHRONIZED`. В выбранном pile уже должны быть синхронизированные части всех переводимых групп. Если параметр не указан, {{ ydb-short-name }} автоматически выбирает сохраняемые копии, которые могут находиться в разных pile для разных групп.

При переключении в режим bridge каждая существующая группа должна находиться внутри одного pile; группу, охватывающую несколько pile, нельзя преобразовать напрямую.

Команда атомарно изменяет режим всех пулов базы данных: если проверка не пройдена, режим ни одного пула не изменяется. После успешного изменения режима фоновая синхронизация или очистка может ещё продолжаться. Подробнее о команде см. в [admin cluster bridge set-database-mode](../../../reference/ydb-cli/commands/bridge/set-database-mode.md).

### Проверить переключение режима хранения {#verify-database-mode}

Успешное завершение `set-database-mode` подтверждает атомарное изменение режима всех пулов базы данных, но не завершение фоновой синхронизации или очистки. Команда `bridge list` не показывает эти операции с группами хранения базы данных; состояния pile могут оставаться прежними.

Для диагностики используйте [системное представление `.sys/ds_groups`](../../../devops/observability/system-views.md#ds_groups). Сначала получите идентификаторы пулов хранения базы данных:

```bash
{{ ydb-cli }} sql -s '
SELECT BoxId, StoragePoolId, Name
FROM `/Root/.sys/ds_storage_pools`
WHERE Name LIKE "/Root/db1:%";
'
```

Затем получите состояние групп каждого пула:

```bash
{{ ydb-cli }} sql -s '
SELECT
    GroupId,
    ProxyGroupId,
    BridgePileId,
    BridgeSyncStage,
    BridgeDataSyncProgress,
    BridgeSyncRunning,
    BridgeSyncLastError
FROM `/Root/.sys/ds_groups`
WHERE BoxId = <box-id>
  AND StoragePoolId = <storage-pool-id>
ORDER BY GroupId;
'
```

Здесь `<box-id>` и `<storage-pool-id>` — идентификаторы из результата первого запроса. Проверяйте строки физических частей групп с заполненным `BridgePileId`; у логических proxy-групп поля синхронизации могут быть пустыми. Поле `ProxyGroupId` связывает физическую часть с логической группой. У исходной inline-части это поле может быть пустым, а её `GroupId` совпадает с идентификатором логической группы.

Критерии завершения зависят от выбранного режима:

- **Полный переход в режим bridge:** все участвующие pile находятся в состоянии `PRIMARY` или `SYNCHRONIZED`, а все их физические части каждой логической группы — в состоянии `SYNCED`.
- **Готовность к переключению в обычный режим с `--retain-pile`:** выбранный pile находится в состоянии `PRIMARY` или `SYNCHRONIZED`, а в каждой преобразуемой логической группе его часть уже находится в состоянии `SYNCED`.
- **Завершение очистки после переключения в обычный режим:** строки избыточных частей сначала показывают состояние `BLOCKS`, а затем исчезают; остаются только сохранённые физические части.

Поле `BridgeSyncLastError` содержит последнюю ошибку синхронизации. `BridgeDataSyncProgress` показывает прогресс только этапа копирования данных, а не всего преобразования. Не используйте `BridgeSyncRunning = false` как единственный признак завершения: синхронизация может ещё ожидать запуска.

### Посмотреть текущее состояние {#list}

Показывает текущее состояние каждого pile, настроенного на кластере {{ ydb-short-name }}, ход преобразования и выполняющиеся операции с pile.

```bash
{{ ydb-cli }} admin cluster bridge list
```

Пример вывода:

```text
Pile pile-a: PRIMARY
Pile pile-b: SYNCHRONIZED
Generation: 4
```

### Плановая смена `PRIMARY` (switchover) {#switchover}

Если известно, что в обозримом будущем запланированы плановые работы в датацентре или на оборудовании, на котором работает текущий `PRIMARY` pile, то рекомендуется заранее переключить кластер на использование другого pile в роли `PRIMARY`. Выберите другой pile в состоянии `SYNCHRONIZED`, чтобы переключить его в состояние `PRIMARY` следующей командой:

```bash
{{ ydb-cli }} admin cluster bridge switchover --new-primary <pile>
```

Переключение выполняется плавно: роли проходят через `PRIMARY/PROMOTED` и завершаются в состоянии `SYNCHRONIZED/PRIMARY`.

### Плановое отключение pile (takedown) {#takedown}

Если плановые работы приведут к недоступности одного из pile, его необходимо вывести из кластера перед их началом с помощью следующей команды:

```bash
{{ ydb-cli }} admin cluster bridge takedown --pile <pile>
# если отключаете текущий PRIMARY:
{{ ydb-cli }} admin cluster bridge takedown --pile <current-primary> --new-primary <synchronized-pile>
```

При выполнении операции pile переводится в `SUSPENDED`, затем — в `DISCONNECTED`; дальнейшие операции с кластером выполняются без участия отключённого pile.

Если отключается текущий `PRIMARY` и не было возможности [сменить его заранее](#switchover), то эти операции можно совместить, указав новый `PRIMARY` в аргументе `--new-primary`, который должен быть в состоянии `SYNCHRONIZED`.

```bash
{{ ydb-cli }} admin cluster bridge takedown --pile <pile>
# если отключаете текущий PRIMARY:
{{ ydb-cli }} admin cluster bridge takedown --pile <current-primary> --new-primary <synchronized-pile>
```

{% note warning %}

Перед началом плановых работ обязательно убедитесь через команду [list](#list), что операция вывода pile из кластера завершилась успешно и все pile находятся в ожидаемом состоянии.

{% endnote %}

### Аварийное отключение недоступного pile (failover) {#failover}

Так как между pile работает синхронная репликация, то при неожиданном выходе одного из них из строя работа кластера по умолчанию останавливается, и необходимо принять решение, продолжать ли работу кластера без этого pile. Это решение может принимать как человек (например, дежурный DevOps-инженер), так и внешняя по отношению к кластеру {{ ydb-short-name }} автоматизация.

В случае положительного решения о продолжении работы кластера необходимо выполнить следующую команду:

```bash
{{ ydb-cli }} admin cluster bridge failover --pile <unavailable-pile>
```

Если недоступен текущий `PRIMARY`, необходимо добавить параметр `--new-primary` с указанием имени pile в состоянии `SYNCHRONIZED`. Если параметр не указан или указан некорректно, команда завершится с ошибкой без изменений в кластере.

```bash
{{ ydb-cli }} admin cluster bridge failover --pile <unavailable-pile>
# если недоступен текущий PRIMARY:
{{ ydb-cli }} admin cluster bridge failover --pile <unavailable-primary> --new-primary <synchronized-pile>
```

Если одновременно отказали несколько pile, перечислите их в одной команде, повторив `--pile`. Например, если отказали `pile-a` и `pile-b`, а `pile-c` остаётся `SYNCHRONIZED`, подключитесь к узлу в `pile-c` и выполните:

```bash
{{ ydb-cli }} admin cluster bridge failover --pile pile-a --pile pile-b --new-primary pile-c
```

Одно обновление конфигурации отключает оба недоступных pile и выбирает новый `PRIMARY`. Отключение по одному может не сработать: пока второй отказавший pile участвует в кворуме конфигурации, для первого обновления невозможно собрать этот кворум. В оставшемся pile по-прежнему должны быть доступны кворумы узлов и хранилища, необходимые для применения новой конфигурации и обработки запросов.

Перед выполнением команды убедитесь, что отказавшие pile остановлены или изолированы и не смогут самостоятельно возобновить обработку запросов. Не выполняйте failover независимо по разные стороны сетевого разделения; см. [восстановление после split-brain](../../../concepts/bridge.md#split-brain). Команда не включает автоматическое переключение и не позволяет назначить несинхронизированный pile новым `PRIMARY`. После успешного выполнения проверьте результат командой [list](#list). После устранения отказа верните каждый pile командой [rejoin](#rejoin).

Недоступный pile будет переведён в состояние `DISCONNECTED`, а при указании нового `PRIMARY` произойдёт переключение этой роли. Если остальные pile находятся в состояниях, отличных от `SYNCHRONIZED`, аварийное отключение также может быть выполнено. Допустимые переходы зависят от текущей пары состояний и приведены на [диаграмме состояний](../../../concepts/bridge.md#pile-states) и в [таблице переходов](../../../concepts/bridge.md#transitions-between-states).

{% note warning %}

Если включена обязательная аутентификация, то в аварийном состоянии кластера аутентификация по логину и паролю не может быть использована — используйте аутентификацию по клиентским сертификатам. Подробнее см. [{#T}](#emergency-auth).

{% endnote %}

### Вернуть pile в кластер (rejoin) {#rejoin}

После завершения плановых работ или устранения причин отказа ранее отключённые pile необходимо явным образом вводить обратно в эксплуатацию следующей командой:

```bash
{{ ydb-cli }} admin cluster bridge rejoin --pile <pile>
```

Сразу после запуска операции pile переходит в состояние `NOT_SYNCHRONIZED` и запускается фоновый процесс синхронизации данных; по её завершении pile автоматически становится `SYNCHRONIZED`. Дождавшись этого состояния, при необходимости можно [переключить роль `PRIMARY` на данный pile](#switchover).

### Особенности аутентификации в аварийном состоянии кластера {#emergency-auth}

Команды управления кластером в режиме bridge требуют прав администратора кластера. Если включена обязательная аутентификация ([`enforce_user_token_requirement: true`](../../../reference/configuration/security_config.md)), то в штатном режиме работы кластера доступны все способы аутентификации, включая [аутентификацию по логину и паролю](../../../security/authentication.md#static-credentials).

Однако при отказе pile кластер приостанавливает обслуживание запросов до выполнения [failover](#failover). В этом состоянии аутентификация по логину и паролю не может быть использована: для проверки учётных данных нужен доступ к [SchemeShard](../../../concepts/glossary.md#scheme-shard), который недоступен на кластере в аварийном состоянии. Попытка входа завершается ошибкой:

```text
SchemeShard is unreachable
```

Единственный способ аутентификации, доступный в аварийном состоянии кластера, — [аутентификация по клиентским сертификатам](../../../reference/configuration/client_certificate_authorization.md). Клиентский сертификат проверяется локально узлом, принявшим запрос, поэтому такая проверка не зависит от доступности кластера в целом.

Аутентификация по клиентским сертификатам должна быть настроена на кластере заранее:

1. Секция [`client_certificate_authorization`](../../../reference/configuration/client_certificate_authorization.md) конфигурации кластера должна присваивать подключениям с доверенным клиентским сертификатом [SID](../../../concepts/glossary.md#access-sid) административной группы:

    ```yaml
    client_certificate_authorization:
      request_client_certificate: true
      client_certificate_definitions:
        - member_groups: ["ADMINS"]
          subject_terms:
          - short_name: "O"
            values: ["YDB"]
    ```

2. Этот SID должен входить в список `administration_allowed_sids` секции [`security_config`](../../../reference/configuration/security_config.md):

    ```yaml
    security_config:
      enforce_user_token_requirement: true
      administration_allowed_sids:
      - "root"
      - "ADMINS"
    ```

Если кластер развёрнут по [инструкции по развёртыванию](initial-deployment/deployment-configuration-v2.md), эти настройки уже включены в конфигурацию, а в качестве клиентского сертификата подойдут файлы `node.crt` и `node.key` из каталога `~/CA/certs/` на любом узле кластера.

Для аутентификации по клиентскому сертификату укажите его в глобальных опциях {{ ydb-short-name }} CLI `--client-cert-file` и `--client-cert-key-file`. Подключаться необходимо к узлу работоспособного pile. Пример выполнения failover:

```bash
{{ ydb-cli }} -e grpcs://<node.ydb.tech>:2135 \
    --ca-file ca.crt \
    --client-cert-file node.crt \
    --client-cert-key-file node.key \
    admin cluster bridge failover --pile <unavailable-pile> --new-primary <synchronized-pile>
```

где:

- `<node.ydb.tech>` — FQDN узла в работоспособном pile;
- `ca.crt` — сертификат доверенного центра сертификации кластера;
- `node.crt`, `node.key` — клиентский сертификат и приватный ключ к нему, удовлетворяющие требованиям секции `client_certificate_authorization`.

{% note warning %}

Проверьте работоспособность аутентификации по клиентским сертификатам заранее, до возникновения аварии. Если аутентификация по клиентским сертификатам не была настроена до аварии, вывод кластера из аварийного состояния существенно усложнится и потребует ручного вмешательства на узлах кластера.

{% endnote %}
