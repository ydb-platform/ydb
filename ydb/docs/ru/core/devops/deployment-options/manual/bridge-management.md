# Управление кластером в режиме bridge

{% include [feature_enterprise.md](../../../_includes/feature_enterprise.md) %}

Управление кластером в режиме bridge включает процедуры преобразования кластера в [режим bridge](../../../concepts/bridge.md), изменения состава pile и режимов пулов хранения, а также восстановления после отказов pile. В статье описаны эти процедуры с использованием [команд {{ ydb-short-name }} CLI](../../../reference/ydb-cli/commands/bridge/index.md) и утилиты {{ ydb-short-name }} DSTool.

## Общие правила выполнения команд {#common}

Выполняйте команды управления через любой доступный узел кластера, указывая его endpoint:

```bash
{{ ydb-cli }} -e grpc://<node>:2135 admin cluster bridge list
```

Где `<node>` — имя хоста или IP-адрес доступного узла кластера, например `node-1.example.com`.

Изменяющие состояние команды `ydb admin` запрашивают подтверждение, а команда `bridge list`, предназначенная только для чтения, — нет. Без TTY подтверждение автоматически отклоняется без вывода сообщения, и команда завершается с кодом 1. Поэтому в скриптах для изменяющих состояние команд необходимо указывать глобальный флаг `-y`. В примерах ниже endpoint для краткости не указан.

{% note warning "Точки невозврата" %}

Преобразование кластера в режим bridge необратимо. После преобразования и после сохранения повышенного уровня функциональности bridge в результате операций с pile, включения неоднородного хранилища или переопределения параметров хранения для отдельных pile узлы без поддержки требуемого уровня отсекаются от кластера. Перед включением функциональности обновите все статические и динамические узлы. Поддерживаемого способа вернуть кластер из режима bridge в обычный режим нет.

{% endnote %}

## Обзор операций {#operations}

| Операция | Команда или действие | Обратимость |
| --- | --- | --- |
| Преобразовать кластер в bridge с одним pile | `{{ ydb-cli }} -y admin cluster bridge convert [--skip-storage-pool-conversion]` | Нет |
| Включить неоднородное хранилище | Установить `bridge_config.enable_non_uniform_storage: true` | Нет |
| Зарегистрировать pile | Добавить его в `bridge_config.piles`, а его узлы — в `hosts`, затем заменить конфигурацию | Да, пока он `INACTIVE` |
| Добавить pile | `{{ ydb-cli }} -y admin cluster bridge add-pile --pile P` | Да, с помощью `remove-pile` |
| Вернуть pile в кластер | `{{ ydb-cli }} -y admin cluster bridge rejoin --pile P` | — |
| Сменить primary pile | `{{ ydb-cli }} -y admin cluster bridge switchover --new-primary P` | — |
| Плановое отключение | `{{ ydb-cli }} -y admin cluster bridge takedown --pile P [--new-primary Q]` | `rejoin` |
| Аварийное отключение | `{{ ydb-cli }} -y admin cluster bridge failover --pile P [--pile R] [--new-primary Q]` | `rejoin` |
| Удалить pile | `{{ ydb-cli }} -y admin cluster bridge remove-pile --pile P` | Нет, данные удаляются |
| Переключить режим пула | `ydb-dstool pool set-bridge-mode --pool-name N (--bridged \| --ordinary [--retain-pile P])` | Да |
| Проверить состояние и прогресс | `{{ ydb-cli }} admin cluster bridge list [--format json]` | — |

## Просмотр текущего состояния {#list}

Команда `list` показывает текущее состояние каждого pile, прогресс преобразования и ожидающие выполнения операции с pile:

```bash
{{ ydb-cli }} admin cluster bridge list
```

Пример вывода:

```text
Pile pile-a: PRIMARY
Pile pile-b: SYNCHRONIZED
Generation: 4
```

Для скриптов используйте `--format json`. Во время преобразования вывод содержит `Conversion from non-bridged cluster is in progress, piles can't be added yet`. Во время добавления или удаления pile — `Pending operation on pile P: ADD` или `REMOVE`. Если последняя попытка завершилась ошибкой и повторяется, вывод также содержит текст ошибки. Формат вывода описан в [справочнике команды](../../../reference/ydb-cli/commands/bridge/list.md).

## Плановая смена `PRIMARY` (switchover) {#switchover}

Если в датацентре или на оборудовании текущего `PRIMARY` pile запланированы работы, заранее переключите кластер на другой pile. Выберите pile в состоянии `SYNCHRONIZED`:

```bash
{{ ydb-cli }} -y admin cluster bridge switchover --new-primary <pile>
```

Где `<pile>` — имя нового primary pile, например `pile-b`.

Переключение выполняется плавно: роли проходят через `PRIMARY/PROMOTED` и завершаются в состоянии `SYNCHRONIZED/PRIMARY`.

## Плановое отключение pile (takedown) {#takedown}

Перед работами, которые сделают pile недоступным, выведите его из кластера:

```bash
{{ ydb-cli }} -y admin cluster bridge takedown --pile <pile>
```

Если отключается текущий `PRIMARY`, укажите синхронизированный pile для замены:

```bash
{{ ydb-cli }} -y admin cluster bridge takedown --pile <current-primary> --new-primary <synchronized-pile>
```

Где:

- `<pile>` — отключаемый pile, например `pile-b`;
- `<current-primary>` — текущий primary pile, например `pile-a`;
- `<synchronized-pile>` — pile в состоянии `SYNCHRONIZED`, например `pile-b`.

Pile переходит в состояние `SUSPENDED`, затем — в `DISCONNECTED`. Дальнейшие операции выполняются без его участия. Перед началом работ проверьте командой [list](#list), что отключение завершено и все pile находятся в ожидаемых состояниях.

После обслуживания верните pile командой [rejoin](#rejoin). При наличии обычных пулов учитывайте дополнительные ограничения:

- При наличии пулов `mirror-3-dc` одновременно выводите из эксплуатации только один pile. При недоступности одного ДЦ такие пулы переживают отказ только ещё одного диска.
- Обычные пулы, размещённые только в отключённом ДЦ, недоступны на протяжении всего обслуживания.
- В течение короткого времени после планового отключения узел, ещё не получивший новую конфигурацию, может записывать в отключённый pile и возвращать его ответы на чтение. Такие чтения могут не учитывать записи, уже выполненные узлами, которые знают об отключении.

## Аварийное отключение недоступных pile (failover) {#failover}

Из-за синхронной репликации неожиданный отказ pile по умолчанию останавливает запись в группы в режиме bridge. Чтобы продолжить работу без отказавшего pile, человек или внешняя автоматизация должны явно выполнить failover.

Сначала убедитесь, что отказавший pile остановлен или изолирован и не может самостоятельно возобновить обработку запросов. Никогда не выполняйте failover независимо на обеих сторонах сетевого разделения; см. [восстановление после split-brain](../../../concepts/bridge.md#split-brain). Затем выполните:

```bash
{{ ydb-cli }} -y admin cluster bridge failover --pile <unavailable-pile>
```

Если недоступен текущий `PRIMARY`, добавьте `--new-primary` с именем pile в состоянии `SYNCHRONIZED`:

```bash
{{ ydb-cli }} -y admin cluster bridge failover --pile <unavailable-primary> --new-primary <synchronized-pile>
```

Где:

- `<unavailable-pile>` — отказавший pile, например `pile-b`;
- `<unavailable-primary>` — отказавший primary pile, например `pile-a`;
- `<synchronized-pile>` — работоспособный синхронизированный pile, например `pile-b`.

Если отказали несколько pile, перечислите всех их в одной команде, повторив `--pile`. Например, если отказали `pile-a` и `pile-b`, а `pile-c` остаётся `SYNCHRONIZED`, подключитесь к узлу в `pile-c` и выполните:

```bash
{{ ydb-cli }} -y admin cluster bridge failover --pile pile-a --pile pile-b --new-primary pile-c
```

Одно обновление конфигурации отключает оба недоступных pile и выбирает новый `PRIMARY`. Отключение по одному может завершиться ошибкой, поскольку второй отказавший pile всё ещё необходим для кворума промежуточной конфигурации. Базы данных в режиме bridge продолжают работать на оставшемся pile. Обычные базы данных `mirror-3-dc` остаются недоступными до возвращения одного из отказавших ДЦ.

При разделении кластера на один и два ДЦ предпочтительно выполнить failover для одиночного ДЦ. Тогда и базы данных в режиме bridge, и обычные базы `mirror-3-dc` продолжат работать на паре ДЦ. Оставляйте только одиночный ДЦ, если пара действительно потеряна; в этом случае у обычных пулов `mirror-3-dc` нет кворума на запись.

В оставшемся pile должны быть доступны кворумы узлов и хранилища, необходимые для применения новой конфигурации и обработки запросов. Failover не включает автоматическое переключение и не позволяет назначить несинхронизированный pile новым `PRIMARY`. Допустимые переходы зависят от текущей пары состояний и приведены на [диаграмме состояний](../../../concepts/bridge.md#pile-states) и в [таблице переходов](../../../concepts/bridge.md#transitions-between-states). После успешного выполнения проверьте результат командой [list](#list).

{% note warning %}

Если включена обязательная аутентификация, в аварийном состоянии кластера нельзя использовать аутентификацию по логину и паролю. Используйте аутентификацию по клиентским сертификатам. Подробнее см. [{#T}](#emergency-auth).

{% endnote %}

## Возврат pile в кластер (rejoin) {#rejoin}

После обслуживания или устранения отказа явно верните каждый отключённый pile:

```bash
{{ ydb-cli }} -y admin cluster bridge rejoin --pile <pile>
```

Где `<pile>` — отключённый pile, например `pile-b`.

Pile переходит в состояние `NOT_SYNCHRONIZED`, и запускается фоновая синхронизация данных. По её завершении pile автоматически становится `SYNCHRONIZED`. Части в режиме bridge синхронизируются механизмом bridge, а обычные VDisk догоняют остальные в ходе штатного восстановления VDisk. Отслеживайте прогресс с помощью [счётчиков мониторинга](#monitoring). После перехода pile в `SYNCHRONIZED` при необходимости можно [переключить на него роль `PRIMARY`](#switchover).

## Предварительные условия для изменения кластера и топологии {#prerequisites}

Перед преобразованием кластера, добавлением или удалением pile и изменением режимов пулов проверьте следующее:

1. На каждом статическом и динамическом узле запущена сборка с поддержкой требуемой функциональности bridge. При необходимости выполните [обновление исполняемого файла](update-executable.md).
2. Используется конфигурация V2 и включено автоматическое управление параметром `self_management_config.enabled: true`. Проверьте полученную конфигурацию способом, описанным ниже. Для конфигурации V1 выполните [миграцию на V2](../../configuration-management/migration/migration-to-v2.md) и [дополнительные шаги для bridge](#migrate-v2).
3. Параметр `default_disk_type` соответствует дискам со статическими группами: `ROT`, `SSD` или `NVME`. Значение по умолчанию — `SSD`.

   - При размещении по умолчанию автоматическое управление размещает статические группы, включая их части в добавляемых позже pile, только на дисках этого типа. Если настроен `blob_storage_config.storage_pool_pile_overrides`, приоритет имеют его фильтры и геометрия для отдельных pile; проверьте также эти диски.
   - При неверном типе `add-pile` завершается ошибкой `group allocation failed ... PDisks# <empty>`.

4. Если планируется преобразование по умолчанию с переводом всех пулов в bridge, не должно выполняться декомиссия BlobDepot. Группы в процессе декомиссии сохраняют состояние преобразования «в процессе», пока не достигнут `DONE`.
5. В каждом добавляемом pile достаточно оборудования для:

   - его части статических групп и State Storage;
   - полной копии каждого пула в режиме bridge. Для `block-4-2` требуется восемь доменов отказа в соответствии с геометрией пула;
   - его доли обычных пулов. Для пула `mirror-3-dc` требуется три стойки в каждом ДЦ.

Получайте и заменяйте конфигурацию через доступный узел:

```bash
{{ ydb-cli }} -e grpc://<node>:2135 admin cluster config fetch > config.yaml
{{ ydb-cli }} -e grpc://<node>:2135 -y admin cluster config replace -f config.yaml
```

Где `<node>` — доступный узел кластера, например `node-1.example.com`. Между командами отредактируйте `config.yaml`. Команда `fetch` выводит следующее значение `metadata.version` для основной конфигурации.

Узлы читают `bridge_config` и собственный параметр `location` только при запуске. Если в процедуре требуется rolling restart, последовательно перезапустите сначала все статические, затем все динамические узлы. Общий механизм описан в статье [Обслуживание кластера без потери доступности](../../concepts/maintenance-without-downtime.md).

## Миграция с конфигурации V1 на V2 с автоматическим управлением {#migrate-v2}

Сначала следуйте общей инструкции [Миграция на конфигурацию V2](../../configuration-management/migration/migration-to-v2.md). Затем выполните дополнительные шаги для bridge:

1. Установите `feature_flags.switch_to_config_v2: true`. Если конфигурацией управляет Console, сначала добавьте флаг туда.
2. Выполните rolling restart.
3. Загрузите конфигурацию в хранилище V2 без изменений. Затем установите `self_management_config.enabled: true` и `default_disk_type` и выполните ещё один rolling restart.
4. Удалите секции, которыми теперь управляет распределённая конфигурация:

   - переместите `domains_config.security_config` на верхний уровень как `security_config`;
   - удалите `domains_config` и `blob_storage_config`;
   - переименуйте `static_erasure` в `erasure`.

5. Выполните rolling restart.

Перед продолжением преобразования проверьте итоговую конфигурацию командой `admin cluster config fetch`.

## Преобразование кластера в bridge с одним pile {#convert}

Преобразование добавляет подсистему управления bridge и преобразует системное хранилище. Для существующих пулов баз данных выберите один из двух режимов:

- **Преобразование по умолчанию** переводит каждый пул в режим bridge. Группы становятся встроенными pile (inline piles) и сохраняют идентификаторы и данные. Во время самого преобразования данные не перемещаются. Каждый последующий `add-pile` создаёт часть для каждой группы, а `rejoin` синхронизирует все данные сразу.
- **Преобразование с `--skip-storage-pool-conversion`** немедленно преобразует только системное хранилище. Существующие пулы остаются обычными, а неоднородное хранилище включается в ходе преобразования. Последующие вызовы `add-pile` синхронизируют только системные данные. Переводите пулы в режим bridge по одному, как описано в разделе [Изменение режима пула хранения](#pool-mode), чтобы контролировать нагрузку синхронизации. Этот режим рекомендуется для больших кластеров и необходим, если планируются обычные пулы.

Чтобы преобразовать кластер:

1. Добавьте конфигурацию bridge с одним pile:

   ```yaml
   bridge_config:
     piles:
       - name: A
     enable_non_uniform_storage: true   # ОБЯЗАТЕЛЬНО с --skip-storage-pool-conversion, ЗАПРЕЩЕНО при преобразовании по умолчанию
   ```

   Замените конфигурацию и выполните rolling restart **всех** узлов, включая динамические. Подключённый динамический узел, запущенный без конфигурации bridge, блокирует преобразование.

2. Выполните команду выбранного режима:

   ```bash
   {{ ydb-cli }} -y admin cluster bridge convert
   {{ ydb-cli }} -y admin cluster bridge convert --skip-storage-pool-conversion
   ```

   Это альтернативные команды: выполните только соответствующую выбранному режиму. Если какой-либо узел не соответствует требованиям, команда завершается ошибкой без изменений и перечисляет идентификаторы узлов. Перезапустите или обновите эти узлы и повторите команду.

3. Дождитесь, пока [bridge list](#list) перестанет выводить `Conversion from non-bridged cluster is in progress, piles can't be added yet` и покажет `A: PRIMARY`.

Пока это сообщение не исчезло, нельзя изменять список pile и отдельно включать неоднородное хранилище. При преобразовании по умолчанию устанавливайте `bridge_config.enable_non_uniform_storage: true` только после завершения преобразования и только если требуется смешанный режим пулов. Отключить эту настройку после включения невозможно.

Рекомендуется выполнить smoke-проверку KV и таблиц. Во время переключения State Storage на схему bridge разрешение имён баз данных может кратковременно завершаться ошибкой. Подробнее см. [admin cluster bridge convert](../../../reference/ydb-cli/commands/bridge/convert.md).

{% note warning "Кластеры в нескольких ДЦ" %}

Не преобразовывайте кластер в нескольких ДЦ, если требуется схема с одним pile на ДЦ. В настоящее время преобразование создаёт один pile, охватывающий все ДЦ. Впоследствии pile нельзя разделить, узел нельзя переместить в другой pile без выхода из кластера, а кластер нельзя преобразовать дважды. Это текущее ограничение операции преобразования.

{% endnote %}

## Назначение имени преобразованному pile {#name-pile}

Преобразованный pile является неявным: к нему относятся узлы без имени pile. Прежде чем регистрировать второй pile или удалять преобразованный, назначьте его имя каждому узлу.

1. Добавьте `location.bridge_pile_name: A` в каждую запись `hosts` и в location каждого динамического узла. NodeBroker принимает изменение отсутствующего имени pile на имя неявного pile. См. [конфигурацию hosts](../../../reference/configuration/hosts.md#hosts-bridge).
2. Если планируются обычные пулы `mirror-3-dc`, также назначьте узлам A метку `data_center`, отличающуюся от меток новых ДЦ. Измените её на этом же шаге. Сначала проверьте это на тестовом кластере, поскольку изменяется location каждого узла A, а после изменения выполните `ydb-dstool group check`.
3. Замените конфигурацию и выполните rolling restart.

## Регистрация и добавление pile {#add-pile}

При добавлении pile создаются его части групп в режиме bridge без остановки кластера. Сначала зарегистрируйте pile и его узлы, затем разместите и синхронизируйте хранилище:

1. **Зарегистрируйте pile** одной заменой конфигурации:

   - добавьте `{name: B}` в `bridge_config.piles`;
   - добавьте `host_configs` и `hosts` для B, указав в каждом `location: {data_center: dc-b, rack: <rack>, bridge_pile_name: B}`, где `<rack>` — идентификатор стойки;
   - дополните `system_tablets`, включая `default_node` и каждый список `node` отдельных таблеток, идентификаторами узлов B. Эти списки определяют, где могут запускаться системные таблетки. Конфигурация, мигрированная с V1, привязывает их к узлам A, и это не проверяется автоматически; без узлов B после failover на B ничто не сможет запуститься.

2. Запустите статические узлы B. Они останутся без нагрузки, а `bridge list` покажет `B: INACTIVE`.
3. **Добавьте pile**:

   ```bash
   {{ ydb-cli }} -y admin cluster bridge add-pile --pile B
   ```

   Команда запускает размещение групп и предварительные проверки одной ожидающей операцией. При успехе BSC создаёт части B для каждой группы в режиме bridge, а pile переходит в `DISCONNECTED`. При временной ошибке BSC ожидающая операция сохраняется и повторяется.

   - При недостатке места команда быстро завершается ошибкой без изменений.
   - Сразу после регистрации возможна ошибка `group allocation failed`, поскольку BSC узнаёт о новых хостах в фоновом режиме. Повторите команду через несколько секунд.
   - Если добавление застряло и `bridge list` показывает `Pending operation on pile B: ADD` и `Last attempt has failed (being retried): ...`, отмените его командой `remove-pile --pile B`.

4. **Верните pile в кластер** после завершения ожидающей операции `ADD`:

   ```bash
   {{ ydb-cli }} -y admin cluster bridge rejoin --pile B
   ```

   Pile переходит из `NOT_SYNCHRONIZED` в `SYNCHRONIZED`. Отслеживайте прогресс с помощью [счётчиков мониторинга](#monitoring).

5. Запустите динамические узлы B для каждой базы данных с `bridge_pile_name: B`. Теперь они обслуживают ведомые таблетки, а после switchover или failover — ведущие.

Одновременно может ожидать выполнения только одна операция добавления или удаления pile. Зарегистрировать можно сразу несколько pile, но последовательное добавление и синхронизация делают нагрузку предсказуемой. Подробнее см. [admin cluster bridge add-pile](../../../reference/ydb-cli/commands/bridge/add-pile.md).

## Изменение режима пула хранения {#pool-mode}

Кластер bridge с [неоднородным хранилищем](../../../concepts/bridge.md#storage-pools) может содержать пулы в режиме bridge и обычные пулы. Преобразование должно быть завершено, а операции с pile — отсутствовать в состоянии ожидания. Используйте `ydb-dstool pool set-bridge-mode`, чтобы изменить режим пула без изменения идентификаторов групп и перемещения данных на уровне базы. Повторите `--pool-name`, чтобы изменить несколько пулов одним запросом. Пулы баз данных имеют имена `<database>:<kind>`, например `/Root/db1:ssd`.

### Перевод пула в режим bridge {#pool-bridged}

Чтобы реплицировать обычный пул в каждый pile:

```bash
ydb-dstool pool set-bridge-mode --pool-name /Root/db1:ssd --bridged
```

Каждая группа должна целиком находиться в одном pile. Группа `mirror-3-dc`, охватывающая несколько ДЦ, отклоняется с ошибкой `resides in several piles`, поскольку её нельзя преобразовать напрямую. Части в остальных pile создаются немедленно, а при недостатке места команда завершается ошибкой без изменений. Синхронизация частей выполняется в фоновом режиме, а группы, созданные после этого, работают в режиме bridge.

{% note warning %}

Пока новые части группы не синхронизированы, группа зависит только от исходного pile. При отказе этого pile группа перестаёт принимать записи до его возвращения; `failover` не помогает. Не отключайте исходный pile во время синхронизации пула.

{% endnote %}

Операция работает и в кластере с одним pile: группы становятся встроенными pile и получают части при следующем `add-pile`.

### Перевод пула в обычный режим {#pool-ordinary}

Чтобы сохранить одну часть каждой группы в режиме bridge и удалить остальные:

```bash
ydb-dstool pool set-bridge-mode --pool-name /Root/db1:ssd --ordinary --retain-pile A
```

Параметр `--retain-pile` необязателен. По умолчанию каждая группа сохраняет часть, из которой была переведена в режим bridge, её встроенный pile или часть в primary pile. Остальные части удаляются в фоновом режиме примерно через 30 секунд. Сохраняемая часть должна быть `SYNCED`, а её pile должен оставаться в кворуме данных. Если сохраняемая часть не является авторитетной, её pile также должен быть `SYNCHRONIZED`.

После этого пул недоступен при каждом выходе сохранённого pile из строя, а `remove-pile` для него отклоняется. `TDefineStoragePool` не может изменить режим существующего пула и возвращает `can't change storage pool BridgeMode`; это может сделать только `set-bridge-mode`. Подробнее см. [pool set-bridge-mode](../../../reference/ydb-dstool/pool-set-bridge-mode.md).

## Создание обычных пулов и баз данных {#create-pools}

Неоднородное хранилище позволяет новым базам данных использовать обычные группы одновременно с базами в режиме bridge. Включите его, как описано в разделе [Преобразование кластера](#convert), и явно задавайте `bridge_mode` для каждого пула. Если значение не указано, оно определяется по сохранённому состоянию bridge кластера, поэтому полагаться на него при выборе режима во время преобразования кластера с одним pile небезопасно.

Для пулов, охватывающих несколько ДЦ, каждый задействованный pile должен быть подключён и не находиться в `SUSPENDED` при создании или добавлении групп. BSC не размещает новые VDisk в pile в состояниях `DISCONNECTED`, `INACTIVE` или `SUSPENDED`.

Следующий фрагмент конфигурации определяет пул в режиме bridge, обычный пул в нескольких ДЦ и обычный пул, привязанный к одному ДЦ:

```yaml
storage_pool_types:
  - kind: reliable
    pool_config:
      box_id: 1
      kind: reliable
      erasure_species: block-4-2
      bridge_mode: true
      vdisk_kind: Default
      pdisk_filter: [{property: [{type: SSD}]}]
  - kind: fast
    pool_config:
      box_id: 1
      kind: fast
      erasure_species: mirror-3-dc
      bridge_mode: false
      vdisk_kind: Default
      pdisk_filter: [{property: [{type: SSD}]}]
  - kind: local-a
    pool_config:
      box_id: 1
      kind: local-a
      erasure_species: block-4-2
      bridge_mode: false
      vdisk_kind: Default
      pdisk_filter: [{property: [{type: SSD}, {location: {data_center: dc-a}}]}]
```

Тип `reliable` создаёт по одной группе `block-4-2` в каждом pile. Тип `fast` создаёт одну обычную группу `mirror-3-dc` в трёх ДЦ. Тип `local-a` создаёт обычные группы `block-4-2` только в `dc-a`, обеспечивая более дешёвое хранилище без отказоустойчивости при отказе ДЦ. Описание полей приведено в разделе [Конфигурация Blob Storage](../../../reference/configuration/domains_config.md#domains-blob).

Создайте базу данных с выбранным типом, например:

```bash
ydbd -s grpc://<node>:2135 admin database /Root/fastdb create fast:4
```

Где `<node>` — доступный узел кластера, например `node-1.example.com`.

База данных ведёт себя как обычная, только если **все** её каналы привязаны к обычным пулам: данные, логи, SchemeShard, координаторы, медиаторы и выделенный Hive, если он есть. Создавайте её только с обычным типом. Эта процедура не проверяет пользовательские профили каналов, семейства колонок или топики, привязанные к другим типам, а также serverless-базы данных; последние используют пулы своей общей базы данных.

Схему избыточности существующего пула изменить нельзя. Чтобы переместить данные из пула в режиме bridge или пула в одном ДЦ в `mirror-3-dc`, выполните перемещение на уровне базы данных с помощью резервного копирования и восстановления или репликации. После включения неоднородного хранилища новые группы существующего обычного пула также могут размещаться в других ДЦ, если это позволяет геометрия. Добавьте свойство `location` в `pdisk_filter` пула, чтобы сохранить их текущее размещение.

## Удаление pile {#remove-pile}

Удаление pile безвозвратно удаляет его части групп хранения и их данные. Перед выполнением команды:

1. Убедитесь, что ничто не зависит только от этого pile:

   - Ни одна обычная группа не должна содержать в нём VDisk. Иначе команда вернёт `GroupId# G has VDisks in the pile, but it is not a part of bridged group, its data would be lost`. Переведите эти пулы в режим bridge, удалите их или переместите их VDisk из pile, как описано в разделе [Безвозвратная потеря ДЦ](#dc-loss).
   - Ни одна группа не должна полагаться исключительно на свою часть в этом pile (`relies on its part in the pile solely`). Дождитесь завершения синхронизации `set-bridge-mode` или сохраните другой pile.

2. Если pile является `PRIMARY`, сначала выполните [switchover](#switchover). Затем выполните [takedown](#takedown) или [failover](#failover), если он уже недоступен. Pile должен находиться в `DISCONNECTED`.
3. Остановите его узлы.
4. Удалите pile:

   ```bash
   {{ ydb-cli }} -y admin cluster bridge remove-pile --pile <pile>
   ```

   Где `<pile>` — отключённый pile, например `pile-b`.

   Команда запускает ожидающую операцию `REMOVE`. BSC удаляет части и данные pile, затем распределённая конфигурация переводит pile в `INACTIVE`. Дождитесь завершения ожидающей операции, прежде чем удалять pile и его хосты из конфигурации.

5. При необходимости удалите pile и его хосты из конфигурации, а их идентификаторы узлов — из `system_tablets`.

Удалённый pile можно добавить снова на новых или тех же хостах с помощью [процедуры добавления](#add-pile). Реестр pile фиксирует новое воплощение, поэтому узлы старого воплощения могут быть заменены текущей конфигурацией. Перед `rejoin` дождитесь завершения операции `ADD`. Подробнее см. [admin cluster bridge remove-pile](../../../reference/ydb-cli/commands/bridge/remove-pile.md).

## Мониторинг {#monitoring}

Для мониторинга преобразования, синхронизации и смешанного хранилища используйте состояния pile и счётчики BSC:

- `ydb admin cluster bridge list` показывает состояния pile, прогресс преобразования, ожидающие операции `ADD` или `REMOVE` и последнюю ошибку повторяемой операции. Для скриптов добавьте `--format json`.
- Счётчики BSC с `subsystem=bsc` показывают прогресс синхронизации:

  - в разрезе `pile`, `database` и `storagePool`: `SyncBytesDone`, `SyncBytesTotal`, `GroupsInStage{stage=...}`, `SyncersRunning` и `SyncErrors`;
  - в разрезе pile: `PileInState{state=...}` и `UnsyncedBSC`.

  Только эти счётчики показывают прогресс `rejoin` и `set-bridge-mode --bridged`.

- Health check относит проблемы групп в режиме bridge к соответствующему pile. У проблем обычных групп pile не указывается.
- Не полагайтесь на прогнозы BSC о доступных группах в смешанных кластерах, поскольку они не учитывают режим bridge пула.

## Сценарии {#scenarios}

### Кластер V1 в одном ДЦ → смешанный bridge в трёх ДЦ {#three-dc}

В этом сценарии создаются pile A, B и C в ДЦ `dc-a`, `dc-b` и `dc-c`. Надёжные базы данных используют группы `block-4-2` в режиме bridge в каждом pile. Базы данных, которым требуются низкая задержка или дешёвое хранилище, используют обычные группы `mirror-3-dc` в трёх ДЦ.

1. Проверьте [предварительные условия](#prerequisites), затем выполните [миграцию с V1 на V2](#migrate-v2) с автоматическим управлением и `default_disk_type`.
2. Выполните [преобразование с `--skip-storage-pool-conversion`](#convert), используя `bridge_config: {piles: [{name: A}], enable_non_uniform_storage: true}` и rolling restart.
3. [Назначьте имена узлам A](#name-pile) и добавьте им `data_center: dc-a`.
4. [Зарегистрируйте и добавьте B](#add-pile), включая `system_tablets`; запустите статические узлы, выполните `add-pile` и `rejoin`, дождитесь `SYNCHRONIZED` и запустите динамические узлы.
5. Повторите процедуру для C.
6. Для существующих баз данных, которые должны быть надёжными, [переведите их пулы в режим bridge](#pool-bridged) по одному и дождитесь синхронизации каждого. Не отключайте A, пока каждый пул не синхронизируется.
7. Создавайте новые надёжные базы данных с типом `reliable`, а новые базы с низкой задержкой или дешёвым хранилищем — с типом `fast`, как описано в разделе [Создание пулов](#create-pools). Создавайте пулы в нескольких ДЦ, когда все три pile подключены.
8. Для существующих баз данных, которые должны использовать `mirror-3-dc`, переместите данные на уровне базы в новую базу `fast`. Существующие пулы в одном ДЦ, оставленные без изменений, сохранят доступность только при работающем A и будут блокировать `remove-pile A`.
9. Убедитесь, что все pile находятся в `SYNCHRONIZED`, а health check не сообщает об ошибках. Во время окна обслуживания выполните `switchover --new-primary B` и обратное переключение.
10. Разместите `PRIMARY` в ДЦ, ближайшем к клиентам баз данных с низкой задержкой, поскольку там работают их ведущие таблетки.

Если используется преобразование по умолчанию, не указывайте `enable_non_uniform_storage` на шаге 2. Каждый существующий пул переводится в режим bridge и синхронизируется при каждом `rejoin`. После завершения преобразования, но перед шагом 7 включите неоднородное хранилище заменой конфигурации, если требуются смешанные пулы.

### Безвозвратная потеря ДЦ {#dc-loss}

Если ДЦ потерян безвозвратно:

1. Выполните [failover](#failover).
2. Если в потерянном ДЦ находятся обычные VDisk, сначала зарегистрируйте и добавьте заменяющий ДЦ. Отметьте диски потерянного ДЦ для декомиссии, чтобы SelfHeal переместил кольца `mirror-3-dc` в заменяющий ДЦ. Прежде чем полагаться на эту последовательность, проверьте замену и поведение SelfHeal на тестовом кластере.
3. [Удалите потерянный pile](#remove-pile).
4. Снова зарегистрируйте заменяющие хосты, затем выполните `add-pile` и `rejoin` по [процедуре добавления](#add-pile).

### Перенос обычного кластера на новое оборудование или в новый ДЦ без простоя {#hardware-move}

Используйте преобразование в bridge для переноса кластера без перемещения данных на уровне базы:

1. [Преобразуйте кластер](#convert) и [назначьте имя исходному pile](#name-pile).
2. [Добавьте новый pile](#add-pile).
3. Выполните `switchover --new-primary NEW`, где `NEW` — настроенное имя нового pile.
4. Выполните `takedown --pile OLD`, остановите узлы OLD и [удалите OLD](#remove-pile), где `OLD` — настроенное имя исходного pile.

В результате получится кластер в режиме bridge с одним pile. Преобразование в bridge необратимо, поэтому сначала проверьте процедуру на тестовом кластере.

| `GroupId# G is being decommitted or recommissioned, it can't be made bridged` | Выполняется декомиссия BlobDepot | Дождитесь `DONE`. |
| `GroupId# G part in pile P is not synchronized` с `--ordinary` | Сохраняемая часть не синхронизирована | Дождитесь синхронизации или выберите другой `--retain-pile`. |
| `can't change storage pool BridgeMode` | Шаблон пула переопределён с другим `bridge_mode` | Используйте [set-bridge-mode](#pool-mode) для существующего пула. |
| `non-uniform storage activation can't be disabled` | Флаг удалён после активации | Оставьте флаг в конфигурации. |
| После failover на новый pile ничто не обслуживает запросы | `system_tablets` привязаны к узлам старого pile | Дополните списки, как описано в шаге 1 [добавления pile](#add-pile). |

## Особенности аутентификации в аварийном состоянии кластера {#emergency-auth}

Команды управления кластером в режиме bridge требуют прав администратора кластера. Если включена обязательная аутентификация ([`enforce_user_token_requirement: true`](../../../reference/configuration/security_config.md)), в штатном режиме доступны все способы аутентификации, включая [аутентификацию по логину и паролю](../../../security/authentication.md#static-credentials).

Однако при отказе pile кластер приостанавливает обслуживание запросов до выполнения [failover](#failover). В этом состоянии аутентификация по логину и паролю не может быть использована: для проверки учётных данных нужен доступ к [SchemeShard](../../../concepts/glossary.md#scheme-shard), который недоступен на кластере в аварийном состоянии. Попытка входа завершается ошибкой:

```text
SchemeShard is unreachable
```

Единственный способ аутентификации, доступный в аварийном состоянии кластера, — [аутентификация по клиентским сертификатам](../../../reference/configuration/client_certificate_authorization.md). Клиентский сертификат проверяется локально узлом, принявшим запрос, поэтому эта проверка не зависит от доступности кластера в целом.

Аутентификация по клиентским сертификатам должна быть настроена на кластере заранее:

1. Секция [`client_certificate_authorization`](../../../reference/configuration/client_certificate_authorization.md) конфигурации кластера должна присваивать подключениям с доверенным клиентским сертификатом [SID](../../../concepts/glossary.md#access-sid) административной группы:

    ```yaml
    client_certificate_authorization:
      request_client_certificate: true
      client_certificate_definitions:
        - member_groups: ["ADMINS"]
          subject_terms:
          - short_name: "O"
            values: ["YDB"]
    ```

2. Этот SID должен входить в список `administration_allowed_sids` секции [`security_config`](../../../reference/configuration/security_config.md):

    ```yaml
    security_config:
      enforce_user_token_requirement: true
      administration_allowed_sids:
      - "root"
      - "ADMINS"
    ```

Если кластер развёрнут по [инструкции по развёртыванию](initial-deployment/deployment-configuration-v2.md), эти настройки уже включены в конфигурацию, а в качестве клиентского сертификата подойдут файлы `node.crt` и `node.key` из каталога `~/CA/certs/` на любом узле кластера.

Для аутентификации по клиентскому сертификату укажите его в глобальных опциях {{ ydb-short-name }} CLI `--client-cert-file` и `--client-cert-key-file`. Подключайтесь к узлу работоспособного pile. Пример выполнения failover:

```bash
{{ ydb-cli }} -e grpcs://<node.ydb.tech>:2135 \
    --ca-file ca.crt \
    --client-cert-file node.crt \
    --client-cert-key-file node.key \
    -y admin cluster bridge failover --pile <unavailable-pile> --new-primary <synchronized-pile>
```

Где:

- `<node.ydb.tech>` — FQDN узла в работоспособном pile;
- `ca.crt` — сертификат доверенного центра сертификации кластера;
- `node.crt` и `node.key` — клиентский сертификат и его приватный ключ, удовлетворяющие требованиям секции `client_certificate_authorization`;
- `<unavailable-pile>` — отказавший pile, например `pile-a`;
- `<synchronized-pile>` — работоспособный синхронизированный pile, например `pile-b`.

{% note warning %}

Проверьте работоспособность аутентификации по клиентским сертификатам заранее, до возникновения аварии. Если она не была настроена до аварии, вывод кластера из аварийного состояния существенно усложнится и потребует ручного вмешательства на узлах кластера.

{% endnote %}
