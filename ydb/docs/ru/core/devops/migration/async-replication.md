# Миграция базы данных с помощью асинхронной репликации

В этом рецепте вы перенесёте строковую таблицу между базами данных {{ ydb-short-name }} с помощью [асинхронной репликации](../../concepts/async-replication.md), а затем переключите приложение на новую базу. Во время первоначального переноса приложение продолжает работать с источником. На время окончательной проверки и переключения потребуется остановить запись.

Выберите способ первоначальной синхронизации по [руководству по планированию миграции](index.md#initial-sync). Варианты ниже используют одни и те же имена объектов; выполните только один из них.

## Входные данные {#input-data}

**Источник** : база данных, с которой приложение работает до миграции. **Приёмник** : база данных, в которую переносятся данные. В примерах используются следующие имена:

| Объект | Значение в примере |
| --- | --- |
| База-источник | `/Root/source`, профиль CLI `source` |
| База-приёмник | `/Root/target`, профиль CLI `target` |
| Исходная таблица | `original_table` |
| Таблица в приёмнике | `replica_table` |
| Объект репликации в приёмнике | `my_replication` |
| Секрет с токеном источника в приёмнике | `source_token` |

Замените эти значения своими и используйте выбранные имена во всех шагах рецепта. Запросы управления репликацией выполняются в приёмнике, а настройки потоков изменений : в источнике.

## Предварительные условия {#prepare}

Перед выполнением рецепта:

* Подготовьте принимающую базу данных и [профили CLI](../../reference/ydb-cli/profile/index.md) `source` и `target`. Проверьте в профилях endpoint, полный путь базы данных и аутентификацию.
* Зафиксируйте состав переносимых таблиц: новые таблицы не добавляются в уже созданную репликацию автоматически. Пути будущих целевых таблиц должны быть свободны.
* Подготовьте отдельно права приложения и все [объекты вне состава репликации](../../concepts/async-replication.md#restrictions). Учитывайте различие между восстановлением определений топиков и переносом их сообщений. Проверьте поддержку нужных индексов и последовательностей в обеих базах.
* Оцените дополнительную нагрузку на обе базы и место для потоков изменений в источнике. До начала миграции выберите способ проверки данных и согласуйте длительность остановки записи.

До запуска проверьте запас ресурсов и место для накопления изменений в источнике. Учитывайте [период доступности изменений](../../concepts/async-replication.md#availability-period).

Выберите **один** способ первоначальной синхронизации:

| Способ | Когда выбирать | Дополнительные условия |
| --- | --- | --- |
| Сканирование через CDC | Для первоначального переноса без отдельного S3-хранилища | Дополнительные данные проходят через CDC |
| Резервное копирование и восстановление через S3 | Для переноса первоначальных данных через резервную копию | S3-хранилище доступно серверам обеих баз |

### Права доступа {#replication-permissions}

Права на корень базы-источника и её каталоги настройте в приёмнике отдельно, до переключения приложения.

Определите владельцев репликации и секрета. Выдайте им и приложению необходимые права в соответствии с таблицей. Названия прав указаны в синтаксисе [GRANT](../../yql/reference/syntax/grant.md#permissions-list):

| Для чего | Необходимый доступ |
| --- | --- |
| Подключение и просмотр схемы | `CONNECT` на каждую используемую базу данных; `DESCRIBE SCHEMA` на используемые каталоги и объекты |
| Работа репликации с источником | `ALTER SCHEMA` на исходные таблицы для создания, изменения и удаления CDC-потоков; `ALTER SCHEMA` на топики потоков для настройки потребителей и retention; `SELECT ROW` на топики для чтения изменений. Эти права нужны пользователю, чей токен использует репликация; права на ручную настройку : также пользователю профиля `source` |
| Создание объектов в приёмнике | `CREATE TABLE` на каталог, в котором создаются секрет, репликация и целевые таблицы; `CREATE DIRECTORY` на родительский каталог, если требуется создание подкаталогов |
| Управление репликацией | `ALTER SCHEMA` на `my_replication` для изменения состояния; `REMOVE SCHEMA` на этот объект для удаления. Для подключения восстановленных таблиц : `ALTER SCHEMA` на эти таблицы у владельца репликации |
| Чтение секрета | `SELECT ROW` на `source_token` у владельца репликации. Проверьте права на секрет отдельно |
| Проверка данных | `SELECT ROW` на исходные и целевые таблицы у пользователей, выполняющих проверку |
| Работа приложения в приёмнике | `SELECT ROW` на целевые таблицы для чтения, `UPDATE ROW` для записи и `ERASE ROW` для удаления строк : в соответствии с операциями приложения |

Для варианта с резервной копией также выполните [подготовку S3, прав экспорта и импорта](../async-replication-initial-sync.md#prerequisites) до создания репликации.

## 1. Подготовка окружения {#setup}

### 1.1. Проверка подключения {#check-connection}

Проверьте доступ к исходной таблице и принимающей базе данных:

```bash
{{ ydb-cli }} -p source scheme describe original_table
{{ ydb-cli }} -p target scheme ls
```

Первая команда должна вернуть описание нужной таблицы, вторая : список объектов приёмника. Если команда завершается ошибкой, исправьте подключение или права до создания репликации.

### 1.2. Получение токена {#token}

Подготовьте токен пользователя источника с [необходимыми правами](#replication-permissions), используя способ [аутентификации](../../security/authentication.md), настроенный в вашей инсталляции. Храните токен в защищённом файле и не включайте его в историю команд и журналы.

### 1.3. Создание секрета {#secret}

Сохраните запрос [создания секрета](../../yql/reference/syntax/create-secret.md) в защищённый файл `create-secret.sql`:

```yql
CREATE SECRET source_token
WITH (value = '<токен-источника>');
```

Замените `<токен-источника>` подготовленным токеном пользователя источника. Затем выполните файл **в приёмнике**:

```bash
{{ ydb-cli }} -p target sql -f create-secret.sql
```

После успешного выполнения проверьте доступ владельца репликации к секрету. Удалите локальный файл с токеном по правилам команды.

## 2. Создание объекта репликации {#create}

Этот раздел выполняется только для первоначального сканирования (`INITIAL_SCAN = TRUE`). Для переноса через резервную копию сразу перейдите к [разделу 3.2](#export-import-sync).

При выборе состава репликации учитывайте [рекомендации по выбору таблиц](index.md#replication-scope).

Сохраните в `create-replication.sql` следующий запрос:

```yql
CREATE ASYNC REPLICATION my_replication
FOR original_table AS replica_table
WITH (
    CONNECTION_STRING = 'grpcs://source.example.com:2135/?database=/Root/source',
    TOKEN_SECRET_PATH = 'source_token',
    CONSISTENCY_LEVEL = 'ROW',
    INITIAL_SCAN = TRUE
);
```

Где:

* `source.example.com:2135` : пример endpoint исходной базы данных, замените его адресом источника;
* `original_table AS replica_table` : соответствие исходной и целевой таблиц;
* `CONSISTENCY_LEVEL = 'ROW'` : режим согласованности в этом примере. Он сохраняет порядок изменений одного ключа, но не обеспечивает атомарную видимость изменений нескольких строк;
* `INITIAL_SCAN = TRUE` : первоначальное сканирование через CDC. Для переноса через S3 выполните [отдельный вариант](#export-import-sync).

Для переноса нескольких таблиц перечислите все пары путей в `FOR`. Остальные параметры описаны в [CREATE ASYNC REPLICATION](../../yql/reference/syntax/create-async-replication.md#params).

Выполните запрос **в приёмнике** и получите описание репликации:

```bash
{{ ydb-cli }} -p target sql -f create-replication.sql
{{ ydb-cli }} -p target scheme describe my_replication --stats --format proto-json-base64
```

Проверьте результат:

| Поле | Ожидаемый результат |
| --- | --- |
| `items` | Все выбранные таблицы с нужными `source_path` и `destination_path` |
| `items[].source_changefeed_name` | Имя созданного потока для каждого объекта; дождитесь заполнения |
| `running` | Присутствует при первоначальном сканировании через CDC |
| `paused` | Присутствует при `INITIAL_SCAN = FALSE`; репликация ожидает восстановления данных |
| `error` | Отсутствует |

Если появился `error`, разберите указанную ошибку до продолжения. При ответе `UNIMPLEMENTED` согласуйте с поддержкой доступный способ наблюдения: ошибка интерфейса не доказывает отсутствие объекта. Не выполняйте повторный `CREATE` для диагностики.

## 3. Перенос первоначальных данных {#initial-sync}

Выполните раздел, соответствующий выбранному значению `INITIAL_SCAN`.

### 3.1. Первоначальное сканирование через CDC {#initial-scan}

Используйте этот вариант, если при создании выбрали `INITIAL_SCAN = TRUE`.

При `INITIAL_SCAN = TRUE` сканирование уже запущено. Дождитесь его завершения:

```bash
{{ ydb-cli }} -p target scheme describe my_replication --stats --format proto-json-base64
{{ ydb-cli }} -p source scheme describe original_table --format proto-json-base64
```

В описании репликации должен оставаться `running`, а не `error`. Прогресс сканирования доступен в статистике репликации и её объектов. В описании исходной таблицы поток после окончания сканирования переходит из `STATE_INITIAL_SCAN` в `STATE_ENABLED`. Проверьте каждый переносимый объект и наличие целевых таблиц.

Завершение сканирования не означает, что приёмник уже применил все накопленные изменения. Когда отставание станет небольшим и стабильным, переходите к [окончательной проверке](#readiness).

### 3.2. Первоначальная синхронизация с помощью резервной копии {#export-import-sync}

Если выбран перенос через резервную копию, **не выполняйте создание репликации из раздела 2**. Сначала выполните [предварительные условия руководства по первоначальной синхронизации](../async-replication-initial-sync.md#prerequisites): подготовьте S3-хранилище, доступы, свободный префикс и период доступности изменений. Секрет `source_token` уже создан на шаге 1.3 этого рецепта; используйте его повторно, не создавая второй секрет. Затем выполните шаги 1–5 того же руководства. Оно включает создание репликации с `INITIAL_SCAN = FALSE`, проверку готовности CDC, экспорт, импорт и запуск применения изменений.

В этом руководстве используйте те же имена объектов: `my_replication`, `replica_table`, `source_token`, `original_table` и профили `source` и `target`. После появления состояния `running` вернитесь к [оценке отставания](#replication-lag) ниже.

Отдельные шаги руководства:

- [Проверка готовности потоков](../async-replication-initial-sync.md#wait-for-changefeeds). {#s3-changefeeds}
- [Экспорт исходных данных](../async-replication-initial-sync.md#export). {#s3-export}
- [Импорт в приёмник](../async-replication-initial-sync.md#import). {#s3-import}
- [Запуск применения изменений](../async-replication-initial-sync.md#start-replication). {#s3-start-replication}

### 3.3. Оценка отставания репликации {#replication-lag}

После завершения выбранного способа первоначальной синхронизации получите статистику в приёмнике:

```bash
{{ ydb-cli }} -p target scheme describe my_replication --stats --format proto-json-base64
```

Проверьте следующие поля:

| Поле | Что проверять |
| --- | --- |
| `running.stats.lag` | Общее отставание репликации |
| `items[].stats.lag` | Отставание каждого переносимого объекта |
| `error` | Поле должно отсутствовать |

Значения `lag` имеют формат длительности, например `5s` означает пять секунд. Повторите команду несколько раз: после первоначального переноса отставание должно уменьшаться и затем оставаться небольшим. Выберите допустимое отставание с учётом времени, на которое приложение может остановить запись. Если оно растёт или в описании появляется ошибка, устраните причину до переключения.

Отсутствие значения `lag` не означает нулевое отставание. Даже значение `0s` не заменяет [окончательную проверку применения изменений и данных](#readiness).

### 3.4. Ошибки и остановка репликации {#replication-overload}

Если в описании появился `error`, сохраните текст ошибки, проверьте доступность источника, права и схемы таблиц. При росте отставания проверьте ресурсы обеих баз и место для CDC в источнике. До устранения причины не переходите к переключению.

После устранения критичной ошибки выполните в приёмнике [приостановку и возобновление](../../yql/reference/syntax/alter-async-replication.md):

```yql
ALTER ASYNC REPLICATION my_replication SET (STATE = 'PAUSED');
ALTER ASYNC REPLICATION my_replication SET (STATE = 'STANDBY');
```

Повторно получите описание. Продолжайте только после появления `running` без `error` и подтверждения, что необходимые изменения CDC ещё доступны. При утрате истории потребуется повторная первоначальная синхронизация.

## 4. Проверка готовности к переключению {#readiness}

Этот раздел выполняется при доступном источнике. Если источник недоступен, используйте [аварийный порядок](#source-unavailable).

### 4.1. Остановка записи {#stop-writes}

Остановите запись приложения, фоновых заданий, загрузчиков и повторных доставок в источник. Дождитесь завершения выполняющихся запросов и транзакций и исключите автоматический перезапуск старых писателей. **С этого момента начинается простой записи.**

### 4.2. Проверка применения изменений {#check-replication}

Получите состояние репликации и статистику её потоков:

После остановки записи дождитесь свежих отчётов с `running.stats.lag = 0s` и `items[].stats.lag = 0s` для всех переносимых объектов. Если значение недоступно, дождитесь возобновления отчётов; отсутствие значения не означает нулевое отставание. До этого не переходите к `DONE/FORCE`. Свежий ноль необходим для этого порядка переключения, но сам по себе не доказывает полноту переноса: продолжите проверки потоков и данных ниже.

Значения `source_path` и `source_changefeed_name` возьмите из каждого элемента `items` в описании репликации:

| Объект | Путь топика CDC |
| --- | --- |
| Таблица | `source_path/source_changefeed_name` |
| Таблица реализации индекса | `source_path/indexImplTable/source_changefeed_name` |

Для индекса описание таблицы и состояние потока проверяются по пути `source_path/indexImplTable`, как в [проверке готовности потоков](../async-replication-initial-sync.md#wait-for-changefeeds). Команды ниже показывают обычную таблицу; повторите их для всех объектов с соответствующими путями.

```bash
{{ ydb-cli }} -p target scheme describe my_replication --stats --format proto-json-base64

CDC_TOPIC='original_table/<имя_потока>'
{{ ydb-cli }} -p source scheme describe "$CDC_TOPIC" --stats --partition-stats
```

В описании топика найдите имя потребителя репликации и подставьте его в следующую команду:

```bash
REPL_CONSUMER='<имя потребителя репликации>'
{{ ydb-cli }} -p source topic consumer describe "$CDC_TOPIC" --consumer "$REPL_CONSUMER" --partition-stats
```

Для каждой партиции смотрите следующие значения:

| Значение | Что означает |
| --- | --- |
| `Start offset` | Начало ещё доступного диапазона сообщений |
| `End offset` | Конец диапазона записанных сообщений, не включая саму границу |
| `Committed offset` | Граница сообщений, обработку которых подтвердил потребитель |

После поступления последних изменений зафиксируйте `End offset` каждой партиции и дождитесь, пока `Committed offset` достигнет этой границы. Например, при границе `120` значение `Committed offset = 115` означает, что потребитель её ещё не достиг; значение `120` означает, что обработка до этой границы подтверждена. Проверьте весь набор потоков и партиций.

Эта проверка относится к сообщениям, уже попавшим в потоки. Она не доказывает, что все изменения вышли из внутренних очередей источника. Нулевое отставание, завершённое сканирование или состояние `running` также не являются самостоятельным подтверждением полноты переноса.

### 4.3. Проверка готовности приложения {#check-data}

После применения оставшихся изменений проверьте чтение данных в принимающей базе от имени приложения. Выполните заранее подготовленные запросы по известным ключам и убедитесь, что они возвращают ожидаемые результаты.

Дополнительно можно сравнить количество строк в исходной и принимающей таблицах:

```yql
-- В исходной базе данных:
SELECT COUNT(*) FROM original_table;

-- В принимающей базе данных:
SELECT COUNT(*) FROM replica_table;
```

Выбирайте проверки с учётом допустимого простоя записи: на больших таблицах `COUNT(*)` может выполняться долго. Совпадение количества строк не гарантирует совпадения их содержимого.

Если свежие отчёты после остановки записи показывают нулевое отставание для всех объектов, все партиции достигли зафиксированных границ, ошибок репликации нет и согласованные проверки данных подтвердили полноту переноса, переходите к [завершению репликации и переключению приложения](#cutover). Если полноту переноса подтвердить не удалось, не выполняйте `DONE/FORCE`: сохраните остановку записи, разберите причину и согласуйте дальнейшие действия с поддержкой вашей инсталляции. При ошибках устраните их причину и повторите проверки.

## 5. Завершение репликации и переключение приложения {#cutover}

{% note warning %}

`DONE/FORCE` не проверяет полноту данных и отставание. Завершённую репликацию нельзя возобновить. Выполняйте команду после [проверки готовности](#readiness).

{% endnote %}

Выполните запрос **в приёмнике**:

```yql
ALTER ASYNC REPLICATION my_replication
SET (STATE = 'DONE', FAILOVER_MODE = 'FORCE');
```

Проверьте результат:

```bash
{{ ydb-cli }} -p target scheme describe my_replication --format proto-json-base64
```

Дождитесь появления поля `done` вместо `running`. Затем от имени приложения выполните согласованную тестовую запись, чтение и очистку тестовых данных в приёмнике. Все нужные таблицы должны быть доступны для записи. Успех SQL-запроса сам по себе не заменяет проверку состояния и доступности таблиц.

Переключите endpoint, путь базы данных, TLS/CA и аутентификацию клиентов на приёмник. В этом примере исходная таблица называется `original_table`, а целевая `replica_table`: замените имя и в относительных SQL-запросах приложения. Также проверьте абсолютные пути в SQL, `PRAGMA TablePathPrefix`, миграторы и фоновые задания. Подготовьте недостающие объекты и индексы до запуска зависимых запросов, затем пересоздайте соединения по процедуре приложения.

Включите запись **только в приёмнике** и проверьте рабочие сценарии реальными клиентами. **На этом простой записи заканчивается.** Источник оставьте закрытым для записи. После первой новой записи возврат приложения в старую базу потребует сверки и переноса новых изменений: одного обратного переключения endpoint недостаточно.

## 6. Удаление объекта репликации (опционально) {#cleanup}

Удаление не требуется для работы приложения после переключения. Выполняйте его отдельно, когда данные приёмника проверены и потоки этой репликации в источнике больше не нужны.

| Что требуется | Порядок действий |
| --- | --- |
| Оставить целевые таблицы доступными для записи | Сначала завершите репликацию через `DONE` и проверьте запись |
| Удалить объект репликации, сохранив целевые таблицы | После завершения выполните обычный `DROP ASYNC REPLICATION`; потоки изменений в источнике также будут удалены |
| Удалить объект репликации и целевые таблицы | Используйте `CASCADE` только при намеренном удалении данных приёмника |

Для удаления экземпляра выполните **в приёмнике** запрос [DROP ASYNC REPLICATION](../../yql/reference/syntax/drop-async-replication.md):

```yql
DROP ASYNC REPLICATION my_replication;
```

Сохраните права на источник до окончания очистки. Проверьте удаление объекта репликации и его потоков, сохранность целевых таблиц и снятие ограничений исходной схемы. Секрет и доступы удаляйте только после проверки, что они не нужны другим потребителям.

Если источник недоступен или удаление зависло, обратитесь в поддержку вашей инсталляции. Не повторяйте удаление с `CASCADE`. Для диагностики приложите пути обеих баз, имя репликации, версии серверов и CLI, время и текст ошибки, состояние репликации и последние известные позиции. Не включайте токены и пароли в диагностические материалы.

## Если источник недоступен {#source-unavailable}

При временном отказе сохраняйте возможность продолжить репликацию и контролируйте доступность истории CDC. Не используйте завершение или пересоздание репликации как способ устранения ошибки подключения.

Если ждать восстановления источника нельзя, аварийное переключение требует решения владельца приложения о допустимых потерях данных. Зафиксируйте состав доступных таблиц, последние известные позиции применения изменений и проверки, которые выполнить невозможно. Исключите возобновление записи в старую базу при восстановлении источника.

Без источника нельзя подтвердить перенос всех последних записей по одному только состоянию приёмника. `DONE/FORCE` не восстанавливает недоставленные изменения. До завершения согласуйте с поддержкой возможность перехода для текущей версии и состояния репликации. После перехода проверьте запись и работу приложения, как при плановом переключении.
