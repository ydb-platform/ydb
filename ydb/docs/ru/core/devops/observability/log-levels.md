# Оптимальный уровень логирования для продакшена

В {{ ydb-short-name }} уровень детализации логов задаётся отдельно для компонентов. В рабочей среде обычно достаточно фиксировать существенные события; для разбора инцидента уровень временно повышают и после сбора данных возвращают обратно.

Полный перечень уровней и параметров секции `log_config` см. в [{#T}](../../reference/configuration/log_config.md). Изменение уровня через интерфейс см. в [{#T}](../../reference/ydb-ui/logs.md#change_log_level).

## Уровни логирования {#levels}

{{ ydb-short-name }} использует **девять** уровней логирования. В конфигурации (`default_level`, поле `level` в `entry`) они задаются **числом от 0 до 8**: чем **меньше** число, тем **важнее** событие (приоритет записи), чем **больше** — тем **подробнее** обычный поток сообщений. Значение `5` (`NOTICE`) — типичный уровень по умолчанию в кластере.

| Уровень | Число | Назначение |
| --- | --- | --- |
| `EMERG` | 0 | Возможен сбой системы (например, отказ кластера) |
| `ALERT` | 1 | Возможна деградация системы |
| `CRIT` | 2 | Критическое состояние |
| `ERROR` | 3 | Некритическая ошибка |
| `WARN` | 4 | Предупреждение, требующее реакции |
| `NOTICE` | 5 | Существенные события |
| `INFO` | 6 | Контекст для статистики и штатного мониторинга |
| `DEBUG` | 7 | Подробности для диагностики |
| `TRACE` | 8 | Максимальная детализация |

Полные формулировки и параметры секции `log_config` — в [{#T}](../../reference/configuration/log_config.md#log-levels).

Уровни `EMERG`–`WARN` отражают ошибки и аварийные состояния. Не выбирайте их как режим логирования. Сообщение появляется, когда компонент фиксирует соответствующее событие. Для штатной работы оставьте `NOTICE`, а для временной диагностики поднимайте детализацию до `INFO`, `DEBUG` или `TRACE`.

## Когда какой уровень использовать {#when}

Ориентир по сценариям:

- **`INFO`** — нормальная работа кластера, когда нужен чуть более подробный контекст, чем на `NOTICE`, без включения отладочного потока.
- **`DEBUG`** — диагностика нестабильного поведения, разбор инцидента, воспроизведение проблемы на стенде или на ограниченном наборе компонентов.
- **`TRACE`** — глубокое расследование единичных случаев; включайте **точечно** (компонент, узел, ограниченный интервал времени), а не на весь кластер без необходимости.

Для продакшена держите базовый уровень **`NOTICE`** (или `INFO`, если этого требует ваша политика наблюдаемости). Не оставляйте `TRACE` или `DEBUG` включёнными для всего кластера постоянно. Иначе растёт объём логов и нагрузка на запись.

## Как изменить уровень {#how}

### Статическая конфигурация

Задайте секцию `log_config` в конфигурации кластера. `KQP` в примере — имя компонента обработки запросов ([Query Processor](../../concepts/glossary.md#kqp)) в логах:

```yaml
log_config:
  default_level: 5  # NOTICE
  entry:
    - component: "KQP"
      level: 6  # INFO
```

Подробнее о полях `default_level`, `entry`, семплировании и формате вывода — в [{#T}](../../reference/configuration/log_config.md).

### Без перезапуска узлов (динамическая конфигурация)

Секция `log_config` входит в список [динамически обновляемых настроек](../configuration-management/configuration-v1/dynamic-config.md#dynamic-kinds). Обновите YAML конфигурации кластера и примените его, например:

```bash
{{ ydb-cli }} admin config replace -f dynconfig.yaml
```

Команда заменяет динамическую конфигурацию целиком. В `dynconfig.yaml` оставьте текущий файл кластера и измените в нём секцию `log_config`. Фрагменты выше не подходят как готовый файл для замены.

После распространения конфигурации новые уровни начнут действовать без перезапуска узлов.

### Через {{ ydb-ui-name }} (CMS)

Если в кластере ещё используется управление через CMS, измените уровни на вкладке **Configs** → `LogConfigItems`, как описано в [{#T}](../../reference/ydb-ui/logs.md#change_log_level).

## Когда повышать уровень {#raise}

Повышайте детализацию, если:

- в логах **не хватает контекста** для понимания сбоя или деградации;
- наблюдается **нестабильное поведение** (периодические ошибки, таймауты, «плавающие» симптомы);
- нужно **воспроизвести** проблему и зафиксировать цепочку событий.

Действуйте по шагам: сначала `INFO` или `DEBUG` для **конкретного компонента**, затем при необходимости `TRACE` и только на ограниченное время. Пример точечной настройки (для инвалидации блокировок транзакций см. [{#T}](../../troubleshooting/performance/queries/tli-logging.md)):

```yaml
log_config:
  default_level: 5
  entry:
    - component: "TLI"
      level: 6  # INFO
```

## Когда понижать уровень {#lower}

После завершения диагностики **обязательно** верните прежние уровни:

- логи для анализа **собраны**;
- проблема **воспроизведена** и передана в обработку, или инцидент **закрыт**;
- временное повышение уровня **больше не нужно**.

Иначе остаётся лишний объём логов, растёт нагрузка на диск и процессор, усложняется поиск новых событий в потоке.

## Ограничения и риски {#limits}

Чем выше уровень детализации, тем больше сообщений генерирует кластер:

- **Объём логов** — быстрее заполняются диск и журналы (`journald`, файлы, внешние агенты сбора).
- **Нагрузка на CPU** — затраты на форматирование и запись строк.
- **Шум** — на `DEBUG` и `TRACE` сложнее выделить редкие ошибки.

Чтобы снизить риск перегрузки, используйте параметры из `log_config`:

- `allow_drop_entries` — буфер в памяти: записи уходят в вывод, когда накопилось 10 сообщений или истёк `time_threshold_ms`; при переполнении буфера отбрасываются сообщения с более низким приоритетом. `time_threshold_ms` — этот период сброса, в миллисекундах;
- `default_sampling_level`, `default_sampling_rate` и поля `sampling_*` в `entry` — частичная запись сообщений между основным и семплируемым уровнем (см. [{#T}](../../reference/configuration/log_config.md)).

Трассировка запросов (OpenTelemetry) настраивается **отдельно** от уровней логов — см. [{#T}](../../reference/observability/tracing/setup.md). Поле **`fraction`** относится к **`tracing_config.sampling`**, а не к `log_config`: им задают долю трассируемых запросов, а не текстовых строк в журнале.

```yaml
tracing_config:
  sampling:
    - level: 10  # Detailed: диагностика в продакшене, не максимум
      fraction: 0.01  # 1% запросов
    - level: 14  # Diagnostic: отладочная детализация по всем слоям
      fraction: 0.001
```

### Пример конфигурации для продакшена

```yaml
log_config:
  default_level: 5  # NOTICE — основной уровень для продакшена
  default_sampling_level: 7  # DEBUG — уровень для семплирования
  default_sampling_rate: 10  # примерно каждое 10-е сообщение между NOTICE и DEBUG

  entry:
    - component: "KQP"
      level: 5  # NOTICE
      sampling_level: 7  # DEBUG
      sampling_rate: 50  # примерно каждое 50-е DEBUG-сообщение для KQP
    - component: "BLOBSTORAGE"
      level: 5
      sampling_level: 8  # TRACE
      sampling_rate: 100

  # Снижение нагрузки при перегрузке канала записи
  allow_drop_entries: true  # разрешить отбрасывание маловажных записей
  time_threshold_ms: 1000   # период сброса буфера логов, мс

  # Формат вывода
  format: "json"  # удобен для парсинга
  cluster_name: "production-cluster"  # имя кластера в формате json
```

### Пример избыточной детализации

```yaml
log_config:
  default_level: 8  # TRACE для всего кластера
  default_sampling_level: 8
  default_sampling_rate: 1

  entry:
    - component: "*"
      level: 8
      sampling_level: 8
      sampling_rate: 1
```

Такая настройка создаёт очень большой поток логов, повышает нагрузку на систему и затрудняет анализ. Используйте её только как кратковременную меру на стенде, а не как норму для продакшена.
