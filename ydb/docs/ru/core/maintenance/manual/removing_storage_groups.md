# Удаление групп хранения из базы данных

В процессе работы у [базы данных](../../concepts/glossary.md#database) может оказаться больше [групп хранения](../../concepts/glossary.md#storage-group), чем ей нужно: например, после удаления данных или после временного расширения базы. Каждая группа хранения занимает [слоты](../../concepts/glossary.md#slot) на [PDisk'ах](../../concepts/glossary.md#pdisk), поэтому неиспользуемые группы удерживают ресурсы кластера, которые могли бы достаться другим базам данных.

Удаление групп хранения позволяет вернуть часть групп базы данных обратно кластеру. Данные, хранящиеся в удаляемых группах, переносятся в оставшиеся группы того же [пула хранения](../../concepts/glossary.md#storage-pool), после чего удаляемые группы удаляются, а их [VDisk'и](../../concepts/glossary.md#vdisk) и слоты на PDisk'ах освобождаются.

{% note info %}

Эта процедура отличается от [декомиссии групп с использованием виртуальных групп](virtual_storage_groups_decommit.md). При декомиссии физическая группа заменяется виртуальной, которая продолжает обслуживать исходный идентификатор группы. При удалении групп хранения, описанном в этой статье, таблетки базы данных полностью перестают использовать удаляемые группы, и виртуальные группы не создаются.

{% endnote %}

## Как это работает

Группы хранения выделяются базе данных в *единицах хранения* (storage units): одна единица хранения определённого вида соответствует одной группе хранения в пуле хранения базы данных этого вида (например, `/Root/db1:ssd` для вида `ssd`). Чтобы удалить группы хранения, нужно уменьшить количество единиц хранения базы данных запросом `AlterDatabase` к [CMS](../../concepts/glossary.md#cms). Всё остальное происходит автоматически, в фоновом режиме:

1. **Изменение требуемого количества групп.** [Console](../../concepts/glossary.md#console) сохраняет новое требуемое количество единиц хранения и сразу отвечает на запрос. База данных переходит в состояние `REMOVING_STORAGE_UNITS`.
1. **Выбор удаляемых групп.** Console просит [Hive](../../concepts/glossary.md#hive) уменьшить пул хранения до нового размера. Hive выбирает группы, в которых сейчас хранится меньше всего данных, и помечает их как неактивные. Новые данные в неактивные группы больше не размещаются. Если у базы данных есть собственный Hive, корневой Hive пересылает ему запрос, и в процессе участвуют оба.
1. **Перенос каналов таблеток.** Каждый [канал](../../concepts/glossary.md#channel) [таблетки](../../concepts/glossary.md#tablet), который сейчас пишет в неактивную группу, переназначается на одну из оставшихся групп пула. С этого момента таблетки пишут новые данные только в оставшиеся группы. Переназначение канала перезапускает таблетку, что обычно занимает доли секунды.
1. **Перенос данных.** Старые данные, записанные до переназначения каналов, всё ещё хранятся в неактивных группах. Hive просит каждую таблетку, у которой есть такие данные, перезаписать их: таблетка выполняет [компакшн](../../concepts/glossary.md#compaction) всех своих данных в новые группы и удаляет старые копии. Таблетки обрабатываются по одной. Когда таблетка заканчивает, Hive перезапускает её, и таблетка перестаёт ссылаться на неактивные группы.
1. **Удаление групп.** Когда ни одна таблетка больше не ссылается на неактивные группы, Hive сообщает об этом Console. Console удаляет группы в [распределённом хранилище](../../concepts/glossary.md#distributed-storage), что освобождает их VDisk'и и слоты на PDisk'ах. Количество выделенных единиц хранения уменьшается, и база данных возвращается в состояние `RUNNING`.

{% note info %}

База данных остаётся полностью доступной в течение всего процесса: пользователи могут читать и записывать данные как обычно. Однако перенос данных создаёт дополнительную нагрузку на базу данных и систему хранения: таблетки выполняют компакшн и перезаписывают все свои данные, хранящиеся в удаляемых группах.

{% endnote %}

Длительность процесса в основном зависит от объёма данных в удаляемых группах и от количества таблеток, у которых есть в них данные: от секунд для пустой базы данных до часов для больших.

## Ограничения

* В базе данных должна остаться хотя бы одна единица хранения каждого вида. Запрос, удаляющий все единицы хранения какого-либо вида, отклоняется.
* Удалять единицы хранения можно только из выделенных (dedicated) баз данных. Общие (shared) и бессерверные (serverless) базы данных эту операцию не поддерживают.
* Выбрать, какие именно группы будут удалены, нельзя: Hive выбирает их автоматически, отдавая предпочтение группам с наименьшим объёмом данных.
* В оставшихся группах пула должно быть достаточно свободного места и пропускной способности, чтобы принять данные из удаляемых групп.

## Удаление единиц хранения

Единицы хранения удаляются вызовом `AlterDatabase` gRPC-сервиса CMS `Ydb.Cms.V1.CmsService`. Форматы запросов и ответов описаны в файле [ydb_cms.proto](https://github.com/ydb-platform/ydb/blob/main/ydb/public/api/protos/ydb_cms.proto). Вызов можно выполнить любым gRPC-клиентом. В примерах ниже используется [grpcurl](https://github.com/fullstorydev/grpcurl) вместе с proto-файлами API {{ ydb-short-name }} из [репозитория {{ ydb-short-name }}](https://github.com/ydb-platform/ydb).

Пользователь, выполняющий запросы, должен быть администратором кластера.

### Получение токена аутентификации

```bash
{{ ydb-cli }} -e grpcs://<cluster-endpoint>:2135 -d /Root --user <user> auth get-token -f > ~/ydb_token
```

### Проверка текущих единиц хранения

Получите состояние базы данных вызовом `GetDatabaseStatus`:

```bash
grpcurl -cacert <path-to-ca-cert> \
  -H "x-ydb-auth-ticket: $(cat ~/ydb_token)" \
  -import-path <path-to-ydb-repo> \
  -proto ydb/public/api/grpc/ydb_cms_v1.proto \
  -d '{"path": "/Root/db1"}' \
  <cluster-endpoint>:2135 \
  Ydb.Cms.V1.CmsService/GetDatabaseStatus
```

Результат содержит, среди прочего, поля:

* `state` — состояние базы данных;
* `requiredResources.storageUnits` — количество единиц хранения каждого вида, которое должно быть у базы данных;
* `allocatedResources.storageUnits` — количество единиц хранения каждого вида, которое фактически выделено базе данных сейчас.

Пример результата (показаны только нужные поля):

```json
{
  "path": "/Root/db1",
  "state": "RUNNING",
  "requiredResources": {
    "storageUnits": [
      { "unitKind": "ssd", "count": "8" }
    ]
  },
  "allocatedResources": {
    "storageUnits": [
      { "unitKind": "ssd", "count": "8" }
    ]
  },
  "generation": "3"
}
```

{% note info %}

API CMS возвращает результаты, обёрнутые в операцию: сообщение `GetDatabaseStatusResult` упаковано в поле `operation.result` ответа. В примерах в этой статье показано только содержимое `operation.result`.

{% endnote %}

### Запуск удаления

Вызовите `AlterDatabase` и перечислите удаляемые единицы хранения в поле `storage_units_to_remove`. Пример ниже удаляет 3 единицы хранения вида `ssd` из базы данных `/Root/db1`:

```bash
grpcurl -cacert <path-to-ca-cert> \
  -H "x-ydb-auth-ticket: $(cat ~/ydb_token)" \
  -import-path <path-to-ydb-repo> \
  -proto ydb/public/api/grpc/ydb_cms_v1.proto \
  -d '{
        "path": "/Root/db1",
        "storage_units_to_remove": [
          { "unit_kind": "ssd", "count": 3 }
        ]
      }' \
  <cluster-endpoint>:2135 \
  Ydb.Cms.V1.CmsService/AlterDatabase
```

Параметры запроса:

* `path` — полный путь к базе данных;
* `storage_units_to_remove` — список удаляемых единиц хранения:
  * `unit_kind` — вид единиц хранения, совпадающий с видом пула хранения базы данных (например, `ssd` для пула `/Root/db1:ssd`);
  * `count` — количество удаляемых единиц хранения (групп хранения);
* `generation` — необязательный. Если задан, запрос применяется, только если текущее поколение базы данных, возвращаемое `GetDatabaseStatus`, совпадает с этим значением. Используйте его, чтобы убедиться, что с момента проверки состояния базу данных никто не изменил;
* `idempotency_key` — необязательный. Если задан, повторный запрос с тем же ключом не применяется повторно, что делает повтор запроса безопасным.

Запрос завершается, как только новое количество единиц хранения сохранено. Статус операции `SUCCESS` означает, что удаление началось, а не что оно закончилось.

Если запрос отклонён, ответ содержит статус `BAD_REQUEST` или `UNSUPPORTED` и описание ошибки. Например, `Not enough units of kind 'ssd' to remove` означает, что запрос удалил бы все единицы хранения этого вида.

### Отслеживание прогресса

Периодически вызывайте `GetDatabaseStatus`. Пока группы удаляются:

* `state` имеет значение `REMOVING_STORAGE_UNITS`;
* `requiredResources.storageUnits` уже показывает новое, уменьшенное количество единиц хранения;
* `allocatedResources.storageUnits` всё ещё показывает прежнее количество единиц хранения.

Удаление завершено, когда `state` возвращается в `RUNNING`, а количество выделенных единиц хранения совпадает с требуемым:

```json
{
  "path": "/Root/db1",
  "state": "RUNNING",
  "requiredResources": {
    "storageUnits": [
      { "unitKind": "ssd", "count": "5" }
    ]
  },
  "allocatedResources": {
    "storageUnits": [
      { "unitKind": "ssd", "count": "5" }
    ]
  },
  "generation": "4"
}
```

Если что-то мешает удалению продвигаться, проблемы отображаются в поле `issues` результата `GetDatabaseStatus`.

Количество групп в пуле хранения (колонка `Groups_TOTAL`) можно также проверить с помощью [{{ ydb-short-name }} DSTool](../../reference/ydb-dstool/index.md):

```bash
ydb-dstool -e <bs_endpoint> pool list
```

### Изменение или отмена удаления

Пока группы удаляются, базу данных всё ещё можно изменять. Чтобы удалить меньше групп, чем было запрошено изначально, или отменить удаление, верните единицы хранения полем `storage_units_to_add` запроса `AlterDatabase`:

```bash
grpcurl -cacert <path-to-ca-cert> \
  -H "x-ydb-auth-ticket: $(cat ~/ydb_token)" \
  -import-path <path-to-ydb-repo> \
  -proto ydb/public/api/grpc/ydb_cms_v1.proto \
  -d '{
        "path": "/Root/db1",
        "storage_units_to_add": [
          { "unit_kind": "ssd", "count": 3 }
        ]
      }' \
  <cluster-endpoint>:2135 \
  Ydb.Cms.V1.CmsService/AlterDatabase
```

Группы, которые ещё не были удалены, снова становятся активными и продолжают обслуживать базу данных. Данные, уже перенесённые в другие группы, остаются там.

Аналогично, можно удалить дополнительные единицы хранения, пока предыдущее удаление ещё выполняется: новый запрос расширяет набор удаляемых групп.
