# Подключение внешней базы YDB с делегированием IAM

[Секрет с делегированием IAM](../concepts/datamodel/iam-delegation-secrets.md) позволяет {{ ydb-short-name }} получать и обновлять токены сервисного аккаунта без хранения его ключа или токена в базе. В этом руководстве вы разрешите делегирование в {{ yandex-cloud }}, настроите права и создадите внешний источник для доступа к топикам другой базы {{ ydb-short-name }}.

Потребуются две базы Managed Service for YDB: рабочая, в которой вы создадите секрет и внешний источник, и внешняя, в которой находятся топики. Установите и настройте [Yandex Cloud CLI](https://yandex.cloud/ru/docs/cli/quickstart) (`yc`) и [YDB CLI](../reference/ydb-cli/install.md) (`ydb`). Настройку облачных прав выполняет администратор соответствующих ресурсов; SQL-команды выполняет пользователь, которому вы выдадите права на следующих шагах.

Выполните общие шаги 1–4, затем выберите один способ:

- [Новый способ: секрет с делегированием](#create-secret). Делегирование настраивается при создании секрета, начальный токен в SQL не передаётся.
- [Существующий способ: `ycp` и начальный токен](#ycp-flow). Делегирование настраивается отдельной командой, а начальный токен пользователя записывается в обычный секрет. Этот способ приведён для пользователей, у которых уже есть доступ к `ycp` и соответствующему API.

Не смешивайте настройки этих способов. Все SQL-команды выполняйте в рабочей базе. В примере сервисный аккаунт принадлежит облаку внешней базы.

{% note info %}

Новый способ описывает планируемую функциональность, а не объявляет о её доступности в публичном облаке. Он требует поддержки секретов с `SOURCE="IAM_DELEGATION"` в рабочей базе. Включение сервиса в IAM не включает поддержку SQL-команды. Если сервис `ydb` не найден на первом шаге или база сообщает, что секреты с делегированием не поддерживаются, уточните доступность функции в [поддержке {{ yandex-cloud }}](https://yandex.cloud/ru/support).

{% endnote %}

## 1. Разрешите делегирование в облаке {#enable-delegation}

Проверьте [статус сервиса](https://yandex.cloud/ru/docs/iam/operations/service-control/list-get) `ydb` в облаке, которому принадлежит делегируемый сервисный аккаунт. Это не обязательно облако рабочей базы:

```bash
yc iam service-control get ydb --cloud-id "<service_account_cloud_id>"
```

Здесь и далее `<service_account_cloud_id>` обозначает идентификатор облака сервисного аккаунта. Если аккаунт ещё не создан, используйте облако каталога, в котором создадите его на следующем шаге.

При статусе `DISABLED` попросите администратора или владельца облака [включить сервис](https://yandex.cloud/ru/docs/iam/operations/service-control/enable-disable):

```bash
yc iam service-control enable ydb --cloud-id "<service_account_cloud_id>"
```

Повторите проверку: ожидается статус `ENABLED`. При исходном статусе `ENABLED` дополнительных действий не требуется; `DEFAULT` допускает автоматическое включение при первом делегировании. Команда `yc` разрешает сервису использовать делегирование, но не настраивает делегирование конкретного аккаунта. Для этого ниже используется `CREATE SECRET` или `ycp`, в зависимости от выбранного способа.

## 2. Подготовьте сервисный аккаунт и его доступ к данным {#service-account}

[Создайте сервисный аккаунт](https://yandex.cloud/ru/docs/iam/operations/sa/create) для чтения внешней базы или используйте существующий:

```bash
yc iam service-account create --name "<service_account_name>" --folder-id "<folder_id>"
```

Где:

- `<service_account_name>`: имя нового аккаунта, например `events-reader`;
- `<folder_id>`: идентификатор каталога в облаке из шага 1.

Сохраните поле `id` из результата команды. Далее оно обозначено как `<service_account_id>`.

Выдайте этому аккаунту роль `ydb.viewer` на внешнюю базу. Она разрешает подключение и чтение данных, но не их изменение:

```bash
yc ydb database add-access-binding --id "<remote_database_id>" \
  --role ydb.viewer --subject "serviceAccount:<service_account_id>"
```

Здесь `<remote_database_id>` обозначает идентификатор внешней базы в {{ yandex-cloud }}, а не её путь. Администратор может настроить более узкие права на нужные объекты вместо доступа ко всей базе. Подробнее: [роли YDB](https://yandex.cloud/ru/docs/ydb/security/) и [назначение роли на базу](https://yandex.cloud/ru/docs/ydb/operations/manage-databases).

## 3. Разрешите пользователю делегировать аккаунт {#caller-permissions}

Пользователю, который выполнит `CREATE SECRET`, нужна роль `iam.serviceAccounts.user` на сервисный аккаунт. Это отдельное право: роль аккаунта на внешнюю базу из предыдущего шага его не заменяет.

```bash
yc iam service-account add-access-binding --id "<service_account_id>" \
  --role iam.serviceAccounts.user --subject "<subject_type>:<subject_id>"
```

Где `<subject_type>:<subject_id>` обозначает именно исполнителя SQL-команды: `userAccount:<идентификатор>` для аккаунта Яндекса, `federatedUser:<идентификатор>` для федеративного пользователя или `serviceAccount:<идентификатор>` для сервисного аккаунта. Подробнее: [назначение прав на сервисный аккаунт](https://yandex.cloud/ru/docs/iam/operations/sa/set-access-bindings).

В рабочей базе этому же пользователю нужны права на создание секретов и внешних источников в выбранной директории, а для использования секрета в запросах нужно право `SELECT ROW` на него. Настройте их по разделу [Управление доступом к секретам](../concepts/datamodel/secrets.md#secret_access).

## 4. Подключитесь к рабочей базе {#connect}

В [консоли {{ yandex-cloud }}](https://console.yandex.cloud/) откройте рабочую базу и скопируйте её эндпоинт и путь из параметров подключения. Создайте [профиль YDB CLI](../reference/ydb-cli/profile/create.md) в интерактивном режиме:

```bash
ydb config profile create "<profile_name>"
```

Вместо `<profile_name>` задайте имя нового профиля, например `delegation-guide`. Укажите эндпоинт с `grpcs://`, путь рабочей базы и [аутентификацию через IAM](../reference/ydb-cli/connect.md) от имени пользователя из шага 3. Локальный логин базы данных для создания такого секрета не подходит. Профили `yc` и `ydb` независимы: вход в `yc` не настраивает аутентификацию `ydb`.

Если для входа в YDB CLI вы выбрали IAM-токен, получите его для этого пользователя по [инструкции IAM](https://yandex.cloud/ru/docs/iam/operations/iam-token/create). Это учётные данные клиента, а не токен делегируемого аккаунта, который {{ ydb-short-name }} получает для доступа к внешней базе. В новом способе клиентский токен не нужно записывать в секрет; в существующем способе отдельно создаётся секрет с начальным токеном пользователя.

## 5. Новый способ: создайте секрет с делегированием {#create-secret}

Сохраните следующий SQL в файл. Замените шаблоны своими значениями:

```yql
CREATE SECRET `<secret_name>` WITH (
    SOURCE="IAM_DELEGATION",
    SERVICE_ACCOUNT_ID="<service_account_id>",
    RESOURCE="<service_account_cloud_id>"
);
```

Где:

- `<secret_name>`: имя нового секрета в рабочей базе, например `events_sa`;
- `<service_account_id>`: идентификатор аккаунта из шага 2;
- `<service_account_cloud_id>`: идентификатор облака этого аккаунта из шага 1. Это не идентификатор каталога и не путь базы.

Выполните файл командой [YDB CLI](../reference/ydb-cli/sql.md):

```bash
ydb -p "<profile_name>" sql -f "<sql_file>"
```

Здесь `<profile_name>` обозначает профиль из шага 4, а `<sql_file>` обозначает путь к сохранённому файлу. Дождитесь успешного завершения `CREATE SECRET`, прежде чем переходить к следующему шагу. При ошибке проверьте статус сервиса и права пользователя; не заменяйте делегирование ручной записью токена в этот секрет.

## 6. Новый способ: создайте внешний источник данных {#create-source}

Теперь откройте в консоли внешнюю базу и скопируйте её эндпоинт и путь. Они отличаются от параметров подключения к рабочей базе, в которой выполняется SQL.

Сохраните следующий SQL в отдельный файл и выполните его той же командой `ydb -p <profile_name> sql -f <sql_file>`:

```yql
CREATE EXTERNAL DATA SOURCE `<source_name>` WITH (
    SOURCE_TYPE="Ydb",
    LOCATION="<remote_host_and_port>",
    DATABASE_NAME="<remote_database_path>",
    USE_TLS="TRUE",
    AUTH_METHOD="TOKEN",
    TOKEN_SECRET_PATH="<secret_name>"
);
```

Где:

- `<source_name>`: имя нового внешнего источника в рабочей базе, например `events_db`;
- `<remote_host_and_port>`: хост и порт внешней базы из её эндпоинта, без `grpcs://` и параметров URL;
- `<remote_database_path>`: путь внешней базы из параметров подключения, а не её облачный идентификатор;
- `<secret_name>`: имя секрета из шага 5.

Источник готов для [чтения топиков внешней базы](streaming_queries/topics.md). Его создание проверяет схему и ссылку на секрет, но не подтверждает доступ к данным внешней базы: получение токена и проверка прав на данные происходят при использовании источника.

В этом способе `CREATE SECRET` заменяет отдельный вызов настройки делегирования через `ycp`. Внешний источник использует `TOKEN_SECRET_PATH`, а не `INITIAL_TOKEN_SECRET_PATH`. {{ ydb-short-name }} получает и обновляет токены сервисного аккаунта самостоятельно.

## Существующий способ: ycp и начальный токен {#ycp-flow}

Вместо шагов 5–6 выполните следующие четыре шага. `ycp` является отдельным инструментом и не входит в публичный CLI `yc`. Пример предполагает, что вам уже предоставлены `ycp`, доступ к API настройки делегирования и профиль для нужной инсталляции. Если такого доступа нет, уточните возможность использования этого способа в [поддержке {{ yandex-cloud }}](https://yandex.cloud/ru/support); замена `ycp` на `yc` в командах ниже не является эквивалентом.

### 1. Настройте делегирование для внешней базы {#ycp-setup}

У исполнителя команды должно быть разрешение `ydb.databases.alter` на внешнюю базу и право использовать сервисный аккаунт. Если разрешения нет, попросите администратора выполнить настройку:

```bash
ycp --profile "<ycp_profile>" ydb database setup-delegation \
  --id "<remote_database_id>" \
  --service-account-id "<service_account_id>"
```

Где:

- `<ycp_profile>`: профиль `ycp` для нужной инсталляции;
- `<remote_database_id>`: облачный идентификатор внешней базы из шага 2, не путь базы и не идентификатор рабочей базы;
- `<service_account_id>`: сервисный аккаунт из шага 2.

Дождитесь успешного завершения команды. Она настраивает делегирование, но не выдаёт аккаунту права на данные: они должны быть настроены на шаге 2.

### 2. Получите начальный IAM-токен пользователя {#ycp-initial-token}

Получите токен своей облачной учётной записи, которой разрешено использовать сервисный аккаунт:

```bash
ycp --profile "<ycp_profile>" iam create-token
```

Здесь `<ycp_profile>` обозначает профиль с вашей учётной записью, а не с целевым сервисным аккаунтом. Профили `ycp`, `yc` и `ydb` настраиваются отдельно. Если делегирование на предыдущем шаге настраивал администратор, не используйте его токен.

Скопируйте полученный токен для следующего шага. Он нужен для первоначальной проверки права пользователя использовать сервисный аккаунт. Это не токен сервисного аккаунта, который {{ ydb-short-name }} будет получать для обращения к данным. Не публикуйте токен и не сохраняйте SQL с ним в репозитории.

### 3. Создайте обычный секрет с начальным токеном {#ycp-value-secret}

В рабочей базе создайте [секрет с `VALUE`](../yql/reference/syntax/create-secret.md). В примере указана демонстрационная строка: фраза «Добро пожаловать на уровень 2» в кодировке Base64. Это не настоящий IAM-токен. Замените всё значение `VALUE` токеном из предыдущего шага:

```yql
CREATE SECRET `events_initial_token` WITH (
    VALUE="0JTQvtCx0YDQviDQv9C+0LbQsNC70L7QstCw0YLRjCDQvdCwINGD0YDQvtCy0LXQvdGMIDI="
);
```

Выполните SQL через профиль рабочей базы: `ydb -p <profile_name> sql -f <sql_file>`. Здесь `<profile_name>` обозначает профиль из шага 4 общего раздела, а `<sql_file>` обозначает файл с запросом. Дождитесь успешного создания секрета.

### 4. Создайте внешний источник с IAM-аутентификацией {#ycp-source}

Сохраните следующий SQL в отдельный файл и выполните его в рабочей базе той же командой YDB CLI. В `INITIAL_TOKEN_SECRET_PATH` укажите созданный секрет:

```yql
CREATE EXTERNAL DATA SOURCE `<source_name>` WITH (
    SOURCE_TYPE="Ydb",
    LOCATION="<remote_host_and_port>",
    DATABASE_NAME="<remote_database_path>",
    USE_TLS="TRUE",
    AUTH_METHOD="IAM",
    SERVICE_ACCOUNT_ID="<service_account_id>",
    RESOURCE_ID="<service_account_cloud_id>",
    INITIAL_TOKEN_SECRET_PATH="events_initial_token"
);
```

Где:

- `<source_name>`: имя нового внешнего источника, например `events_db`;
- `<remote_host_and_port>` и `<remote_database_path>`: хост с портом без `grpcs://` и путь внешней базы из её параметров подключения;
- `<service_account_id>` и `<service_account_cloud_id>`: идентификаторы аккаунта и его облака из общих шагов 1–2.

Дождитесь успешного создания источника. Как и в новом способе, это не подтверждает доступ к данным внешней базы: он проверяется при использовании источника. В примерах секрет и источник создаются в одном каталоге. Для разных каталогов укажите полный путь к секрету в `INITIAL_TOKEN_SECRET_PATH` или `TOKEN_SECRET_PATH`.
