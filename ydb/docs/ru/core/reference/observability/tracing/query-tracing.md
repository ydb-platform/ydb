# Трассировка выполнения запросов

Трасса запроса показывает, какие операции выполняла {{ ydb-short-name }} и сколько времени они заняли. Спан описывает отдельную операцию: время начала, длительность и результат. Дополнительные поля спана называются атрибутами: в них могут быть указаны таблица, число обработанных строк или код ошибки.

Порядок сбора спанов описан в статьях о [настройке трассировки](setup.md) и [передаче внешнего trace-id](external-traces.md). Ниже описаны спаны обработчика запросов и их атрибуты.

## Обработчик запросов {#query-processor}

[Обработчик запросов](../../../concepts/query_execution/index.md) подготавливает план выполнения запроса, запускает вычисления, чтение и запись данных. Подготовка плана называется компиляцией. Спаны этих операций помогают понять, сколько времени запрос потратил на подготовку, ожидание и выполнение.

Этот раздел описывает спаны, создаваемые обработчиком запросов. В общей трассе у них могут быть дочерние спаны других компонентов, участвующих в выполнении запроса.

### Уровни детализации {#levels}

[Уровень детализации трассы](setup.md#tracing-levels) определяет, какие спаны появятся в системе просмотра трасс. Более высокий уровень включает спаны предыдущих уровней.

| Минимальный `level` | Уровень обработчика запросов | Что можно увидеть |
| --- | --- | --- |
| 1 | `TopLevel` | Запрос целиком, его итоговый статус и сводные показатели. |
| 6 | `Basic` | Подготовку и выполнение плана, ожидание начала выполнения, отдельные задачи, чтение и запись данных. |
| 10 | `Detailed` | Подготовку сведений о таблицах, стадии плана со сводками по задачам, этапы фиксации транзакции. |
| 14 | `Diagnostic` | Спаны `Read shard` и `Scan shard`, события со статистикой чтения и подтверждениями шардов. |

На уровне 0 спаны обработчика запросов не создаются. Для запросов, выбранных правилами сэмплирования, уровень задаётся полем `level`. Запрос с внешним trace-id получает уровень 13, если проходит ограничения [`external_throttling`](setup.md#external-throttling). Для обработчика запросов это соответствует детализации `Detailed`: спаны `Read shard` и `Scan shard` уровня `Diagnostic` в такую трассу не входят.

### Структура спанов {#structure}

Спан `Query Proxy` охватывает обработку запроса на принимающем узле, включая ожидание ответа от сессии. Вложенный `Query session` охватывает выполнение одного запроса в сессии. Для других действий используются имена `Prepare query`, `Explain query`, `Validate query`, `Begin transaction`, `Commit transaction` и `Rollback transaction`.

Спан `Query session` относится к одному запросу, а не ко всему времени существования сессии или транзакции. Несколько запросов одной транзакции можно сопоставить по атрибуту `ydb.tx.id`, если он присутствует.

Если запрос перенаправлен на другой узел, в трассе может быть несколько спанов `Query Proxy`. Перенаправление показано спаном `KQP redirect`: его атрибуты `ydb.source_node_id` и `ydb.target_node_id` указывают узлы отправления и назначения.

#### Основные этапы {#phases}

Имена спанов помогают определить, на каком этапе запрос провёл время. Спан появляется, если соответствующая операция выполнялась и выбран достаточный уровень детализации.

| Спан | Что он описывает |
| --- | --- |
| `Queued` | Ожидание разрешения на выполнение в [пуле ресурсов](../../../concepts/glossary.md#resource-pool). Атрибут `ydb.pool_id` позволяет определить пул, ограничения которого применялись к запросу. |
| `Get query plan` | Получение готового плана из кеша либо ожидание его компиляции. |
| `Compile query` | Создание плана выполнения запроса. |
| `Load metadata`, `Load statistics` | Получение сведений о структуре таблицы и статистики её данных для построения плана. Таблица указана в `db.collection.name`. |
| `Acquire snapshot` | Получение [снимка данных](../../../concepts/query_execution/mvcc.md), который будет использоваться при чтении. |
| `Execute plan` | Выполнение плана или его части. В одном запросе может быть несколько таких спанов. |
| `Resolve tables` | Получение сведений о таблицах перед выполнением. Вложенные `Metadata` и `Partitioning` показывают получение описания таблиц и информации об их разбиении на шарды. |
| `Locate shards` | Определение расположения шардов, к которым нужно обратиться. |
| `Run tasks` | Выполнение задач на узлах базы данных. |
| `Stage: …`, `Task: …` | [Стадию плана и отдельную задачу](#stages-and-tasks) этой стадии. |

На уровне `Basic` спаны задач уже доступны, но спаны `Run tasks` и `Stage: …`, которые их объединяют, ещё не создаются.

#### Компиляция и кеш {#compilation}

Если план найден в кеше, повторная компиляция не нужна и `Compile query` отсутствует. На использование кеша указывает `ydb.compile.cache_hit=true`.

Если такой же запрос уже компилируется, новый запрос может дождаться готового плана. В этом случае на `Get query plan` появляется `ydb.trace.coverage=joined_in_progress`. Спан `Compile query` принадлежит запросу, который выполняет компиляцию. При наличии его трассы добавляется связь с его спаном `Get query plan`, позволяющая найти причину ожидания.

### Атрибуты запроса {#query-attributes}

Атрибуты `Query session` помогают найти нужный запрос и оценить его выполнение без просмотра всех вложенных спанов. Некоторые поля появляются только после завершения соответствующего этапа.

| Атрибут | Значение |
| --- | --- |
| `db.namespace` | Путь базы данных. |
| `db.operation.name` | Вид операции, например `SELECT`, `UPSERT`, `DDL` или `EXECUTE SCRIPT`. |
| `db.query.summary` | Краткое описание операции, например `SELECT /Root/Orders`. Путь таблицы добавляется, если её можно однозначно определить. |
| `db.query.text` | Текст запроса. Поле отсутствует, если текст недоступен или превышает 64 КиБ. Для запросов с чувствительными данными вместо текста может выводиться сообщение о его сокрытии. |
| `ydb.session_id`, `ydb.tx.id` | Идентификаторы сессии и транзакции для сопоставления связанных запросов. |
| `ydb.status_code` | Результат запроса: например, `SUCCESS` означает успех, `ABORTED` означает прерывание, `CANCELLED` означает отмену. |
| `ydb.cpu_us` | Суммарное процессорное время выполнения плана, в микросекундах. |
| `ydb.compile.cpu_us`, `ydb.compile.duration_us` | Процессорное время и длительность компиляции, в микросекундах. |
| `ydb.compile.cache_hit` | Использован ли готовый план из кеша. |
| `ydb.rows_read`, `ydb.bytes_read` | Число прочитанных строк и байт. |
| `ydb.rows_written` | Суммарное число записанных и удалённых строк. |

Начиная с уровня `Basic` доступны также показатели ожидания, записи промежуточных данных на диск и различий в длительности задач. Они описаны ниже.

{% note info %}

Длительность спана показывает, сколько времени прошло между началом и завершением операции. Процессорное время и время ожидания суммируются по задачам, которые могут работать параллельно, поэтому эти суммы могут превышать длительность запроса. Показатели родительских и вложенных спанов могут учитывать одну и ту же работу: складывать их для получения общего времени нельзя.

{% endnote %}

### Стадии и задачи {#stages-and-tasks}

Чтобы найти длительную часть выполнения, на уровне `Detailed` раскройте `Execute plan` и найдите спаны `Stage: …`. Каждый из них объединяет работу над частью [плана запроса](../../../concepts/query_execution/optimizer.md), например чтением данных или вычислением агрегатов. Такая часть называется стадией.

Вложенные спаны `Task: …` показывают отдельные задачи, между которыми распределена работа стадии. Например, несколько `Task: Read` внутри `Stage: Read` могут читать разные части данных параллельно. Сравнение длительностей этих задач помогает понять, вся ли стадия выполняется долго или задержку создаёт отдельная задача.

Имена стадий и задач показывают выполняемые операции: чтение (`Read`), поиск по ключам (`Lookup`), соединение (`Join`), фильтрацию (`Filter`), агрегацию (`Aggregate`), сортировку (`Sort`) и запись (`Write`). В одном спане могут сочетаться несколько операций. Если имя сокращено, например до `Task: Read + Filter + ...`, полный список можно посмотреть в `ydb.stage.operations` или `ydb.task.operations`. Имя `Compute` используется для вычислений без уточнения операции.

Идентификаторы `ydb.stage_id` и `ydb.task_id` помогают найти спаны стадий и задач, указанных в сводке выполнения.

При разборе трассы:

1. Найдите стадию, которая занимает значительную часть времени `Execute plan`. Стадии могут выполняться одновременно и передавать данные друг другу, поэтому их длительности нельзя складывать для получения времени выполнения запроса.
2. Сравните задачи внутри выбранной стадии. Если одна задача заметно дольше остальных, найдите её по `ydb.task_id` и проверьте вложенные операции чтения или записи. Если длительности близки, изучите общие показатели стадии.
3. Сопоставьте процессорное время `ydb.cpu_us` со временем ожидания `ydb.wait_us`. Большое ожидание получения или передачи данных означает, что для дальнейшего разбора нужно проверить связанные операции, от которых зависит задача. Перед выводами проверьте [полноту статистики](#statistics-availability).

#### Длительность и распределение работы {#task-timing}

Длительность `Stage: …` измеряется от запуска задач до получения подтверждения об их завершении. Если запрос прерван, статистика стадии может быть неполной.

| Атрибут стадии | Как его читать |
| --- | --- |
| `ydb.tasks`, `ydb.reported_tasks` | Общее число задач и число задач, от которых получены сведения о завершении. |
| `ydb.cpu_us`, `ydb.wait_us` | Суммарное процессорное время и время ожидания получения и передачи данных, в микросекундах. |
| `ydb.input_rows`, `ydb.output_rows` | Суммарное число строк на входе и выходе задач. |
| `ydb.task_duration_min_us`, `ydb.task_duration_avg_us`, `ydb.task_duration_max_us` | Минимальная, средняя и максимальная измеренная длительность задачи, в микросекундах. |
| `ydb.timed_tasks` | Число задач, для которых доступна длительность. |
| `ydb.task_skew` | Во сколько раз самая долгая из измеренных задач дольше средней. |
| `ydb.fastest_task_node`, `ydb.slowest_task_node` | Узлы с самой быстрой и самой долгой из измеренных задач. |
| `ydb.failed_tasks` | Число задач, завершившихся с ошибкой. |

Например, `ydb.task_skew=3` означает, что самая долгая из измеренных задач выполнялась втрое дольше средней. Атрибут `ydb.max_task_skew` на спане выполнения или запроса содержит максимальное такое отношение среди учтённых стадий. Если измерений нет или их суммарная длительность равна нулю, значение равно 0; это не подтверждает равномерность выполнения.

В `ydb.ranked_tasks` можно посмотреть подробности не более чем о пяти задачах, выбранных для диагностики: с ошибками, повторами чтения, записью промежуточных данных на диск, большим временем ожидания или выполнения. Это выборка; полный набор спанов задач может быть больше.

На спане отдельной задачи `ydb.queue_delay_us`, если он доступен, показывает время ожидания её запуска в микросекундах.

#### Полнота статистики и сброс на диск {#statistics-availability}

Перед сравнением показателей проверьте, какие данные были собраны. Прерванный запрос или ограничение объёма диагностических данных могут привести к неполной статистике.

| Атрибут | Значение |
| --- | --- |
| `ydb.task_stats_incomplete` | При `true` сведения по задачам неполны. |
| `ydb.task_duration_incomplete` | При `true` длительность известна не для всех учтённых задач. Доступен на спанах стадии и выполнения. |
| `ydb.spilled_bytes_available` | Доступна ли статистика [сброса промежуточных данных на диск](../../../concepts/query_execution/spilling.md). |
| `ydb.spilled_bytes` | Объём промежуточных данных, записанных на диск при выполнении, в байтах. |

Само включение трассировки не включает полную статистику выполнения. Показатель `ydb.spilled_bytes` следует интерпретировать только при `ydb.spilled_bytes_available=true`; для его сбора нужен режим статистики запроса `FULL` или `PROFILE`. При `false` нулевой объём не доказывает, что сброса на диск не было.

### Чтение и запись данных {#data-access}

Спаны чтения и записи помогают определить, на какую таблицу и операцию приходится задержка. Они измеряют время работы с данными со стороны обработчика запросов.

| Спан | Операция |
| --- | --- |
| `Read table` | Чтение строк таблицы. |
| `Lookup rows` | Поиск строк по ключам. |
| `Full-text search` | Получение данных для полнотекстового поиска. |
| `Scan table` | Сканирование таблицы; доступно с уровня `Detailed`. |
| `Check rows` | Чтение существующих строк при подготовке записи. |
| `Lock rows` | Операции с блокировками строк. |
| `Buffer rows` | Передача строк для последующей записи. |
| `Write rows` | Запись строк. |

На спанах чтения могут присутствовать `db.collection.name` с именем таблицы, `ydb.rows` с числом полученных строк и `ydb.read_retries` с числом повторов чтения. Последний показатель относится к повторам отдельных чтений, а не к повторным попыткам всего запроса со стороны приложения.

#### Обращения к шардам {#shards}

На уровне `Diagnostic` доступны `Read shard` и `Scan shard`. Они позволяют сравнить длительности обращений к отдельным шардам по атрибуту `ydb.shard_id`. Атрибут `ydb.node_id` указывает узел, `ydb.rows` содержит число полученных строк, а `ydb.finished=true` означает, что чтение завершилось успешно. При ошибке или остановке чтения значение равно `false`.

Длительность этих спанов измеряется на стороне обработчика запросов: от отправки запроса на шард до последнего сообщения либо остановки чтения. В этот интервал входят доставка сообщений и ожидание ответа.

События `Shard read statistics` на спане чтения содержат сводки не более чем по пяти выбранным шардам. Они помогают найти обращения с ошибками, повторами или большой длительностью.

Атрибут `ydb.shard_stats_incomplete=true` означает, что часть обращений или накопленных сведений не удалось сохранить из-за ограничений объёма диагностических данных. Значение `false` не означает, что события содержат полный список шардов: ограничение в пять сводок действует в любом случае. Количество сводок, не вошедших в события, указано в `ydb.shard_summaries_dropped`.

#### Фиксация транзакции {#commit}

Если задержка возникает при завершении записи, проверьте спаны `Flush effects`, `Commit` и `Rollback`: они показывают отправку накопленных изменений, фиксацию и откат транзакции.

На уровне `Detailed` могут быть видны отдельные этапы фиксации: `Prepare shards`, `Coordinator` и `Apply commit`. Они показывают, сколько времени обработчик запросов потратил на подготовку изменений, согласование их фиксации и ожидание завершения. Набор этапов зависит от способа выполнения транзакции.

На уровне `Diagnostic` события `Shard acknowledged` показывают получение подтверждений от шардов. Список событий может быть сокращён; число пропущенных событий указано в `ydb.shard_events_dropped`.

### Ошибки и неполные трассы {#errors}

Начните разбор ошибки с `ydb.status_code` спана запроса, затем найдите вложенный спан этапа, на котором возникла ошибка. Успешно завершённый этап может иметь статус `OK`, даже если запрос завершился ошибкой позже.

Для описанных спанов `SUCCESS` соответствует статусу `OK`, а ошибка соответствует `ERROR`. Если окончательный результат операции неизвестен, спан может завершиться без отметки успеха или ошибки. Например, остановленное чтение может иметь `ydb.finished=false` и `ydb.status_code=STATUS_CODE_UNSPECIFIED`.

При раннем отклонении запроса на `Query Proxy` появляется `ydb.rejected=true`. В этом случае спаны выполнения могут отсутствовать, поскольку запрос не был запущен.

Отсутствие ожидаемого спана не всегда означает сбой трассировки: операция могла не выполняться, быть скрыта выбранным уровнем детализации или не попасть в коллектор из-за [ограничений экспорта](setup.md#uploader). Проверьте также [полноту статистики](#statistics-availability).

### Пример разбора чтения {#read-example}

Рассмотрим, как отличить время подготовки плана от времени чтения данных. В примере используется таблица `otel_orders` с идентификатором заказа `order_id` типа `Uint64` и суммой заказа `amount`. Следующий [запрос `SELECT`](../../../yql/reference/syntax/select/index.md) выбирает заказы с идентификатором не меньше 101 и сортирует результат по идентификатору:

```yql
SELECT order_id, amount
FROM otel_orders
WHERE order_id >= 101u
ORDER BY order_id;
```

Для просмотра стадий и задач нужна трасса с детализацией не ниже `Detailed`. Ниже приведены округлённые длительности из тестового запуска. На других данных и в другом окружении значения будут отличаться.

Первый запуск завершился с `ydb.status_code=SUCCESS`. Атрибут `ydb.compile.cache_hit=false` показывает, что готовый план не был использован. Сравним основные этапы:

| Спан | Длительность |
| --- | --- |
| `Get query plan` | 17,55 мс |
| Вложенный `Compile query` | 17,52 мс |
| `Execute plan` | 0,90 мс |

Почти всё время получения плана заняла компиляция. Само выполнение оказалось значительно короче, поэтому в этом запуске длительность запроса прежде всего определялась подготовкой плана. Складывать времена `Get query plan` и вложенного `Compile query` не нужно: время компиляции уже входит в длительность получения плана.

Теперь раскроем выполнение. В `Stage: Read` видны две задачи `Task: Read` длительностью 0,33 и 0,37 мс. Стадия целиком заняла 0,43 мс: задачи выполнялись параллельно. Вложенные `Read table` заняли 0,19 и 0,22 мс, в обоих случаях `ydb.read_retries=0`. Эти спаны показывают короткие обращения к таблице без повторов чтения; признаков задержки на повторных обращениях в этом запуске нет.

При повторном запуске того же запроса `ydb.compile.cache_hit=true`, спан `Compile query` отсутствует, а `Execute plan` занимает 0,79 мс. Трасса показывает, что готовый план использован повторно, а длительность выполнения остаётся близкой к первому запуску. Такое сравнение позволяет отдельно оценить подготовку плана и работу с данными.
