# Аутентификация OIDC в CLI

Аутентификация [OIDC](../../concepts/glossary.md#oidc) в {{ ydb-short-name }} CLI позволяет получать токены доступа у [внешнего провайдера идентификации (IdP)](https://csrc.nist.gov/glossary/term/identity_provider) и использовать их для запросов к базе данных. IdP является отдельным сервисом, который проверяет пользователя или приложение и выпускает токены. В этой статье описаны режимы аутентификации, параметры, файлы конфигурации, профили и кеш токенов CLI.

## Поддерживаемые режимы {#flows}

Режим определяет, откуда CLI получает первоначальный токен. Он задаётся параметром `--oidc-flow`:

| Режим | Назначение | Спецификация |
| --- | --- | --- |
| `static`, готовый токен | CLI читает уже полученный токен и отправляет его серверу без автоматического обновления. | Использование токена предъявителем: [Bearer Token, RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-1.2). Отдельного запроса токена к IdP в этом режиме нет. |
| `client`, секрет приложения | Автоматическое задание получает токен по идентификатору и секрету зарегистрированного приложения без участия пользователя. | [Client Credentials Grant, RFC 6749, раздел 4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4). В запросе к IdP используется `grant_type=client_credentials`. |
| `device`, код устройства | Пользователь подтверждает вход в браузере по показанному коду, а CLI ожидает результат от IdP. | [Device Authorization Grant, RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html). В запросе токена используется `grant_type=urn:ietf:params:oauth:grant-type:device_code`. |

`client` и `device` являются названиями режимов CLI. Поле `grant_type` в запросе к IdP обозначает соответствующий способ получения токена в протоколе OAuth 2.0. [Способ проверки самого приложения](#client) (например, `client_secret_basic`) задаётся отдельно.

Примеры команд для каждого режима находятся в [рецептах OIDC для CLI](../../recipes/ydb-cli/auth-oidc.md).

## Участники обмена и токены {#tokens}

Участники выполняют следующие [роли OAuth 2.0](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.1):

- **CLI** является клиентом: получает токен у IdP и передаёт его с запросами к базе данных.
- **IdP** является сервером авторизации: проверяет приложение или вход пользователя и выдаёт токены.
- **Сервер {{ ydb-short-name }}** является сервером ресурсов: проверяет токен и права доступа к базе данных.
- **Пользователь** подтверждает вход у IdP в режиме `device`. В режиме `client` его участие не требуется.

Обмен CLI с IdP служит для получения и обновления токенов. Запросы CLI к базе данных идут по отдельному соединению. Получение токена не предоставляет прав на объекты базы данных и не гарантирует, что сервер примет этот токен.

[Токен доступа](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.4) `access_token` передаётся серверу {{ ydb-short-name }}. Необязательный [токен обновления](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.5) `refresh_token` используется только для получения нового токена у IdP. [Тип токена](https://www.rfc-editor.org/rfc/rfc6750.html#section-1.2) `Bearer` означает использование токена предъявителем без отдельного доказательства владения ключом.

[Токен результата аутентификации](https://openid.net/specs/openid-connect-core-1_0.html#IDToken) `id_token` содержит сведения о входе пользователя. OIDC-аутентификация CLI его не использует. Также не реализованы [обмен кода авторизации](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1) `authorization_code`, [приём перенаправления браузера локальным HTTP-сервером](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3) и [проверка](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) `id_token`.

## Предварительная настройка {#prerequisites}

Перед первым подключением настройте получение токена у IdP и его проверку сервером {{ ydb-short-name }}:

1. **Зарегистрируйте приложение в IdP.** Для режима `client` разрешите получение токена по секрету приложения (`client_credentials`) и [проверку секрета](#client) через `client_secret_basic`. Для `device` разрешите вход по коду устройства для приложения без секрета. Названия настроек зависят от IdP. Для `static` получите токен вне CLI.
2. **Проверьте доступность [Discovery-документа](#discovery)** по HTTPS, если CLI должен получать или обновлять токены. Он содержит адреса служб IdP и поддерживаемые способы проверки приложения.
3. **Проверьте формат токена доступа.** Для встроенной проверки внешнего IdP сервером {{ ydb-short-name }} нужен подписанный [JWT](https://www.rfc-editor.org/rfc/rfc7519.html#section-3), соответствующий [требованиям к токену и ключам](../../security/authentication.md#trebovaniya-k-tokenu-i-klyucham).
4. **Настройте [проверку внешнего IdP](../configuration/auth_config.md#external-idp-auth-config) и [права доступа](../../security/authorization.md)** на сервере {{ ydb-short-name }}. Согласуйте издателя и ожидаемого получателя токена с настройками IdP.

JWT содержит **утверждения (claims)**, именованные сведения о субъекте и условиях действия токена ([RFC 7519, раздел 4](https://www.rfc-editor.org/rfc/rfc7519.html#section-4)).

- **Издатель `iss`** указывает, кто выпустил токен ([раздел 4.1.1](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.1)).
- **Получатель `aud`** указывает сервис, для которого предназначен токен ([раздел 4.1.3](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.3)).
- **Срок действия `exp`** задаёт момент истечения срока действия токена ([раздел 4.1.4](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4)).

**Подпись** позволяет серверу проверить происхождение и целостность токена. Её формат описан в [JSON Web Signature, RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html#section-3).

CLI не проверяет подпись, издателя и получателя JWT. Это делает сервер.

После настройки проверьте вход [командой](commands/discovery-whoami.md) `discovery whoami` по [рецепту выбранного режима](../../recipes/ydb-cli/auth-oidc.md). Если токен получен, но сервер отклоняет запрос, отдельно проверьте [требования к токену](../../security/authentication.md#trebovaniya-k-tokenu-i-klyucham), [параметры серверной проверки](../configuration/auth_config.md#external-idp-auth-config) и [назначенные права](../../security/authorization.md).

## Обнаружение адресов IdP {#discovery}

**OIDC Discovery-документ** является JSON-описанием провайдера по стандарту [OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfig). CLI получает его по адресу, составленному из настроенного URL издателя `issuer` без завершающих `/` и пути `/.well-known/openid-configuration`. Документ позволяет найти службы IdP по одному заранее известному адресу.

| Поле | Назначение |
| --- | --- |
| `issuer` | [Идентификатор издателя](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata). Должен точно совпадать с настройкой CLI, включая завершающий `/`. |
| `token_endpoint` | [Адрес получения и обновления токенов](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.2). |
| `device_authorization_endpoint` | [Адрес выдачи кода устройства](https://www.rfc-editor.org/rfc/rfc8628.html#section-4). Нужен для начала нового входа в режиме `device`. |
| `token_endpoint_auth_methods_supported` | [Список способов проверки приложения](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata). Если поле присутствует, для режима `client` в нём должен быть `client_secret_basic`. При отсутствии поля CLI использует этот способ без дополнительной проверки списка. |

Адреса IdP и ссылки для входа должны использовать HTTPS. Имя пользователя, пароль и фрагмент URL запрещены. У `issuer` также запрещены параметры запроса. Полученные адреса сохраняются в текущем экземпляре провайдера учётных данных. Чтобы применить изменение адресов в Discovery-документе к работающему CLI, перезапустите процесс. Режим `static` и использование пригодного кеша могут обойтись без обращения к IdP.

## Выбор режима и запуск {#quickstart}

CLI поддерживает интерактивный вход, автоматическое получение токена по секрету и передачу готового токена. Команды запуска вынесены в [рецепты](../../recipes/ydb-cli/auth-oidc.md). Ниже описано поведение каждого режима.

### Вход пользователя через браузер {#device}

Для входа пользователя используйте режим `device` и [идентификатор зарегистрированного приложения](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.2) `client_id`. Пример подключения приведён в [рецепте входа по коду устройства](../../recipes/ydb-cli/auth-oidc.md#device).

CLI выведет в стандартный поток ошибок ссылку на страницу IdP и код. Откройте ссылку в браузере, при необходимости введите код и подтвердите вход. Браузер можно открыть на другом устройстве. CLI автоматически его не запускает. Если IdP вернул [готовую ссылку](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.2) `verification_uri_complete` с включённым кодом или эквивалентными данными, CLI также покажет её.

[Область доступа](#scopes) `openid` добавляется автоматически. [Область доступа](#scopes) `offline_access` нужно запросить явно, если её поддерживает IdP. Её наличие само по себе не гарантирует выдачу токена обновления.

Команда продолжит работу после подтверждения. Отказ или истечение срока действия кода завершает попытку ошибкой. Для повторного входа запустите команду заново. Чтобы сохранить вход между запусками, настройте [файловый кеш](#cache).

При запуске CLI без подкоманды интерактивная SQL-оболочка сначала ожидает завершения первоначального входа OIDC. Нажатие `Ctrl+C` прерывает это ожидание.

{% note info %}

В режиме `device` требуется участие пользователя и при перенаправленном вводе или выводе. Параметры `--assume-yes` и `auth get-token --force` не подтверждают вход у IdP. Для автоматических заданий используйте режим `client` или готовый токен `static`.

{% endnote %}

### Подключение приложения по секрету {#client}

Для автоматического задания выберите `client` и укажите путь к файлу с [секретом приложения](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.3.1) `client_secret`, известным только приложению и IdP. Пример находится в [рецепте подключения автоматического задания](../../recipes/ydb-cli/auth-oidc.md#client).

CLI получает токен [способом получения токена по секрету приложения](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4) `client_credentials`. Приложение в IdP должно разрешать `client_secret_basic`: [проверку идентификатора и секрета приложения через HTTP Basic](https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication). Они передаются в заголовке `Authorization` по [правилам RFC 6749, раздел 2.3.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.3.1). Способ `client_secret_post`, при котором секрет передаётся в теле запроса, не поддерживается. IdP также должен разрешать [область доступа](#scopes) `openid`. Наличие файла секрета не выбирает режим `client` автоматически, поэтому указывайте `--oidc-flow client` явно.

### Подключение с готовым токеном {#static}

Если токен доступа получен другим инструментом, используйте режим `static`. Подготовка файла и команда подключения показаны в [рецепте готового токена](../../recipes/ydb-cli/auth-oidc.md#static).

Файл может содержать токен без префикса или строку с точным префиксом `Bearer` и одним пробелом перед токеном. CLI убирает префикс и разделяющий пробел перед передачей в провайдер учётных данных, который добавляет их при формировании данных для запроса. Начальные и конечные пробельные символы содержимого файла удаляются.

В этом режиме клиент не обращается к IdP и не обновляет токен. При каждом запуске CLI файл читается заново. Для замены токена в уже работающем процессе потребуется его перезапуск. `issuer` остаётся обязательным параметром конфигурации.

## Параметры и переменные окружения {#options}

Глобальные параметры OIDC указываются перед подкомандой, как и другие [параметры соединения](connect.md#command-line-pars).

| Параметр | Переменная окружения | Назначение |
| --- | --- | --- |
| `--oidc-config PATH` | Нет | Путь к отдельному [файлу YAML или JSON](#config-file). |
| `--oidc-issuer URL` | `YDB_OIDC_ISSUER` | HTTPS-адрес [издателя токенов](#discovery). Обязателен при настройке прямыми параметрами. |
| `--oidc-flow VALUE` | `YDB_OIDC_FLOW` | [Способ получения токена](#flows): `static`, `client` или `device`. |
| `--oidc-client-id VALUE` | `YDB_OIDC_CLIENT_ID` | [Идентификатор приложения](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.2) `client_id` для `client` и `device`. Это не имя пользователя. |
| `--oidc-client-secret-file PATH` | `YDB_OIDC_CLIENT_SECRET` | Файл [секрета приложения](#client) для `client`, переменная содержит **сам секрет**, а не путь. |
| `--oidc-access-token-file PATH` | `YDB_OIDC_ACCESS_TOKEN` | Файл [токена доступа](#tokens) для `static`, переменная содержит **сам токен**, а не путь. |
| `--oidc-scope VALUE` | `YDB_OIDC_SCOPE` | [Области доступа](#scopes) для `client` и `device`, разделённые пробелами. Параметр можно повторять. |
| `--oidc-cache-path PATH` | `YDB_OIDC_CACHE_PATH` | Путь к [файлу кеша токенов](#cache). По умолчанию файловый кеш выключен. |

Если режим не указан, наличие `--oidc-access-token-file` или непустой `YDB_OIDC_ACCESS_TOKEN` выбирает `static`. В остальных случаях выбирается `device`. При сочетании профилей и переменных окружения полезно задавать режим явно.

В режиме `static` нельзя задавать идентификатор приложения, файл секрета и области доступа. В режиме `device` не допускаются файлы секрета и токена доступа. В режиме `client` не допускается файл готового токена. Эти поля относятся к другим способам получения учётных данных.

Несколько областей доступа можно указать одной строкой через пробелы или повторяющимися параметрами `--oidc-scope`. Повторяющиеся пробельные разделители игнорируются. Пустое значение параметра и области с недопустимыми символами отклоняются. Примеры обоих вариантов приведены в [рецепте настройки областей доступа](../../recipes/ydb-cli/auth-oidc.md#scopes).

Параметров для передачи секрета или токена непосредственно в командной строке нет: используйте файл или соответствующую переменную окружения. Переменная `YDB_OIDC_CONFIG` не поддерживается, путь к конфигурации задаётся параметром или профилем.

### Области доступа {#scopes}

`scope` задаёт именованные [области доступа](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3), их допустимые значения и влияние на токен определяет IdP. В OpenID Connect используются, в частности:

- `openid` [обозначает запрос OpenID Connect](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest). CLI добавляет эту область, если её нет, в режимах `client` и `device`.
- `offline_access` [запрашивает доступ без присутствия пользователя с помощью токена обновления](https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess). CLI не добавляет эту область автоматически. Возможность её использования в выбранном режиме зависит от IdP.
- `profile` [запрашивает сведения профиля пользователя](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims). Набор утверждений именно в токене доступа определяется IdP.

Области доступа не заменяют [права на объекты {{ ydb-short-name }}](../../security/authorization.md).

### Приоритет источников {#precedence}

Выбор метода аутентификации следует [общему порядку CLI](connect.md): явные параметры, профиль из `--profile`, окружение, активированный профиль. Явное указание другого метода может перекрыть OIDC из профиля. Файл невыбранной OIDC-конфигурации при этом не читается.

При выборе метода только по окружению OIDC применяется после других поддерживаемых методов. Например, при наличии `YDB_TOKEN` и `YDB_OIDC_ISSUER` будет выбран `YDB_TOKEN`. Явный `--oidc-issuer` выбирает OIDC с более высоким приоритетом, чем окружение.

Дополнительные параметры берутся из доступных источников с тем же приоритетом, но CLI не переносит учётные данные профиля на другого издателя: при переопределении `issuer` связанные поля другого источника профиля отбрасываются. При переопределении `client_id` файл секрета из другого источника также не подставляется. Укажите полный набор параметров нового приложения. Недостающий секрет можно передать через окружение.

Не совмещайте явно выбранный OIDC с другим методом аутентификации. `--oidc-config` также нельзя совмещать с явно заданными параметрами `--oidc-*`. При использовании отдельного файла значения `YDB_OIDC_ISSUER`, `YDB_OIDC_FLOW`, `YDB_OIDC_CLIENT_ID`, `YDB_OIDC_SCOPE` и `YDB_OIDC_CACHE_PATH` не переопределяют его содержимое. Из окружения могут быть взяты только отсутствующие в конфигурации секрет или токен соответствующего режима.

Для прямых настроек сначала действует приоритет источников: явно заданный файл и файл из явно выбранного профиля имеют приоритет над переменной с секретом, а окружение имеет приоритет над файлом из активированного профиля. В отдельной OIDC-конфигурации указанный файл всегда имеет приоритет над окружением. Если выбранный файл не читается или пуст, настройка завершается ошибкой. CLI не подставляет значение из окружения вместо неисправного файла.

## Отдельный файл конфигурации {#config-file}

Файл для `--oidc-config` объединяет настройки одного режима OIDC. YAML и JSON имеют одинаковую структуру: корневой набор именованных полей, обязательный `issuer`, необязательный `cache_path` и ровно один блок получения учётных данных. Названия блоков являются ключами конфигурации CLI и соответствуют [режимам получения токена](#flows).

| Поле или блок | Содержимое |
| --- | --- |
| `issuer` | Непустая строка с HTTPS-адрес [издателя](#discovery). |
| `cache_path` | Необязательная непустая строка с путём к [кешу токенов](#cache). Для `static_credentials` не используется. |
| `static_credentials` | [Готовый токен](#static): путь `access_token_file` либо значение из `YDB_OIDC_ACCESS_TOKEN`, необязательный [срок действия](#static-config) `expires_at`. |
| `client_credentials_grant` | [Секрет приложения](#client): обязательный `client_id`, путь `client_secret_file` либо секрет из `YDB_OIDC_CLIENT_SECRET`, необязательный список [областей доступа](#scopes) `scope`. |
| `device_authorization_grant` | [Код устройства](#device): обязательный `client_id`, необязательный список [областей доступа](#scopes) `scope`. |

Относительные пути `access_token_file`, `client_secret_file` и `cache_path` внутри этого файла разрешаются относительно его каталога. Путь, заданный параметром `--oidc-config`, разрешается относительно рабочего каталога запуска. Используйте абсолютные пути или обычные относительные пути, не рассчитывайте на раскрытие `~` внутри YAML.

### Файл для кода устройства {#device-config}

Блок `device_authorization_grant` задаёт идентификатор приложения и области доступа для входа пользователя. Поле `cache_path` позволяет сохранить токены для следующего запуска. YAML-файл и команда проверки приведены в [рецепте кода устройства](../../recipes/ydb-cli/auth-oidc.md#device-config).

### Файл для секрета приложения {#client-config}

Блок `client_credentials_grant` задаёт идентификатор приложения и источник его секрета. Секрет читается из `client_secret_file` либо, при отсутствии этого поля, из `YDB_OIDC_CLIENT_SECRET`. Пример конфигурации приведён в [рецепте секрета приложения](../../recipes/ydb-cli/auth-oidc.md#client-config).

### Файл для готового токена {#static-config}

В блоке `static_credentials` поле `expires_at` задаёт абсолютный момент истечения срока действия токена в целых секундах Unix, отсчитываемых от 1 января 1970 года UTC. Оно имеет приоритет над [утверждением](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4) `exp` в JWT. Если поле отсутствует, CLI пытается извлечь срок из JWT. Нулевой срок означает уже истёкший токен, строка в кавычках вместо числа не принимается.

Токен читается из `access_token_file` либо из `YDB_OIDC_ACCESS_TOKEN`. При использовании окружения и отсутствии явного срока блок может не содержать полей. Если ни файл, ни переменная не заданы, конфигурация отклоняется. Пример YAML находится в [рецепте готового токена](../../recipes/ydb-cli/auth-oidc.md#static-config).

### Проверка формата {#config-validation}

Загрузчик отклоняет неизвестные и повторяющиеся ключи, несколько блоков получения токена, пустые обязательные строки и неверные типы. В частности:

- `scope` должен быть списком строк, по одной [области доступа](#scopes) в каждом элементе;
- `client_id` из одних цифр нужно заключить в кавычки, чтобы YAML не превратил его в число;
- `expires_at` должен быть неотрицательным целым числом секунд Unix в поддерживаемом диапазоне;
- `access_token` и `client_secret` в самом документе запрещены. Используются файлы или окружение;
- [токен обновления](#tokens) `refresh_token`, [адрес выдачи токенов](#discovery) `token_endpoint`, получатель токена `audience`, настройки тайм-аутов и отключение HTTPS в этом формате не предусмотрены.

Токен обновления клиент получает от IdP и сохраняет через кеш. Адрес получения токенов определяется через [Discovery-документ](#discovery). Получатель и утверждения токена настраиваются в IdP и согласуются с [проверкой на сервере](../configuration/auth_config.md#external-idp-auth-config).

## Профили CLI {#profiles}

Профиль сохраняет параметры соединения и способ получения токенов. Для настройки OIDC используйте [команды управления профилями](profile/create.md) `config profile create` или `config profile update`.

Команды создания и проверки профилей, а также примеры их YAML-представления приведены в [рецепте настройки профилей OIDC](../../recipes/ydb-cli/auth-oidc.md#profiles).

Создание профиля проверяет локальную конфигурацию и необходимые секретные файлы, но не получает токен у IdP. При использовании отдельного OIDC-файла в профиль записывается путь к нему, а не его содержимое. Первый вход происходит при выполнении команды, которой нужны учётные данные. Новый профиль не активируется автоматически: используйте `--profile` или отдельно выполните `config profile activate` с именем профиля.

В блоке `authentication` профиля `method` задаёт способ аутентификации, а `data` содержит его настройки. Для `method: oidc` поле `data` хранит прямые параметры. Для `method: oidc-config` оно содержит путь к отдельному файлу OIDC.

Формат `method: oidc` отличается от формата отдельного файла: используются поле `flow` со значением `static`, `client` или `device` и строковый `scope`, а не блоки `*_grant` и список областей. Для `static` и `client` в `data` можно сохранять соответственно `access_token_file` и `client_secret_file`. Сами секреты в профиль не записываются.

Относительные пути в прямом профиле и путь `data` метода `oidc-config` отсчитываются от рабочего каталога запуска, а не от файла профилей. Для профилей предпочтительны абсолютные пути.

При `config profile create/update` задавайте `issuer`, режим, `client_id`, области доступа и путь к кешу явными параметрами. Эти команды не копируют обычные OIDC-настройки из окружения автоматически. Исключение касается чтения самого секрета или токена и выбора `static` при наличии `YDB_OIDC_ACCESS_TOKEN`. Значение секрета всё равно не сохраняется, поэтому оно потребуется и при последующих запусках.

Обновление аутентификации заменяет весь блок `authentication`. Передавайте полный набор OIDC-настроек, один `--oidc-client-id` не дополняет прежний блок. Параметр `--no-auth` нельзя объединять с новыми OIDC-настройками.

## Постоянный кеш токенов {#cache}

Без `--oidc-cache-path`, `cache_path` в файле или соответствующей переменной окружения CLI хранит токены только в памяти текущего процесса. Для `client` и `device` файловый кеш позволяет использовать их при следующем запуске. В режиме `static` кеш не используется даже при указанном пути.

Перед включением кеша создайте его родительский каталог с доступом только владельцу: CLI не создаёт его автоматически. Подготовка каталога и пример отдельного пути для приложения и пользовательской сессии показаны в [рецепте](../../recipes/ydb-cli/auth-oidc.md#preparation).

Кеш представляет собой незашифрованный JSON с токенами доступа и обновления и известными сроками их действия. Он содержит секреты. Исключите его из системы контроля версий и общедоступных резервных копий.

При работе с кешем CLI проверяет:

- файл является обычным файлом, а не каталогом, именованным каналом (FIFO) или символической ссылкой;
- владельцем является текущая учётная запись;
- доступ разрешён только владельцу: в системах семейства Unix нет прав группы и остальных, на Windows проверяется список управления доступом (DACL), на macOS также учитываются расширенные списки управления доступом (ACL).

Для существующего кеша в системах семейства Unix обычно подходят права `600`, разрешающие чтение и запись только владельцу. Новые файлы создаются с доступом только владельцу. Запись выполняется через временный файл в том же каталоге с последующей атомарной заменой.

Кеш привязан к отпечатку настроек. Этот идентификатор вычисляется по издателю, режиму, идентификатору приложения, секрету и запрошенным областям доступа. Кеш с другим отпечатком не используется и не перезаписывается. При смене приложения, секрета или областей выберите другой путь либо осознанно удалите старый кеш. Для разных пользователей одного приложения также используйте разные файлы: отпечаток конфигурации не является идентификатором вошедшего пользователя.

Межпроцессной блокировки нет. Атомарная запись предотвращает чтение частично записанного JSON, но не объединяет параллельные входы и обновления токенов разных процессов. Если IdP заменяет токен обновления при каждом использовании, избегайте одновременной работы нескольких процессов с одной сессией.

Если кеш отсутствует, повреждён или несовместим, CLI считает, что сохранённых токенов нет. При проблемах доступа CLI выводит предупреждение в стандартный поток ошибок. Ошибка чтения приводит к получению токенов заново. Ошибка записи не мешает использовать полученный токен в текущем процессе, но следующий запуск может снова потребовать входа.

Удаление локального кеша не отзывает токены на стороне IdP и не очищает токен уже работающего процесса. Для завершения внешней сессии используйте средства IdP и остановите использующие её процессы.

## Получение токена для другого инструмента {#get-token}

[Команда](auth-get-token.md) `auth get-token` получает текущие данные аутентификации выбранным способом. Для OIDC результатом будет одна строка с префиксом `Bearer`, пробелом и токеном доступа. [Токен обновления](#tokens) и `id_token` не выводятся.

Команды сохранения токена в файл с ограниченным доступом приведены в [рецепте передачи токена другому инструменту](../../recipes/ydb-cli/auth-oidc.md#get-token).

`--force` отключает только подтверждение вывода секрета. При новом входе `device` ссылка и код по-прежнему выводятся в стандартный поток ошибок, поэтому не попадут в файл при перенаправлении только стандартного вывода. Параметр `--timeout` этой команды не задаёт предельное время ожидания входа по коду устройства.

Сохранённый файл можно использовать с `--oidc-access-token-file`. При передаче другому инструменту проверьте, ожидает ли он всю строку `Bearer ...` или только значение токена.

## Диагностика {#troubleshooting}

| Симптом | Что проверить |
| --- | --- |
| Неизвестный параметр `--oidc-issuer` или `--oidc-config` | Вывод `ydb --help` и установленную сборку CLI: она должна содержать поддержку этих параметров. |
| Ошибка отсутствующего `client_id` | Для `device` и `client` нужен идентификатор приложения. Наличие секрета не выбирает `client` автоматически. |
| Ошибка формата `scope` | В отдельном файле нужен список, в прямом профиле строка, в параметрах список через пробелы. |
| `discovery issuer mismatch` | Сравните `issuer` конфигурации с полем [Discovery-документа](#discovery) побайтно, включая завершающий `/`. |
| `client_secret_basic is not supported` | Разрешите [проверку секрета приложения через HTTP Basic](#client) в IdP. |
| `invalid_client`, `unauthorized_client` или `invalid_scope` | [Ошибки получения токена](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2) означают соответственно: приложение не прошло проверку, ему не разрешён способ получения токена либо недопустимы запрошенные области доступа. Проверьте идентификатор, секрет, режим и [области доступа](#scopes), включая `openid`. |
| `device authorization expired` или `access_denied` | Срок действия кода истёк либо [вход отклонён пользователем или IdP](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.5). Повторите команду и завершите вход до истечения срока действия нового кода. |
| При каждом запуске требуется вход через браузер | Проверьте путь, права и предупреждения кеша, наличие и срок действия токена обновления, а также настройки его выдачи в IdP. |
| `identity differs; use a separate cache path` | Настройки отличаются от записанных в кеше. Выберите отдельный файл. |
| Токен получен, но {{ ydb-short-name }} отклоняет запрос | Проверьте [требования к токену и ключам](../../security/authentication.md#trebovaniya-k-tokenu-i-klyucham), [настройки серверной проверки](../configuration/auth_config.md#external-idp-auth-config) и [права пользователя](../../security/authorization.md). |

Обновление токенов, повторы при сетевых ошибках и токены с неизвестным сроком описаны в [разделе о сроке действия](#refresh).

## Срок действия и обновление {#refresh}

В режимах `client` и `device` CLI обновляет токен в процессе работы. Если IdP вернул `expires_in`, [срок действия токена](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.1) отсчитывается в секундах от начала запроса токена. Иначе клиент пытается прочитать `exp` из JWT. При известном сроке обновление планируется примерно через половину оставшегося времени.

Для [обновления по RFC 6749, раздел 6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6) CLI сначала использует пригодный `refresh_token`. Если его нет, он истёк или IdP отклонил его постоянной ошибкой `invalid_grant`, повторяется первоначальный способ получения токена. Для `device` это может потребовать нового подтверждения пользователя. Другие постоянные ошибки, например `invalid_client`, не запускают повторный вход. Значения этих ошибок определены в [RFC 6749, раздел 5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2).

При неизвестном сроке полученного токена фоновое обновление не планируется, даже при наличии токена обновления. Однако при новом запуске CLI сначала обновляет кешированный токен с неизвестным сроком, если вместе с ним сохранён токен обновления. Без него используется сохранённый токен доступа. Режим `static` не обновляет токен и не использует кеш.

Ошибки транспорта и HTTP-статусы `408`, `429`, `500`, `502`, `503`, `504` допускают повторные попытки. Вне входа по коду устройства пауза начинается с 200 мс и удваивается до 30 секунд. При опросе кода начальный интервал задаёт IdP (по умолчанию он равен 5 секундам). Применяются [правила Device Authorization Grant](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.5): ожидание подтверждения `authorization_pending` сохраняет интервал, а `slow_down` увеличивает его на 5 секунд. При временной сетевой ошибке или повторяемом HTTP-статусе CLI удваивает интервал. Локальное истечение срока действия кода завершает попытку. Повторяемый HTTP-статус считается временной ошибкой даже при коде `access_denied` или `expired_token` в теле ответа.

Параметры HTTP-клиента OIDC не задают единый срок всей операции. Учитывайте также ограничения [команды получения токена](#get-token).
