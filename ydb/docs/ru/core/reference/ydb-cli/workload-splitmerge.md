# Нагрузка split/merge

Инструмент для создания управляемого потока [делений (сплитов)](../../concepts/glossary.md#split) и [слияний](../../concepts/glossary.md#merge) [партиций](../../concepts/datamodel/table.md#partitioning)/шардов строчных таблиц (механика split-merge применима только к строчным таблицам). Предназначен для проверки механики [автопартиционирования](../../concepts/glossary.md#auto-partitioning): очереди split/merge, лимита одновременно выполняемых операций split-merge и fair scheduler под постоянной нагрузкой.

В отличие от других нагрузок, его цель — не измерение пропускной способности, а создание контролируемой, воспроизводимой split-merge нагрузки на таблицы: по превышению порога размера данных, по превышению порога CPU (split-by-load), полный merge-каскад одним `ALTER TABLE` или колебания между этими состояниями.

Ключевая идея тестирования слияний: **удаление данных не требуется**. Таблица, уже разбитая на множество мелких партиций, после одного `ALTER TABLE`, повышающего `AUTO_PARTITIONING_PARTITION_SIZE_MB`, порождает [каскад слияний](../../concepts/glossary.md#merge-cascade) — повышенный порог сразу делает соседние партиции пригодными для слияния.

Значения по умолчанию намеренно минимальные (`AUTO_PARTITIONING_PARTITION_SIZE_MB = 1`, полезная нагрузка ~1 КБ): пороги преодолеваются уже несколькими тысячами строк, так что давление достижимо без гигабайтов данных. Значения по умолчанию не соответствуют типичному production-окружению; настройки нужно подбирать под тестируемый сценарий.

## Виды нагрузки {#workload-types}

Нагрузочный тест запускает несколько видов нагрузки. Каждый примитив назван по сигналу, который запускает серверную операцию: **by-size** (по размеру) — накопленный размер данных пересекает `AUTO_PARTITIONING_PARTITION_SIZE_MB`; **by-load** (по нагрузке) — устойчивая нагрузка на CPU шарда (включается настройкой `AUTO_PARTITIONING_BY_LOAD`). Нагрузка генерирует трафик; сервер сам решает, когда выполнять сплит или слияние:

* [split-by-size](#split-by-size): рост партиций сверх порога `AUTO_PARTITIONING_PARTITION_SIZE_MB` за счет последовательной записи новых строк.
* [split-by-load](#split-by-load): точечный UPSERT-трафик по узкому срезу ключей: CPU растет, а размер данных остается неизменным, что запускает [сплит по нагрузке](../../concepts/glossary.md#split-by-load) — сплиты, вызываемые устойчивой CPU-нагрузкой на шард и включаемые настройкой `AUTO_PARTITIONING_BY_LOAD`.
* [merge-by-size](#merge-by-size): повышает порог размера партиций одним `ALTER TABLE` (выполняется один раз за запуск), затем дожидается конца merge-каскада.
* [merge-by-load](#merge-by-load): запускается после остановки горячего трафика; после split-by-load нагрузка на горячий шард спадает, и слияния запускаются по снижению нагрузки; режим опрашивает и печатает убывание числа партиций.
* [split-burst](#split-burst): все шарды одновременно превышают порог размера (split-by-size на всех шардах разом); требуется `--key-distribution striped` (без него режим вырождается в последовательный split-by-size), чтобы каждый запрос попадал в другой регион пространства ключей.
* [merge-burst](#merge-burst): полный merge-by-size-каскад с максимально возможной скоростью, которую допускают серверные лимиты (один ALTER повышает порог размера, затем каскад завершается на предельной скорости).
* [multi-table-split](#multi-table-split): множество таблиц параллельно разбивается сплитами, конкурируя за общие ресурсы механизма split-merge.
* [small-table-starvation](#small-table-starvation): маленькая требовательная таблица (split-by-load-трафик на маленькой таблице) конкурирует с большой неактивной таблицей за общие ресурсы механизма split-merge.
* [split-vs-merge-race](#split-vs-merge-race): волна merge-by-size конкурирует с параллельным спросом split-by-size (запускается вместе с `merge-by-size` во втором процессе).
* [flap](#flap): чередование фаз grow/merge-by-size/split-by-size на одной таблице (порог размера повышается и понижается через ALTER).
* [status](#status): опрашивает первую таблицу (`<path>0`) раз в секунду и выводит динамику числа партиций, ширины ключевых интервалов и распределения строк.

## Инициализация нагрузочного теста {#init}

Для начала работы необходимо создать тестовые таблицы:

```bash
{{ ydb-cli }} workload splitmerge init [опции init...]
```

* `опции init`: [опции инициализации](#init-options).

Посмотреть описание команды инициализации таблиц:

```bash
{{ ydb-cli }} workload splitmerge init --help
```

### Доступные параметры {#init-options}

Имя параметра | Описание параметра
---|---
`--path <value>` | Префикс имени таблиц. Таблицы создаются как `<path>0` ... `<path>N-1`. По умолчанию: `splitmerge`.
`--tables <value>` | Количество создаваемых таблиц. По умолчанию: 1.
`--initial-partitions <value>` | `UNIFORM_PARTITIONS` для каждой таблицы: одно значение N для всех таблиц или список через запятую (например, `"4,64"`). По умолчанию: 4.
`--min-partitions <value>` | `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT`: одно значение N для всех таблиц или список через запятую. По умолчанию: 1.
`--max-partitions <value>` | `AUTO_PARTITIONING_MAX_PARTITIONS_COUNT`: одно значение N для всех таблиц или список через запятую. По умолчанию: 256.
`--partition-size <value>` | `AUTO_PARTITIONING_PARTITION_SIZE_MB` — порог размера для фазы сплитов. По умолчанию: 1.
`--auto-partition <value>` | Включение/выключение `AUTO_PARTITIONING_BY_LOAD`: 0 или 1, одно значение для всех таблиц или список через запятую (например, `"1,0"`). По умолчанию: 0.
`--cpu-threshold <value>` | Принимается, но не влияет на эту версию сервера; применяется серверное значение по умолчанию порога CPU для split-by-load. Оставлено для совместимости в будущем. По умолчанию: 1.

Для создания таблицы используется следующая команда:

```yql
CREATE TABLE `<path>0`(
    k Uint64,
    payload String,
    PRIMARY KEY(k)) WITH (
        STORE = ROW,
        AUTO_PARTITIONING_BY_LOAD = ENABLED, -- если --auto-partition 1
        UNIFORM_PARTITIONS = partsNum,
        AUTO_PARTITIONING_MIN_PARTITIONS_COUNT = minPartsNum,
        AUTO_PARTITIONING_MAX_PARTITIONS_COUNT = maxPartsNum,
        AUTO_PARTITIONING_PARTITION_SIZE_MB = sizeMb);
```

Пример: создать две таблицы — маленькую (4 партиции, включен split-by-load) и большую неактивную (64 партиции, зафиксированную через `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT = 64`):

```bash
{{ ydb-cli }} workload splitmerge init --tables 2 --initial-partitions "4,64" --min-partitions "1,64" --auto-partition "1,0" --partition-size 1
```

## Запуск нагрузки {#run}

Запускается один из видов нагрузки:

```bash
{{ ydb-cli }} workload splitmerge run [вид нагрузки...] [глобальные опции workload...] [специальные опции...]
```

* `вид нагрузки`: один из [видов нагрузки](#workload-types).
* `глобальные опции workload`: [глобальные параметры workload](commands/workload/index.md#global_workload_options).
* `специальные опции`: [опции запуска](#run-options).

Посмотреть описание команды запуска нагрузки:

```bash
{{ ydb-cli }} workload splitmerge run --help
```

### Доступные параметры {#run-options}

Имя параметра | Описание параметра
---|---
`--path <value>` | Префикс имени таблиц, должен совпадать с init. По умолчанию: `splitmerge`.
`--tables <value>` | Количество таблиц, должно совпадать с init. По умолчанию: 1.
`--table <value>` | Запуск на существующей таблице вместо созданных init таблиц `<path>N`. Повторяемая опция или список через запятую. См. [Запуск на существующей таблице](#existing-table).
`--key-column <value>` | Имя единственной колонки первичного ключа типа `Uint64` (режим существующей таблицы). По умолчанию: `k`.
`--payload-column <value>` | Имя колонки полезной нагрузки (режим существующей таблицы). По умолчанию: `payload`.
`--payload-type <value>` | Тип колонки полезной нагрузки (режим существующей таблицы): `string`, `utf8`, `uint64` или `int64`. По умолчанию: `string`.
`--start-key <value>` | Первый ключ для последовательной записи (режим существующей таблицы); позволяет не перезаписывать существующие строки. По умолчанию: 0.
`--initial-partitions <value>` | `UNIFORM_PARTITIONS` из init; задает позицию целевого горячего диапазона ключей. Одно значение или список через запятую.
`--min-partitions <value>` | `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT` (нижняя граница фазы слияний): одно значение или список через запятую.
`--partition-size <value>` | Размер партиции фазы сплитов, МБ (используется фазой сплитов во flap). По умолчанию: 1.
`--partition-size-high <value>` | Размер партиции фазы слияний, МБ (используется merge-режимами и фазой слияний во flap). По умолчанию: 64.
`--rows <value>` | Число строк в одном запросе записи. По умолчанию: 1000.
`--len <value>` | Длина строки полезной нагрузки, байт. По умолчанию: 1024.
`--key-distribution <value>` | Распределение ключей записи: `sequential` (по умолчанию), `targeted` или `striped`.
`--target-shards <value>` | Шарды, на которых концентрируется трафик (режим targeted): индексы через запятую или `random`. По умолчанию: 0.
`--target-share <value>` | Доля диапазона ключей каждого целевого шарда, получающая трафик, в процентах (1..100). По умолчанию: 1.
`--concurrent-phases` | Flap: запускать фазы параллельно (merge ALTER выполняется, пока продолжается запись).
`--phase-time <value>` | Максимальная длительность одной фазы flap, секунд. По умолчанию: 60.
`--cycles <value>` | Количество циклов flap. По умолчанию: 3.
`--max-rows <value>` | Принудительная остановка по общему числу записанных строк. По умолчанию: без ограничения.

### Как опции формы трафика соотносятся с типами давления

Опции формы трафика ортогональны сигналу давления: вид нагрузки выбирает, *какая* статистика пересекает порог, а опции распределения определяют, *на каких* шардах он проявляется.

| Режим / сигнал | `--key-distribution` | `--target-shards` / `--target-share` | Эффект |
|---|---|---|---|
split-by-size (по умолчанию) | `sequential` | — | Монотонные ключи заполняют шарды один за другим; каждый по очереди пересекает порог размера — последовательный спрос на сплиты. |
split-by-size, вариант targeted | `targeted` | `0`, доля 50 | Новые строки сконцентрированы в половине диапазона шарда 0 — он быстро пересекает порог размера — спрос на сплит одного шарда. |
split-by-load | `targeted` | один шард, доля 1 | Точечные UPSERT по фиксированному набору горячих ключей (1% диапазона одного шарда) — его CPU пересекает порог нагрузки — split-by-load, размер не затронут. |
split-burst | `striped` | — | Все шарды записываются одновременно — все пересекают порог размера вместе — массовый одновременный спрос. |
merge-by-size | (не имеет значения) | — | Форма трафика не важна; ALTER повышает порог размера, после чего следует merge-каскад. |
merge-by-load | `targeted`, затем остановка | — | Нагрузка на горячий шард опускается ниже порога нагрузки, и запускаются слияния; ход каскада отслеживается опросом числа партиций. |

Два следствия:

* `sequential` и `striped` **не могут** создать давление split-by-load: последовательные upsert перемещают точку записи по шардам по мере заполнения диапазонов (нет устойчивой горячей точки), striped равномерно распределяет CPU-нагрузку по всем шардам. split-by-load **требует** `targeted` с малым `--target-share`, чтобы CPU-нагрузка сконцентрировалась на одном шарде.
* By-size работает с **любым** распределением — сигналу нужны только накопленные байты. `targeted` заставляет один шард пересечь порог быстрее; `striped` — все шарды вместе; `sequential` дает последовательный спрос.

Режимы split-by-load выполняют **UPSERT по фиксированному набору горячих ключей**, не создавая новых строк: новые ключи увеличивают размер данных шарда и могут вызвать нежелательные сплиты по размеру наряду со сплитами по нагрузке. Первая итерация создает строки, последующие их перезаписывают, так что CPU растет, а размер данных остается неизменным.

### Списки политик по таблицам

`--initial-partitions`, `--min-partitions`, `--max-partitions` и `--auto-partition` принимают либо одно значение (применяется ко всем таблицам), либо список через запятую (по значению на таблицу). Списки по таблицам — общий механизм для асимметричных сценариев, например, маленькая таблица с включенным split-by-load рядом с большой таблицей, зафиксированной на высоком `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT` (см. [small-table-starvation](#small-table-starvation)).

### Запуск на существующей таблице {#existing-table}

Команда `run` может работать с существующей таблицей вместо созданных init, если передать `--table` (повторяемая опция или список через запятую). Это позволяет создавать split/merge-давление на таблице с реальными данными, production-подобной схемой или заранее заданной политикой партиционирования — например, на большой таблице, зафиксированной на высоком `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT`.

Требования к совместимости:

* Таблица должна иметь единственную колонку первичного ключа типа `Uint64` (ее имя передается через `--key-column`).
* Таблица должна иметь доступную для записи колонку полезной нагрузки (ее имя и тип передаются через `--payload-column` и `--payload-type`).
* Режимы by-load требуют включенного на таблице `AUTO_PARTITIONING_BY_LOAD`.

При старте инструмент проверяет схему через `DescribeTable` и останавливает запуск с понятной ошибкой, если таблица несовместима. Фактическое число партиций, полученное при проверке, используется в расчетах горячего диапазона ключей, поэтому `--initial-partitions` для существующих таблиц не нужен.

Пример — split-by-load на таблице с ключом `id Uint64` и полезной нагрузкой `value Uint64`:

```bash
{{ ydb-cli }} workload splitmerge run split-by-load --seconds 60 \
  --table my_table --key-column id --payload-column value --payload-type uint64
```

{% note warning %}

В режиме существующей таблицы инструмент **записывает данные** в таблицу и **выполняет ALTER** на ней (merge-режимы меняют `AUTO_PARTITIONING_PARTITION_SIZE_MB` и `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT`). Последовательная запись начинается с `--start-key` (по умолчанию 0); используйте ее, чтобы не перезаписывать существующие строки. Команды `init` и `clean` не применяются к таблицам, заданным через `--table`, и никогда их не удаляют.

{% endnote %}

### Воспроизведение режимов вручную

Каждый режим высокого уровня — композиция четырех примитивов (`split-by-size`, `split-by-load`, `merge-by-size`, `merge-by-load`) плюс опции формы трафика и политик — те же сценарии можно воспроизвести вручную отдельными вызовами CLI и оркестрацией в shell. Встроенные режимы существуют ради удобства, воспроизводимости тайминга (параллельные фазы сложно скриптовать отдельными процессами) и встроенной status-отчетности.

### split-by-size {#split-by-size}

Последовательная запись новых строк увеличивает размер таблицы сверх порога `AUTO_PARTITIONING_PARTITION_SIZE_MB`, запуская сплиты по размеру:

```bash
{{ ydb-cli }} workload splitmerge run split-by-size --seconds 60
```

### split-by-load {#split-by-load}

Требуется таблица, инициализированная с опцией `--auto-partition 1`. Точечный UPSERT-трафик по фиксированному набору горячих ключей: CPU растет, а размер данных остается неизменным, что запускает split-by-load. Набор горячих ключей — настраиваемая доля диапазона ключей одного шарда:

```bash
{{ ydb-cli }} workload splitmerge run split-by-load --initial-partitions 4 --target-shards 0 --target-share 1
```

`--target-shards random` выбирает случайный шард; список через запятую (например, `--target-shards 0,2`) поочередно распределяет трафик между несколькими шардами.

### merge-by-size {#merge-by-size}

Повышает `AUTO_PARTITIONING_PARTITION_SIZE_MB` до `--partition-size-high` одним `ALTER TABLE` (выполняется один раз за запуск), затем дожидается конца merge-каскада без повторного выполнения ALTER:

```bash
{{ ydb-cli }} workload splitmerge run merge-by-size --min-partitions 1 --partition-size-high 64 --seconds 120
```

### merge-by-load {#merge-by-load}

После запуска [split-by-load](#split-by-load) и остановки трафика нагрузка на горячий шард спадает ниже порога нагрузки, и слияния запускаются по снижению нагрузки. В отличие от merge-by-size, который повышает порог размера одним `ALTER TABLE`, merge-by-load ничего не меняет: порог размера остается прежним, и слияния идут только по сигналу нагрузки. Пока сервер выполняет слияния, режим раз в секунду опрашивает число партиций таблицы и печатает строку вида `merge-by-load\tpartitions\t<путь>\t<число>`, а после нескольких подряд неизменных опросов — итоговую строку `merge-by-load\tdone\t<путь>\t<итоговое число>`, так что завершение каскада можно проверить по выводу:

```bash
{{ ydb-cli }} workload splitmerge run merge-by-load --seconds 120
```

### split-burst {#split-burst}

С `--key-distribution striped` каждый запрос берет блок из другого региона пространства ключей, заставляя все шарды одновременно превысить порог размера. Без `--key-distribution striped` режим вырождается в последовательный split-by-size:

```bash
{{ ydb-cli }} workload splitmerge run split-burst --key-distribution striped --seconds 60
```

### merge-burst {#merge-burst}

Полный merge-каскад с максимально возможной скоростью, которую допускают серверные лимиты: то же поведение «один ALTER, затем ожидание», что и в [merge-by-size](#merge-by-size); предназначен для запуска сразу после большого сплит-каскада:

```bash
{{ ydb-cli }} workload splitmerge run merge-burst --min-partitions 1 --partition-size-high 64 --seconds 120
```

### multi-table-split {#multi-table-split}

Запись новых строк по всем таблицам в режиме round-robin, чтобы они конкурировали за общие ресурсы механизма split-merge параллельно. Требуется `--tables N > 1` при init:

```bash
{{ ydb-cli }} workload splitmerge run multi-table-split --tables 3 --seconds 60
```

### small-table-starvation {#small-table-starvation}

Маленькая требовательная таблица (с включенным split-by-load) конкурирует с большой неактивной таблицей. Инициализация выполняется со списками по таблицам, чтобы большая таблица оставалась большой:

```bash
{{ ydb-cli }} workload splitmerge init --tables 2 --initial-partitions "4,64" --min-partitions "1,64" --auto-partition "1,0" --partition-size 1
{{ ydb-cli }} workload splitmerge run small-table-starvation --tables 2 --initial-partitions "4,64" --seconds 60
```

### split-vs-merge-race {#split-vs-merge-race}

Волна слияний конкурирует с параллельным спросом на сплиты. Сторона спроса на сплиты запускается в одном процессе, а сторона слияний ([merge-by-size](#merge-by-size)) — параллельно во втором процессе:

```bash
{{ ydb-cli }} workload splitmerge run split-vs-merge-race --seconds 60 &
{{ ydb-cli }} workload splitmerge run merge-by-size --min-partitions 1 --partition-size-high 64 --seconds 60
```

### flap {#flap}

Чередование фаз grow/merge/split на одной таблице: каждая фаза длится не более `--phase-time` секунд, один `ALTER TABLE` на фазу, всего `--cycles` циклов. Фаза слияний повышает порог размера (`--partition-size-high`), фаза сплитов возвращает его обратно (`--partition-size`). С `--concurrent-phases` merge ALTER выполняется один раз во время первой фазы роста, пока продолжается запись:

```bash
{{ ydb-cli }} workload splitmerge run flap --phase-time 60 --cycles 3 --seconds 600
```

### status {#status}

Опрашивает первую таблицу (`<path>0`) раз в секунду и выводит динамику числа партиций, распределения ширины ключевых интервалов и распределения строк по партициям:

```text
partitions  /Root/db/splitmerge0  13  widths  min=1  med=1  max=uint64_max  rows  min=0  med=46  max=97
```

У последней партиции нет верхней границы ключа, поэтому ее ширина не ограничена и выводится как `uint64_max`. Поля в строке вывода разделены табуляцией.

Узкие интервалы, сгруппированные вокруг горячего диапазона, — характерный признак split-by-load; широкие равномерные интервалы — признак слияний. Режим запускается во втором процессе параллельно с любым режимом нагрузки:

```bash
{{ ydb-cli }} workload splitmerge run status --seconds 120
```

## Практические замечания {#practical-notes}

* **Режимы слияний по размеру (merge-by-size, merge-burst) выполняют `ALTER TABLE` ровно один раз за запуск**, затем дожидаются конца каскада. Длительность запуска должна превышать ожидаемое время завершения каскада (`--seconds` больше этого времени); повторный запуск режима снова выдаст ALTER, что лишь добавит нагрузку на сервер, не изменив результат.
* **`--max-rows` — штатная остановка для режимов записи.** Запись останавливается после первого запроса, достигшего или превысившего лимит, поэтому итоговое число строк может превысить его менее чем на объем одного запроса (`--rows`); это можно использовать для воспроизводимых объемов данных. `--seconds` останавливает запуск по времени независимо от прогресса записи.
* **Временные ошибки во время активных сплитов или слияний — нормальное явление.** Пока идут сплиты или слияния, часть запросов может завершаться ошибками (перегрузка шарда, устаревшие границы партиций; драйвер выполняет повтор автоматически); это поведение сервера при перемещении партиций, а не неисправность инструмента. Однопоточные запуски (`--threads 1`) обычно проходят без ошибок.

## Очистка {#clean}

Удаление тестовых таблиц выполняется командой:

```bash
{{ ydb-cli }} workload splitmerge clean [опции clean...]
```

* `опции clean`: [опции очистки](#clean-options).

### Доступные параметры {#clean-options}

Имя параметра | Описание параметра
---|---
`--path <value>` | Префикс имени таблиц, должен совпадать с init. По умолчанию: `splitmerge`.
`--tables <value>` | Количество удаляемых таблиц; значение должно быть больше или равно числу созданных, чтобы удалить их все (несуществующие таблицы пропускаются). По умолчанию: 1.

Пример:

```bash
{{ ydb-cli }} workload splitmerge clean --tables 2
```
