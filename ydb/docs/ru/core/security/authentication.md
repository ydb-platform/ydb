По умолчанию используется значение `sso`.

Например, при `sub: user1`, `groups: [admins, developers]` и домене по умолчанию формируются следующие SID:

- пользователь `user1@sso`.
- группы `admins@sso` и `developers@sso`.

{{ ydb-short-name }} использует список групп из токена без дополнительных вызовов к IdP и без раскрытия вложенных групп. Управлять пользователями и группами внешнего IdP с помощью команд `CREATE USER`, `ALTER USER`, `CREATE GROUP` и `ALTER GROUP` нельзя. Права назначаются сформированным SID с помощью методов, описанных в разделе [{#T}](./authorization.md).

### Конфигурация сервера

Аутентификация через внешний IdP включается в [конфигурации аутентификации](../reference/configuration/auth_config.md#external-idp-auth-config) при наличии раздела `external_idp_config`.

## Аутентификация по клиентскому сертификату {#client-certificate}

{{ ydb-short-name }} позволяет аутентифицировать клиента по данным клиентского сертификата, полученным при установке TLS-соединения. Проверка выполняется на уровне прикладного протокола (gRPC и т. д.), когда сервер уже принимает запросы по открытому соединению.

Такой подход подходит, например, в корпоративных сценариях с централизованной выдачей сертификатов.

### Как это работает

1. Клиент устанавливает TLS-соединение с сервером {{ ydb-short-name }}, передавая клиентский сертификат (и цепочку доверия).
2. При обработке запроса сервер извлекает сертификат из TLS-контекста.
3. Сервер использует сертификат для аутентификации и проверяет его по правилам раздела [client_certificate_authorization](../reference/configuration/client_certificate_authorization.md).
4. В результате успешной проверки сертификата клиенту назначается идентификатор безопасности [SID](../concepts/glossary.md#access-sid), которому назначены все [права](../concepts/glossary.md#access-right), соответствующие этому идентификатору.

Аутентификация по сертификату применяется только к запросам без [токена аутентификации](../concepts/glossary.md#auth-token). Если клиент передает токен аутентификации — например, в заголовке `Authorization` для HTTP или через механизмы SDK/CLI для IAM, логина и пароля — токен имеет приоритет. В этом случае сертификат передается на уровне TLS, но не используется для аутентификации.

### Формирование SID

{% note info %}

Проверка клиентского сертификата для [аутентификации устройств](#device-auth) и аутентификация пользователя по клиентскому сертификату — это разные механизмы. Аутентификация устройств ограничивает сетевой периметр без формирования SID; аутентификация пользователя по клиентскому сертификату формирует SID и группы для [авторизации](./authorization.md).

{% endnote %}

Успешная аутентификация по сертификату создает SID пользователя с суффиксом `@<domain>`, где `<domain>` — это [значение параметра](../reference/configuration/auth_config.md#certificate-auth-config) `certificate_authentication_domain` в разделе `auth_config` (по умолчанию: `cert`). Имя формируется из всех атрибутов поля Subject сертификата в нотации `Имя=Значение,...@<domain>`. Порядок атрибутов соответствует порядку полей в сертификате. Пример:


```text
C=RU,ST=MSK,O=MyOrg,CN=account1.apps.example.net@cert
```


### Получение групп

Если в разделе [client_certificate_authorization](../reference/configuration/client_certificate_authorization.md) указаны блоки `client_certificate_definitions`, сертификат принимается, если он соответствует хотя бы одному из них. Для каждого подходящего блока клиент включается в группы из `member_groups`. Если `member_groups` не указано, используется группа по умолчанию — `default_group` (значение по умолчанию: `DefaultClientAuth@cert`).

### Конфигурация сервера

Правила проверки сертификата и назначения групп задаются в разделе [client_certificate_authorization](../reference/configuration/client_certificate_authorization.md) статической конфигурации кластера. Чтобы включить запрос клиентского сертификата при TLS-рукопожатии через gRPC, установите параметр `request_client_certificate: true`.

### Конфигурация клиента

Подробнее о настройке [{{ ydb-short-name }} CLI](../reference/ydb-cli/index.md) см. в разделе [Параметры TLS-соединения](../reference/ydb-cli/connect.md#tls).

## Аутентификация устройств по сертификату {#device-auth}

Аутентификация устройств — это проверка [клиентского сертификата](../concepts/glossary.md#client-certificate) при установке TLS-соединения; в этом случае [SID](../concepts/glossary.md#access-sid) не формируется. Если сертификат предоставлен, проверяется цепочка доверия к CA; непроверенный сертификат приводит к отклонению соединения до обработки прикладных запросов. Необходимость предоставления сертификата зависит от интерфейса (см. раздел [Использование в {{ ydb-short-name }}](#device-auth-interfaces)).

### Зачем нужна аутентификация устройств {#device-auth-motivation}

Аутентификация устройств решает следующие задачи в {{ ydb-short-name }}:

1. Изоляция кластера — ограничение набора хостов и приложений, которые могут установить TLS-соединение с узлами {{ ydb-short-name }}.
2. Защита от ошибок конфигурации — предотвращение подключения к внешним {{ ydb-short-name }}кластерам. Например, если параметр [node-broker](../devops/configuration-management/configuration-v1/node-authorization.md) указан неверно, динамический узел не подключится к внешнему кластеру, тогда как при обычном TLS такое подключение могло бы быть установлено.
3. Усложнение атак на уровне приложения — процесс на внешнем хосте без подходящего сертификата не получает доступ к API кластера, даже если существует сетевой маршрут к порту.

После аутентификации устройства может потребоваться [аутентификация](./authentication.md) пользователя или приложения для доступа к данным. Она может выполняться не только с помощью проверенного клиентского сертификата, но и с использованием других методов аутентификации в {{ ydb-short-name }}, например, по [логину и паролю](./authentication.md#static-credentials).

### Как это работает {#device-auth-how-it-works}

1. Клиент устанавливает TLS-соединение с сервером {{ ydb-short-name }} и, если интерфейс соединения требует этого, предоставляет клиентский сертификат.
2. Если сертификат предоставлен, сервер проверяет его на уровне TLS: цепочку доверия к настроенному центру сертификации (CA), срок действия и т. д. Дополнительные правила сопоставления полей сертификата (например, `require_same_issuer`, Subject и SAN) применяются при [аутентификации по клиентскому сертификату](./authentication.md#client-certificate).
3. Если проверка успешна, соединение открывается; если нет — отклоняется.

### Использование в {{ ydb-short-name }} {#device-auth-interfaces}

Аутентификация устройств необязательна и настраивается независимо: механизм можно включить на одних портах и отключить на других.

- **Interconnect** — при включенном TLS в разделе [interconnect_config](../reference/configuration/tls.md#interconnect), [Interconnect](../concepts/glossary.md#actor-system-interconnect) требует клиентский сертификат.
- **Kafka API** — при включенном mTLS требует клиентский сертификат. Проверяется только цепочка доверия к CA, и соединение без сертификата или с непроверенным сертификатом не устанавливается. Конфигурация сервера описана в разделе [kafka_proxy_config](../reference/configuration/kafka_proxy_config.md), а подключение клиента — в разделе [Аутентификация устройств по mTLS](../reference/kafka-api/auth.md#device-auth).
- **gRPC** и **YDB Monitoring** — можно включить запрос клиентского сертификата для аутентификации устройств, а также отдельно включить его обязательную проверку (непроверенный сертификат всегда отклоняется). Конфигурация gRPC описана в разделах [grpc_config](../reference/configuration/tls.md#grpc) и [client_certificate_authorization](../reference/configuration/client_certificate_authorization.md), а подключение клиента — в разделе [Параметры TLS-соединения](../reference/ydb-cli/connect.md#tls). Конфигурация YDB Monitoring описана в разделе [monitoring_config](../reference/configuration/monitoring_config.md#tls).

## Аутентификация с использованием стороннего IAM-провайдера {#iam}

* **Access Token** — фиксированный токен задается как параметр для клиента (SDK или CLI) и передается в запросах.
* **Refresh Token** — [OAuth-токен](https://auth0.com/blog/refresh-tokens-what-are-they-and-when-to-use-them/) личного аккаунта задается как параметр для клиента (SDK или CLI), на основе которого клиент периодически обращается к IAM API в фоновом режиме для ротации (получения следующего) токена, передаваемого в запросах.
* **Service Account Key** — атрибуты сервисного аккаунта и ключ подписи задаются как параметры для клиента (SDK или CLI), на основе которых клиент периодически обращается к IAM API в фоновом режиме для ротации (получения следующего) токена, передаваемого в запросах.
* **Metadata** — клиент (SDK или CLI) периодически обращается к локальному сервису для ротации (получения следующего) токена, передаваемого в запросах.
* **OAuth 2.0 token exchange** — клиент (SDK или CLI) обменивает токен другого типа на токен доступа с помощью [протокола OAuth 2.0 token exchange](https://www.rfc-editor.org/rfc/rfc8693),, который затем передается в запросах к {{ ydb-short-name }} API.

Любой обладатель действительного токена может получить доступ для выполнения операций, поэтому основная задача системы безопасности — обеспечить секретность токена и предотвратить его компрометацию.

Режимы аутентификации с ротацией токена, **Refresh Token** и **Service Account Key**, обеспечивают более высокий уровень безопасности по сравнению с режимом с фиксированным токеном, **Access Token**, потому что по сети к серверу {{ ydb-short-name }} передаются только короткоживущие секреты.

Максимальная безопасность и производительность обеспечиваются при использовании режима **Metadata**, так как он исключает необходимость работы с секретами при развертывании приложения, а также позволяет получить доступ к IAM и кэшировать токен заранее, до запуска приложения.

При выборе режима аутентификации среди поддерживаемых сервером и окружением следуйте этим рекомендациям:

* **Anonymous** обычно используется на самостоятельно развернутых локальных кластерах {{ ydb-short-name }}, которые недоступны по сети.
* **Access Token** используется, когда другие режимы не поддерживаются на стороне сервера или для целей настройки и отладки. Он не требует взаимодействия клиента с IAM. Однако, если IAM поддерживает API для ротации токенов, фиксированные токены, выдаваемые таким IAM, обычно имеют короткий срок жизни, что вынуждает регулярно вручную обновлять их в IAM.
* **Refresh Token** можно использовать для разовых ручных операций под личным аккаунтом, например, связанных с обслуживанием данных в базе, выполнением разовых операций в CLI или запуском приложений с рабочей станции. Такой токен можно получить вручную в IAM один раз на длительный период и хранить в переменной окружения на вашей рабочей станции, чтобы он автоматически применялся при запуске CLI без дополнительных параметров аутентификации.
* **Service Account Key** в основном используется для приложений, предназначенных для работы в средах, поддерживающих режим **Metadata**, при тестировании их вне таких сред (например, на рабочей станции). Его также можно использовать для приложений вне таких сред, выступая в качестве аналога **Refresh Token** для сервисных аккаунтов. В отличие от личного аккаунта, объекты доступа и роли сервисного аккаунта могут быть ограничены.
* **Metadata** используется при развертывании приложений в облаках. В настоящее время этот режим поддерживается на виртуальных машинах и в {{ sf-name }} {{ yandex-cloud }}.

Токен, который нужно указать в параметрах, можно получить из системы IAM, связанной с конкретной {{ ydb-short-name }}установкой. В частности, для сервиса {{ yandex-cloud }} в {{ ydb-short-name }} используются Yandex.Passport OAuth и сервисные аккаунты {{ yandex-cloud }}. При использовании {{ ydb-short-name }} в корпоративных контекстах могут использоваться стандартные централизованные системы аутентификации организации.

При использовании режимов, предполагающих {{ ydb-short-name }}обращение клиента к IAM, можно дополнительно указать URL IAM, предоставляющего API выдачи токенов. По умолчанию существующие SDK и CLI пытаются обратиться к IAM API {{ yandex-cloud }}, размещенному на `iam.api.cloud.yandex.net:443`.
