# Кеширование результатов аутентификации

В процессе аутентификации пользовательская сессия получает [аутентификационный токен](../concepts/glossary.md#auth-token), который передаётся вместе с каждым запросом к кластеру {{ ydb-short-name }}. Поскольку {{ ydb-short-name }} — распределённая система, пользовательские запросы в конечном итоге обрабатываются на одном или нескольких [узлах {{ ydb-short-name }}](../concepts/glossary.md#node). Получив запрос, узел [проверяет аутентификационный токен](./authentication.md#token-validation) и в случае успешной проверки создаёт **токен пользователя**.

Токен пользователя содержит идентификатор пользователя и список групп, действует **только внутри текущего узла {{ ydb-short-name }}** и используется при авторизации операций. Узел сохраняет токен пользователя в кеше. Ключ записи учитывает аутентификационный токен и контекст проверки, например базу данных и запрошенные разрешения. При последующих запросах с теми же данными узел получает готовый токен пользователя из своего кеша. Клиент не получает токен пользователя и продолжает передавать аутентификационный токен с каждым запросом.

Время жизни токена пользователя и другие ключевые аспекты его работы настраиваются в [секции `auth_config` конфигурации {{ ydb-short-name }}](../reference/configuration/auth_config.md#caching-auth-results).

## Время жизни токена пользователя

Токен пользователя удаляется из кеша по одному из двух условий:

- Токен пользователя не использовался в течение периода `auth_config.life_time`. Каждый запрос с соответствующим аутентификационным токеном обновляет время последнего использования. Значение по умолчанию — `1h`.
- Истёк срок действия записи. Для большинства типов аутентификационных токенов срок задаётся параметром `auth_config.expire_time`; значение по умолчанию — `24h`. После успешного обновления отсчёт начинается заново. Для токенов входа по логину и паролю и токенов внешнего провайдера идентификации используется срок действия самого аутентификационного токена, а для запросов с подписью ключом доступа — отдельный параметр `auth_config.as_signature_expire_time`.

Удаление происходит во время периодической обработки очереди токенов. Интервал между обработками задаётся параметром `auth_config.refresh_period`, поэтому токен удаляется не точно в момент наступления условия.

{% note warning %}

Если приложение регулярно отправляет запросы на один узел, токен пользователя не удаляется по `life_time`. При временных ошибках обновления узел продолжает использовать ранее сформированный токен пользователя, включая сохранённый в нём список групп. Для AccessService каждая временная ошибка переносит срок удаления записи: на `expire_time` для обычных токенов и на `as_signature_expire_time` для запросов с подписью ключом доступа. Поэтому повторные попытки могут продолжаться до успешного обновления, постоянной ошибки или прекращения запросов на период `life_time`. Для токенов входа по логину и паролю и токенов внешнего провайдера идентификации повторы дополнительно ограничены сроком действия аутентификационного токена.

До следующего успешного обновления кешированный список групп может оставаться устаревшим, поэтому изменения аккаунта могут применяться на конкретном узле с задержкой. Под изменениями аккаунта здесь понимаются удаление локального или внешнего пользователя и изменение его принадлежности к [группам пользователей](./authorization.md#group).

[Права доступа](../concepts/glossary.md#access-right) в {{ ydb-short-name }} привязываются к [объекту доступа](../concepts/glossary.md#access-object) и хранятся в списках прав — [ACL](../concepts/glossary.md#access-control-list) (Access Control List) — как для пользователей, так и для групп. Сами ACL не кешируются: их изменения применяются при следующей проверке прав. В токене пользователя кешируется список групп.

Допустим, [ACL](../concepts/glossary.md#access-control-list) таблицы `Tbl1` предоставляет право на запись группе `Grp1`. После удаления пользователя из этой группы сформированный для него токен пользователя на конкретном узле может содержать `Grp1` до успешного обновления. Добавленный в группу пользователь, наоборот, получит соответствующее право на этом узле после успешного обновления токена пользователя.

{% endnote %}

## Обновление токенов пользователя {#refreshing-user-tokens}

Для типов аутентификационных токенов, которые поддерживают обновление, узел периодически повторяет проверку и заменяет токен пользователя в кеше. В зависимости от способа аутентификации обновление выполняется по локальному состоянию {{ ydb-short-name }} или требует обращения к внешней системе. При успешном обновлении актуализируются идентификатор пользователя и список его групп.

Параметр `auth_config.refresh_time` задаёт базовый интервал обновления; значение по умолчанию — `1h`. После успешной проверки следующее обновление назначается на случайный момент в интервале от `refresh_time/2` до `refresh_time`.

После временной ошибки узел повторяет попытку. Начальная базовая задержка задаётся параметром `min_error_refresh_time`; после каждой ошибки она увеличивается с учётом `max_error_refresh_time`. Фактическая задержка перед каждой попыткой выбирается случайным образом от половины до полного значения текущей базовой задержки. Эти параметры ограничивают задержку между попытками, но не их суммарную длительность.

Для AccessService повторные попытки могут продолжаться до успешного обновления, постоянной ошибки или удаления записи после `life_time` без запросов. Для токенов входа по логину и паролю и токенов внешнего провайдера идентификации повторы также прекращаются после истечения срока действия аутентификационного токена.

{% note info %}

Количество ошибок обработки токенов сервисом Ticket Parser, включая ошибки при первичной проверке и последующем обновлении, можно увидеть в [метриках](../reference/observability/metrics/index.md) `auth.TicketParser.TicketsErrors`, `auth.TicketParser.TicketsErrorsPermanent` и `auth.TicketParser.TicketsErrorsRetryable` или в поле `Error` на странице **Developer UI** > **Actors** > **Ticket Parser** (`https://<ydb-server-address>:<embedded-ui-port>/actors/ticket_parser`).

Ошибки могут возникать из-за следующих проблем:

- узел {{ ydb-short-name }} не может связаться с внешней системой аутентификации из-за сетевых проблем;
- не работает внешняя система аутентификации;
- сильно перегружен узел {{ ydb-short-name }} (наименее вероятная причина).

{% endnote %}
