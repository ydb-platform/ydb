# Консоль хранения YDB

Чтобы развернуть три DC на одном хосте и запустить TPC-C на отдельной базе, используйте [инструкцию по развёртыванию стенда](deploy/README.md).

Консоль показывает группы хранения и VDisk по датацентрам, запускает нагрузку TPC-C и выполняет команды политики DC через установленный на хосте YDB CLI. Скопируйте каталог `ydb/tools/dc_admin` на хост с Python 3.9 или новее, установите PyYAML для используемого интерпретатора и перейдите в каталог с `server.py`. Укажите базу для нагрузки, адрес встроенного мониторинга YDB и имена своих датацентров.

```sh
python3 server.py --endpoint grpcs://ydb-v6.example.net:2135 --database /Root \
  --workload-endpoint grpcs://compute-v6.example.net:2135 --workload-database /Root/tpcc \
  --monitoring-url http://ydb-v6.example.net:31001/monitoring/ \
  --datacenter zone-0 --datacenter zone-1 --datacenter zone-2
```

Для IPv6-кластера укажите имя с DNS-записью AAAA в `--endpoint`. Сервер передаёт этот адрес CLI. По умолчанию запускается `ydb` из PATH. Параметр `--ydb` позволяет указать путь к бинарнику.

Откройте обычный HTTP-адрес сервера. API принимает подключения с localhost и с адресов и из CIDR-сетей, перечисленных в повторяемом параметре `--allow-client`. По умолчанию он слушает `[::1]:8765`. Для работы через SSH запустите на своём компьютере `ssh -N -L '[::1]:8765:[::1]:8765' HOST` и откройте ту же ссылку. Для другого адреса или порта используйте `--listen` и `--port`.

Укажите реальные имена DC в повторяемом параметре `--datacenter`. Если опустить этот параметр, имя можно ввести в форме. Для подключения CLI использует учётные данные процесса сервера или профиль из `--profile`. Путь базы можно передать в `--database`.

## Нагрузка и команды

«Запустить TPC-C» подготавливает данные 100 складов в подкаталоге `dc-admin-tpcc-100/data` выбранной базы, затем запускает транзакции двумя потоками на 30 минут. Следующий запуск использует подготовленные данные. Кнопка «Остановить» завершает прогон досрочно. Вывод CLI и состояние нагрузки доступны и после перезагрузки страницы. Учётной записи CLI нужны права на таблицы в этой базе и на управление политикой DC.

Во вкладке «Консоль админа» откройте «Администрирование стораджа» и выберите карточку датацентра. Доступны проверка исключения, исключение с подтверждением и возврат DC. Терминал показывает выполненную команду, объединённый вывод stdout и stderr и код завершения. Операции доступны во время нагрузки.

В разделе «Управление хостами» отображаются локальные сервисы `ydb_<DC>_node<N>.service` из /etc/systemd/system для указанных при запуске датацентров. Кнопки вызывают `sudo -n systemctl stop/start` для выбранной ноды.
Нажмите заголовок карточки DC, чтобы остановить или запустить все его ноды одной командой systemctl. Остановка требует подтверждения. Политика исключения DC задаётся отдельно.

### Ручное изменение конфига

Третья кнопка в консоли открывает две независимые операции для стенда 3×3.

* **Статическая группа · Solo DC** исключает второй DC из целевой политики и сохраняет подтверждённый уровень группы 0. Из `DC_FAILURE_INV1` группа переходит в `DC_SOLO_INV1`, из `DC_FAILURE_INV2` — в `DC_SOLO_INV2`. Запустите три ноды выбранного DC и остановите шесть остальных.
* **StateStorage и обе Board** размещает реплики StateStorage, StateStorageBoard и SchemeBoard на трёх статических узлах каждого работающего DC. DC считается работающим, если хотя бы один его сервис ноды имеет состояние `active`. При одном, двух или трёх DC каждый сервис получает соответственно 3, 6 или 9 колец с таким же `NToSelect`.

Перед записью админка останавливает ноды выбранных DC, сверяет конфиги их PDisk и сохраняет исходные метаданные и diff. После обратного чтения она запускает ранее работавшие ноды. При прерывании записи повторите ту же операцию в окне ручного изменения конфига.

Для включения операции задайте DC_ADMIN_STATIC_RECOVERY_DIR с путём к каталогу резервных копий и установите рядом с этим каталогом ydbd-recovery для чтения и записи PDisk и утилиту dc-admin-prepare-solo из prepare_solo. Операция сама по себе не восстанавливает кворум distconf. Динамические группы получают целевую политику через штатную сверку BSC.

Кнопка «Размещение StateStorage и Board» меняет размещение трёх сервисов через YDB CLI. Каждый из четырёх шагов получает актуальный YAML через `admin cluster config fetch`, применяет его через `admin storage replace -f` и проверяется повторным чтением. Для онлайн-операции нужен кворум distconf. Выберите один или несколько DC. Переход проходит через совместное размещение старых и новых реплик с минутой между шагами. После прерывания выберите те же DC, чтобы продолжить.

На локальном стенде переменная службы `DC_ADMIN_NODES` указывает на `nodes.json` с полями `unit`, `dc`, `grpc` и `mon` по каждой статической ноде. Для ручного изменения конфигурации задайте в поле `pdisk` абсолютный путь к блочному устройству этой ноды. Для более ранних инвентарей без этого поля используется `/dev/mapper/ydb_<DC>_node<N>_pdisk`. Админка выбирает доступную ноду при чтении мониторинга, изменении размещения и запуске команд DC. Нагрузка использует отдельный gRPC endpoint своей базы.

Для постоянного адреса YDB UI при остановке одной ноды можно использовать `monitor_proxy.py` с systemd socket activation. Укажите в `ExecStart` путь к Python, скрипту и список локальных портов мониторинга. Прокси принимает соединение через сокет systemd и подключается к первому доступному порту на `::1`.
